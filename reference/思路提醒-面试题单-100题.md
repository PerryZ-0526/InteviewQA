## 模块一：项目 1 —— 教育智能体（Q1–Q30）

### Q1 整体架构
- 分层描述：接入层（FastAPI）→ 编排层（LangGraph 双图）→ 能力层（RAG 检索 / 画像 / 工具调用）→ 数据层（Milvus / Neo4j / MySQL / Redis）
- 画出一次对话的数据流路径：请求 → 意图理解 → 检索（政策 RAG + 在线检索子图）→ 画像注入 → 生成 → 返回
- 每个组件一句话说清职责与选型理由；Kafka = 异步解耦（推送/画像更新），Redis = 会话状态与缓存
- 不要背简历，用自己的话复述一遍架构再讲细节

### Q2 两层编排图
- 划分核心：任务对「响应时效」的要求——对话要秒回，画像更新/推送可分钟级
- 实时图：同步请求-响应闭环；异步图：事件驱动 + 定时触发
- follow-up 触发：定时扫描「待跟进」状态（如上次对话遗留问题）+ 事件触发（政策节点）
- 状态共享：两图不直接通信，通过 MySQL/Redis 作中转（写入最新画像、实时图读取）

### Q3 State schema 与 checkpoint
- State 字段按「跨节点必须传递的数据」设计：消息列表、检索结果、画像快照、工具调用记录
- checkpoint 作用：持久化图执行状态、支持 human-in-the-loop、断点恢复
- 子图 state 映射：注意字段命名冲突与序列化（如 Milvus 结果对象不能直接塞 state）
- 提一个实际踩过的坑（如 checkpoint 膨胀、reducer 误用）

### Q4 ReAct 子图与查询改写
- 改写目的：消除指代（「上次那个导师」）、补全约束（「帮我找」→ 找什么类型的资源）
- 改写依据：历史对话 + 画像（专业方向、年级）+ 原始 query
- 有效性判断：改写后检索结果是否变化、轮次上限（如最多 3 轮）
- 降级：改写失败直接用原 query 检索，保证可用性

### Q5 结果聚合
- 去重：内容指纹 / 标题相似度；排序：rerank 模型或 LLM 精选
- 冲突处理：时效优先（新政策覆盖旧政策）、来源权威性
- 合并进主 prompt：结构化组织（分来源列证据），而非简单拼接

### Q6 为什么不用低代码平台
- 定制需求：多图编排、自定义记忆系统、评测闭环——平台黑盒满足不了
- 可控性：低代码难以做 tracing、版本管理、A/B
- LangGraph 的坑：状态序列化、调试成本、文档更新快
- 结论要辩证：小团队快速验证用平台合理，深度定制必须自研

### Q7 FastAPI 异步模型
- async def 端点内避免同步阻塞调用：用异步 SDK，或 run_in_executor 丢线程池
- uvicorn 单 worker 单事件循环；CPU 密集任务会卡事件循环
- 瓶颈分析：这个项目 IO 密集（检索/DB），异步收益明显；向量计算在 Milvus 侧

### Q8 文档解析
- 格式覆盖：PDF / docx / markdown，选型可提 unstructured 等库
- 表格难点：跨页表格拼接（按表头识别）、合并单元格还原（占位填充）
- 兜底：解析失败转 OCR 或人工导入；解析质量评估（抽查 + 评测集覆盖）

### Q9 父子切块
- 「结构感知」：以标题层级、条款编号作为切分边界，而不是机械按字数
- 父块 = 完整条款/章节（几百到上千字），子块 = 更细粒度（百字级）
- 召回：子块命中 → 返回对应父块（保证上下文完整）
- 参数依据：chunk 大小由评测集调优得出，而非拍脑袋

### Q10 证据覆盖度
- 量化信号：检索分数分布（Top1 与 Top5 分差）、LLM 判断「缺了哪些维度」
- 阈值：来自评测集统计（覆盖不足的 case 特征）
- 补充查询：针对缺失维度定向生成（如「补充『申请条件』相关条款」）

### Q11 自适应检索策略
- 三者定位：缺失维度补充 = 定向补查；语义扩展 = 同义/上下位改写；HyDE = 假设答案引导
- 选择机制：先规则判定（分数阈值、问题类型），必要时 LLM 决策
- HyDE 风险：假设答案若含幻觉会误导 embedding；政策查询偏事实检索，HyDE 慎用
- 权衡：补充轮次设上限，每轮结果过质量过滤（分数阈值）

### Q12 混合检索与 Milvus
- Milvus 支持稠密 + 稀疏向量混合检索；RRF 融合排名（k 值经验 60）
- 标量过滤字段：政策类型、发布/生效时间、适用人群、效力状态
- rerank：收益明显但增加延迟与成本，说明取舍
- 准备说清：索引类型（HNSW 常用）、维度（embedding 模型决定）、metric（cosine/IP）

### Q13 知识库更新一致性
- 变更检测：定时扫描 + 文件哈希对比；或导入接口触发
- 删除同步：按文档/条目 ID 删除向量（Milvus delete by expr）
- 版本管理：「现行有效」字段 + 时间过滤，历史版本可查不可主推
- 评测集联动：政策大改时评测集参考答案需人工复核

### Q14 两套评测集
- 检索评测集：只测检索组件，跑得快、可高频回归
- 端到端评测集：测完整链路，贵但反映真实体验
- section_path 的好处：与切块解耦，切块策略变了评测集不用改
- 构建：人工标注 + 线上 bad case 回流双来源

### Q15 引用校验
- 规则校验：答案引用是否命中「必须引用的证据」的 section_path（精确/包含）
- LLM 校验：答案是否真的被引用证据支撑（防「引用正确但答案无关」）
- 计分：答案质量与引用质量分开打分；自建指标如引用精确率、拒答率

### Q16 数据闭环
- 定位路径：检索指标劣化 → 查切块/embedding；端到端劣化 → 查 prompt/编排
- 回归：任何改动先跑评测集对比分数，劣化不发布
- prompt 版本管理：变更记录 + 双跑对比

### Q17 防过拟合
- 评测集定期扩充（新 bad case）、轮换（划分 held-out 集）
- 监控线上 query 分布与评测集差异
- 回流标准：高频、典型、有明确正确答案的 case

### Q18 画像融合
- 三层来源：校内系统同步（选课/借阅/科研）、LLM 从对话提取标签、长期统计沉淀偏好
- 冲突裁决：事实 > 统计偏好 > LLM 标签（置信度层级）
- 防漂移：标签需频次/时间阈值才「转正」，长期未出现自动衰减

### Q19 分层注入
- 常驻摘要：画像的压缩版，每次对话必带（预算固定，如 200-300 token）
- Tool 深读：模型需要细节时按需检索长期记忆库（按需付费）
- 更新时机：异步图周期重写摘要（如每周）
- 风险：摘要过期导致回答偏差 → 摘要带时间戳，模型可感知新旧

### Q20 短期记忆
- 窗口：按轮次或 token 上限（如最近 10 轮 / 8k token）
- 摘要触发：窗口将满或话题切换时，增量式压缩旧轮次
- 跨会话：默认清空；标记为「长期价值」的内容写入长期记忆

### Q21 长期记忆
- schema：事件类型、时间戳、来源对话 ID、正文向量
- 召回：向量检索 + 时间衰减加权（近期优先）
- 遗忘：TTL 过期 / 新事件覆盖旧事件
- 写入：异步图批量写，避免拖慢实时对话

### Q22 记忆一致性
- 实时图读到的是「上一次沉淀的画像」，接受秒级/分钟级延迟（最终一致）
- 冲突合并：同一事件多来源取最新 + 置信度
- 记忆污染治理：每条记忆标来源（对话 ID），可追溯、可人工纠错

### Q23 异步推送机制
- 事件来源：画像更新事件、政策节点事件（如选课截止）、follow-up 待办
- 流程：事件 → Kafka topic → 消费 → 窗口内聚合 → 圈选 → 推送
- 防轰炸：每人每渠道频率上限 + 优先级排序（重要提醒可插队）
- 内容：模板填充为主，LLM 生成仅用于个性化文案（控成本）

### Q24 分渠道分级 + 圈选 + 去重限频
- 渠道差异：成本（短信贵）、实时性（微信快）、触达率（站内信必达但可能不看）
- 分级规则：紧急（短信+微信）> 普通（站内信）> 资讯（邮件周报）
- 圈选：画像标签的组合条件（如「大三 + 准备保研」），运营可配置
- 去重：事件指纹（事件 ID + 学生 ID）跨渠道查重；限频：按学生/渠道/事件类型多粒度

### Q25 推送可靠性
- 渠道失败：指数退避重试（如 1min/5min/30min），超限进死信
- 状态跟踪：发送状态表（待发/成功/失败/已读）
- Kafka：手动 ack + 消费失败重试；关注重复消费（消息幂等设计）
- 兜底：关键提醒（如选课截止）多渠道互为备份

### Q26 幻觉与拒答边界
- 置信度信号：检索分数、证据覆盖度、政策库「有据可查」判定
- 低置信策略：明确拒答话术 + 转人工/客服入口（比答错好）
- 敏感内容：心理危机、投诉等关键词触发规则路由（转人工）
- 反馈入口：用户点「回答有误」→ bad case 回流评测集

### Q27 多租户与权限
- 隔离层级：会话级（对话历史）、画像级（个人信息）、知识级（政策可见范围）
- 技术手段：检索时 tenant_id/user_id 标量过滤；画像按用户 ID 隔离存储
- 日志脱敏：不打印姓名/学号，用匿名 ID

### Q28 冷启动
- 策略：群体画像兜底（按年级/专业默认画像）+ 首次对话主动询问（问卷式引导）
- 脱离冷启动标准：积累 N 次交互或 M 条画像标签
- 评估：冷启动用户与老用户的回答满意度对比

### Q29 可观测性
- tracing：LangGraph 节点级耗时/token/检索结果记录（LangSmith 或自建）
- 指标：P50/P95 延迟、检索命中率、拒答率、用户满意度
- 告警：延迟超阈值、检索异常（空召回率突增）
- 回滚：prompt/配置版本化，快速切换

### Q30 反思题
- 技术债：如实说（如评测体系起步晚、记忆系统耦合重）
- 得意设计：分层记忆注入 / 自适应检索 / 两套评测集（选一个展开）
- 资源投入：优先评测基建与可观测性（这是 Agent 项目的护城河）

## 模块二：项目 2 —— 邮箱智能助手（Q31–Q50）

### Q31 Brief workflow 全流程
- 串一遍数据流：扫描 → 去重过滤 → LLM 批量初筛 → 方向感知过滤 → LLM 精细化评估 → cards
- 两级原因：初筛用便宜模型/批量处理快速筛掉低价值，精筛只处理少量高价值邮件（成本精度平衡）
- 明确区分：哪些环节是规则（去重、方向感知），哪些是 LLM（初筛、精筛）

### Q32 批量初筛
- 批量收益：单次调用处理多封，摊薄 prompt 固定开销、提升吞吐
- 批大小权衡：太大 → 输出超长易截断、单封失败影响面大；太小 → 成本优势消失
- prompt 设计：结构化分隔（编号、分隔符）、要求输出 JSON 数组
- 失败处理：输出格式校验失败 → 该批拆分重试

### Q33 方向感知过滤
- 过滤目标：营销推广、系统通知、新闻订阅等低价值邮件
- 实现：规则（发件人域名、关键词）+ LLM 判断结合
- 漏判兜底：白名单（重要发件人不过滤）；过滤只影响「是否精筛」，不直接丢弃

### Q34 精细化评估
- 维度：紧急度、与用户的相关性、是否需要行动（回复/审批/知悉）
- 打分：分档（高/中/低）+ 一句话理由，阈值由产品校准
- 冲突裁决：精筛结果覆盖初筛（精筛信息更全）
- 上下文：注入联系人记忆 + Thread 历史（保证判断不丢脉络）

### Q35 cards 流式展示
- 按批推送：用户体验（渐进反馈、可边看边处理）+ 避免长时间空白
- 推送机制：SSE 或轮询（结合项目实际说）
- 失败 cards：标记状态展示，收尾重跑后更新

### Q36 批量重跑与幂等
- 失败分类：超时、限流、输出格式错乱（分别对应不同处理）
- 幂等：以「邮件 ID + 批次 ID」为幂等键，重跑覆盖旧结果
- 部分成功：只重跑失败项，成功后按时间戳合并排序
- 上限：重试 N 次后进人工队列

### Q37 首轮语义展开
- 展开内容：多个搜索词 + 约束条件（时间范围、发件人、已读状态）
- 首轮原因：规划阶段信息最全，展开能减少后续无效工具轮次
- 修正：后续轮次检索无果时可重新展开

### Q38 清退引导层 prompt
- 引导层：规划阶段的任务说明与示例（教模型怎么展开），规划完成即失效
- 实现：物理裁剪历史消息 / 标记忽略（按项目实际）
- 对比项目 1：项目 1 是「持续分层注入」，这里是「一次性用完即弃」
- 效果：token 节省量、后续轮次速度提升

### Q39 工具集设计
- 原则：单一职责、参数语义明确、描述含使用示例
- 失败处理：返回结构化错误信息（而非裸异常），模型可据此换策略
- 数据传递：工具结果写入对话 state，后续工具/生成阶段引用

### Q40 多轮动态探索
- 复杂度信号：多条件（时间+发件人+主题）、多实体（多个联系人）
- 终止：结果满足 / 轮次上限 / 无进展检测（连续两轮无新信息即停止）
- 防重复：搜索历史去重，禁止重复调用相同参数

### Q41 联系人记忆
- 提取维度：关系状态（合作中/冷淡）、待办（欠对方的回复）、交互摘要
- 模型：小模型 + 批处理（离线）控制成本
- 冲突合并：新证据更新旧记忆（时间戳 + 置信度加权）
- 时机：异步批处理，不阻塞主流程

### Q42 记忆注入点
- Phase 2 评估：需要发件人历史判断「这封邮件重不重要」（如老板的习惯）
- Ask 阶段：生成回复需要关系脉络（语气、未完成事项）
- 注入方式：检索召回 + token 预算截断；无记忆时降级为通用 prompt

### Q43 两种记忆策略对比
- 常驻摘要：持续占用 token，但上下文稳定（适合长会话）
- 阶段注入：按需使用，省 token（适合流水线式批处理）
- 设计原则：按信息使用频率与稳定性分层——高频稳定的进常驻，低频按需检索
- 互换推演：项目 1 若阶段注入 → 对话中途频繁检索，延迟高；项目 2 若常驻 → 批量任务 token 浪费

### Q44 多邮箱与 OAuth
- 协议抽象：统一适配层屏蔽各家差异（Gmail API / IMAP / 授权码）
- OAuth：access token 短效 + refresh token 长效，过期自动刷新
- 调度：多账户并发扫描，注意服务商 API 限流

### Q45 安全与合规
- 脱敏：正文送 LLM 前处理敏感信息（电话、身份证等，按公司规范）
- 模型选择：是否可用云端 API 由公司合规评审决定（数据出境）
- 授权：用户显式授权 + 可随时撤销；撤销后清理该用户数据

### Q46 误判风险控制
- 兜底规则：VIP 发件人（老板/客户）强制高优先级，绕过模型判断
- 人工确认：草稿生成后用户确认才发送（默认不自动发）
- 纠正入口：用户可修改优先级判断结果，形成反馈

### Q47 反馈闭环
- 隐式信号：采纳率、修改率、未打开率
- 回流：不采纳的 case 作为记忆证据（该发件人偏好）与评估样本
- 指标：采纳率目标值（按实际说）

### Q48 触发机制
- 方案对比：IMAP IDLE（推送但连接不稳定）、Webhook（Gmail 支持）、轮询（通用但延迟）
- 增量扫描：游标/时间戳，只处理新邮件
- 平衡：高频轮询 → 实时性好但成本高；低频 → 反之

### Q49 规模化成本
- 估算方法：邮件数 × 每封平均 token × 单价
- 优化：模型路由（初筛小模型）、批处理、结果缓存（同 Thread 不重复评估）
- 并发控制：令牌桶限流，防止触发供应商限流

### Q50 效果衡量
- 离线：分类准确率/召回率、单封成本、处理时长
- 线上：草稿采纳率、用户处理邮件时间节省、日活
- 基线：与「不用助手」或「全量精筛」方案对比

## 模块三：技能特长相关（Q51–Q65）

### Q51 B+ 树索引
- 结构三要素：多叉平衡树、非叶只存索引键、叶子层双向链表串起全部数据
- 对比 B 树：B+ 树非叶不存数据 → 同样页大小能容纳更多键 → 树更矮 → IO 次数更少
- 对比哈希：哈希点查快但无范围查询；对比红黑树：二叉树太高，磁盘 IO 多
- 页分裂：插入导致页满 → 分裂成两页，代价高；自增主键顺序写入避免随机分裂

### Q52 聚簇索引与回表
- 聚簇索引：叶子节点存整行数据，主键即聚簇索引
- 二级索引：叶子存主键值；查非索引列需「回表」再走聚簇索引
- 覆盖索引：查询列全在索引中 → 不回表（Using index）
- UUID 主键：随机插入 → 页分裂频繁 + 索引树碎片（对比自增的顺序追加）

### Q53 MVCC 与隔离级别
- 四级别：读未提交 / 读已提交 / 可重复读 / 串行化（默认 RR）
- MVCC 三件套：隐藏列（trx_id、roll_pointer）、Undo log 版本链、ReadView
- ReadView 可见性判断：trx_id 与活跃事务列表比较
- RR 下快照读（普通 SELECT）防幻读；当前读（for update）靠间隙锁防幻读

### Q54 Redo / Undo / Binlog
- Redo：物理日志，崩溃恢复（保证持久性）；WAL 先写日志再写盘
- Undo：逻辑日志，事务回滚 + MVCC 版本链（保证原子性/隔离性）
- Binlog：Server 层逻辑日志，主从复制 + 数据归档
- 两阶段提交：redo prepare → binlog → redo commit，保证两者一致性（主从一致）

### Q55 行锁 / 间隙锁 / next-key
- 行锁：锁具体记录；间隙锁：锁记录之间的区间；next-key = 行锁 + 间隙锁
- 间隙锁产生条件：RR 级别 + 当前读 + 等值/范围查询
- 死锁排查：SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK
- 避免：统一加锁顺序、事务尽量小、必要时用乐观锁

### Q56 联合索引与最左前缀
- 本质：B+ 树按 (a, b, c) 列顺序组织，必须先匹配 a 才能利用索引
- `b=1 AND c=2` 用不上（缺少 a）
- 失效场景：列上函数/运算、隐式类型转换、LIKE '%x' 前置通配、OR 部分无索引
- 结合项目：自己的表里哪个联合索引，查询怎么写

### Q57 Redis 数据类型
- 五种 + 各自底层：String（SDS）、List（quicklist）、Hash（listpack/哈希表）、Set、ZSet（listpack/跳表）
- SDS 优势：O(1) 取长度、二进制安全、预分配减少重分配
- 小对象用 listpack 省内存，超阈值升级（hash-max-listpack-entries 等）
- 结合项目：缓存什么、什么类型、为什么

### Q58 RDB 与 AOF
- RDB：全量快照，fork 子进程 + COW 写时复制（fork 瞬间阻塞、之后不阻塞主进程）
- AOF：命令追加，重写解决文件膨胀（子进程重写 + 重写缓冲）
- 混合持久化：RDB 快照 + 增量 AOF（4.0+）
- 取舍：RDB 丢数据窗口大但恢复快；AOF 可配 everysec 近似不丢；everysec 最坏丢 1 秒

### Q59 缓存三问题
- 穿透：查不存在的 key 直达 DB → 空值缓存（短 TTL）或布隆过滤器
- 击穿：热点 key 过期瞬间高并发 → 互斥锁重建 / 逻辑过期（异步重建）
- 雪崩：大量 key 同时过期 → TTL 加随机值 / 多级缓存 / 限流降级
- 布隆过滤器：位图 + 多个哈希，有误判率、不可删除

### Q60 淘汰策略
- 8 种：noeviction / allkeys-lru / volatile-lru / allkeys-lfu / volatile-lfu / random / volatile-ttl 等
- 近似 LRU：采样 + 时钟（LRU 时钟字段），非精确
- LFU：访问频率 + 时间衰减（lfu-decay-time）
- allkeys vs volatile：是否只淘汰带 TTL 的 key

### Q61 Redis 分布式锁
- SET key value NX PX timeout：加锁与过期必须原子
- 过期时间：需大于业务最长执行时间，否则锁被提前释放
- watchdog：Redisson 后台线程自动续期（防业务没跑完锁过期）
- Redlock 争议：时钟跳跃、GC 停顿导致锁失效窗口；Martin Kleppmann 与 Antirez 的论战

### Q62 Redis 集群
- 三种模式：主从复制（读写分离）、哨兵（自动故障转移）、Cluster（分片）
- Cluster：16384 槽、key → CRC16 → 槽；gossip 协议传播节点状态
- 槽迁移：ASK（迁移中单次）与 MOVED（永久）重定向
- 哨兵 vs Cluster：哨兵是「高可用」不是「分片」；数据量大必须 Cluster

### Q63 缓存一致性
- Cache-Aside 顺序：先更 DB 再删缓存——避免「先删缓存、后更 DB」窗口内旧数据写回缓存
- 延迟双删：删缓存 → 更 DB → 延时再删一次（防并发读旧值回填）
- 失败补偿：删除失败 → 重试队列 / 订阅 binlog（canal）异步兜底
- 本质：接受短暂不一致（最终一致），用补偿机制收敛

### Q64 GIL
- GIL：CPython 解释器全局锁，同一时刻仅一个线程执行字节码
- 影响：CPU 密集多线程无效甚至更慢；IO 密集有效（IO 等待时释放 GIL）
- 绕开：多进程、C 扩展（计算中释放 GIL）、free-threading（3.13 实验版）
- 结合项目：推送/扫描 IO 密集可用线程/协程，CPU 密集走多进程

### Q65 FastAPI 异步
- async def：事件循环直接跑；def：线程池跑（不阻塞事件循环）
- 阻塞调用（同步 DB driver）放 async def = 卡死整个事件循环
- 实践：全异步驱动，或同步调用 run_in_executor
- uvicorn：asyncio 事件循环 + worker 配置

## 模块四：计算机基础（Q66–Q80）

### Q66 进程线程协程
- 三要素对比：隔离性（地址空间）、调度权（内核/用户态）、切换成本（页表+TLB vs 栈 vs 用户态切换）
- 进程：资源分配单位；线程：CPU 调度单位；协程：用户态协作式调度
- 协程切换不陷入内核，成本最低；但一个阻塞全卡住（协作式）
- 结合项目：异步推送/扫描用协程，CPU 密集用进程

### Q67 虚拟内存与分页
- 目的：进程地址空间隔离 + 内存换入换出（磁盘作后备）
- 多级页表：按需分配、省内存（未用地址空间不占页表）
- TLB：页表缓存（硬件），miss 代价大（多级页表遍历）
- 缺页中断：页不在内存 → 从磁盘换入 → 重新执行指令；频繁缺页 = 抖动

### Q68 IPC
- 管道：单向、父子进程；共享内存：最快（无拷贝）但需同步；消息队列：内核维护、有边界；信号：异步通知；socket：跨主机
- 共享内存快的原因：数据不经过内核拷贝，双方直接映射同一物理页
- 结合项目：跨进程用 Kafka（解耦 + 持久化 + 多消费者），不是共享内存（同机、耦合）

### Q69 epoll
- 核心：红黑树管理 fd + 就绪链表返回就绪事件；O(1) 获取就绪 fd，不用遍历
- 对比 select/poll：轮询 O(n) + fd 上限（select 1024）；epoll 事件驱动
- LT：未处理完一直通知（默认、安全）；ET：状态变化只通知一次（高效、需非阻塞+读完）
- 惊群：多进程 epoll 同一 fd 同时唤醒 → EPOLLEXCLUSIVE / SO_REUSEPORT

### Q70 死锁
- 四条件：互斥、占有且等待、不可剥夺、循环等待（破坏其一即可预防）
- 银行家：资源分配前检查是否处于安全状态（安全序列）
- 工程：统一加锁顺序、锁超时、减少锁粒度/持有时间
- 联系 MySQL：innodb 死锁检测（wait-for graph）与自动回滚牺牲事务

### Q71 用户态内核态
- 特权级别：内核态可访问全部资源，用户态受限；通过系统调用切换
- 系统调用过程：陷入内核 → 查表 → 执行 → 返回（现代 CPU 用 syscall 快速指令）
- 上下文切换开销：寄存器保存/恢复、TLB 刷新、缓存失效
- 优化：减少系统调用次数（批处理、vDSO 不陷入内核）

### Q72 malloc 与内存管理
- brk：移动堆顶指针，小块内存；mmap：独立映射，大块（默认阈值 128KB，可调）
- 碎片：内部碎片（分配粒度）、外部碎片（空闲块不连续）
- 内存池：预分配 + 复用减少 malloc 开销与碎片
- Python：引用计数 + 分代 GC 处理循环引用；与 C 手动管理对比（安全 vs 性能）

### Q73 TCP 握手挥手
- 三次：SYN → SYN+ACK → ACK；两次的问题：服务端无法确认客户端收包能力、历史连接问题
- 四次挥手：双向关闭（FIN → ACK；FIN → ACK），中间 ACK 与 FIN 可合并为三次
- TIME_WAIT：主动关闭方等 2MSL（保证对端收到 ACK、旧包消亡）
- SYN Flood：半连接队列打满 → SYN Cookie（无状态校验）

### Q74 拥塞控制
- 四阶段：慢启动（指数增长）→ 拥塞避免（线性）→ 快重传（3 个重复 ACK）→ 快恢复
- 拥塞窗口（cwnd）与接收窗口（rwnd）取小者为发送窗口
- BBR：基于带宽时延积建模，不把丢包当拥塞信号（适合高丢包链路）
- 结合项目：文件上传/流式响应对拥塞的感知

### Q75 HTTP 演进
- 1.1：连接复用（keep-alive）但队头阻塞；2：二进制分帧 + 多路复用，但 TCP 层仍有队头阻塞
- 3：QUIC（UDP 上实现可靠传输 + TLS 1.3），解决 TCP 队头阻塞、连接迁移
- 结合项目：SSE 流式对话走 HTTP/1.1 也可以，HTTP/2 多路复用更适合并发资源

### Q76 HTTPS
- 握手：非对称加密协商会话密钥 → 后续对称加密通信（性能）
- 证书链：服务器证书 → 中间 CA → 根 CA（信任锚预置在系统）
- 防中间人：证书校验（CA 签名 + 域名匹配）+ CT 证书透明日志
- TLS 1.3：握手 1-RTT（0-RTT 重连但无前向安全重放风险）

### Q77 DNS
- 流程：浏览器缓存 → hosts → 本地 DNS 服务器 → 递归/迭代查根域 → 顶级域 → 权威服务器
- 记录：A（IPv4）/ AAAA（IPv6）/ CNAME（别名）/ MX（邮件）
- 劫持：运营商/本地 DNS 返回错误 IP → HTTPDNS（走 HTTP 直接查权威）、DoH 加密

### Q78 粘包拆包
- 根因：TCP 是字节流，无消息边界；发送端合并、接收端按缓冲区大小任意切分
- 方案：定长消息 / 长度前缀 / 分隔符（各自优缺点）
- 框架层已解决：HTTP 用 Content-Length、WebSocket 有帧格式
- 结合项目：如果自研 TCP 协议才需自己处理，HTTP/WS 场景框架兜底

### Q79 WebSocket 与 SSE
- WebSocket：全双工、二进制支持、需升级握手；SSE：单向（服务器→客户端）、基于 HTTP、自动重连
- AI 流式输出常用 SSE：单向够用、穿透代理友好、实现简单
- 心跳：WS 无数据时发 ping/pong（保活 + 检测死连接）；代理 60s 空闲断连是常见坑
- 断线重连：指数退避 + 消息序号补偿（重连后拉取漏掉的数据）

### Q80 Nagle 与延迟 ACK
- Nagle：小包合并发送（等待 ACK 或凑满 MSS）；延迟 ACK：收到数据延迟确认（最多 200ms）
- 两者叠加：小包交互场景产生 40ms 级延迟
- TCP_NODELAY 禁用 Nagle：游戏、实时交互、SSE 推送场景
- 原则：交互式应用关 Nagle，批量传输保留

## 模块五：Agent 领域（Q81–Q100）

### Q81 RAG 流程与瓶颈
- 三段：索引构建（切块 → embedding → 入库）→ 检索（向量召回 + 可选重排）→ 生成（证据注入 prompt）
- 瓶颈：召回不全/不准、延迟（检索+生成串行）、证据组织不好导致生成忽略
- 与长上下文取舍：小规模文档可全文塞入，大规模/高频更新必须 RAG
- 结合项目：两个项目各自瓶颈与解法（自适应检索 / 证据覆盖度）

### Q82 Chunking 策略
- 固定长度：简单、成本低，但语义断裂
- 结构感知：按标题/条款边界切，保语义完整（政策场景最优）
- 语义切分：按 embedding 相似度找边界，成本高
- 父子切块：子块精确召回 + 父块补全上下文
- 参数来源：评测驱动调优，不是拍脑袋

### Q83 GraphRAG vs RAG
- GraphRAG：实体关系抽取 → 知识图谱 → 社区检测 → 社区摘要；擅长多跳与全局性问题（「总结全文」）
- RAG：局部相似度检索，擅长事实性点查
- 成本：GraphRAG 构建贵（抽取 + 摘要），查询也贵（多社区摘要）
- 结合项目：Neo4j 存结构化关系（学生-课程-活动），与 GraphRAG 社区摘要是两回事——主动说明区别

### Q84 HyDE
- 原理：用 LLM 生成「假设答案」，以假设答案的 embedding 检索（文档与答案在语义空间更近）
- 适用：问题与文档表述差异大（口语化问题 vs 书面文档）
- 风险：假设答案的幻觉会误导检索；事实性政策查询慎用
- 结合项目：HyDE 是备选策略，触发条件与频率（按实际说）

### Q85 ReAct
- 循环：Thought（推理）→ Action（调工具）→ Observation（观察结果）→ 重复
- 与 function calling：function calling 是 Action 的落地机制，ReAct 是推理范式
- 不收敛原因：工具结果差/重复、目标描述不清、观察信息不足
- 干预：轮次上限、重复动作检测、进度评估；结合两个项目的上限设置

### Q86 Plan-and-Execute vs ReAct
- P&E：先完整规划（任务分解）再逐步执行；适合多步骤、依赖明确、可预规划的任务
- ReAct：边想边做，依赖环境反馈；适合探索性、不确定任务
- P&E 风险：规划错误全局失败；补救：执行中检测偏差触发重规划
- 结合项目：在线检索探索性强 → 选 ReAct；推送等批处理流程 → 固定 pipeline 而非 P&E

### Q87 Reflection
- 核心：执行后自我评估 → 发现问题 → 带着教训重新执行
- Reflexion：将反思结果存入长期记忆，跨任务复用（区别简单 self-correction 的一次性）
- 反思内容：动作是否有用、结果是否达预期、下次怎么改
- 成本：额外 LLM 调用；结合项目：评测驱动优化算「外循环反思」，对话内可加「自查引用」步骤

### Q88 MCP
- 定位：模型与外部工具/数据的标准化协议（客户端-服务器）
- 三原语：Tools / Resources / Prompts；对比普通 API：统一发现机制、上下文传递、少适配
- 2026-07 无状态化：移除持久 session，引入 server/discover 等（知识库 mcp/001 有详细解析）
- 结合实际：用过哪些 MCP server，解决了什么问题

### Q89 A2A vs MCP
- MCP：Agent ↔ 工具/数据（垂直集成）；A2A：Agent ↔ Agent（水平协作）
- A2A 解决：能力发现（Agent Card）、任务委派、状态同步、多 Agent 会话
- 两者互补不冲突：Agent 用 MCP 连工具，用 A2A 连别的 Agent
- 结合项目：实时图 + 异步图若改为独立 Agent 协作，A2A 是可选方案（对比现在的 DB/Redis 中转）

### Q90 上下文压缩
- 四策略：滑动窗口（简单丢旧）、递进摘要（压缩保语义）、向量检索（按需召回）、重要性评分（选择性保留）
- 适用判断：长对话用摘要，跨会话用检索，关键指令用评分保留
- 信息保真：摘要与丢弃的边界——「不可再生的关键约束」不能丢
- 结合项目：项目 1 分层注入、项目 2 清退引导层，都属于「按需裁剪」思路

### Q91 工具设计
- 描述质量：一句话职责 + 参数说明（类型/格式/示例）+ 何时用/何时不用
- 失败处理：结构化错误返回（模型能理解并调整），重试上限，降级路径
- 工具治理：数量爆炸 → 命名空间分组、按任务阶段动态注入工具集
- 结合项目：项目 2 五个工具按「查询-读取-生成」职责拆分，单一大工具会让模型混淆

### Q92 子智能体
- 机制：独立上下文 + 专项任务 + 结果回传（与主对话隔离）
- 与工具的区别：子智能体多步推理/自主规划，工具单步动作
- 拆分子智能体时机：任务可独立定义、需要大量中间探索、避免污染主上下文
- 实践：并行调研多个代码库、独立审查——结合自己日常使用 Claude Code 的经验

### Q93 Skill
- 定位：可复用「知识 + 流程 + 提示词模板」的打包（渐进式披露，按需加载）
- 与 MCP 边界：Skill 管「怎么想/怎么做」（提示词层），MCP 管「能连什么」（能力层）
- 适合承载：写作规范、领域 SOP、检索流程
- 结合实践：你写过什么 Skill（本项目 interview-qa 规范就是 Skill 的实例）

### Q94 Hook
- 事件：PreToolUse / PostToolUse / Stop / Notification / UserPromptSubmit 等
- 用途：权限控制（拦截危险命令）、日志审计、注入上下文、触发外部流程
- 失败语义：非零退出码的行为（阻止工具执行等），设计健壮性（超时、幂等）
- 结合实践：本项目的 settings 里配置过的 hook 例子

### Q95 Harness Engineering
- 定义：把 Agent 当作「产品」工程化交付——评测集、指标、CI 回归、可复现实验
- 与评测系统关系：评测是 harness 的核心组件，harness 还包括数据管线、版本管理
- 结合项目：项目 1 的 Ragas 系统 + 数据闭环就是 harness 实践
- 必备能力：版本化评测集、可复现跑分、新改动自动回归

### Q96 Agent 评测方法
- judge 偏差：位置偏差（先出现得分高）、长度偏好（长回答虚高）、自利偏差
- 缓解：随机顺序、成对比较、多个 judge 交叉验证、锚定示例
- 组件评测（检索 recall@k、工具成功率）与端到端评测（任务完成率）结合
- Ragas 只覆盖 RAG 部分，完整 Agent 评测还需任务成功率、轨迹质量

### Q97 多 Agent 共享记忆
- 三层区分：消息（即时交换）、共享任务状态（黑板模式）、长期记忆（知识沉淀）
- 一致性：并发写入冲突 → 版本化/最后写入者 + 置信度
- 权限边界：哪些记忆对哪些 Agent 可见
- 结合项目：实时图 + 异步图通过 DB/Redis 共享画像 = 一种「黑板式共享状态」，可主动类比

### Q98 长循环注意事项
- 上下文膨胀：压缩策略兜底（摘要/清退）
- 目标漂移：周期性对照初始目标自检
- 死循环防护：重复动作检测（哈希动作序列）、最大步数、token/时间预算
- 结合项目：异步图长时运行，靠状态持久化 + 幂等 + 告警防护

### Q99 成本优化
- 手段谱系：prompt 缓存（稳定前缀）> 模型路由（简单任务小模型）> 批量处理 > 上下文压缩 > 精简 prompt
- 结合项目：项目 2 批量初筛 + 清退 prompt；项目 1 分层注入 + 模板推送
- 平衡原则：关键路径（精筛、政策回答）用强模型保质量，非关键路径（分类、摘要）用小模型
- 可量化：单次对话成本、单封邮件成本（算出来更有说服力）

### Q100 沙箱
- 隔离层级：进程级 < 容器级 < 微虚拟机（gVisor/Firecracker）< 全虚拟化
- 核心：权限最小化 + 资源限制（CPU/内存/网络）+ 可观测
- 结合项目：教育智能体执行「业务办理」若涉及真实系统操作 → 需要只读沙箱 + 人工确认
- 项目 2 若自动发送邮件：审批闸门（先草稿后确认）就是「行为沙箱」的产品形态

# 谈谈什么样的代码是可复用、可扩展的

## 题目

面试中常被问到：「你觉得什么样的代码是可复用、可扩展的？写代码时你怎么保证可复用性和可扩展性？」常见追问包括：复用和扩展是什么关系、开闭原则怎么落地、什么时候不该抽象、继承与组合怎么选等。

## 面试直接答

> 可复用与可扩展是同一枚硬币的两面，都要求代码围绕「变化」来组织：可复用指一段代码不修改自身就能在多个场景被安全使用，可扩展指新需求以「添加新代码」而非「修改旧代码」的方式落地。核心机制是抽象——把稳定部分收敛为契约，把易变部分隔离为实现，让依赖永远指向稳定抽象，这正是开闭原则与依赖倒置的实质。它的适用边界在于：抽象只为真实出现过的变化买单，一次性代码和稳定代码不需要预留扩展点。

什么样的代码可复用？我认为有三个条件：功能内聚、契约清晰、无隐藏依赖。功能内聚指一段代码只做一件事，换个上下文它做的事不变味；契约清晰指输入输出只依赖公开接口，不靠隐式约定；无隐藏依赖指它不悄悄读全局变量、不自己 new 具体实现、不写死环境。典型反例是把税率、数据库连接串、时区都写死在函数里——逻辑本身可能很正确，但离开当初那个项目一步都走不动。改法是参数化与依赖注入：同一段计价逻辑，把税率变成参数就能跨国家复用，把仓储变成接口就能跨存储复用。

可扩展的代码，核心标准是开闭原则——软件实体对扩展开放、对修改关闭。这句话的工程含义是：预期内的行为变化应当通过增加新代码实现，而不是改动已有代码。实现的机制是把变化点收敛到稳定的扩展点上：策略模式把算法变体变成可替换的实现，模板方法把流程骨架固化、把易变步骤留白，注册表与 SPI 让插件在编译期之后接入，事件让发布方不知道订阅方存在。衡量指标很简单：为代码列出三种最可能的变化——新增一种实现、修改一条规则、替换一个底层依赖——如果每种变化都只影响一个模块，可扩展性就是好的。

可复用和可扩展高度相关但不完全等同。复用侧重「不修改自己就能被多个场景使用」，扩展侧重「新增能力时不动旧代码」，两者共同依赖抽象质量。关键手段有四：一是依赖倒置，依赖抽象而非具体类；二是接口隔离，接口按使用方定制而不是按实现方堆积；三是组合优于继承，通过组合复用行为而不是通过继承链条复用实现细节；四是配置与代码分离，把变与不变的边界显式画出来。继承是最容易被滥用的复用手段——它复用的是实现而不是契约，基类一改所有子类跟着变，而组合只依赖对方的接口。

判断该不该抽象，工程界有一条经验法则叫「三次法则」：第一次出现直接写，第二次出现保持观察，第三次出现再抽象。前两次复制，是因为样本还不足以判断真正的变化轴在哪里；过早抽象往往选错抽象，比重复代码更贵——重复代码删除即可，错误抽象要拆开还债。抽象的正当性来自两个以上真实用例，或者一条已经发生过的变更记录，而不是来自想象中的未来需求。

总结来说，可复用可扩展不是代码的装饰属性，而是真实变更成本的投影：好的设计，新需求落地时改动的文件少、改动的都是独立模块；坏的设计，一个需求要横切十几个文件。答案可以归结为三句话：让频繁一起变化的代码聚在一起，让变化节奏不同的代码彼此隔离，让依赖指向稳定的抽象。代码库的复用性和扩展性，最终由重复代码的收敛速度和新需求落地时改动的文件数来验证，而不是由接口和抽象类的数量来验证。

### 通俗版：用生活场景快速理解

可复用像标准零件：轮胎、灯泡、充电器都有国家标准接口，任何车、任何灯、任何手机都能换着用，零件本身不需要为某一台设备做任何改造。不可复用的代码像定制的焊死零件——修这台机器很好用，换一台机器就得重做。

可扩展像模块化改装：游戏电脑预留了 PCIe 插槽和标准电源接口，加显卡、加硬盘都不用动主板；不可扩展的代码像一体机，想换个硬盘只能整机报废。

合起来就是一句话：好代码像宜家的家具系统——零件是通用的（复用），接口是标准的（扩展），新配件不断上架，旧家具不用拆。但也要记住反例：如果连一把一次性凳子都要做成五十个通用零件，说明书会比凳子还贵——抽象本身也有成本。

## 详细解析

### 一、可复用代码的三个条件

| 条件 | 含义 | 反面症状 |
| --- | --- | --- |
| 功能内聚 | 只做一件事，换个上下文不「变味」 | 上帝函数，一半逻辑与调用场景绑定 |
| 契约清晰 | 输入输出只依赖公开接口 | 隐式约定，靠文档口口相传 |
| 无隐藏依赖 | 不读全局变量、不 new 具体实现 | 悄悄读环境变量、内部 new 出第三方客户端 |

同一个「折扣计算」的三种写法，恰好对应复用能力的三个台阶：

```
// 写法1：不可复用——税率、数据库、渠道全部写死
public class PriceService {
    public double getFinalPrice(Item item) {
        double tax = 0.13;                          // 写死的税率
        Connection conn = DbUtils.getConn();        // 全局连接池
        double discount = conn.queryDiscount(item.getSku());
        return item.getPrice() * (1 + tax) * (1 - discount);
    }
}
// 换一个国家、换一个数据源，都得改这个函数
```

```
// 写法2：参数化——去掉硬编码，跨场景复用
public class PriceService {
    public double getFinalPrice(Item item, double taxRate, double discount) {
        return item.getPrice() * (1 + taxRate) * (1 - discount);
    }
}
// 同一段逻辑，任意税制、任意折扣规则下都可复用；测试只需三个数字
```

```
// 写法3：接口化——把"变化的规则"抽象出去，扩展时不动这段代码
public interface DiscountRule {
    double discount(Item item);
}

public class PriceService {
    private final double taxRate;
    private final DiscountRule rule;

    public PriceService(double taxRate, DiscountRule rule) {
        this.taxRate = taxRate;
        this.rule = rule;
    }

    public double getFinalPrice(Item item) {
        return item.getPrice() * (1 + taxRate) * (1 - rule.discount(item));
    }
}
// 新增"双十一规则" = 新增一个 DiscountRule 实现类，PriceService 一行不改
```

### 二、可扩展代码的标准：开闭原则

**开闭原则**（Open-Closed Principle，OCP）最初由 Bertrand Meyer 在 1988 年出版的《Object-Oriented Software Construction》中提出：软件实体应当对扩展开放、对修改关闭。Robert C. Martin 将其纳入 SOLID，并给出了更工程化的表述——应当能够在不修改模块源代码的情况下改变模块的行为。Martin 后来提出的多态版 OCP（Polymorphic OCP）进一步建议用**接口**而非继承作为扩展点，因为继承会把子类绑定在基类的实现细节上。

五种常用扩展点，按变化类型选择：

| 扩展点 | 机制 | 适合的变化 | 成本 |
| --- | --- | --- | --- |
| 接口 + 多态 | 调用方只依赖接口，新增实现类 | 算法/渠道/格式变体 | 低 |
| 模板方法 | 基类固化流程骨架，子类填空 | 流程固定、步骤可变 | 低 |
| 事件/发布订阅 | 发布方发事件，订阅方自行接入 | 新模块订阅既有流程 | 低（引入异步语义） |
| 注册表/SPI | 运行时发现实现，如 ServiceLoader | 编译期之后接入插件 | 中 |
| 配置化 | 规则/阈值外置 | 参数级变化 | 低（类型安全下降） |

**接口 + 多态**——扩展前加一种导出格式就要改方法，扩展后新增类即可：

```
// 扩展前：每加一种格式都要改这个方法（违反 OCP）
public class ReportExporter {
    public byte[] export(String format, Report report) {
        if ("pdf".equals(format)) return renderPdf(report);
        if ("excel".equals(format)) return renderExcel(report);
        throw new IllegalArgumentException("unsupported: " + format);
    }
}
```

```
// 扩展后：新增格式 = 新增类，原文件不再变化
public interface ReportRenderer {
    String format();
    byte[] render(Report report);
}

public class PdfRenderer implements ReportRenderer { /* ... */ }
public class ExcelRenderer implements ReportRenderer { /* ... */ }

public class ReportExporter {
    private final Map<String, ReportRenderer> renderers = new HashMap<>();

    public ReportExporter(List<ReportRenderer> registry) {  // 构造时注入全部实现
        for (ReportRenderer r : registry) renderers.put(r.format(), r);
    }

    public byte[] export(String format, Report report) {
        ReportRenderer r = renderers.get(format);
        if (r == null) throw new IllegalArgumentException("unsupported: " + format);
        return r.render(report);
    }
}
// 新增 CsvRenderer 后，ReportExporter 源码一行不改——"对扩展开放、对修改关闭"
```

**模板方法**——流程骨架固化在基类，易变步骤留给子类：

```
// 模板方法：先抽取、再清洗、后装载的顺序是稳定规则
public abstract class AbstractEtlJob {

    public final void run() {            // final：骨架不允许子类改
        List<Row> raw = extract();
        List<Row> clean = transform(raw);
        load(clean);
    }

    protected abstract List<Row> extract();
    protected abstract List<Row> transform(List<Row> raw);
    protected abstract void load(List<Row> rows);
}

public class UserEtlJob extends AbstractEtlJob {
    @Override protected List<Row> extract() { /* 从 MySQL 抽 */ }
    @Override protected List<Row> transform(List<Row> raw) { /* 脱敏 */ }
    @Override protected void load(List<Row> rows) { /* 写入数仓 */ }
}
// 新增一个报表任务 = 再写一个子类；"先验后载"的流程规则永远不会被子类破坏
```

**SPI**——编译期之后的扩展，插件与宿主只共享一个接口契约：

```
// 契约（打成独立 jar）：META-INF/services/com.example.IdGenerator
// 内容：com.example.snowflake.SnowflakeIdGenerator

// 宿主程序：运行时发现所有实现，不 import 任何具体类
public class App {
    public static void main(String[] args) {
        for (IdGenerator gen : ServiceLoader.load(IdGenerator.class)) {
            System.out.println(gen.next());
        }
    }
}
// JDBC 驱动就是最大的 SPI 实践：加数据库只需加驱动 jar，不动任何应用代码
```

### 三、核心机制：让依赖指向稳定抽象

```
坏的方向：依赖指向易变的具体实现
   OrderService ──► WechatPayClient
                 ──► MysqlOrderDao
   改一个实现类，调用方全要改

好的方向：依赖指向稳定的抽象契约
   OrderService ──► PaymentGateway（接口） ◄── WechatPayClient
                 ──► OrderRepository（接口） ◄── MysqlOrderDao
   实现随便换，调用方只与契约绑定
```

组合优于继承的经典对比——Java 标准库自己就是最好的教材：

```
// 继承复用：父类实现细节全部泄露给子类
public class ArrayListStack extends ArrayList<String> {
    public void push(String s) { add(s); }
    public String pop() { return remove(size() - 1); }
}
// 用户能绕过 push/pop 直接 add(0, x)、set(1, y)，栈的语义被破坏
// 真实案例：JDK 的 Stack 继承 Vector，insertElementAt 可以往"栈中间"插元素
```

```
// 组合复用：只依赖 List 接口，内部封装细节
public class Stack<E> {
    private final List<E> data = new ArrayList<>();

    public void push(E e) { data.add(e); }
    public E pop() { return data.remove(data.size() - 1); }
    public boolean isEmpty() { return data.isEmpty(); }
}
// 只有三个操作对外可见，语义不可绕过；实现换成 LinkedList 不影响任何调用方
```

### 四、什么时候抽象：三次法则与错误抽象

**三次法则**（Rule of Three，出自 Martin Fowler《Refactoring》一书，由 Don Roberts 提出）：代码第一次出现直接写；第二次出现可以复制；第三次出现再抽象。前两次复制是因为样本不足，无法判断真正的变化轴；这个法则刻意推迟抽象，用来对冲过早抽象的风险。Sandi Metz 在《The Wrong Abstraction》中把后果说得很直白：重复代码删除即可，**错误的抽象**要拆开还债，比重复更贵。

过早抽象的错误示范——两个「看起来一样」的函数被合并：

```
// 过早抽象：两种规则的变化原因不同，被迫挤在一个函数里
public class ShipmentCalculator {
    public double calcCost(double base, double factor, boolean isInternational) {
        return isInternational
                ? base * factor * EXCHANGE_RATE      // 国际：汇率随时波动
                : base * factor * 0.8;               // 国内：固定折扣
    }
}
// 每次汇率规则调整都要改这个"共用"函数，两个业务被迫一起回归测试
```

```
// 正确做法：变化原因不同，就保留两份各自独立的代码
public class DomesticShipping {
    public double cost(double base) { return base * 0.8; }
}

public class InternationalShipping {
    private final ExchangeRateProvider rates;

    public InternationalShipping(ExchangeRateProvider rates) { this.rates = rates; }

    public double cost(double base) { return base * rates.current(); }
}
// 表面"重复"了，实际解除了两个变化原因的耦合（呼应 002 题 DRY 冲突的追问）
```

抽象决策清单：

| 信号 | 该抽象 | 不该抽象 |
| --- | --- | --- |
| 用例数 | 已有两个以上真实调用方 | 只有一个调用方 |
| 变化证据 | 已经发生过一次变更 | 想象中的未来需求 |
| 相似度 | 逻辑与变化原因都相同 | 只是长得像，原因不同 |
| 契约质量 | 一句话能说清接口职责 | 接口名都起不出来 |

### 五、面试追问

**追问 1：复用和扩展是同一个东西吗？**

不是。可复用的代码不一定可扩展：一个写死的工具函数可以在很多场景被调用，但每来一个新场景就要改它本身。可扩展的代码也不一定被复用：一个带插件机制的模块可能只有一个插件。两者的共同基础是「稳定的契约 + 可替换的实现」，但衡量方向不同——复用看「被多少场景调用而不改」，扩展看「新增能力时改动多少旧代码」。所以代码评审里我会分开打分：复用看接口是否足够小、依赖是否足够少；扩展看变化点是否收敛、扩展点是否真的被用过。

**追问 2：开闭原则是不是说代码写好就永远不改？**

不是。Martin 自己对 OCP 的实用态度是「fool me once」：只为已经发生过一次的变化建立扩展点，不为所有想象的变化设防。Bug 修复、领域模型重构、废弃没人用的扩展点，该改就改。「对修改关闭」关闭的是预期内扩展时的旧代码，不是把代码锁进保险箱。一个从未发生过替换的接口，往往应该删掉合并回去——这个判断和 002 题里「解耦不是零耦合」是同一个逻辑。

**追问 3：继承不就是为复用和扩展设计的吗？为什么都说组合优于继承？**

继承复用的是实现，组合复用的是接口。继承有三个硬伤：一是基类实现细节对子类可见，子类被绑定在基类的具体实现上，基类一升级子类行为跟着变；二是继承是编译期的静态关系，运行时无法替换；三是多层继承链让语义难以推理——Java 标准库的 Stack 继承 Vector，继承来的 insertElementAt 可以往「栈中间」插元素，直接破坏栈语义（代码见上文）。继承仍然有正当用途：真正的 is-a 关系且需要多态替换，模板方法就是教科书级的合法继承。默认策略是组合，继承留到有明确替换需求时再用。

**追问 4：你怎么保证抽象出来的契约是稳定的？**

契约不稳定，抽象就是负资产。三条防线：一是接口由使用方定义——依赖倒置的完整含义是「接口跟着调用方的需求走」，使用方只会提出自己真正需要的操作；二是接口隔离——多个窄接口比一个宽接口稳定，宽接口上任何一个实现的变更都会牵动所有使用方；三是契约测试——把接口行为写成一组测试，所有实现共同继承这组测试，实现方换了也不怕行为漂移。实践上我还会限制接口的方法数量，一个接口超过五六个方法，就怀疑它是不是该拆。

**追问 5：可复用的代码怎么让别人真的用起来？**

复用是组织行为，不只是技术属性。技术侧：清晰的契约、文档、语义化版本。组织侧有一条反直觉的经验：不要强制复用——强制共享一个通用模块，会把所有团队的发布节奏耦合在一起，公共组件团队反而成为瓶颈，这也是不少「中台」失败的原因。更好的路径是让相似代码自然出现，出现第三次后由团队自愿收敛成内部库；模块要小、要独立发版、要有示例。复用的引力来自「用它比自写更省事」，而不是来自架构评审的命令。

**追问 6：函数式语言里怎么理解可复用可扩展？**

函数式下可复用的最小单元是纯函数：无副作用、输出只依赖输入，复用不需要理解任何上下文，测试也不需要搭环境。可扩展的核心手段从「接口 + 多态」变成高阶函数与组合子——把变化的部分作为函数参数传入，策略模式退化成一个函数参数；用 map、filter、reduce 组合小函数，而不是继承类。语言虽然不同，结论同构：都是把变化收敛成参数，让依赖指向稳定抽象。

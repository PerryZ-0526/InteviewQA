# ✅Agent 长时间循环的注意事项

## 题目

Agent 在一个任务里面循环了上百次、上千次会发生什么？需要注意什么？

## 面试直接答

Agent 在任务中循环上百次甚至上千次时，主要面临七类问题，而且它们之间会互相加剧。

### 第一是`上下文膨胀`

每次循环通常会产生工具调用参数、工具返回结果、LLM 的推理中间步骤，这些内容全部堆积在主上下文中。假设每次循环新增 1000 token，1000 次累计会生成约 100 万 token；如果每轮还重发不断增长的历史，累计输入量会远大于 100 万，单轮上下文也可能超过所用模型的窗口。

### 即使采用滑动窗口或摘要压缩，也会带来第二个问题——`「信息丢失」`

早期的重要约束条件、用户原始需求、关键决策，可能在多轮压缩后被丢弃或扭曲。Agent 可能做着做着就偏离了初始目标，出现`「目标漂移」`——一直在干活但干的已经不是最初那件事了。所以需要设置不可压缩区来保护用户要求、权限边界和关键决策。

> 1. 除去压缩上下文外，还可以使用`SubAgent`来隔离上下文，SubAgent 只返回结论给主智能体，以缓解主智能体的上下文膨胀；
> 2. 为避免丢失重要信息：1）关键信息会沉淀到记忆系统；2）压缩时优先清理旧工具输出（低风险，可通过再次调用 tool 再次获得），不够了再发起 llm 摘要压缩请求，输出结构化压缩摘要（使用预定义字段指导模型生成任务状态摘要，来保留有价值的信息）

### 第三是 `成本和延迟失控`

每一轮都可能包含模型调用、检索和工具执行，如果每轮成本稳定，整体成本近似随循环次数线性增长；如果每轮重发完整历史，累计输入成本通常会接近二次增长。

> 因此，长循环 Agent 必须具备明确的运行约束。首先要设置最大轮数、最大 Token、最大费用、最长执行时间和工具调用次数等硬预算。其次不能只靠模型判断“任务是否完成”，还要设计可验证的退出条件，例如测试是否通过、目标文件是否生成、待办列表是否为空，或者关键指标是否达到阈值。

### 第四是`错误积累与状态污染`

每次循环中如果工具调用产生了错误结果或幻觉数据，这些错误信息会被写入上下文，后续的推理可能基于错误前提继续推导。更隐蔽的是多次自动重试中部分成功的状态——比如修改了文件 A 但没有修改文件 B，导致代码不一致。

### 第五是`执行停滞（Agent 陷入某种循环逻辑无法跳出）`

表现为两种典型模式：

- 「打乒乓球」，LLM 和工具之间反复调用但每次都得到相似结果、做不出有效进展；
- 「自我纠错死循环」，LLM 意识到有问题后进入修正模式，但修正本身又引入新问题，持续反复。

> 需要检测循环是否仍在产生有效进展。可以记录每轮的目标、动作、结果和状态变化，如果连续多轮没有新增信息、状态没有变化，或者动作模式高度重复，就判定为停滞，触发重新规划、切换策略或提前终止。

### 第六是`模型输出质量随上下文增长而下降`

- `「Lost in the Middle」`现象表明 LLM 对上下文中间位置的信息关注度最低，<span style="background-color: rgb(255, 243, 205)">经典实验中，相关信息位于长上下文中部时表现通常最差；开头和结尾往往相对更好，但超长上下文仍可能让各位置的信息利用率下降。</span>
- 定期对长时间运行的任务做状态总结、`阶段性重置推理焦点`，可以一定程度上缓解这个问题。

### 第七是`工具副作用`

重复发送消息、重复创建资源、重复扣款或重复修改文件，可能造成真实业务事故。

> 工具执行还要保证幂等性、可重试和可回滚。
>
> - 每个操作最好带唯一任务编号，执行前检查是否已经完成；对于高风险操作，应设置审批节点或人工确认。
> - 系统还需要保存检查点，使任务失败后能够从最近状态恢复，而不是从头重新执行。

所以，Agent 能否循环上千次，关键不在于模型能不能持续调用，而在于系统是否具备预算控制、进展检测、上下文压缩、状态持久化、幂等执行、异常恢复和人工接管机制。否则循环次数越多，通常不是能力越强，而是成本和风险越不可控。

## 详细解析

### 一、四种不同的 Token 增长

若每轮新增 1000 Token，共 n 轮：生成量约为 `1000n`；第 n 轮携带完整历史时，输入约为 `1000n`；累计输入约为 `1000 × n(n+1)/2`。所以 10、50、100、500、1000 轮的累计输入约为 5.5 万、127.5 万、505 万、1.2525 亿、5.005 亿 Token，尚未计入系统提示和工具定义。注意力计算复杂度和计费还受模型架构、KV/Prompt Cache 及服务实现影响。

### 二、进展检测

每轮记录子目标、动作指纹、观察、状态差异和新证据。连续多轮没有状态变化、重复动作、错误不变或待办不减少时，先重规划，再无进展则暂停或终止。语义相似度只能辅助，不能代替验收条件和状态不变量。

### 三、上下文与状态

用户目标、当前有效约束、完成证据、未决事项和副作用状态应存为结构化权威状态；摘要不是唯一事实源。完整日志外置并保留源指针，压缩后检查关键数字、否定条件和权限。

### 四、预算与受控停止

预算包括轮数、累计 Token、费用、墙钟时间、工具次数和高风险操作次数。触发上限时先保存检查点，再返回 `PAUSED_BUDGET`、`NEEDS_APPROVAL` 或 `FAILED`。工具结果未知时进入查询/补偿流程，不能直接重跑。

### 五、Lost in the Middle

经典研究观察到长上下文检索常呈 U 形：相关信息在开头或结尾时表现较好，在中间时明显下降。这是经验现象，不代表每个模型和任务都相同。关键约束应进入结构化状态并在决策前显式回读，而不是只调整文本位置。

### 六、四类增长量不能混用

新生成总量、单轮输入长度、累计计费输入和模型内部计算量是不同概念。Prompt Cache 可能降低重复前缀计费或延迟，但逻辑上下文仍存在；滑窗减少输入却丢失历史；摘要新增一次生成成本，收益取决于后续复用次数。

多 Agent 的增长还受通信拓扑影响。局部状态传递可能接近单 Agent；若每轮把所有 Agent 的完整历史广播给所有人，复制量会远高于简单的 `Agent 数 × 轮数 × 单轮消息`。

### 七、基于状态的停滞检测

为每轮记录动作指纹、状态差异、新证据和待办变化。以下信号组合出现时应诊断：等价动作重复且结果不变；错误指纹持续相同；待办不减少；文件状态在两个版本间振荡；连续多轮只解释而不产生可验证进展。

处理顺序可以是诊断、重规划、切换工具或模型、缩小问题、人工接管。阈值要根据合法分页、迭代优化和工具延迟校准，避免误杀正常循环。

### 八、污染控制与阶段化

工具观察要带来源、时间、版本和验证状态；模型推断不能未经验证直接升级为共享事实。失败结果也不能在摘要中改写为成功。文件和数据库修改使用隔离工作区、事务或可恢复版本，重启前先识别已经生效的部分。

长任务按探索、设计、实现、验证和交付等语义阶段切分。阶段结束后外置原始日志，主上下文保留任务契约、阶段结论、证据和下一阶段输入，比固定轮数摘要更能保持信息边界。

### 九、多维预算与安全停止

预算包括累计输入/输出 Token、费用、墙钟时间、工具次数、并发、搜索和高风险动作。软阈值用于预警、压缩和降级；硬阈值触发保存检查点。不可中断操作应先到达安全点，不能在任意指令中间强制终止。

检查点保存任务版本、当前阶段、步骤状态、证据、失败指纹、剩余预算、幂等键和回执、未知操作、未决问题及下一步。恢复时重新核验外部状态，不能把陈旧快照当成当前事实。

### 十、退出状态必须可区分

验收断言通过才是成功；没有新证据但仍有分歧，可以交付显式分歧；预算到顶是暂停；缺权限是等待审批；外部结果未知进入查询或人工处理。模型声称完成只是候选信号，控制器仍要执行验收器。

上千轮不一定意味着设计失败：仿真、搜索、数据处理或长期监控可能天然需要大量迭代。风险在于上千轮都由同一模型读取完整历史自主循环，同时缺少状态外置、预算、阶段验证和恢复协议。

### 十一、一次振荡故障的推演

Agent 修改配置后测试 A 通过、测试 B 失败，于是撤销配置使 B 通过、A 又失败。若系统只看“每轮都有文件变化”，会误判为持续进展。正确做法是记录状态指纹和失败集合，识别两个状态来回切换，要求重新分析共同约束，而不是继续局部修补。

### 十二、一次未知副作用的推演

第 300 轮调用发布 API 后连接中断，随后预算耗尽。停止前必须保存发布意图、幂等键和未知状态；恢复时先查询发布平台，而不是从第 300 轮重放。若已发布则进入验证，未发布才重试，无法确认则人工接管。这个边界比“能不能继续生成下一轮”更重要。

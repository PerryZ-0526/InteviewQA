# Agent 从接收需求到完成工作的完整流程

## 题目

一个 Agent 从收到一个工作需求，到最后把工作做出来，整个过程是怎么样的？请尽量详细地讲清楚里面的技术、架构、运行流程。

## 面试直接答

一个可靠 Agent 从接收需求到完成工作，可以概括为“澄清目标、形成计划、受控执行、持续验证、提交结果、保存证据”六个阶段。入口先把自然语言转成结构化任务，明确目标、非目标、验收条件、权限和预算；如果缺失信息会改变实现方向或触发高风险副作用，就先向用户澄清，否则记录合理假设继续推进。

计划阶段不是追求一次性完美分解，而是确定最小可验证步骤、依赖和风险点。执行器每次只选择一个当前动作，调用工具后把观察结果转成结构化状态，并检查任务是否真实推进。文件、测试、数据库状态或外部回执等客观证据优先于模型自称完成。

外部副作用要单独设计提交协议。每个操作携带幂等键，区分未执行、已执行和结果未知；调用超时但对方可能已成功时，不能盲目重试，应查询确认、补偿或转人工。高风险操作执行前审批，执行后核验。

长任务还需要预算、检查点和恢复状态机。暂停审批、预算耗尽、工具故障和进程崩溃都要先保存任务、计划、完成证据、外部操作状态和下一步。最终交付不仅包含结果，还包含验证证据、未完成项和风险。

所以核心不是堆很多组件，而是保证三件事：开始前知道什么叫完成，执行中每一步都让状态可观察，结束时能用外部证据证明目标达成。

## 详细解析

### 一、最小闭环

`需求 → 任务契约 → 计划 → 动作 → 观察 → 状态更新 → 验证 → 完成或重规划`

模型负责理解、规划和动作选择；控制器负责预算、权限、状态机和工具执行；验证器依据环境证据判断完成，避免模型一句“已完成”直接结束。

### 二、任务契约与状态机

任务契约包含目标、非目标、输入、验收条件、允许范围、禁止事项、预算、风险和假设。只有会改变结果或授权边界的问题才阻塞。

状态机应区分 `PLANNING`、`RUNNING`、`WAITING_APPROVAL`、`PAUSED`、`VERIFYING`、`SUCCEEDED`、`FAILED` 和 `UNKNOWN_SIDE_EFFECT`。审批恢复时重新加载任务版本并检查外部状态，而不是直接继续旧动作。

### 三、副作用提交协议

1. 持久化操作意图和幂等键。
2. 执行前查询是否已有完成回执。
3. 调用外部工具。
4. 可恢复地记录回执和状态。
5. 超时且结果未知时进入 `UNKNOWN_SIDE_EFFECT`，优先查询外部系统。
6. 无法确认时补偿或人工处理。

这处理了“工具成功、进程落盘前崩溃”的窗口；只在调用后记录结果并不足够。

### 四、风险分级验证

读静态文件可以检查路径和内容；写代码要运行格式化、类型检查和针对性测试；发信、付款、删除要同时做审批、幂等、回执确认和审计。验证强度与可逆性、影响面及外部副作用成正比。

### 五、恢复与交付

检查点保存任务契约、计划版本、完成步骤及证据、未决问题、预算、外部操作状态和下一步。失败也应产出可接续状态，而不是只返回异常字符串。

### 六、入口层与任务版本

入口层识别目标对象、产物、验收、权限、预算、时效和风险。低风险细节可以记录假设继续；会改变架构、覆盖数据或联系外部人员的歧义必须澄清。用户补充要求后生成新任务版本，并记录新增、撤销和收窄的约束。

### 七、计划不是一次性作文

每个步骤要声明输入、预期状态变化、验证方法、允许工具、风险和失败动作。无法验证的大步应拆小，但不能把一个原子事务拆成暴露不一致状态的半成品。获得新证据后允许重规划，同时保留触发原因和旧轨迹，防止反复走同一失败路径。

### 八、执行循环的职责分离

模型负责提出候选动作；策略层检查权限、预算和风险；工具层验证参数并调用；观察层规范化结果；状态层记录变化；验证器依据环境证据判断完成。这样“模型建议执行”与“外部动作已经成功”不会混在一起。

```text
while task.state is RUNNING:
    snapshot = load_latest_state(task.id)
    action = planner.next_action(snapshot)
    policy.authorize(action, snapshot.contract)
    intent = persist_intent(action, idempotency_key)
    result = tool.execute(intent)
    observation = normalize_and_validate(result)
    commit_observation(intent, observation)
    verify_or_replan()
```

这只是控制流伪代码。真实实现必须捕获预算、授权、调用、验证和持久化各边界的失败，也不能假设一个本地数据库事务能覆盖任意第三方系统。

### 九、结果未知与补偿

付款 API 超时可能表示请求未到、扣款成功但响应丢失或服务处理中。幂等键由调用方生成并在重试中保持不变；外部系统支持查询时先查最终状态。不支持幂等时，需要业务唯一约束、outbox、对账或补偿降低风险。

补偿不等于回滚。邮件已经发出后只能更正，生产数据被外部消费后也可能无法无痕撤销。因此可逆性、影响范围和人工审批必须在执行前设计。

### 十、审批恢复协议

审批请求要展示动作、参数、影响范围、依据、补偿方案和任务版本。参数或任务版本变化后旧审批失效。恢复时重新读取外部状态和前置条件，因为等待期间资源可能已经被其他执行者修改。

### 十一、验证与异常分型

最强证据来自目标环境：测试退出码、数据库约束、文件哈希、API 回执和业务不变量。验证失败要区分实现失败、验证器故障和环境波动。相同错误连续出现时记录失败指纹，切换策略或暂停，而不是无限让模型重写。

### 十二、并发与多 Agent

共享任务需要步骤所有权、状态版本和冲突策略。乐观并发用版本号拒绝陈旧写入；不可合并的资源使用租约或锁。消息到达不等于任务状态已提交，权威完成状态来自共享状态库和验证证据。

### 十三、交付与可观测性

成功交付包含产物位置、变更、验证结果、限制和后续动作；部分成功要列出完成项、未完成项和未知副作用。每次运行记录任务版本、模型/提示版本、动作、状态差异、证据、费用和延迟，并对敏感参数脱敏。

复盘关注哪个输入、状态或控制边界允许了错误动作，再把案例转成回归测试、策略规则或工具契约，而不是依赖模型对自身推理的事后叙述。

## 面试直接答

我认为 Agent 的效果不能只看最终回答是否正确，而应该从任务结果、执行过程、系统效率、安全性和用户价值几个角度综合定义。因为 Agent 不只是生成一段文字，它还会规划任务、调用工具、修改外部状态，所以最终答案正确，并不代表整个 Agent 系统就是有效的。

### 首先是`任务结果层面`，最核心的是它有没有真正完成用户目标

- 这里不仅看`生成内容的质量`，比如回答是否准确、清晰、可执行，是否覆盖用户需求；
- 还要看完整性、约束满足度和外部状态是否真实生效。

> 比如用户让代码 Agent 修复一个问题，不能只看它是否给出了修改建议，而要看代码是否真正修改、测试是否通过、有没有遗漏关联模块，也要检查是否违反了“不能改接口”或“只能修改指定目录”这类约束。

### 其次是`执行过程`层面，要看 Agent 的规划是否合理、工具选择是否正确、`每一轮循环是否产生有效进展`

一个 Agent 即使最终完成了任务，但中间反复搜索相同内容、不断修改又撤销、依赖大量重试才偶然成功，这种效果也不能算好。

真正稳定的 Agent 应该能够识别失败原因，区分哪些错误可以重试，哪些需要重新规划，并且在出现`部分成功`或`状态污染`时能够验证、回滚和恢复。

### 第三是`系统层面`，需要关注延迟、Token 消耗、模型调用次数、工具成本和资源利用率

效果好的 Agent 不是一味使用最强模型，而是能够把简单步骤交给规则或小模型，把复杂规划交给强模型，并通过上下文压缩、缓存和减少无效调用来控制成本。

> 评价时通常还要看`单位成功任务成本`，而不是只看单次模型价格。

### 另外是`安全性`和`可靠性`

Agent 接入邮件、数据库、代码仓库或生产系统后，必须遵守`权限边界`，高风险操作要有`确认机制`，重复执行要保证`幂等`，整个过程还要`可审计、可恢复`。

> 一个成功率很高但偶尔会误删数据、重复发邮件的 Agent，在真实业务中依然不可用。

### 最后是`用户价值`

Agent 是否减少了用户的操作步骤，是否降低了人工介入和纠正次数，结果是否容易理解和控制，这些都属于效果的一部分。

---

总结来说，我会把 Agent 的效果定义为：
```
在安全和成本约束下，稳定、完整、可验证地完成真实任务，并尽可能减少用户介入，而不是单纯看模型生成内容的质量。
```


## 详细解析

### 一、效果必须绑定真实任务

Agent 的评测对象不是一段文本，而是“在约束下改变环境状态的完整轨迹”。首先把任务写成可判定的目标状态、必须满足的约束、禁止副作用和预算。HumanEval 等基准能覆盖代码正确性的一部分，但不足以独立衡量工具使用、长程恢复和业务价值。

### 二、五层指标

| 层级 | 核心问题 | 优先指标 |
|---|---|---|
| 结果 | 目标状态是否达成 | 可执行断言、业务状态、约束满足率 |
| 过程 | 轨迹是否合理 | 无效步骤率、重复动作率、恢复成功率 |
| 效率 | 成功任务用了多少资源 | 单位成功任务成本、P95 延迟 |
| 安全 | 是否越权或产生副作用 | 越权率、重复执行率、事故率 |
| 用户价值 | 是否减少用户负担 | 完成时间、纠正次数、放弃率 |

安全和正确性应作为硬门槛，再在合格方案中比较成本与延迟，不能随意压成一个总分。

### 三、验证信号优先级

第一优先是测试、数据库状态、文件哈希、API 回执和业务不变量等确定性验证。第二是有金标的人评或经过人类标注校准的模型评审。第三才是多次采样、自洽性、自报置信度和投票；这些只能用于调度，不能证明正确。

LLM Judge 要控制位置、长度、同源模型和提示注入偏差，并用人工金标校准。序数评分可使用加权 Kappa 或相关性，分类任务才适合普通 Kappa。阈值由风险和校准数据确定，不设通用值。

### 四、根因定位与稳定性

参数错误可能来自提示、工具 schema、过时状态或序列化；路径错误可能来自规划、检索或环境信息缺失。应基于结构化轨迹和对照实验定位，不能按表象直接归因。

temperature=0 也不保证系统确定，模型服务、并发、检索和外部数据都可能变化。离线评测应多次运行并报告分位数和失败分布；线上灰度比例和告警阈值由流量、风险及统计功效决定。


### 五、从任务契约推导评测

每条样本应包含初始环境、用户目标、允许操作、禁止操作、验收断言、预算和扰动。以代码修复为例，结果断言包括目标测试通过、回归不退化、公共接口不变和修改范围合规；过程指标记录重复搜索、无效编辑和恢复次数；安全断言检查是否访问禁区或执行未授权命令。

开放任务没有唯一金标时，可以拆成必须满足的事实约束、可比较的质量维度和允许多样化的风格维度。风格开放不代表事实、引用和副作用无法验证。

### 六、过程指标用于诊断，不用于取代结果

步骤更少不一定更好，多一次验证可能显著降低事故。理论最优轨迹通常不可得，可与专家轨迹、强基线、历史最佳分位数或成本—质量 Pareto 前沿比较。参数错误也可能来自工具 schema、序列化或陈旧状态，不能机械归因给提示词。

平均成功率会掩盖关键失败，应按任务类型、难度、权限、工具和输入长度切片，并关注最差切片。高风险任务中的低频严重事故不能被大量简单成功抵消。

### 七、Judge 的正确使用方式

Judge 适合评价语言质量和难以编码的软维度。成对比较通常比绝对打分稳定，但要随机交换顺序；候选内容按不可信输入隔离，防止提示注入。先由人类建立 rubric 和金标，再检查 Judge 在各切片上的偏差和需要人工复核的区间。

同源 Judge 可能与被评模型共享盲区。多 Agent 投票只有在错误相对独立时才可能提高可靠性；相同模型、相同证据和相似提示下，多个回答的一致不是真值证明。

### 八、线上与离线闭环

离线集负责快速复现和版本回归，线上负责发现分布漂移。线上失败要沉淀为可复现样本，并定位到理解、规划、工具、环境、权限、验证器或恢复协议。修复后同时跑原案例和邻近案例，避免对单题过拟合。

记录任务契约、模型和提示版本、工具轨迹、验证证据、费用、延迟及人工纠正；敏感数据要最小化和脱敏。评价结果不仅给总分，还应给失败类型与证据。

### 九、推荐的分层门禁

1. 安全、权限和禁止副作用断言必须通过。
2. 核心目标与关键约束必须通过。
3. 在合格候选中比较完成度、单位成功任务成本和延迟。
4. 软质量再使用校准后的人评或 Judge。

这种设计避免用低成本抵消误删数据，也避免多个弱代理指标相加后制造虚假精确度。

### 十、案例：代码 Agent 的评测样本

初始环境固定在含缺陷的提交，任务要求修复超时重试且不得改变公共接口。验收器检查目标测试、完整回归、接口签名、修改目录和重复请求只执行一次；轨迹侧记录搜索、编辑、测试、回退与 Token。若测试通过但接口被改，结果层直接失败；若结果正确但反复改写 30 次，则在合格结果中以效率指标区分。

### 十一、长期效果的谨慎定义

Agent 通过记忆或规则沉淀改善后续任务时，要同时测正迁移和负迁移。某条经验提高同类任务成功率，却让不同版本 API 被错误套用，就是记忆污染。长期评测应使用时间切分的新任务、记录记忆来源和删除能力，而不是只在用于生成经验的旧样本上复测。

### 一、为什么不能只用“回答准确率”评价 Agent

传统大模型通常输入一个问题，输出一段文本，因此比较容易使用准确率、相关性、事实性等指标进行评估。

Agent 不同。Agent 的输出不仅是文本，还可能包含规划、检索、工具调用、代码修改、数据库写入、邮件发送、流程审批等一系列动作。因此，Agent 的效果本质上是一个多维指标，而不是单一的回答质量指标。

例如，一个代码 Agent 最终生成了正确代码，但它可能执行了以下过程：

- 修改了大量无关文件；
- 重复调用模型几十次；
- 删除了已有测试；
- 引入了安全漏洞；
- 依赖人工多次纠正；
- 只是碰巧通过了当前测试。

这种 Agent 的最终结果看似正确，但过程不稳定，无法用于真实生产环境。

因此，评价 Agent 时至少需要同时关注以下几个层面：


| 评价层面 | 核心问题          |
| ---- | ------------- |
| 结果效果 | 最终任务是否真正完成    |
| 过程效果 | 执行路径是否合理、稳定   |
| 系统效果 | 成本、延迟、可靠性如何   |
| 安全效果 | 是否遵守权限和风险边界   |
| 用户效果 | 是否减少用户工作量     |
| 长期效果 | 是否能够持续学习和复用经验 |


---

### 二、任务结果层面：Agent 到底有没有完成任务

任务结果是最核心的一层，但不能简单理解为“模型给出了答案”。

对于 Agent 来说，任务完成度通常包括正确性、完整性、约束满足度和外部状态一致性。

#### 1. 正确性

正确性表示 Agent 输出的结论、生成的内容或者执行的操作是否正确。

例如：

- RAG Agent 返回的信息是否与知识库一致；
- 邮箱 Agent 是否找到了真正重要的邮件；
- 代码 Agent 修改后是否通过测试；
- 数据分析 Agent 的计算结果是否正确；
- 工作流 Agent 是否创建了正确的任务记录。

正确性可以通过标准答案、规则校验、单元测试、人工评审或者外部系统状态进行判断。

#### 2. 完整性

很多 Agent 的问题不是完全错误，而是只完成了一部分。

例如，用户要求“扫描最近一个月与项目延期相关的全部邮件”，Agent 可能找到了三封，但实际上有十封。此时回答本身可能没有错误，但召回不完整。

因此，任务效果还要看是否覆盖了用户要求的全部范围。

在不同场景中，完整性的评价方式不同：


| 场景     | 完整性指标   |
| ------ | ------- |
| 邮件检索   | 相关邮件召回率 |
| RAG 问答 | 关键事实覆盖率 |
| 代码修改   | 需求点覆盖率  |
| 报告生成   | 必要章节覆盖率 |
| 工作流执行  | 子任务完成率  |


#### 3. 约束满足度

Agent 不只是要完成任务，还要满足用户给出的限制。

例如：

- 只能修改指定目录；
- 不能删除已有接口；
- 输出必须是 Markdown；
- 邮件只能生成草稿，不能直接发送；
- 查询只能使用某个数据源；
- 成本不能超过某个阈值。

因此，可以将任务成功定义为：
```text
任务成功 = 目标完成 × 约束满足 × 结果正确
```

其中任何一项为零，都不能算真正成功。

#### 4. 外部状态是否正确

对于执行型 Agent，不能只看它“声称自己完成了什么”，而要检查系统真实状态。

例如：

- Agent 说代码已经修改，需要检查 Git 差异；
- Agent 说邮件已经发送，需要检查邮件系统；
- Agent 说数据库写入成功，需要重新查询数据库；
- Agent 说部署完成，需要检查线上版本；
- Agent 说任务已创建，需要检查任务系统。

这类评估通常称为状态验证或者结果验证。

---

### 三、执行过程层面：Agent 是怎么完成任务的

Agent 的效果不仅取决于结果，还取决于完成结果的过程是否稳定。

#### 1. 规划质量

需要观察 Agent 是否正确拆解任务，子任务之间是否存在合理依赖。

例如，一个代码修改任务可能包含：
```text
理解需求
→ 定位代码
→ 分析影响范围
→ 制定修改方案
→ 修改代码
→ 运行测试
→ 修复问题
→ 最终验证
```

如果 Agent 没有先分析影响范围就直接修改代码，即使最终成功，过程也存在较高风险。

规划质量可以观察：

- 是否遗漏关键步骤；
- 是否存在无效步骤；
- 步骤顺序是否合理；
- 是否能够根据执行结果动态调整；
- 是否能识别需要人工确认的节点。

#### 2. 工具选择质量

Agent 通常拥有多个工具，例如数据库查询、搜索、代码执行、浏览器、文件操作和外部 API。

需要评价：

- 是否选择了正确工具；
- 是否错误使用了高成本工具；
- 是否重复调用相同工具；
- 是否在不需要模型时仍调用模型；
- 是否对工具参数进行了正确构造；
- 是否验证了工具调用结果。

例如，能通过数据库精确查询解决的问题，不应该反复依赖模型猜测。

#### 3. 循环效率

Agent 往往采用循环执行结构：
```text
观察 → 推理 → 行动 → 获取结果 → 再推理
```

因此需要观察循环是否真正产生进展。

常见问题包括：

- 重复搜索同一信息；
- 重复修改同一文件；
- 修改后又撤销；
- 不断重新规划但不执行；
- 连续多轮没有新增状态；
- 在多个错误方案之间来回切换。

可以定义进展率：
```text
进展率 = 产生有效状态变化的轮数 / 总循环轮数
```

如果 Agent 循环了一百次，但只有十次产生真实进展，说明执行效率很低。

#### 4. 错误恢复能力

真实任务中工具调用失败是正常情况，例如网络超时、权限不足、格式错误、依赖缺失。

Agent 的效果要看它能否：

- 判断失败原因；
- 区分可重试错误和不可重试错误；
- 调整参数后重试；
- 切换替代工具；
- 回滚部分成功状态；
- 从检查点继续执行；
- 在无法处理时请求人工介入。

因此，一个成熟 Agent 的关键能力不仅是成功执行，还包括失败后的恢复。

### 四、系统性能层面：效果是否值得对应成本

即使 Agent 能完成任务，如果成本和延迟过高，也很难实际使用。

#### 1. 延迟

可以将 Agent 总延迟拆解为：
```text
总延迟
= 模型推理时间
+ 工具执行时间
+ 检索时间
+ 重试时间
+ 排队时间
```

不同任务对延迟要求不同。


| 场景        | 延迟要求        |
| --------- | ----------- |
| 实时聊天      | 秒级          |
| 邮箱批量扫描    | 分钟级可接受      |
| 代码仓库分析    | 数分钟到数十分钟    |
| 长周期研究任务   | 更关注最终质量     |
| 自动交易或控制系统 | 可能要求毫秒级或亚秒级 |


因此不能脱离任务场景单独评价速度。

#### 2. 成本

成本包括：

- 输入 Token；
- 输出 Token；
-上下文压缩成本；
- 模型调用次数；
- 搜索 API 成本；
- 数据库或向量库调用；
- 浏览器执行成本；
- 人工审核成本；
- 失败和重试成本。

可以使用单位成功任务成本：
```text
单位成功任务成本 = 总执行成本 / 成功完成任务数量
```

这个指标通常比单次模型调用价格更有意义。

有些系统使用更便宜的模型，但由于错误率高、重试次数多，最终任务成本反而更高。

#### 3. 资源效率

还需要看 Agent 是否合理分配不同层级资源。

例如：

- 简单分类使用小模型；
- 复杂规划使用强模型；
- 能用规则完成的步骤不调用模型；
- 重复前缀使用提示词缓存；
- 历史内容通过摘要和检索管理；
- 工具返回结果先进行裁剪再写入上下文。

效果优秀的 Agent 不一定调用最强模型，而是能够在不同步骤使用合适的资源。

---

### 五、稳定性与可靠性层面：能否重复得到相似结果

大模型具有随机性，同一个任务多次执行可能产生不同路径和结果。

因此评估 Agent 时，不能只运行一次。

可以对同一任务重复运行多次，并观察：

- 成功率；
- 结果一致性；
- 平均成本；
- 成本方差；
- 执行步骤数量；
- 错误类型；
- 最坏情况下的行为。

例如，一个 Agent 十次中有九次成功，但一次错误删除了关键数据，那么它仍然不能用于生产环境。

常见可靠性指标包括：


| 指标     | 含义             |
| ------ | -------------- |
| 任务成功率  | 多次运行中成功完成任务的比例 |
| 一致性    | 多次运行结果差异程度     |
| 平均恢复时间 | 发生错误后恢复所需时间    |
| 重试成功率  | 初次失败后成功恢复的比例   |
| 最坏路径成本 | 极端情况下消耗的资源     |
| 中断恢复率  | 任务中断后能否继续执行    |


---

### 六、安全层面：Agent 是否在允许范围内行动

Agent 一旦接入真实工具，就存在误操作风险。

安全效果主要包括权限控制、风险识别、副作用控制和人工审批。

#### 1. 权限边界

Agent 应该遵守最小权限原则，只获得完成任务所需的最低权限。

例如：

- 邮箱 Agent 默认只能读取和生成草稿；
- 代码 Agent 默认不能直接合并主分支；
- 数据库 Agent 默认只能查询；
- 文件 Agent 只能访问指定目录；
- 部署 Agent 不能直接操作生产环境。

#### 2. 高风险动作控制

对于以下操作，一般需要单独确认：

- 发邮件；
- 删除文件；
- 转账或支付；
- 修改生产数据；
- 发布内容；
- 部署上线；
- 修改权限；
- 执行不可逆操作。

这类动作不能只依赖 Agent 自己判断。

#### 3. 幂等和防重复

长循环 Agent 可能因为超时或状态判断错误重复执行操作。

例如：

- 重复发送邮件；
- 重复创建订单；
- 重复写入数据库；
- 重复触发部署；
- 重复创建任务。

因此每个操作最好带唯一操作编号，并在执行前检查是否已经完成。

#### 4. 审计能力

系统需要记录：

- 用户原始请求；
- Agent 的规划；
- 每次工具调用；
- 工具参数；
- 工具返回结果；
- 状态变化；
- 人工确认记录；
- 最终输出。

这样才能在出现问题后进行追踪和责任定位。

---

### 七、用户体验层面：是否真正减少用户负担

Agent 的目标不是展示模型能力，而是减少用户完成任务的成本。

因此可以从以下角度评价用户价值：

#### 1. 用户介入次数

如果 Agent 每执行一步都需要用户确认，虽然安全，但自动化价值较低。

可以统计：
```text
平均人工介入次数
平均澄清次数
平均纠正次数
人工接管率
```

好的 Agent 应该在风险可控的前提下减少不必要的打断。

#### 2. 可理解性

用户需要知道：

- Agent 当前在做什么；
- 为什么选择这个工具；
- 哪些步骤已经完成；
- 哪些结果尚未验证；
- 为什么任务失败；
- 接下来需要用户做什么。

这里并不是要求输出完整思维过程，而是提供必要的执行依据和状态说明。

#### 3. 可控性

用户应该能够：

- 暂停任务；
- 修改目标；
- 限制工具；
- 撤销操作；
- 查看执行记录；
- 从某个检查点恢复；
- 接管高风险步骤。

#### 4. 最终业务价值

最重要的是 Agent 是否带来了真实收益，例如：

- 降低处理时间；
- 提高信息召回率；
- 减少人工重复工作；
- 降低错误率；
- 提高响应速度；
- 提高任务吞吐量；
- 改善用户决策质量。

---

### 八、长期效果：Agent 能否随着使用逐渐变好

如果 Agent 是长期运行的，还要评价它的记忆和经验积累能力。

#### 1. 用户偏好学习

例如邮箱 Agent 应逐渐了解：

- 哪些发件人重要；
- 哪些主题需要优先处理；
- 用户偏好的摘要形式；
- 哪些操作可以自动执行；
- 哪些情况必须确认。

但偏好学习不能无限制进行，还需要支持查看、修改和删除。

#### 2. 任务经验复用

Agent 可以将成功任务中的经验沉淀为：

- 模板；
- 规则；
- 工作流；
- 工具使用策略；
- 检索策略；
- 错误处理方案；
- 可复用技能。

评价时要看这些经验能否在新任务上提高成功率，而不是单纯积累越来越多的记忆。

#### 3. 长期退化问题

长期使用也可能产生：

- 错误记忆；
- 过时信息；
- 用户偏好漂移；
- 不同任务经验相互污染；
- 提示词和技能无限膨胀；
- 错误策略被反复复用。

因此长期效果还要包括记忆更新、过期、冲突处理和质量评估。

---

### 九、离线评测与在线评测

Agent 评测通常分为离线评测和在线评测。

#### 离线评测

离线评测是在预先构建的任务集上运行 Agent。

任务集通常包含：
```text
用户请求
环境初始状态
允许使用的工具
目标状态
约束条件
标准执行结果
评测规则
```

优点是可重复、便于比较不同版本，缺点是任务集可能无法覆盖真实用户行为。

#### 在线评测

在线评测基于真实用户使用数据，常见指标包括：

- 任务完成率；
- 用户纠正率；
- 人工接管率；
- 用户满意度；
- 平均完成时长；
- 成本；
- 次日或长期使用率；
- 操作撤销率；
- 投诉和事故率。

离线评测适合开发阶段，在线评测更能反映真实业务效果。

---

### 十、不同类型 Agent 的评价重点不同

#### RAG Agent

重点关注：

- 检索召回率；
- 引用准确性；
- 答案忠实度；
- 关键信息覆盖率；
- 无答案识别能力；
- 检索和生成延迟。

#### 代码 Agent

重点关注：

- 测试通过率；
- 需求覆盖率；
- 是否引入回归；
- 修改范围是否合理；
- 静态检查结果；
- 安全漏洞；
- 人工修改量。

#### 邮箱 Agent

重点关注：

- 重要邮件召回率；
- 噪声过滤准确率；
- 摘要质量；
- 优先级判断准确性；
- 是否漏掉关键线程；
- 是否产生误发、重复发送等风险。

#### 数据分析 Agent

重点关注：

- 数据选择是否正确；
- 计算过程是否可复现；
- 统计方法是否合理；
- 结论是否被数据支持；
- 是否存在数据泄漏或错误解释。

#### 多 Agent 系统

重点关注：

- 角色分工是否有效；
- 通信成本；
- 信息是否重复传递；
- 是否产生冲突；
- 协作是否优于单 Agent；
- 最终收益是否覆盖多模型调用成本。

### 十一、可以建立一套分层指标体系

一个较完整的 Agent 指标体系可以设计为：


| 一级指标 | 二级指标 | 示例          |
| ---- | ---- | ----------- |
| 任务效果 | 正确性  | 最终结果是否正确    |
| 任务效果 | 完整性  | 是否完成全部子任务   |
| 任务效果 | 约束满足 | 是否遵守用户要求    |
| 执行过程 | 规划质量 | 是否正确拆解任务    |
| 执行过程 | 工具质量 | 工具选择和参数是否正确 |
| 执行过程 | 循环效率 | 是否存在无效重复    |
| 可靠性  | 成功率  | 多次运行成功比例    |
| 可靠性  | 恢复能力 | 失败后能否恢复     |
| 性能   | 延迟   | 任务完成时间      |
| 性能   | 成本   | Token 与工具费用 |
| 安全   | 越权率  | 是否违反权限边界    |
| 安全   | 事故率  | 是否产生错误副作用   |
| 用户体验 | 介入次数 | 用户需要确认多少次   |
| 用户体验 | 纠正率  | 用户需要修改多少结果  |
| 长期价值 | 经验复用 | 是否能复用历史经验   |


实际项目中不一定需要全部指标，而应该根据业务场景选择最关键的一组。

### 十二、面试中可能出现的追问

#### 追问一：任务成功率怎么定义

任务成功率不能只由模型自评，而应尽可能根据确定性结果定义。

例如代码 Agent 可以定义为：
```text
任务成功
= 测试全部通过
∧ 核心需求覆盖
∧ 无新增严重静态检查问题
∧ 修改范围符合约束
```

复杂开放任务可以采用规则评分、人工评审和模型评审结合，但模型评审不能作为唯一依据。

#### 追问二：最终结果正确，为什么还要评价过程

因为 Agent 会操作真实系统。一个结果正确但过程不可控的 Agent，可能在下一次任务中产生严重问题。

过程指标可以提前发现：

- 过度重试；
- 工具误用；
- 状态污染；
- 成本失控；
- 高风险操作；
- 结果偶然正确。

#### 追问三：大模型作为裁判是否可靠

模型裁判适合评价语言质量、相关性和部分开放性指标，但存在偏差、位置敏感、自我偏好和结果不稳定等问题。

更稳妥的方式是：
```text
确定性程序校验
+ 外部真实状态检查
+ 人工抽样
+ 模型辅助评审
```

模型裁判应该是补充，而不是唯一标准。

#### 追问四：Agent 效果和大模型能力是什么关系

大模型能力只是 Agent 效果的一部分。

Agent 的最终效果还取决于：

- 上下文组织；
- 工具设计；
- 工作流设计；
- 状态管理；
- 检索质量；
- 错误恢复；
- 权限控制；
- 评测和反馈机制。

强模型放在设计较差的 Agent 系统中，仍然可能出现成本高、循环失控和误操作问题。

#### 追问五：如何比较两个 Agent

比较时需要保证：

- 使用相同任务集；
- 环境初始状态一致；
- 工具权限一致；
- 模型预算一致；
- 最大执行时间一致；
- 重复运行多次；
- 同时比较结果、成本和稳定性。

不能只挑几个成功案例进行展示。

---

### 十三、最终总结

Agent 的效果不是单一的“回答质量”，而是一个多目标评价问题。最核心的是任务是否正确、完整地完成，但同时还要关注执行过程是否稳定、成本是否可接受、失败是否可恢复、操作是否安全，以及是否真正减少了用户的工作量。

在工程实践中，可以将 Agent 效果概括为：
```text
Agent 效果
= 任务完成质量
× 执行可靠性
× 安全性
× 用户价值
÷ 时间与成本
```

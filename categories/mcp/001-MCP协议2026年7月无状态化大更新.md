# MCP 协议 2026-07-28 大版本更新：无状态化重构

## 面试直接答

MCP 最近一次大版本更新是 2026 年 7 月 28 日发布的 2026-07-28 规范，这是 MCP 开源以来最大的一次架构重构：协议核心从有状态的会话模型改为**无状态请求/响应模型**，移除了 `initialize` 握手与会话绑定，新增必选的 `server/discover` 能力发现机制、Multi Round-Trip Requests 交互机制和正式的扩展框架，并以至少 12 个月的弃用窗口保证存量实现平滑迁移。这次更新要解决的核心问题，是 MCP 服务在企业级负载均衡部署下的横向扩展难题。

先交代背景。MCP 于 2024 年 11 月由 Anthropic 开源，2025 年 3 月 26 日的修订引入了 Streamable HTTP 并弃用 HTTP+SSE，2025 年 6 月 18 日修订进一步稳定了工具、资源、提示三大原语。但在此之前协议一直维持客户端初始化会话模型：客户端先发送 `initialize` 握手，服务端返回 capabilities，之后所有请求通过 `Mcp-Session-Id` 头绑定到具体服务端实例。这个设计在单机或直连场景没有问题，一旦放到企业环境就成了瓶颈——负载均衡器后面的多个服务端实例共享不了会话状态，必须做 sticky session 或引入 Redis 之类的共享状态存储，服务端无法真正做到无状态水平扩展。同时，elicitation、sampling、roots 这些服务端主动发起的请求依赖长连接推送，也把架构钉死在了有状态模型上。

2026-07-28 的修订直接删掉了握手和会话。每个请求通过 `_meta` 字段携带 `io.modelcontextprotocol/protocolVersion`、`clientCapabilities`、`clientInfo`，配合 `MCP-Protocol-Version` 头实现逐请求的版本自描述，负载均衡器后面任何一个实例都能独立处理任意请求，不需要会话亲和，也不需要外部状态存储。版本不匹配时服务端返回 `UnsupportedProtocolVersionError`（-32022），并列出自己支持的版本号。

第二层变化是发现与路由机制。新增必选的 `server/discover` RPC，服务端通过它广播自己支持的协议版本、capabilities 和身份信息，客户端可以在发出业务请求前先探测选版，也可以把它当作对老服务的兼容性探针。同时新增 `Mcp-Method`、`Mcp-Name` 等路由头，让网关、审计系统这些中间设施不需要解析 JSON-RPC 报文体就能完成路由和可观测性，头与体不一致时返回 `HeaderMismatch` 错误（-32020）。这一条的意义在于把协议元数据提升到了 HTTP 层，MCP 流量从此可以被普通 HTTP 基础设施治理。

第三层变化是交互模型的替换。服务端发起请求的机制被 Multi Round-Trip Requests（MRTR，SEP-2322）取代：服务端需要补充输入时不再推送请求，而是在原请求的响应里返回 `inputRequired` 结果和一段不透明的 `requestState`，客户端收集好 `inputResponses` 后重试原请求。请求中间状态由客户端持有，服务端保持无状态。随之而来的是 SSE 断线重连机制（`Last-Event-ID`）被移除，流中断后客户端需要以新 ID 重新发起请求。

扩展和弃用同步进行。新增了正式的扩展框架：MCP Apps（`io.modelcontextprotocol/ui`）允许在聊天界面内渲染交互式 UI，Tasks（SEP-2663）支持长耗时异步操作；工具、提示、资源的列表结果支持 TTL 缓存（SEP-2549）和确定性排序。弃用方面，Roots、Sampling、Logging 正式进入弃用流程，`ping`、`logging/setLevel`、`resources/subscribe` 直接移除，HTTP+SSE 传输被正式标记为弃用并强制迁移到 Streamable HTTP，OAuth 授权要求客户端在元数据中显式声明 issuer 并按 RFC 9207 校验。生命周期政策保证从标记弃用到移除至少 12 个月，最早移除窗口在 2027 年 7 月。

兼容策略上，官方把实现分为 Modern（2026-07-28 起）、Legacy（2025-11-25 及以前）和 Dual-era（双栈）三类。TypeScript 和 Python 官方 SDK 发布了 v2 大版本，重写后同时支持新版和全部历史版本，Go SDK 1.7、C# SDK 2.0 同步跟进；客户端先用 `server/discover` 探测，探测失败回退到 legacy 的 `initialize` 握手，保证老客户端不被破坏。治理层面，MCP 已经移交 Linux Foundation 旗下的 Agentic AI Foundation（AAIF），Anthropic 发起、OpenAI、Google、Microsoft、Amazon 参与贡献，最终技术决策由独立维护者做出。

我的整体评价是，这次更新标志着 MCP 从"桌面 agent 的工具协议"转向"企业基础设施协议"，无状态化方向符合云原生的一贯演进逻辑，是正确的选择。代价是 Modern 与 Legacy 并存的过渡期会产生生态混沌，MRTR 把一次逻辑调用拆成多次往返也增加了客户端实现复杂度，短期内应该重点关注 SDK 的成熟度和实际部署中的失败率波动。

## 详细解析

### 架构对比：从有状态会话到无状态请求

更新前的 MCP 部署模型：

```
Client ──initialize──▶ LB ──▶ Server A（创建 session，绑定 Mcp-Session-Id）
  │                              │
  ├──────── request ────▶ LB ──▶ Server A（必须回到同一实例）
  │                              │
  │     （Server A 扩容为 A/B/C 后：
  │       请求可能被路由到没有 session 的实例 → 404 / 需共享状态存储）
```

更新后的部署模型：

```
Client ──server/discover──▶ LB ──▶ 任意实例（返回支持版本与能力）
  │
  ├── request（_meta + MCP-Protocol-Version + Mcp-Method/Mcp-Name 头）
  │                              │
  │                        LB 按头信息路由，任意实例独立处理
  │                        无需 sticky session，无需共享状态存储
  │
  └── MRTR：inputRequired + requestState ──▶ 客户端持有中间状态并重试
```

### 2025-11-25 与 2026-07-28 关键差异对比

| 维度 | 2025-11-25 及以前 | 2026-07-28 |
|---|---|---|
| 会话模型 | 有状态：`initialize` 握手 + `Mcp-Session-Id` 绑定实例 | 无状态：逐请求自描述（`_meta` + `MCP-Protocol-Version`） |
| 版本协商 | 握手阶段一次性协商 | 每请求携带版本，`server/discover` 可选预探测 |
| 服务端发起请求 | elicitation / sampling / roots 走长连接推送 | MRTR：`inputRequired` + `requestState` + 客户端重试 |
| SSE 断线重连 | 支持 `Last-Event-ID` 续传 | 移除，流中断以新 ID 重发 |
| 路由可观测 | 中间件需解析 JSON-RPC 体 | `Mcp-Method` / `Mcp-Name` 头即可路由与审计 |
| 传输 | Streamable HTTP + HTTP+SSE | Streamable HTTP 为主；HTTP+SSE 正式弃用 |
| 扩展机制 | 无正式框架 | MCP Apps（ui）、Tasks（SEP-2663） |
| 弃用政策 | 无 | 12 个月最低窗口，最早移除 2027-07 |

### 关键机制的报文示例

`server/discover` 响应（服务端广播自身能力）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersions": ["2026-07-28", "2025-11-25"],
    "serverInfo": { "name": "payment-mcp", "version": "2.1.0" },
    "capabilities": { "tasks": {}, "apps": {} }
  }
}
```

MRTR 交互（服务端中途索要输入）：

```json
// 客户端发起 createTask，服务端需要补充输入：
{
  "jsonrpc": "2.0",
  "id": 9,
  "result": {
    "resultType": "inputRequired",
    "inputRequests": [{ "id": "req-1", "type": "approval", "description": "确认扣款金额 ¥128.00" }],
    "requestState": "opaque-token-abcd"
  }
}
// 客户端收集应答后重试原请求：
{
  "jsonrpc": "2.0",
  "id": 10,
  "method": "tasks/createTask",
  "params": { "inputResponses": { "req-1": { "approved": true } }, "requestState": "opaque-token-abcd" }
}
```

### 面试追问

**追问一：无状态化之后，原先依赖会话的功能（资源订阅、日志级别设置）怎么处理？为什么是移除而不是改造？**

`resources/subscribe`、`logging/setLevel`、`ping` 在 2026-07-28 中被直接移除，Roots、Sampling、Logging 整体弃用。原因有两层：第一，订阅和级别设置本质是"跨请求的服务端状态"，与无状态模型直接冲突，改造它们等于重新引入会话；第二，这些能力在真实使用中渗透率低，而维持它们会迫使所有实现保留状态机。替代路径是 MRTR 和应用层显式句柄——需要"订阅语义"的场景由客户端定时拉取或由 Tasks 扩展承载异步操作，把状态从协议层上移到应用层。这也体现了规范组的态度：无状态是协议底线，任何违背底线的特性宁删勿留。

**追问二：MRTR 把中间状态推给客户端，如果客户端在两次往返之间崩溃或重试，`requestState` 怎么保证安全？**

这正是 MRTR 的设计张力所在。`requestState` 是不透明令牌，其安全语义由服务端自定义：可以是短 TTL 的一次性令牌，也可以是对初始请求参数的确定性签名。客户端崩溃后令牌失效，重试等于重新发起原请求，所以**原请求必须幂等**——这与无状态架构对幂等性的总体要求一致。反过来看，如果客户端把 `requestState` 泄漏给第三方，服务端应能校验绑定关系（如绑定客户端身份或原始 method）。面试时可以补充：MRTR 的往返次数没有硬性上限，服务端应在 `requestState` 内记录轮次，防止恶意或故障客户端造成无限交互循环。

**追问三：如果你现在要从零写一个 MCP server，你会选哪个协议版本和传输？为什么不是直接选最新的？**

我会做 Dual-era 双栈：同时实现 `server/discover` 与 legacy `initialize` 握手，传输统一用 Streamable HTTP。理由有三：第一，2026 年 7 月规范刚落地，存量客户端（IDE 插件、老版本 SDK 钉在 2025-06-18 或 2025-11-25 的情况很常见）仍然大量存在，只支持新版等于拒绝这部分用户；第二，`server/discover` 本身就是为兼容设计的，双栈的实现成本集中在适配层，业务逻辑不重复；第三，Go SDK 的实践已经给出了模式——默认协商到 2025-11-25，显式声明 Stateless 后才接受 2026-07-28 的 HTTP 流量，说明生态仍在过渡期。等到 2027 年弃用窗口关闭前再收缩 legacy 分支即可。

**追问四：这次更新对 Claude Code、Codex 这类客户端意味着什么？终端用户能感知到吗？**

对客户端实现方影响最大：SDK 升级到 v2 后，内部的握手、会话、重连逻辑全部要重写，尤其 SSE 重连移除后要处理流中断重发。终端用户大部分场景无感知——协议变化被 SDK 吸收，工具调用照常工作。可感知的变化有两处：一是 MCP Apps 扩展让 server 可以在对话里渲染交互式 UI（表单、图表），这是产品层面的新能力；二是过渡期某些老旧 MCP server 会出现间歇性失败，因为客户端从 SSE 迁移到 Streamable HTTP 或从握手迁移到 discover 的过程中存在兼容性边界。Claude Code 与 Codex 都把 MCP 作为工具扩展层（见 [002-Claude Code与Codex架构区别](../claude-code/002-Claude%20Code与Codex架构区别.md)），所以两者的升级节奏会直接影响各自生态里 MCP server 的兼容表现。

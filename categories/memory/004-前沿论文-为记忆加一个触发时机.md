# 前沿论文-为记忆加一个触发时机

## 题目

如何让 Agent 不只是“记住一条经验”，还知道“以后遇到什么情况时应该想起它”？

## 标签

Agent Memory、Procedural Memory、ReMe、Usage Scenario、经验检索、长期记忆

## 题目导航

← [长短期记忆-存储机制](003-长短期记忆-存储机制.md) | 无 →

## 面试直接答

2026 年 ACL Findings 论文 **Remember Me, Refine Me** 提出了动态程序性记忆框架 ReMe。它的关键洞察是：一条经验不能只有“经验内容”，还需要在写入时生成一个 `when_to_use`，说明这条经验未来适用于什么场景。系统对 `when_to_use` 而不是整段执行轨迹建立向量索引，新任务到来时，用任务描述去匹配这些“适用场景”，因此更容易找回真正有用的经验。

ReMe 不只有这一项改动。完整流程还包括细粒度经验提炼、检索后重排与改写、成功经验选择性写入、失败反思，以及按历史效用删除低价值记忆。实验显示 ReMe 在 BFCL-V3 和 AppWorld 上优于无记忆、A-Mem 和 LangMem；检索键消融中，`usage scenario` 整体取得最好或接近最好的任务成功率。

需要严谨表述：论文报告的是使用不同检索键后的 **Avg@4 / Pass@4 任务成功率**，并没有单独报告 Recall@K、MRR 等“记忆召回准确率”。因此应该说“提高了经验检索后的任务效果”，不能把 ReMe 的全部性能增益都归因于 `when_to_use`。

## 一句话理解

> 普通记忆只保存“我学到了什么”；ReMe 还保存“将来遇到什么情况时，这条经验应该被唤醒”。

这里的“触发时机”不是定时器，也不是严格的 `if` 条件，而是一段由 LLM 生成、可参与语义检索的 **适用场景描述**。

## 论文要解决的问题

很多 Agent Memory 系统把历史轨迹或总结直接丢进向量数据库：

```text
历史任务 -> 执行轨迹/总结 -> embedding -> 向量库
新任务   -> embedding       -> 相似度检索
```

这种方法存在四个问题：

1. **表示错位**：当前任务描述的是“我要做什么”，旧记忆正文描述的是“当时做了什么”，两者不一定具有足够高的字面或向量相似度。
2. **轨迹太粗**：完整轨迹包含大量只对当时任务有用的步骤和环境噪声。
3. **直接复用不适配**：旧经验可能方向正确，但约束、参数和工具环境已经变化。
4. **只增不减**：过时或有害经验长期堆积，最终形成论文所说的 `toxic noise`。

ReMe 的目标不是简单扩大记忆库，而是管理经验从 **生成、召回、使用到淘汰** 的完整生命周期。

## 核心设计：为记忆生成 `when_to_use`

论文将一条经验形式化为：

```text
E = <usage_scenario, experience, keywords, confidence, tools>
```

| 字段 | 含义 |
| --- | --- |
| `usage_scenario` / `when_to_use` | 什么情况下应该使用这条经验 |
| `experience` | 从成功、失败或对比轨迹中提炼出的核心经验 |
| `keywords` | 用于分类的关键词 |
| `confidence` | 经验可信度 |
| `tools` | 该经验涉及的工具 |

论文的实际提示词还要求生成 `task_query` 和 `generalized_query`，用于与不同检索键做消融比较。最终 ReMe 选择：

```text
写入：embedding(when_to_use) -> vector database
查询：embedding(new_task)    -> top-K usage scenarios
```

也就是说，向量库索引的重点不是“记忆讲了什么”，而是“它什么时候有用”。

### 一个贴近本项目的例子

普通记忆可能写成：

```json
{
  "experience": "Tiptap 的 NodeView 尚未挂载时访问 editor.view，或在 React 生命周期中重复 setContent，可能触发 view unavailable 或 flushSync 警告。"
}
```

ReMe 风格会额外生成：

```json
{
  "when_to_use": "当 Next.js 中的 Tiptap 编辑器在初始化、切换文档或渲染代码块时出现 editor view unavailable、flushSync 或挂载时序异常",
  "experience": "等待编辑器挂载后再访问 DOM；副作用中检查 editor.isDestroyed；避免对 useEditor 已初始化的内容重复 setContent。",
  "tags": ["Tiptap", "React", "NodeView", "setContent"],
  "confidence": 0.9
}
```

之后即使用户只说“代码块一加载就出现 React 生命周期警告”，查询文本没有复述原记忆正文，也可能与 `when_to_use` 高度匹配。

## 为什么它会更容易被召回

本质上，这是在写入阶段提前构造一个 **面向未来查询的语义地址**。

```text
经验内容：过去发生了什么、最后学到了什么
适用场景：未来的任务会以什么方式需要这条经验
```

普通向量检索希望“问题”和“答案”天然相似，但现实中二者经常使用不同词汇。`when_to_use` 相当于让 LLM 在写入时反向预测未来查询，把经验从“事后总结语言”改写成“任务触发语言”，从而缓解 query-memory representation mismatch。

它和 RAG 中为文档块预生成“可能被问到的问题”思路相似，但 ReMe 将它用于 Agent 的程序性经验：检索的不只是事实答案，而是可复用的行动策略。

## ReMe 的完整流程

```text
历史执行轨迹
    |
    v
1. Experience Acquisition
   成功模式 + 失败分析 + 成败对比
    |
    v
结构化经验 <when_to_use, experience, tags, confidence, tools>
    |
    v
LLM Judge 校验 -> 去重 -> 按 when_to_use 建立向量索引
    |
    v
2. Experience Reuse
   Top-K 检索 -> 上下文重排 -> 针对新任务改写
    |
    v
Agent 执行新任务
    |
    v
3. Experience Refinement
   选择性新增 + 失败反思 + 低效经验删除
```

### 1. Experience Acquisition：经验获取

ReMe 对同一训练任务采样多条执行轨迹，然后用总结模型进行三类分析：

- **成功模式识别**：提取导致成功的关键步骤和决策。
- **失败分析**：定位最早导致失败的关键步骤，形成防错经验。
- **对比分析**：比较高分与低分轨迹，找出真正造成结果差异的动作。

论文强调提炼 **keypoint-level experience**，而不是保存一整条轨迹。生成结果还会经过 LLM-as-a-Judge 校验和向量相似度去重。

### 2. Experience Reuse：经验复用

新任务到来后：

1. 用新任务查询 `when_to_use` 向量索引，默认召回 Top-5。
2. 可选地使用 LLM 根据新任务的目标、上下文和约束重新排序。
3. 将多条旧经验改写为一份适配当前任务的指导，而不是原样拼接。
4. 将指导加入执行 Agent 的上下文。

这里的设计思想是：**检索负责找到大致可用的旧经验，重排和改写负责解决“相似但不完全相同”。**

### 3. Experience Refinement：经验精炼

ReMe 让记忆池持续演化：

- **选择性写入**：在线运行时只直接保存成功轨迹提炼出的经验。
- **失败反思**：任务失败后先反思并重试，只有重试成功，反思所得经验才进入记忆池；最多反思 3 次。
- **效用删除**：记录每条经验被召回次数 `f(E)`，以及它参与成功任务的次数 `u(E)`。

当一条经验至少被召回 `alpha` 次，且平均效用不高于阈值 `beta` 时删除：

```text
f(E) >= alpha 且 u(E) / f(E) <= beta
```

论文默认 `alpha = 5`、`beta = 0.5`。大白话说就是：一条经验如果已经多次被想起，却经常帮不上忙，就不要继续留在记忆库中制造噪声。

## 实验怎么做

论文使用两个 Agent 基准：

- **BFCL-V3**：多轮 Function Calling，考察工具选择、参数生成与状态跟踪。
- **AppWorld**：跨应用、多步骤任务执行。

主要对比：

- No Memory
- A-Mem
- LangMem
- ReMe (fixed)：运行期间不更新经验池
- ReMe (dynamic)：运行期间持续精炼经验池

指标：

- **Avg@4**：四次独立执行的平均任务成功率。
- **Pass@4**：四次执行中至少成功一次的概率。

## 最关键的实验结果

### 1. `usage scenario` 检索键消融

BFCL-V3、ReMe (fixed)：

| 模型 | 检索键 | Avg@4 | Pass@4 |
| --- | --- | ---: | ---: |
| Qwen3-8B | task query | 44.00% | 63.33% |
| Qwen3-8B | generalized query | 42.50% | 63.77% |
| Qwen3-8B | query keywords | 44.22% | 65.33% |
| Qwen3-8B | **usage scenario** | **44.50%** | **65.77%** |
| Qwen3-14B | task query | 50.11% | 71.77% |
| Qwen3-14B | generalized query | 50.49% | 72.22% |
| Qwen3-14B | query keywords | 51.16% | 71.11% |
| Qwen3-14B | **usage scenario** | **51.89%** | **72.44%** |
| Qwen3-32B | task query | 56.22% | 72.22% |
| Qwen3-32B | generalized query | 55.33% | 73.33% |
| Qwen3-32B | query keywords | **56.89%** | 74.44% |
| Qwen3-32B | **usage scenario** | 56.05% | **74.89%** |

结论不是“每一个指标都碾压”，而是：

- `usage scenario` 在 8B、14B 上同时取得最高 Avg@4 和 Pass@4。
- 在 32B 上 Avg@4 略低于关键词，但 Pass@4 最高。
- 相比直接使用原任务或关键词，LLM 生成的适用场景整体更稳定。

### 2. 细粒度经验优于整条轨迹

| 模型 | 经验粒度 | Avg@4 | Pass@4 |
| --- | --- | ---: | ---: |
| Qwen3-8B | trajectory-level | 43.00% | 60.00% |
| Qwen3-8B | **keypoint-level** | **44.50%** | **65.77%** |
| Qwen3-14B | trajectory-level | 49.66% | 69.33% |
| Qwen3-14B | **keypoint-level** | **51.89%** | **72.44%** |

这说明除了“何时调用”，记忆本身也应该短、准、可迁移。把完整轨迹塞入上下文，会让真正有价值的决策淹没在步骤噪声里。

### 3. 完整 ReMe 的整体收益

- Qwen3-8B + ReMe 相比 No Memory，跨 BFCL-V3 与 AppWorld 平均提升 **8.83 个百分点 Avg@4** 和 **7.29 个百分点 Pass@4**。
- Qwen3-8B + ReMe (dynamic) 的平均 Pass@4 为 **55.03%**，超过无记忆 Qwen3-14B 的 **54.65%**。
- Qwen3-14B + ReMe (dynamic) 也超过无记忆 Qwen3-32B：Avg@4 为 **44.66% vs. 40.89%**，Pass@4 为 **63.71% vs. 61.52%**。
- 在额外测试的 GPT-4.1、o4-mini、Qwen3-Max、Kimi-K2-Thinking、DeepSeek-V3.2 和 GLM-4.7 上，ReMe 同样带来一致收益。

论文将这个现象称为 **memory-scaling effect**：高质量外部记忆在一定程度上可以抵消模型参数规模差距。

## 应该怎样理解实验结论

### 可以得出的结论

1. 给程序性经验增加 `when_to_use`，比只用原任务、泛化任务或关键词做索引更有效、更稳定。
2. 记忆质量比记忆数量更重要，细粒度关键经验优于完整轨迹。
3. 记忆需要重排、适配和淘汰，不应被当成只增不减的日志数据库。
4. 对工具调用 Agent 来说，正确复用经验能显著提高任务成功率。

### 不能过度推导的结论

1. **论文没有直接测标准检索召回率。** 表格展示的是最终任务成功率，而不是 Recall@K、Precision@K、MRR 或 nDCG。
2. **8.83 / 7.29 个百分点是完整 ReMe 的收益。** 不能说这是单独增加 `when_to_use` 获得的提升。
3. **检索键消融的单项提升并非都很大。** 例如 Qwen3-8B 的 Avg@4 从 task query 的 44.00% 提升到 44.50%；更明显的收益体现在 Pass@4 和跨模型稳定性。
4. **实验主要是程序性记忆。** 对个人偏好、长期事实、开放式对话记忆是否同样有效，还需要专门评测。

## 对 Agent Memory 设计的启发

### 1. 记忆应当同时保存“内容”和“地址”

建议的最小数据结构：

```json
{
  "content": "真正需要长期保留的事实、规则或经验",
  "when_to_use": "哪些任务、状态、异常或目标出现时应召回",
  "type": "semantic | episodic | procedural | preference",
  "evidence": "来源对话、文件或执行轨迹",
  "confidence": 0.9,
  "tools": [],
  "created_at": "...",
  "last_used_at": "...",
  "recall_count": 0,
  "success_count": 0
}
```

`content` 供 Agent 阅读，`when_to_use` 供检索器匹配，两者职责不同。

### 2. 不要只对正文做 embedding

可以分别建立两个向量：

```text
content_embedding     = embed(content)
activation_embedding  = embed(when_to_use)
```

检索时组合评分：

```text
score =
  lambda * similarity(query, activation_embedding)
  + (1 - lambda) * similarity(query, content_embedding)
```

再叠加时间、可信度、作用域和历史效用等特征。ReMe 论文主要验证了 `usage scenario` 索引；双索引融合属于在此基础上的工程扩展，需要自行做消融实验。

### 3. `when_to_use` 要写成可观察条件

差的写法：

```text
当这条知识有用时。
```

好的写法：

```text
当用户询问 Tiptap 初始化、NodeView 挂载、setContent，
或出现 editor view unavailable / flushSync 警告时。
```

应尽量包含：

- 当前目标；
- 可观察状态或症状；
- 关键实体、工具或资源；
- 必要的前置约束；
- 不应触发的边界。

### 4. 召回之后还要验证

相似不代表适用。生产系统至少还需要：

1. 向量检索生成候选集；
2. reranker 判断当前约束是否匹配；
3. 检查来源、时效与冲突；
4. 将多条经验改写成当前任务可执行的指导；
5. 根据实际结果更新经验效用。

## 我的评价

这篇论文最有价值的地方，不是提出了更复杂的数据库，而是改变了记忆条目的写法：

> **记忆不是只有 payload，还应该有 activation semantics。**

它把记忆检索从“这两段文字像不像”推进到“当前处境是否满足这条经验的适用条件”。这个设计很轻量，可以直接叠加在现有向量数据库、RAG 或 Agent Runtime 上，也非常适合落地到代码 Agent 的跨会话经验库。

论文的不足也很明确：`when_to_use` 仍由 LLM 自动生成，若描述过宽会误触发，过窄会漏召回；实验没有独立评估检索质量；主要基准集中在工具调用和应用操作。因此，真正落地时应同时建设 **触发条件质量评测、误召回率、漏召回率和任务收益归因**，而不能只看最终成功率。

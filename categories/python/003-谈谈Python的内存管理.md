## 面试直接答

> CPython 的内存管理可以理解为`“对象引用模型 + 引用计数为主的回收机制 + 循环引用检测 + 小对象内存池”`，既保证了自动内存管理，也通过内存复用降低了频繁申请释放内存的成本。

需要先说明，通常我们讨论的其实是 **CPython 的内存管理机制**，因为 Python 是语言规范，而 CPython 是最常用的解释器实现。

首先，在对象管理层面，Python 中几乎所有东西都是对象，比如整数、字符串、函数、类实例等。

> `一切皆对象`意味着整数、字符串、函数、类甚至模块在 Python 中都通过`对象模型`统一表示

变量本身并不是直接存储对象，而更像是++保存了一个对象的引用++。例如 `a = [1, 2]` 创建一个列表对象，`b = a` 并不会复制列表，而只是让 `b` 也引用这个对象。

> 因此 Python 的内存释放主要围绕“对象还有没有被引用”来进行。

CPython 最核心的垃圾回收机制是`引用计数`。

<span style="background-color: #fff3cd">每个对象内部都会维护一个引用计数</span>，当有新的引用指向对象时加一，引用消失时减一。当引用计数下降到 0 时，对象通常可以立即被释放。它的优点是++对象回收比较及时，不需要等到统一的垃圾回收阶段++；缺点是++无法单独处理循环引用++。例如两个对象互相引用，即使外部已经没有变量引用它们，它们的引用计数仍然不为 0。

因此 CPython 还引入了`循环垃圾回收机制`作为补充。它会针对`能够形成引用环的容器对象`检测不可达对象，从而解决循环引用问题。传统上这套机制还会根据对象存活情况进行`分代管理`，核心思想是<span style="background-color: #fff3cd">“存活时间越长的对象，后续检查频率可以越低”</span>。

> 所以可以把 Python 的垃圾回收总结为：**引用计数负责主要回收，循环垃圾回收负责解决引用环问题。**

再往底层看，Python 对`小对象`++并不是每次都直接向操作系统申请内存++，因为这样系统调用成本比较高。

CPython 有自己的`小对象内存分配器` `pymalloc`。它大致会把内存按照 **Arena → Pool → Block** 进行分层管理，++小对象最终使用 Block++。这样做的目的主要是减少频繁调用 `malloc/free` 的开销，提高大量小对象创建和销毁时的性能。

> - **Arena**：`pymalloc` 向底层内存分配器一次申请的`一大块连续内存`，是小对象内存管理的最高层单位。
> - **Pool**：从 Arena 中划分出的`固定大小内存区域`，每个 Pool 通常负责管理某一种大小类别的 Block。
> - **Block**：Pool 中进一步切分出的`最小分配单元`，最终直接提供给 Python 小对象使用。

---

这里还有一个很容易被追问的问题：**为什么 Python 对象已经释放了，但是进程内存没有明显下降？** 

原因是<span style="background-color: #fff3cd">对象释放并不意味着内存一定马上还给操作系统</span>。很多内存会先回到 Python 自己的`内存池`中，供后续对象复用。因此从 Python 对象层面看已经释放了，但从操作系统监控工具看，进程占用的内存可能没有同步下降。

如果继续深入，Python 对象本身也有`额外的内存开销`。比如一个 Python 整数不仅保存整数值，还需要保存对象类型、引用计数等元数据，所以它通常比 C++ 中一个普通的 `int` 占用更多内存。列表保存的也主要是对象引用，而不是像 C++ 的连续基础类型数组那样直接存储所有值。

> 这也是 Python 开发效率高，但在内存效率上通常不如 C/C++ 的原因之一。

**核心概念补充：引用计数**指“当前有多少引用指向这个对象”；**垃圾回收**是发现并释放程序已经无法使用的对象；**内存池**则是 Python 为了减少频繁向操作系统申请和释放小块内存而增加的一层管理机制。这三者不是一个概念：前两个解决“对象什么时候死”，后一个解决“对象的内存怎么高效地分配和复用”。

## pymalloc

`pymalloc` **并不是垃圾回收机制，而是 CPython 在“已经决定要创建对象”之后，负责高效分配小块内存的一套分配器。** 

> 默认的非自由线程 CPython 中，`pymalloc` 主要针对 `512B 及以下的小内存`**申请**；更大的申请通常会退回到更底层的原始内存分配器。

它的核心思想是：Python 程序会非常频繁地创建和销毁小对象，如果每创建一个整数、元组或其他小对象，都直接调用系统的 `malloc/free`，成本会比较高，还容易造成`内存碎片`。所以 CPython 会<span style="background-color: #fff3cd">先向操作系统申请一大块内存，然后自己在这块内存内部进行切分和复用</span>。

整体可以理解成三级：
```
操作系统
   ↓
Arena
   ↓
Pool
   ↓
Block
   ↓
Python 对象使用
```

最上层是 **Arena**，可以理解成 <span style="background-color: #fff3cd">CPython 一次向操作系统申请的一大块连续内存</span>。

> 当前 CPython 文档中，64 位平台默认 Arena 是 `1 MiB`，32 位平台是 256 KiB。Arena 是 `pymalloc` 和操作系统之间交互的较大粒度单位。

Arena 里面继续划分为多个 **Pool**。Pool 的作用是<span style="background-color: #fff3cd">把内存按照不同大小进行分类管理</span>。

> 比如某个 Pool 当前可能<span style="background-color: #fff3cd">专门服务某一类大小的内存请求</span>，<span style="background-color: #fff3cd">而不是同时塞各种不同尺寸的对象</span>。这样做的好处是可以减少`外部碎片`，并且++查找空闲空间非常快++。CPython 的 `obmalloc` 本质上采用了按大小类别管理空闲块的思想。

Pool 再进一步划分为<span style="background-color: #fff3cd">真正提供给对象使用的 **Block**</span>。假设程序需要申请一个几十字节的小对象，CPython 不需要重新向操作系统申请内存，而是找到`对应大小类别的 Pool`++，从里面取一个空闲 Block++：
```
申请小对象
   ↓
找到对应 size class
   ↓
找到还有空闲空间的 Pool
   ↓
取出一个 Block
   ↓
返回给对象使用
```

对象销毁以后，这个 Block 通常也不是马上还给操作系统，而是<span style="background-color: #fff3cd">重新进入</span> `pymalloc` <span style="background-color: #fff3cd">的空闲结构</span>，之后创建类似大小的对象时可以直接复用。

> 这就是为什么 Python 中经常出现：**对象已经被垃圾回收了，但操作系统看到的进程内存并没有立刻下降。** 内存可能只是从“对象正在使用”变成了“`Python 内存池保留待复用`”。

所以面试时可以总结为：

> `pymalloc` 的核心是++用 **Arena → Pool → Block** 的分层结构管理小对象内存++。Arena 负责批量向操作系统申请内存，Pool 按大小类别组织内存，Block 最终提供给具体对象。这样对象频繁创建销毁时，大多数情况下只需要在 Python 自己的内存池中取出和归还 Block，而不用反复调用系统 `malloc/free`，从而降低分配开销并减少内存碎片。对于超过 512B 的申请，则通常交给更底层的分配器处理。

这里还要注意区分两个概念：**垃圾回收解决“这个对象什么时候可以释放”，**`pymalloc` **解决“对象需要内存时从哪里拿、释放后这块内存怎么复用”。** 这两个机制属于不同层次。<!-- created: 2026-08-17 17:36:38 -->

# 谈谈 Python 中的垃圾回收机制

## 题目

谈谈 Python 中的垃圾回收机制。请区分语言语义与 CPython 实现，并说明引用计数、循环 GC 和常见调优误区。

## 面试直接答

Python 语言并没有规定唯一垃圾回收算法，面试中通常讨论 CPython。CPython 主要依靠引用计数：对象的强引用数归零时通常立即触发清理；引用计数无法单独处理容器之间的环，所以另有可选的循环垃圾收集器，追踪可能参与引用环的对象并找出不可达集合。原子对象和部分经过优化的容器不一定被循环 GC 跟踪。

当前 CPython 3.14.6 文档重新使用 0、1、2 三代，新对象进入年轻代，存活后晋升，年轻代更频繁收集；但 3.14.0 到 3.14.4 曾移除 generation 1，3.14.5 又恢复，说明代数和阈值是实现与小版本细节，不能当成 Python 永久规范。

调优时不能看到 RSS 高就直接关闭 GC。对象释放后内存可能留在 pymalloc 或系统分配器中复用，RSS 不立即下降不一定是泄漏。应先用 gc、tracemalloc、对象计数和分配器统计定位引用链，再决定是否调整阈值；gc.disable 只适合确认不会产生引用环或特定 fork 优化等受控场景。

## 详细解析

### 一、引用计数

每个 CPython 对象维护引用计数。赋值、容器插入和参数传递等会改变计数；归零后进入析构/释放路径。它的优点是多数对象回收及时，代价是每次引用变更有开销，并且环中的对象即使整体不可达，计数也不会归零。

### 二、循环 GC

循环 GC 只跟踪可能构成环的对象，通过遍历容器引用判断一组对象是否仍可从外部到达。当前 CPython 3.14.6 有三代，年轻对象更频繁检查；完整收集还会清理部分内建类型 free list。并非所有对象都在 gc.get\_objects 中。

### 三、finalizer 与资源

文件、锁和网络连接应使用 with/context manager 或显式 close，不应依赖 **del** 的具体执行时机。现代 CPython 能处理许多带 finalizer 的循环，但 finalizer 仍可能复活对象或产生复杂顺序，资源生命周期要显式。

### 四、诊断

- gc.get\_count/get\_stats 观察收集频率和结果。
- gc.is\_tracked 判断对象是否被循环 GC 跟踪。
- gc.DEBUG\_LEAK、get\_referrers 仅用于谨慎调试。
- tracemalloc 定位 Python 分配栈，但看不到所有原生扩展内存。
- RSS、Python heap 和外部库内存要分开观察。

### 五、自由线程构建

CPython 3.14 自由线程构建还会参考进程内存增长和净分配量决定是否运行收集，因此调优必须绑定构建方式。不要直接照搬旧版默认阈值或“高并发关闭 GC”的经验。

### 六、参考

- gc：[https://docs.python.org/3.14/library/gc.html](https://docs.python.org/3.14/library/gc.html)
- CPython 内存管理：[https://docs.python.org/3/c-api/memory.html](https://docs.python.org/3/c-api/memory.html)


### 七、引用计数不是可达性分析

强引用计数记录有多少拥有引用指向对象，不知道这些引用是否整体来自一个不可达环。`a → b → a` 即使外部引用全部删除，两个对象的计数仍非零，所以需要循环 GC。弱引用不增加强引用计数，可用于缓存和观察，但回调与对象终结顺序要谨慎。

赋值、容器更新和 C API 会改变引用计数。扩展模块若漏掉应有的引用增减，可能造成泄漏或悬空对象；这不是循环 GC 调参能够修复的问题。

### 八、循环检测的核心思路

收集器从被跟踪容器构成的候选集合出发，暂时分析集合内部引用，识别仍有集合外引用、因而可达的对象；剩余不可达环才进入清理。实际实现有代际、增量和内部优化细节，面试回答应说明机制，不必把某个小版本源码常量当语言规范。

### 九、代际假设与版本边界

代际策略利用“多数新对象较快死亡”的经验，让年轻对象更频繁检查、长期存活对象较少检查。但具体代数、阈值含义和每次扫描比例会随 CPython 版本与构建方式变化。回答时给出目标版本，生产调优也要读取该版本官方文档和运行统计。

### 十、终结器、复活与不可回收误解

现代 CPython 能处理许多含 `__del__` 的环，但终结器可以运行任意代码，甚至重新建立引用使对象复活。资源释放仍应使用上下文管理器，保证控制流离开作用域时执行明确清理，而不是等待对象何时被收集。

`del x` 删除的是名字绑定，不保证对象立即销毁；若还有其他引用，对象继续存在。函数局部变量离开作用域也可能因闭包、traceback、容器或缓存而继续被引用。

### 十一、为什么禁用 GC 有时“看起来变快”

禁用循环 GC 减少扫描开销，但引用计数仍工作，引用环会积累。只有已经证明执行阶段不会产生环、或 fork 前冻结/布局等特定优化场景，才可能受控使用。长期服务直接关闭 GC 往往把暂停问题换成内存增长。

调整阈值前先观察收集次数、每代回收对象数、暂停和分配速率。阈值提高会降低扫描频率但增加候选集合和内存，阈值降低则相反；不存在通用最佳值。

### 十二、泄漏诊断步骤

1. 用 RSS 和业务指标确认是持续增长还是高水位复用。
2. 用 tracemalloc 比较快照，定位 Python 分配栈。
3. 用对象计数、`gc.is_tracked` 和受控的引用关系工具查找活对象来源。
4. 若 Python heap 稳定但 RSS 增长，检查原生扩展、allocator 碎片、线程栈和映射。
5. 在可复现实验中验证修复，避免调试工具自身持有引用。

### 十三、与其他 Python 实现的区别

PyPy 等实现可以使用追踪式 GC，对象销毁时机和暂停特性与 CPython 不同。依赖 CPython 引用归零时机的代码在其他实现上可能延迟释放，所以可移植代码要显式管理外部资源。面试中先限定 CPython，能避免把实现经验误说成语言承诺。

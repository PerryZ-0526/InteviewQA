> 多模态 RAG 的核心，不是给传统 RAG 增加一个“图片输入框”，而是让检索系统能够保留、定位、组合并引用原本存在于文字、图像、版面、声音和时间序列中的证据。

# 1. 多模态 RAG 到底是什么

**多模态检索增强生成（Multimodal Retrieval-Augmented Generation，MM-RAG）**，是指系统从包含两种或更多信息模态的外部知识库中检索证据，并让生成模型基于这些证据完成回答、分析或内容生成。

它仍然遵循 RAG 最基本的结构：

```text
用户问题 → 检索外部证据 → 组织上下文 → 模型生成答案
```

真正发生变化的是“外部证据”的形态。传统 RAG 的知识单元通常是一段文本，而多模态 RAG 的知识单元可能是：

- PDF 中的一段正文、一个表格、一张图表或整页截图；
- 商品图片及其属性、标题和用户评论；
- 视频中的一个事件片段、关键帧、字幕和音轨；
- 会议录音中的一段发言、说话人和非语言声音；
- 医疗影像与检查报告；
- 网页截图中的界面状态、控件位置和配套说明。

因此，多模态 RAG 不是单一算法，而是一套围绕**多模态知识表示、跨模态检索、证据对齐和多模态生成**展开的系统设计。

## 1.1 判断一个系统是否真正属于多模态 RAG

不能只看系统是否调用了视觉语言模型。更准确的判断方式，是从五个维度检查模态出现在什么位置：

| 维度 | 可能形式 | 示例 |
|---|---|---|
| 查询模态 | 文本、图片、音频、视频、混合输入 | 上传设备照片并询问型号 |
| 语料模态 | 文本、页面图像、自然图片、音频、视频 | 说明书、监控视频、故障录音 |
| 检索表示 | OCR 文本、描述文本、视觉向量、音频向量、多向量 | 用文本向量和页面视觉向量同时召回 |
| 生成上下文 | 原文、原图、裁剪区域、音频片段、视频帧 | 把命中的图表和相邻正文交给 VLM |
| 输出模态 | 文本、图片、语音、视频或结构化结果 | 返回文字答案并标出原图区域 |

只要其中某个环节出现视觉或音频，并不能自动证明系统完成了多模态理解。

例如：

- 将扫描 PDF OCR 成文字，再按普通文本 RAG 处理，属于**多模态数据的文本化处理**，但生成阶段未必使用视觉证据；
- 使用 CLIP 根据文字搜索图片，属于**跨模态检索**，但如果没有生成步骤，还不是完整的 RAG；
- 把用户上传的图片直接交给 VLM 回答，属于视觉问答，但如果没有从外部知识库检索证据，也不属于 RAG；
- 先用 OCR 文本定位页面，再把原始页面图像交给 VLM 回答，才是典型的**文本检索、视觉生成**方案。

## 1.2 多模态大模型不等于多模态 RAG

多模态大模型解决的是“模型能否理解当前输入中的图片、声音或视频”，多模态 RAG 解决的是“面对一个大规模、持续更新的外部知识库，系统能否找到正确的多模态证据并据此回答”。

二者的关系可以概括为：

```text
多模态大模型
负责：看懂当前交给它的少量多模态内容

多模态 RAG
负责：从大量候选内容中找到应该交给模型的证据
```

上下文窗口再大，也不等于可以稳定地把数万页文档、数千张图片或数百小时视频全部塞给模型。大规模多模态理解最终仍然会转化为一个**搜索、定位和证据压缩问题**。

## 1.3 表格和知识图谱是不是独立模态

在工程文章中，文本、表格、知识图谱经常被统称为“多模态数据”。严格来说，表格和知识图谱更接近不同的**结构化表示形式**，不一定是与视觉、听觉并列的感知模态。

但这种区分不会削弱它们在系统中的重要性。表格同时包含文本、数值、行列结构和视觉布局；图表同时包含文字标注、几何关系和颜色编码。它们恰好说明了多模态 RAG 最关键的事实：

> 信息不只存在于内容本身，还存在于内容之间的空间、结构和时间关系中。

# 2. 为什么多模态 RAG 比文本 RAG 难得多

传统文本 RAG 的主要问题是“该切成什么文本块、如何找到相关文本”。多模态 RAG 还必须回答三个更困难的问题：

1. 原始资料中究竟包含哪些不能被文字完整替代的信息？
2. 不同模态应该如何切分，切分后如何保持彼此关联？
3. 用于检索的表示与最终交给生成模型的证据是否应该相同？

## 2.1 多模态信息至少包含五种不同信号

| 信息类型 | 典型载体 | 文本化后容易损失的内容 |
|---|---|---|
| 语言语义 | 正文、字幕、语音 | 专有名词可能被 OCR 或 ASR 识别错误 |
| 视觉外观 | 照片、截图、医学影像 | 颜色、形状、材质、缺陷和细微差异 |
| 空间结构 | 页面、表格、流程图、UI | 行列关系、箭头、对齐、区域归属 |
| 声学特征 | 环境声、机械声、语调 | 音高、节奏、情绪、异常噪声 |
| 时间关系 | 视频、长录音、操作轨迹 | 先后顺序、持续时间、状态变化和因果过程 |

多模态系统的第一原则是：**不要在入库阶段过早丢弃未来查询可能需要的信息。**

## 2.2 模态转换会形成有损的信息瓶颈

将图片描述成文字、将语音转录成文字、将视频概括成摘要，都可以降低检索难度，但每次转换都相当于让一个模型提前决定“什么信息值得保留”。

假设一张设备面板图片中同时包含：

- 一个红色指示灯；
- 数字仪表显示 `8.7 bar`；
- 阀门位于关闭位置；
- 铭牌上的型号；
- 管路与阀门之间的连接关系。

通用图片描述可能只生成“一个带有仪表和阀门的工业设备面板”。这段文字适合回答“图片里是什么”，却无法回答“压力是多少”“哪个阀门关闭”“红灯是否位于主泵旁边”。

因此，**图片描述不是图片的无损替代物，ASR 文本也不是音频的无损替代物，关键帧集合更不是视频的无损替代物。**

## 2.3 多模态切分同时面对语义边界和物理边界

文本可以按段落、标题或 token 数量切分；图片、音频和视频则具有不同的自然边界：

- 文档页面可以按整页、布局区域、图表或表格切分；
- 自然图片可以按整图、目标对象或局部区域切分；
- 音频可以按静音、说话人、语义句段或固定时间窗切分；
- 视频可以按镜头、事件、动作阶段或固定时间窗切分。

切得过粗，检索结果中会混入大量无关内容；切得过细，又会破坏跨区域和跨时间关系。

例如，一张表格若按 OCR 行拆开，“Q3”表头可能与“12.8%”数据分离；一段操作视频若每两秒独立切片，“先关闭电源，再释放压力”的完整顺序可能被拆散。

## 2.4 相关性不再只有一个含义

文本 RAG 中常把相关性近似为语义相似度。多模态场景至少存在以下相关性：

- **语义相关**：图片内容与查询描述相符；
- **实体相关**：图片、正文和视频都指向同一个设备或人物；
- **空间相关**：数值属于某一行、某一列或某个图形区域；
- **时间相关**：事件发生在另一个事件之前或之后；
- **证据相关**：内容不仅主题相似，而且足以支持具体答案。

“一张关于季度营收的图表”与“能够证明第三季度亚太区营收为多少的图表”并不是同一个检索目标。

## 2.5 多模态上下文的成本并不等价

一段 500 token 的文字、一张高分辨率页面和 30 秒视频，对模型造成的上下文成本、延迟和注意力压力完全不同。图片越多不一定越好，帧采样越密也不一定越好。

多模态 RAG 必须进行**证据预算管理**：决定送入多少文字、多少图片、图片采用什么分辨率、视频保留哪些片段，以及哪些内容只用于检索而不进入生成上下文。

# 3. 多模态 RAG 的完整系统架构

一个生产级多模态 RAG 通常同时维护原始资源、结构化解析结果和一种或多种检索表示，而不是把所有内容强行转换成同一种格式。

```text
离线知识构建

原始资源
├── PDF / 网页 / Office 文档
├── 图片 / 扫描件
├── 音频
└── 视频
      │
      ▼
多模态解析与对齐
├── 文本、OCR、表格、公式
├── 页面、区域、对象、图注
├── ASR、说话人、声音事件
└── 镜头、关键帧、字幕、时间段
      │
      ▼
证据对象层
├── 原始内容 URI
├── 文本化表示
├── 空间坐标 / 时间戳
├── 父子与跨模态关系
├── 权限、版本、来源
└── 质量与置信度
      │
      ▼
多路索引
├── BM25 / 全文索引
├── 文本向量索引
├── 图文共享向量索引
├── 页面多向量索引
├── 音频 / 视频向量索引
└── 元数据与关系索引

在线问答

图文音视频查询
      │
      ▼
查询理解与模态路由
      │
      ▼
多路召回 → 分数校准与融合 → 多模态重排
      │
      ▼
证据扩展与定位
├── 补回相邻正文
├── 裁剪相关图像区域
├── 扩展前后视频片段
└── 关联表头、图注和来源
      │
      ▼
上下文打包 → 多模态模型生成 → 证据核验与引用
```

## 3.1 检索表示与生成证据必须解耦

多模态 RAG 中最重要的架构原则之一是：

> 用什么表示找到证据，与最终让模型阅读什么证据，是两个独立决策。

常见组合包括：

| 检索阶段 | 生成阶段 | 适用情况 |
|---|---|---|
| OCR 文本检索 | 原始页面图像 | 文本定位可靠，但答案依赖表格或版面 |
| 图片描述检索 | 原图加描述 | 语义搜索图片，需要回看细节 |
| 页面视觉向量检索 | 页面图像加相邻正文 | 复杂 PDF、幻灯片、图表 |
| ASR 文本检索 | 原始音频片段 | 先找到说话位置，再判断语气或环境声 |
| 视频字幕检索 | 关键帧和视频片段 | 语言线索定位，视觉过程回答 |
| 多模态向量检索 | 结构化数值和原图 | 先召回候选，再精确计算或核验 |

如果把检索表示直接当作最终证据，系统就容易出现“找对了，但回答时信息不够”的问题。

## 3.2 多模态 RAG 的最小闭环

一个能够上线验证的最小闭环，至少应具备：

1. 原始资源可回溯，检索结果能够定位到页码、区域或时间段；
2. 至少存在一种文本检索和一种非文本证据保留机制；
3. 检索后能够取回原图、音频或视频片段，而不是只返回描述文本；
4. 生成模型被要求基于证据回答，并能在证据不足时拒答；
5. 评测集包含必须使用非文本信息才能回答的问题。

如果评测问题仅靠 OCR 文本即可作答，即使系统接入了图片向量，也无法证明它真正获得了多模态能力。

# 4. 离线阶段：把多模态资料变成可检索证据

离线阶段的目标不是“生成一批向量”，而是构建一个可以被搜索、组合、引用和更新的**证据对象系统**。

## 4.1 原始资源、证据单元和检索表示

建议至少区分三层：

- **Asset**：不可变或带版本的原始资源，例如 PDF、PNG、WAV、MP4；
- **Evidence Unit**：可以被引用的证据单元，例如页面、表格区域、音频片段；
- **Representation**：服务于检索或生成的派生表示，例如 OCR 文本、caption、embedding。

一个简化的数据结构可以表示为：

```json
{
  "evidence_id": "manual-v7:p42:figure-3",
  "asset_id": "manual-v7",
  "modality": "document_region",
  "location": {
    "page": 42,
    "bbox": [0.12, 0.18, 0.88, 0.71]
  },
  "relations": {
    "parent": "manual-v7:p42",
    "caption": "manual-v7:p42:caption-3",
    "neighbors": ["manual-v7:p41", "manual-v7:p43"]
  },
  "representations": {
    "ocr_text": "额定压力 8.0 bar ...",
    "description": "压力限制与阀门状态示意图",
    "text_embedding_ref": "vec:text:...",
    "visual_embedding_ref": "vec:vision:..."
  },
  "provenance": {
    "source_uri": "s3://kb/manual-v7.pdf",
    "parser_version": "parser-2026-09",
    "content_hash": "sha256:...",
    "acl": ["maintenance-team"]
  }
}
```

这里的关键不是字段名称，而是**原始证据、派生内容和检索向量不能混成一个不可追溯的 chunk**。

## 4.2 复杂文档解析

PDF 不是天然的语义文档格式。它可能包含可提取文本层，也可能只是扫描图；视觉阅读顺序与文件内部对象顺序也可能不同。

典型解析流程包括：

1. 判断页面是否包含可靠文本层；
2. 对扫描区域执行 OCR，并保留字符或文本块坐标；
3. 识别标题、正文、列表、页眉页脚、表格、公式和图片区域；
4. 恢复多栏页面的阅读顺序；
5. 将图片与图注、表格与表题、脚注与正文重新关联；
6. 同时保存结构化结果和原始页面渲染图。

Docling、MinerU 一类工具可以输出带布局、表格、公式和来源坐标的结构化结果，但工具能力不能替代针对自身语料的解析评测。合同、财报、论文和手写扫描件的错误分布并不相同。

## 4.3 图片处理

对自然图片或文档内图片，通常同时生成多种派生对象：

- 原图和缩略图；
- 全图视觉向量；
- OCR 文本；
- 通用描述；
- 领域描述；
- 目标检测或区域分割结果；
- EXIF、来源、时间等元数据。

通用描述回答“这是什么”，领域描述回答“哪些特征对当前业务有意义”。例如，同一张轴承照片，通用描述可能是“一个金属圆环”，设备维护描述则应覆盖滚道剥落、锈蚀和裂纹位置。

描述生成应当保留模型版本和提示词版本。否则更换 caption 模型后，无法判断索引内容为何变化。

## 4.4 音频处理

音频至少需要并行保留两条信息通道：

- **语言通道**：ASR 文本、词级或句级时间戳、说话人；
- **声学通道**：原始波形或声谱特征、声音事件、音乐和环境声向量。

会议搜索主要依赖语言通道；机械故障、动物声音、语气识别等任务则不能只依赖 ASR。

切分时应优先结合静音、说话人变化和语义边界。固定 30 秒切片实现简单，但可能把一句话或一个完整声音事件切成两段。每个片段都应保留起止时间，并允许向前、向后扩展上下文。

## 4.5 视频处理

视频不是“很多张独立图片”，而是至少由视觉帧、音频、字幕和时间结构共同组成。

离线阶段可以构建：

- 视频级摘要和全局向量；
- 镜头或事件级片段；
- 固定频率帧和场景变化关键帧；
- ASR 字幕与屏幕 OCR；
- 对象、人物和动作标签；
- 片段描述与事件关系；
- 帧、字幕、音频之间的时间对齐。

如果只做固定间隔抽帧，短暂但关键的动作可能完全缺失；如果把每一帧都索引，存储和检索成本又会急剧上升。因此视频通常需要“视频 → 场景 → 片段 → 帧”的分层表示。

## 4.6 多模态切分的正确单位是证据闭包

**证据闭包**指的是：为了使一个知识单元可以被独立理解，必须一并保留的最小上下文。

例如：

- 表格中的一个数值，需要同时保留行标题、列标题和单位；
- 图表中的一条曲线，需要保留图例、坐标轴和图注；
- 一张产品图片，需要保留产品 ID 和对应属性；
- 一句会议发言，需要保留说话人和时间戳；
- 一个操作动作，需要保留动作前后的设备状态。

因此，实际系统通常采用“细粒度索引、父级上下文回取”的策略：检索时命中区域或片段，生成时补回父页面、相邻区域或前后时间窗。

# 5. 多模态检索的五条主要技术路线

多模态 RAG 并不存在一条在所有场景都最优的检索路线。不同方法保留的信息、延迟、索引大小和可解释性差异很大。

## 5.1 路线一：全部转换成文本

这条路线先通过 OCR、ASR、图片描述、图表转写或视频摘要将内容文本化，再复用成熟的 BM25、文本向量和文本 reranker。

```text
图片 / 音频 / 视频
        │
        ▼
OCR / ASR / Caption / Summary
        │
        ▼
文本分块 → 文本索引 → 文本检索 → LLM
```

优点是工程简单、成本可控、可解释性较强，也能直接使用文本检索领域的大量成熟工具。

缺点是转换过程不可逆。系统只能检索到转换模型当时写下来的信息。精确视觉细节、复杂空间关系、非语言声音和时间过程很容易丢失。

这条路线适合：

- 以正文和语音语义为主的资料；
- 图片只是辅助说明；
- 延迟和成本要求严格；
- 需要快速建立可工作的基线。

更稳妥的实现不是“文本化之后删除原始内容”，而是**用文本召回，用原始证据回答**。

## 5.2 路线二：共享嵌入空间中的跨模态检索

CLIP 类模型使用图像编码器和文本编码器，把匹配的图文对拉近，把不匹配的图文对推远。训练完成后，文本和图片可以映射到可比较的向量空间：

```text
文本查询 ──文本编码器──► q
                            cosine(q, d)
图片语料 ──图像编码器──► d
```

于是“红色工业阀门”可以直接检索图片，图片也可以反向检索相关文本。SigLIP 将批内图文配对改写为 sigmoid 二分类目标；SigLIP 2 又加强了多语言、定位和稠密视觉特征能力。

“可以比较”不等于图像向量和文本向量的整体分布完全重合。实践中仍可能存在 **modality gap**，同一相似度阈值在不同检索方向、语言和数据域上表现不同，因此需要分别校准并使用真实查询验证。

相似度通常使用余弦相似度：

```text
sim(q, d) = (q · d) / (||q|| ||d||)
```

共享空间的优势是检索快、索引简单，适合大规模图片搜索和跨模态粗召回。

但一个全局向量必须压缩整张图片或整页文档。它擅长表示“整体是什么”，不保证精确保留小字、数值、局部对象、否定关系和复杂空间结构。CLIP 的“相似”也不等于可以完成逻辑推理。

CLAP 将相同思想扩展到音频和文字；ImageBind 则尝试把图像、文本、音频、深度、热成像和 IMU 等信号绑定到共享空间。这些模型证明了 any-to-any 检索的可能性，但通用共享空间不等于领域检索已经解决，仍然需要领域数据和真实查询评测。

## 5.3 路线三：每种模态保留专用索引，再进行融合

生产系统中常见的稳健方案，是让每种检索器做自己擅长的事：

- BM25 负责型号、编号、精确词；
- 文本向量负责语义近似；
- 图片向量负责视觉内容；
- 页面视觉检索负责复杂文档；
- CLAP 类向量负责非语言声音；
- 元数据过滤负责时间、权限和业务范围。

查询时并行召回，再进行分数校准、排名融合和统一重排。

这种方案没有强迫所有模态服从一个向量空间，便于单独升级每个检索器。UniDoc-Bench 的实验也显示，在其文档场景与统一设置下，分别检索文本和图像再融合，优于纯文本、纯图像以及统一联合嵌入方案。这不是一个对所有数据集都成立的定律，但足以说明：**统一模型更整洁，不代表专用检索器融合一定更差。**

## 5.4 路线四：把文档页面直接作为图像检索

复杂 PDF 的问题在于，文字、表格、图表和布局通常共同表达含义。视觉文档检索直接把页面渲染成图像并编码，绕过或弱化 OCR、布局分析和文本拼接。

VisRAG 使用视觉语言模型分别构建视觉检索器和生成器，直接检索页面图像并将页面交给 VLM。其论文在对应实验设置中报告，相比文本 RAG 获得了 25% 至 39% 的端到端相对提升。

这里的“不依赖 OCR”应理解为不依赖一个显式的 OCR 中间管线。视觉语言模型仍会在内部学习文字识别能力，并不代表字符识别已经消失，也不代表系统天然拥有可审计的 OCR 文本和坐标。

这类结果说明视觉路线的价值，但不能推导出“OCR 已经无用”。纯视觉检索仍面临：

- 小字号和低分辨率导致的细节丢失；
- 精确字符串、长数字和专有名词匹配不稳定；
- 页面级结果粒度过粗；
- 图像 token 和视觉推理成本较高；
- 权限审计、文本高亮和精确引用更困难。

更合理的工程结论是：对版式重、图表多的资料保留视觉通道，同时保留 OCR 和结构化通道。

## 5.5 路线五：多向量与 late interaction

单向量检索将整段文本或整页图片压缩成一个向量。**多向量检索**则为多个文本 token、图像 patch 或局部区域分别保留向量。

ColBERT 提出的 late interaction 在离线阶段独立编码文档，在查询阶段计算细粒度匹配。其典型 MaxSim 评分可以写成：

```text
score(Q, D) = Σ_i max_j (q_i · d_j)
```

含义是：对每一个查询 token `q_i`，在文档的所有局部向量 `d_j` 中找到最相似的一个，再把这些最大相似度相加。

ColPali 将这一思想用于视觉文档检索：查询被表示为多个文本 token 向量；页面图像先经过 PaliGemma，使视觉 patch token 在语言模型中得到上下文化，再投影成 128 维多向量。查询中的“Q3”“亚太区”“营收”等成分，可以分别与页面中不同局部区域发生匹配，而不是要求一个全局页面向量同时表达所有细节。

ColPali 同时发布了 ViDoRe 页面级视觉文档检索基准。后续 ColQwen 系列和其他视觉 late-interaction 模型沿着更强 VLM、更高分辨率、多语言和更高效索引继续演进。

这种方法的代价也很明确：

- 每页存储多个向量，索引体积远高于单向量；
- 查询需要执行大量 MaxSim 计算；
- ANN、压缩、token pooling 和候选裁剪更复杂；
- patch 相关性可以帮助解释命中位置，但不天然等于精确的区域边界。

原始 ColPali 实验中的页面表示为约 `1030 × 128` 个 float16 向量，约占 `257.5 KB/页`；论文中的三级 token pooling 可减少约 `66.7%` 的向量，并保留约 `97.8%` 的原始检索表现。作为对照，VisRAG-Ret 将页面池化成一个 2304 维向量，约为 `4.5 KB/页`。这些数字只代表论文实现中的原始表示，不包含 ANN 索引结构、副本和元数据，但足以说明单向量与 late interaction 的存储量级差异。

因此生产中常采用两阶段架构：先用 BM25 或单向量 ANN 粗召回，再对少量候选执行 late interaction；或者直接使用针对多向量检索优化的引擎。

## 5.6 五条路线的选择

| 路线 | 保留信息 | 检索成本 | 主要优势 | 主要风险 |
|---|---:|---:|---|---|
| 全部文本化 | 低到中 | 低 | 简单、成熟、易审计 | 转换后信息不可恢复 |
| 共享单向量 | 中 | 低 | 跨模态粗召回高效 | 局部细节和组合关系弱 |
| 专用索引融合 | 高 | 中 | 各模态发挥专长 | 系统与评测更复杂 |
| 页面视觉检索 | 高 | 中到高 | 保留布局、图表和视觉内容 | 页面粒度粗、视觉成本高 |
| 多向量 late interaction | 很高 | 高 | 细粒度匹配能力强 | 存储、计算和部署复杂 |

实践中最常见的正确答案不是五选一，而是：

> 文本与元数据负责便宜的高召回，视觉或音频向量补回文本无法表达的证据，late interaction 或 VLM reranker 负责高精度排序，最终返回原始证据。

# 6. 在线阶段：从多模态查询到可信证据

在线流程的重点不只是调用多个检索器，而是根据问题决定**查什么模态、使用什么粒度、如何融合、是否需要继续查看原始证据**。

## 6.1 查询理解与模态路由

查询路由器可以识别以下信息：

- 用户提供了哪些输入模态；
- 问题需要语言语义、视觉外观、精确数值、空间关系还是时间关系；
- 哪些索引可能包含答案；
- 是否需要结构化计算；
- 期望返回文本答案、定位框还是时间段。

例如：

| 查询 | 主要需求 | 优先检索路径 |
|---|---|---|
| “设备 X120 的额定压力是多少？” | 精确实体和数值 | BM25 + 文本向量 + 表格 |
| “这张照片中的设备是哪一款？” | 图像实体识别 | 图片向量 + 产品元数据 |
| “图中红线为什么突然下降？” | 图表视觉关系 | 页面视觉检索 + 图表区域 |
| “录音里是什么异常声音？” | 非语言声学特征 | 音频向量 + 相似故障录音 |
| “视频中操作员在哪一步忘了泄压？” | 时间过程与动作 | 字幕召回 + 片段检索 + 前后扩展 |

路由不一定由 LLM 独立决定。稳定系统通常结合输入类型、规则、轻量分类器和 LLM，并设置保底的多路召回。

## 6.2 图文组合查询

当查询同时包含图片和文字时，文字往往不是图片的描述，而是对检索意图的约束。

例如，用户上传一张鞋的图片并说“找同款，但要黑色”。系统不能简单平均图片向量与“黑色”的文本向量，否则可能只找到视觉上相似但仍是白色的鞋。

图文组合查询需要显式理解：

- 图片提供了哪些参考属性；
- 文字要求保留、修改还是排除哪些属性；
- 检索目标是同一实体、相似外观还是满足新约束的对象。

UniIR 等工作把检索指令纳入训练，正是因为零样本通用向量模型未必能够理解“用什么方式相似”。

## 6.3 多路召回的分数不能直接相加

BM25 分数、余弦相似度、late-interaction 分数和 VLM 判断分数不在同一量纲，直接按原始值相加没有稳定含义。

常见处理方式包括：

- 对每路分数进行归一化或基于验证集校准；
- 学习一个融合模型；
- 使用不依赖原始分数量纲的 Reciprocal Rank Fusion；
- 按查询类型动态调整各模态权重。

RRF 的简化形式为：

```text
RRF(d) = Σ_r 1 / (k + rank_r(d))
```

其中 `rank_r(d)` 是证据 `d` 在第 `r` 路结果中的排名，`k` 用于减弱头部排名差异。RRF 易于建立稳健基线，但它同样需要评测，不能替代领域相关性判断。

## 6.4 多模态重排

粗召回追求不漏掉正确证据，重排负责判断候选是否真正支持当前问题。

常见重排层次是：

1. 便宜的词法或单向量检索召回数十到数百个候选；
2. 多向量模型、跨编码器或 VLM 对候选进行精排；
3. 对最高分候选执行局部放大、OCR 核验或时间段扩展；
4. 去重并控制来自同一文档、同一视频的证据数量。

VLM reranker 能直接比较“问题 + 页面图像”，但其成本高且可能受候选顺序影响。应当记录排序前后的候选、模型版本和提示词，以便复现。

## 6.5 命中之后还要进行证据扩展

检索命中的最小单元通常不够直接回答问题：

- 命中正文段落后，补回它引用的图 3；
- 命中表格单元格后，补回行列标题和单位；
- 命中图表后，补回图注和解释段落；
- 命中视频帧后，补回前后若干秒；
- 命中一句发言后，补回说话人和上一个问题；
- 命中低分辨率页面后，重新渲染或裁剪高分辨率区域。

证据扩展应依赖离线阶段保存的结构关系，而不是在线阶段临时猜测。

# 7. 生成阶段：让模型真正使用多模态证据

检索正确不代表答案正确。模型可能忽略图片，只依赖更容易阅读的文本；也可能受到无关图片干扰，或者把不同页面的证据错误拼接。

## 7.1 原始证据优先，派生文本辅助

推荐将上下文组织为：

```text
[证据 E1]
来源：manual-v7.pdf，第 42 页，图 3
派生文字：压力限制与阀门状态示意图
原始内容：高分辨率图表裁剪

[证据 E2]
来源：manual-v7.pdf，第 41 页，第 2 段
原始文字：当压力超过 8.0 bar 时……
```

派生描述帮助模型快速理解，原始证据用于核验细节。对于需要精确数字、颜色、空间位置和视觉比较的问题，不能只提供 caption。

## 7.2 上下文打包需要显式预算

可以为不同证据设置统一的效用函数：

```text
utility(e) =
  relevance(e)
  × evidence_quality(e)
  × modality_necessity(e)
  × source_trust(e)
  / context_cost(e)
```

这不是必须照搬的数学模型，而是一种工程思维：高相关但模糊的截图、质量很高但与问题无关的页面、重复出现的同一张图，都不应无限占用上下文。

常用策略包括：

- 先放最关键证据，再放补充证据；
- 文本保留关键段落，图片只传高相关页面或裁剪区域；
- 同时给一张低分辨率整页和一张高分辨率局部图；
- 视频只传关键片段，并保留时间顺序；
- 限制同一来源的重复候选；
- 对长表格传结构化行列，而不是只传截图。

## 7.3 模型必须区分观察、推断和外部知识

高质量提示应要求模型：

1. 先列出每条证据中能够直接观察到的事实；
2. 再基于这些事实推断；
3. 不把图片中不可读的内容猜出来；
4. 证据冲突时指出冲突；
5. 每个关键结论引用具体证据 ID；
6. 证据不足时明确拒答或请求更清晰的输入。

这可以减少模型把常识、参数知识和检索证据混在一起的情况。

## 7.4 精确数值问题需要工具而不是纯视觉猜测

VLM 可以解释图表，但在小字号、密集表格和复杂计算中并不稳定。涉及金额、比例、坐标、公式时，推荐使用：

- OCR 或表格解析获得候选数值；
- 原图核验数值与表头关系；
- 代码或计算器执行运算；
- 最终答案引用原始页面和计算过程。

这是一种“视觉定位 + 结构化提取 + 确定性计算”的组合，不应要求模型仅凭截图完成全部工作。

## 7.5 多模态引用必须比文本引用更精确

仅引用文件名不足以支持审计。理想引用粒度包括：

- 文档：文件版本、页码、区域坐标；
- 图片：图片 ID、区域框；
- 音频：起止时间、说话人；
- 视频：起止时间、关键帧或空间区域；
- 表格：表格 ID、行、列、单元格；
- 派生内容：解析器、caption 模型和版本。

引用系统应指向原始证据，而不是只指向由模型生成的摘要。

# 8. 复杂文档是多模态 RAG 最典型的战场

企业知识库中的 PDF、PPT、扫描件和报表，通常同时包含正文、表格、公式、图表、图片和版面关系。它们不是“带几张图片的文本”，而是一种由多种视觉和结构信号共同组成的知识载体。

## 8.1 正文检索与页面检索解决的问题不同

正文检索的优势是：

- 精确匹配专有名词、编号和长数字；
- 文本分块粒度细；
- 索引成本低；
- 便于高亮、引用和权限审计。

页面视觉检索的优势是：

- 保留多栏布局、颜色、字体和区域关系；
- 图表、流程图和信息图无需先完整转写；
- 避免 OCR 阅读顺序错误直接污染文本；
- 页面可以被原样交给 VLM。

二者的关系不是替代，而是互补。对于纯文字页，文本检索通常更直接；对于图表页、复杂幻灯片和扫描材料，视觉检索更有价值。

## 8.2 表格不能只被当作一串文本

表格中的含义来自“值位于哪一行、哪一列、使用什么单位”。以下三种表示各有作用：

| 表格表示 | 优势 | 风险 |
|---|---|---|
| 页面或表格截图 | 最大程度保留视觉关系 | 精确数值读取与计算不稳定 |
| Markdown / HTML 表格 | 便于模型阅读和引用 | 合并单元格、跨页表格可能解析错误 |
| 结构化 JSON / 数据库行 | 便于过滤、聚合和计算 | 需要可靠 schema 与字段映射 |

可靠方案通常同时保存三种表示。检索时可以用表题、表头和语义向量定位表格；回答时根据问题选择截图核验、结构化查询或计算工具。

如果问题是“2025 年 Q3 亚太区收入是多少”，证据闭包至少应包含：

```text
表格标题 + Q3 列标题 + 亚太区行标题 + 数值 + 单位 + 页码
```

仅命中数值单元格没有意义。

## 8.3 图表理解需要区分检索和数据读取

图表检索回答的是“哪张图可能包含答案”，图表读取回答的是“图中具体表达了什么”。

图表可以派生出：

- OCR 文本：标题、坐标轴、图例、标注；
- caption：总体趋势和主题；
- 结构化数据：系列、横轴、纵轴和值；
- 原始图片：颜色、位置和未被提取的视觉细节。

对于“哪张图讨论能源消耗”，caption 和视觉向量已经可能足够。对于“2024 年比 2023 年增长多少”，则需要可靠读取数据点并执行计算。

颜色不能成为唯一的引用方式。回答“蓝线增长最快”时，还应引用图例中的系列名称，因为色觉差异、主题切换和图像压缩都可能造成歧义。

## 8.4 流程图和架构图依赖关系结构

流程图中的文字只是节点标签，真正的信息还包括箭头方向、分支、泳道和包含关系。OCR 可能识别出所有文字，却仍然无法恢复流程。

可以采用三层证据：

1. 原始流程图；
2. OCR 后的节点和坐标；
3. 通过视觉模型或图解析器生成的节点边关系。

生成答案时，模型既可以查看原图，也可以使用结构化关系进行路径搜索。结构化结果必须保留对原图区域的映射，防止解析错误被当成事实。

## 8.5 公式需要同时保留视觉、LaTeX 和上下文

只保存公式截图不利于检索，只保存 LaTeX 又可能丢失编号、上下标位置和邻近定义。理想证据包括：

- 公式区域截图；
- LaTeX 或 MathML；
- 公式编号；
- 前后解释段落；
- 变量定义及其所在位置。

“这个公式是什么意思”通常需要上下文；“公式中分母是什么”需要视觉或结构化表达；“代入参数计算结果”还需要计算工具。

## 8.6 页面级检索不是终点

ColPali、ColQwen 等视觉文档检索方法主要解决“正确页面能否进入 Top-K”。页面命中后，系统仍可能面对：

- 一页有多个图表，只有一个相关；
- 目标文字太小，VLM 看不清；
- 多页表格需要跨页合并；
- 答案需要页面正文与图表共同支持；
- 同一页面存在相似数字，必须精确定位。

因此更完整的流程是：

```text
文档级过滤
  → 页面级召回
  → 区域级定位
  → 高分辨率裁剪
  → 结构化读取或 VLM 核验
  → 带区域引用的答案
```

视觉 late interaction 的 patch 相似度热力图可以帮助定位，但它是相关性线索，不应直接被解释成严格的目标检测框。区域级检索与视觉 grounding 仍是独立能力。

# 9. 音频 RAG：语音内容与声音本身必须分开处理

音频 RAG 最常见的错误，是把所有音频都等同为“待转写的语音”。实际上，音频同时承载语言信息和声学信息。

## 9.1 ASR 文本路线

对会议、客服录音、播客和课程，最实用的基线通常是：

```text
音频
  → 语音活动检测
  → 说话人分离
  → ASR 与时间戳
  → 文本检索
  → 回取对应音频片段
```

这条路线可以使用成熟的文本检索，并方便按关键词、人物和主题搜索。

但 ASR 错误会直接传播到检索。产品名、人名、缩写、数字和低频术语尤其容易识别错误。可以通过领域词表、热词偏置、拼音或音素级召回，以及保留多个转写候选进行缓解。

若需要词级引用，还应使用带语音活动检测和强制对齐的时间戳方案，例如 WhisperX 一类工具。段落级大致时间并不足以支持逐句回放和精确引用。

## 9.2 原生音频检索路线

CLAP 使用音频编码器和文本编码器，通过对比学习把匹配的音频与描述映射到共享空间。它可以支持：

- 用“金属连续摩擦声”搜索相似录音；
- 用一段故障声音搜索历史案例；
- 搜索掌声、警报、狗叫或特定音乐风格；
- 在没有 ASR 文本时进行语义音频检索。

WavRAG 等工作进一步探索直接编码音频或音频加文本查询，并从文本与音频混合知识库中检索。

这类方法并不意味着 ASR 应被删除。文本检索更适合“说了什么”，音频向量更适合“听起来像什么”。生产系统通常同时保留两路。

## 9.3 长音频需要时间定位

将一小时录音压缩成一个向量，只能表达整体主题，无法定位某一句话或短暂异响。更合理的索引层次是：

```text
录音级
├── 章节或议题级
├── 说话人轮次级
└── 声音事件级
```

查询命中短片段后，需要按任务扩展上下文：

- 问会议决策：补回前一个问题和后续结论；
- 问情绪变化：补回前后语调；
- 问机械异响：补回异响出现前后的设备状态；
- 问一句话原文：回取精确时间段并播放。

## 9.4 音频答案的引用

音频引用至少应包含：

```text
录音 ID + 起止时间 + 说话人或声源 + 转写版本
```

若答案依赖非语言声音，还应允许用户直接试听证据片段。只显示 ASR 文本无法证明模型真的依据了声音本身。

# 10. 视频 RAG：检索的不是帧，而是事件

视频是多模态 RAG 中成本最高、时间结构最强的场景。它同时包含画面、语音、环境声、屏幕文字和动作顺序。

## 10.1 为什么只检索字幕不够

字幕适合回答“讲解者说了什么”，却无法完整回答：

- 操作员实际按下了哪个按钮；
- 人物表情如何变化；
- 哪个零件先发生位移；
- 屏幕上出现了什么警告；
- 说话内容与实际操作是否一致。

反过来，只检索关键帧也会漏掉语言说明、环境声和动作过程。因此视频 RAG 需要让不同通道在同一时间轴上对齐。

## 10.2 视频检索应采用分层结构

一个常见的层次是：

```text
视频
├── 全局摘要与元数据
├── 章节 / 场景
│   ├── 事件片段
│   │   ├── 关键帧
│   │   ├── ASR 字幕
│   │   ├── 屏幕 OCR
│   │   └── 音频事件
│   └── 事件关系
└── 原始连续媒体
```

第一阶段先找到相关视频或章节，第二阶段定位事件片段，第三阶段在片段内提高采样密度。这样比从全部帧中一次性搜索更节省成本，也更容易保持时间连续性。

这里的时间轴应被视为跨模态关联的主键：ASR 单词、说话人轮次、OCR、镜头、关键帧和事件片段都通过起止时间连接，而不是依赖各自数组中的序号。

## 10.3 固定抽帧、关键帧和查询相关采样

| 采样方式 | 优势 | 主要问题 |
|---|---|---|
| 固定间隔抽帧 | 简单、稳定、易缓存 | 容易错过短暂事件 |
| 场景变化关键帧 | 去除大量重复画面 | 一个镜头内的动作过程可能被压缩 |
| 事件级切片 | 更符合语义边界 | 依赖事件检测质量 |
| 查询相关采样 | 将预算集中到相关时段 | 首轮定位错误会放大后续错误 |
| 粗到细自适应采样 | 兼顾全局搜索和局部细节 | 流程复杂、延迟更高 |

VideoRAG 的代表性思路是同时使用视觉与文本特征检索视频，并在上下文受限时选择信息量较高的帧。更新的长视频研究继续表明，时序定位本身是核心瓶颈：系统必须先找到相关时间段，再在局部范围内理解细节。

## 10.4 时间顺序不能在上下文打包时被破坏

如果将检索到的帧按相似度高低排序后直接交给模型，原本的时间关系会被打乱。所有帧和片段必须携带时间戳，并按回答任务组织：

- 状态识别问题可以使用少量独立关键帧；
- 动作顺序问题必须按时间排列连续证据；
- 因果问题需要包含事件发生前后的上下文；
- 计数问题需要去重相同事件，避免重复片段导致重复计数。

“找到正确画面”和“理解发生顺序”是两项不同能力。

## 10.5 视频查询存在多种粒度

同一个视频知识库可能接收：

- “哪段视频介绍了泵的维护？”：视频或章节级检索；
- “操作员何时关闭阀门？”：时间段定位；
- “关闭阀门之前做了什么？”：局部时序推理；
- “三段维修视频的步骤有什么不同？”：跨视频对齐与比较；
- “视频中的设备声音是否异常？”：视觉、音频和领域知识联合检索。

如果所有问题都使用同一种固定 Top-K 片段和固定帧数，系统很难同时满足这些任务。

## 10.6 视频 RAG 的生成上下文

对一个命中的事件片段，可以同时提供：

```text
时间段：00:13:42 - 00:14:08
字幕：操作员说“现在已经完成泄压”
屏幕 OCR：压力 3.2 bar
关键帧：00:13:45、00:13:57、00:14:04
原始片段：26 秒
```

模型可以利用字幕定位意图，利用帧判断操作，利用 OCR 读取仪表，利用连续片段核对状态变化。单独任何一路都可能产生错误。

# 11. 一个完整案例：设备运维多模态知识库

下面用“工业设备故障排查助手”串起完整流程。知识库包含：

- 设备说明书和维修手册；
- 参数表、线路图和故障码表；
- 正常与异常部件照片；
- 历史维修记录；
- 标准操作视频；
- 设备运行声音；
- 用户上传的现场图片、录音或视频。

## 11.1 离线知识构建

```text
说明书
→ 解析正文、表格、图表和页面图像
→ 建立文本索引、页面视觉索引和关系索引

维修照片
→ OCR 铭牌、生成领域描述、提取视觉向量
→ 关联设备型号和工单

故障录音
→ 生成声学向量、声音事件标签
→ 关联故障原因和维修结果

操作视频
→ 场景切分、ASR、屏幕 OCR、关键帧和片段向量
→ 关联标准步骤与安全规则
```

每个派生对象都指向原始资源的版本、页码、坐标或时间段。

## 11.2 查询一：设备的额定压力是多少

查询包含明确型号和精确数值需求。路由器优先选择 BM25、文本向量和表格索引。

系统命中说明书参数表中的一行，补回表头与单位；再使用页面截图核验型号和数值对应关系。最终回答引用“第 12 页，表 2，第 4 行”，而不是只说“来自说明书”。

这里视觉通道是核验手段，文本与结构化通道承担主要检索。

## 11.3 查询二：用户上传的部件是否出现裂纹

系统先用图片向量找到相似部件和历史故障照片，再根据设备型号过滤候选。VLM 比较用户图片与正常、异常样本，必要时调用局部放大或检测工具。

最终答案应区分：

- 图片中直接可见的现象；
- 与历史裂纹样本的相似点；
- 无法仅凭图片确认的结论；
- 建议执行的无损检测步骤。

这里不能让模型根据一张模糊照片直接给出确定性安全结论。

## 11.4 查询三：这段声音是不是轴承故障

系统并行执行：

1. 音频向量检索相似故障录音；
2. 根据设备型号和工况过滤；
3. 检索对应维修记录；
4. 对比正常工作声音；
5. 返回相似片段、历史原因和置信度。

如果用户录音包含人声说明，ASR 文本可作为额外查询条件；真正判断异响仍需要声学证据。

## 11.5 查询四：操作视频中哪一步违反安全规范

系统先通过 ASR 和片段描述定位“泄压、断电、拆卸”相关时段，再回取连续视频片段与安全手册。

证据可能显示：

```text
标准手册：断电 → 锁定挂牌 → 泄压 → 拆卸
现场视频：断电 → 拆卸 → 泄压
```

模型依据时间顺序指出违规步骤，并分别引用手册页码和视频时间段。此问题需要跨模态、多来源和时序对齐，单纯搜索字幕不足以完成。

## 11.6 在线编排伪代码

```python
def answer_multimodal(query):
    intent = analyze_query(query)

    candidates = parallel_retrieve(
        lexical=query.text,
        text_embedding=query.text,
        visual_embedding=query.image,
        audio_embedding=query.audio,
        video_query=intent.temporal_query,
        metadata_filters=intent.filters,
    )

    fused = reciprocal_rank_fusion(candidates)
    reranked = multimodal_rerank(query, fused[:80])
    evidence = expand_and_localize(reranked[:8], intent)
    context = pack_under_budget(evidence, intent)

    draft = generate_with_citations(query, context)
    return verify_claims_against_evidence(draft, context)
```

伪代码最值得注意的是：检索、证据扩展、上下文打包和答案核验是四个不同阶段。把向量库 Top-K 直接拼进提示词，只完成了其中最简单的一部分。

# 12. 多模态 RAG 应该怎样评测

只评测最终答案会掩盖故障位置。多模态 RAG 至少需要分别评测解析、检索、定位、生成、引用和鲁棒性。

更通用的文本 RAG 评测可参考 [004-RAG-评测](004-RAG-评测.md)，这里重点补充多模态特有部分。

## 12.1 解析与对齐评测

| 对象 | 可评测内容 |
|---|---|
| OCR | 字符错误率、词错误率、数字准确率 |
| 版面 | 区域检测、阅读顺序、标题层级 |
| 表格 | 单元格识别、行列关系、结构相似度 |
| 图文关系 | 图片与图注匹配准确率 |
| ASR | WER、专有名词准确率、时间戳偏差 |
| 视频 | 场景边界、关键事件覆盖率 |
| 跨模态对齐 | 文本、图片、音频、视频是否关联到同一证据 |

必须针对真实业务资料抽样标注。公开 OCR 分数无法代表系统在自家扫描合同、医疗报告或设备铭牌上的表现。

## 12.2 检索评测

常用指标包括：

- **Recall@K**：正确证据是否进入前 K；
- **Precision@K**：前 K 中有多少真正相关；
- **MRR**：第一个正确证据出现得有多早；
- **nDCG@K**：考虑多级相关性和排名位置；
- **mAP**：多个相关结果的整体检索质量。

ViDoRe 主要评测页面级视觉文档检索；M-BEIR 覆盖多种查询与候选模态组合；DocHaystack 类任务强调从大量视觉文档中检索；VisR-Bench 进一步关注长文档和多语言视觉检索。引用公开结果时还应注明基准版本：ViDoRe V1/V2 常见主指标为 nDCG@5，V3 使用 nDCG@10，不能把不同候选集和指标下的数字直接横向排列。

不能只测“相关页面是否命中”。若产品要高亮区域或定位视频时间，还需要：

- 区域定位的 IoU、命中率；
- 时间定位的 temporal IoU；
- 关键事件覆盖率；
- 引用位置偏差。

## 12.3 生成评测

最终答案至少应从以下维度评估：

- 答案正确性；
- 关键信息完整性；
- 每个陈述是否被证据支持；
- 是否遗漏相反证据；
- 引用是否指向真正支持该结论的区域或时间段；
- 是否错误依赖模型参数知识；
- 证据不足时是否正确拒答。

MRAG-Suite 的思路是把长答案拆成原子 claim，再分别判断图片或文本证据对 claim 的蕴含、矛盾或中立关系。这比单个“答案质量分”更容易定位问题。

## 12.4 必须构造真正需要多模态的问题

评测集应按证据需求分层：

| 问题类型 | 示例 | 目的 |
|---|---|---|
| 文本即可回答 | “手册规定的保修期多久？” | 验证多模态方案没有伤害文本能力 |
| 视觉必要 | “红色曲线在哪一年达到峰值？” | 验证系统真的使用图片 |
| 图文联合 | “结合图 3 与正文，下降原因是什么？” | 验证跨模态融合 |
| 精确数值 | “A 组比 B 组高多少？” | 验证读取与计算 |
| 空间关系 | “警告标志位于哪个按钮上方？” | 验证局部定位 |
| 时间顺序 | “操作员在泄压前做了什么？” | 验证视频时序 |
| 音频必要 | “录音中是否出现连续摩擦声？” | 验证非语言声音 |
| 多跳跨模态 | “视频中的故障码对应手册哪种处理？” | 验证多来源推理 |
| 不可回答 | “看不清的铭牌序列号是什么？” | 验证拒答能力 |

如果所有问题都能从 caption、OCR 或字幕回答，那么评测到的是文本 RAG，不是多模态 RAG。

## 12.5 消融实验比单一总分更重要

至少运行以下对照：

1. 只使用文本；
2. 只使用视觉或音频；
3. 文本与原始模态融合；
4. 去掉 reranker；
5. 去掉证据扩展；
6. 只给 caption，不给原图；
7. 图像顺序或视频帧顺序打乱；
8. 加入视觉相似但答案错误的干扰项；
9. 降低图片分辨率；
10. 使用 gold evidence 测生成上限。

其中 `gold evidence` 实验可以回答一个关键问题：系统失败到底是因为没检索到，还是因为模型拿到正确证据也不会使用。

## 12.6 端到端总分不能替代分层诊断

典型错误链路可能是：

```text
OCR 识别错一个数字
→ 文本检索漏召回
→ 视觉索引召回了相似页面
→ reranker 选错图表
→ VLM 基于错误证据生成流畅答案
```

如果只看最终答案错误，无法判断应该更换 OCR、优化召回、调整重排还是修改生成提示。生产系统必须记录每一层的输入、输出、分数、模型版本和耗时。

# 13. 生产化中的关键工程问题

多模态 RAG 的难点往往不在 demo，而在索引体积、媒体处理成本、权限、版本一致性和可观测性。

## 13.1 存储与计算成本

成本通常来自：

- PDF 页面渲染与 OCR；
- VLM caption 和页面编码；
- 多向量索引；
- 视频解码、抽帧和片段描述；
- 音频转写和声学编码；
- 多图片或视频上下文推理；
- 多模态 reranker。

降低成本的常见方式包括：

- 按内容哈希去重；
- 缓存页面渲染、caption 和 embedding；
- 文本优先粗召回，视觉模型只处理候选；
- 根据页面类型决定是否启用视觉索引；
- 对多向量执行降维、量化或 token pooling；
- 视频先做章节级检索，再局部密集抽帧；
- 为简单查询设置纯文本快速路径；
- 将离线模型版本和派生结果版本化，避免无意义全量重算。

## 13.2 更新一致性

一个原始 PDF 更新后，可能需要同步更新：

- OCR 文本；
- 页面图片；
- 表格和图片区域；
- caption；
- 文本向量；
- 视觉向量；
- 跨模态关系；
- 引用位置。

应使用 `asset_version + parser_version + model_version + content_hash` 标识派生结果。新索引完成前保留旧版本，切换时原子更新，避免查询同时命中新旧证据。

## 13.3 权限必须在所有模态和派生物上继承

图片缩略图、OCR 文本、音频转写和 embedding 都是原始内容的派生物，不能因为换了存储系统就失去权限标签。

检索前或检索过程中必须执行 ACL 过滤。不能先跨权限召回再依赖生成模型“不要泄露”，因为证据一旦进入模型上下文就已经越权。

视频和会议录音还可能涉及人脸、声纹、个人信息和录音授权，需要单独的数据保留与脱敏策略。

## 13.4 多模态 Prompt Injection

恶意指令可以藏在：

- PDF 正文或白色小字中；
- 图片中的文字；
- 网页截图；
- 音频转写；
- 视频字幕或单帧画面；
- OCR 和 caption 的派生文本中。

检索到的内容必须始终被视为**不可信数据**，不能获得系统指令权限。工具调用、数据访问和最终输出仍需经过权限与策略层控制。

对高风险场景可以：

- 标记证据来源和信任等级；
- 将内容与系统指令使用明确的数据边界隔离；
- 检测“忽略之前指令”等模式，但不把规则匹配当作唯一防线；
- 对从图片、音频中识别出的指令采用同样的安全策略；
- 在执行外部动作前进行独立授权。

## 13.5 可观测性

一次查询应记录：

```text
查询及输入模态
→ 路由决策
→ 各检索器候选与原始分数
→ 融合后排名
→ 重排结果
→ 证据扩展
→ 最终上下文
→ 答案中的 claim 与引用
→ 每阶段延迟和成本
```

图片、音频和视频内容体积较大，可以记录对象引用、缩略图、时间戳和哈希，而不是在日志中重复复制原始媒体。日志本身也必须继承敏感数据权限。

## 13.6 降级策略

多模态模型、媒体解析和视频处理都可能超时。生产系统应提前定义：

- 页面视觉模型不可用时，是否退回 OCR 文本；
- 图片过大时如何降采样；
- 视频处理超时时是否先返回字幕答案；
- 音频噪声过大时是否请求重新录制；
- 区域无法定位时是否只提供页面级引用；
- 证据冲突时是否停止自动回答。

降级结果必须向用户说明证据能力的变化，不能把“只看了字幕”伪装成“分析了完整视频”。

# 14. Agentic 多模态 RAG：从一次检索变成主动取证

固定流水线适合查询类型稳定的场景。当问题需要逐步放大图片、查看视频局部、比较多个来源或根据新线索继续搜索时，可以引入 Agent。

## 14.1 Agent 可以执行哪些多模态动作

- 搜索文字、图片、音频和视频；
- 打开某一页或某一时间段；
- 放大、裁剪或旋转图片；
- 对局部区域重新 OCR；
- 对视频片段提高抽帧密度；
- 提取表格并执行计算；
- 根据图中型号继续搜索说明书；
- 比较多个证据并检查冲突；
- 判断当前证据是否足够，决定继续检索或停止。

其循环可以表示为：

```text
提出证据假设
  → 选择模态与工具
  → 获取局部证据
  → 检查是否支持假设
  → 调整查询或查看更细粒度内容
  → 形成带引用结论
```

## 14.2 主动感知比一次性传入大量图片更有效

面对一张高分辨率电路图，模型可能先查看整图确定相关区域，再裁剪局部读取编号，最后查询元件手册。面对一小时视频，模型可能先用字幕搜索缩小到五分钟，再用关键帧定位一分钟，最后查看十秒连续片段。

这种“粗到细”的过程把检索、视觉 grounding 和工具使用结合起来，本质上是**按需分配感知预算**。

## 14.3 Agent 不会自动修复错误的感知工具

如果 OCR 持续把 `8.0` 识别成 `3.0`，或者首轮视频定位漏掉关键事件，Agent 可能围绕错误线索反复推理。Agentic 架构还会增加延迟、成本和不可重复性。

因此，Agent 应建立在：

- 可评测的基础检索器；
- 可追溯的工具输出；
- 严格的步数和成本预算；
- 证据充分性检查；
- 失败时的确定性降级；
- 工具级权限控制。

Agentic RAG 的通用原理可继续参考 [005-Agentic-RAG](005-Agentic-RAG.md) 和 [006-Agentic-RAG-如何进行构建](006-Agentic-RAG-如何进行构建.md)。

# 15. 如何为实际项目选择方案

选型时不要先问“用哪个多模态模型”，而应先问：答案依赖哪种信息，正确证据的自然粒度是什么，错误成本有多高。

## 15.1 按数据与问题选择

| 场景 | 推荐起点 | 何时升级 |
|---|---|---|
| 正文为主的 PDF | 结构化解析 + 文本混合检索 | 图表、扫描页召回差时增加页面视觉索引 |
| 财报、论文、幻灯片 | 文本索引 + 页面视觉检索 | 页面噪声大时增加区域定位和 late interaction |
| 商品与素材图片 | 图文共享向量 + 元数据过滤 | 组合属性复杂时增加指令检索和 VLM reranker |
| 会议与客服录音 | ASR + 说话人 + 文本检索 | 语气、环境声重要时增加音频向量 |
| 机械或环境声音 | CLAP 类音频检索 + 领域标签 | 长录音定位差时增加事件级索引 |
| 教学与操作视频 | 字幕 + 场景切分 + 关键帧 | 动作顺序重要时增加片段级时序检索 |
| 长视频库 | 视频级粗召回 + 片段级细检索 | 多跳问题增加图结构或 Agent 粗到细查看 |
| 高风险数值问答 | 文本/视觉定位 + 结构化提取 + 计算 | 无法可靠核验时拒答并返回原始证据 |

## 15.2 推荐的迭代顺序

一个务实的建设顺序是：

1. 建立真实问题集，并标注答案依赖的模态和证据位置；
2. 实现 OCR、ASR 和文本混合检索基线；
3. 保留原始资源，做到文本召回后回取原始证据；
4. 针对文本基线失败的问题增加视觉或音频检索；
5. 引入多路融合和 reranker；
6. 增加区域、表格和时间段定位；
7. 建立 claim 级引用与拒答评测；
8. 只有复杂查询确实需要时，再引入 Agentic 粗到细取证。

这个顺序避免了为了“多模态”而把所有数据都送进昂贵模型，也避免系统永久停留在“把图片变成一句 caption”的伪多模态阶段。

## 15.3 三个最终判断

可以用三个问题快速判断设计是否合理：

1. **信息是否保住了？** 原图、空间关系、声音或时间关系有没有在入库时被不可逆丢弃？
2. **证据是否找对了？** 检索目标是主题相似，还是足以支持问题的具体证据？
3. **答案是否可核验？** 用户能否回到具体页、区域、音频或视频时间段验证结论？

只有三个问题都能回答，系统才真正完成了多模态 RAG 的闭环。

# 16. 总结

多模态 RAG 的本质，是把原本散落在文字、像素、声音和时间中的知识，组织成可以被检索、组合、验证和引用的证据。

它与文本 RAG 的差异不只是多了几个编码器，而是整个系统对象发生了变化：

- chunk 从文本段落变成带空间或时间位置的证据单元；
- embedding 从单一文本向量变成文本、视觉、音频和多向量表示；
- Top-K 从同一种分数排序变成多路召回、校准、融合和重排；
- context 从字符串拼接变成带预算的图文音视频证据包；
- citation 从文件链接变成页码、区域和时间段；
- evaluation 从答案相似度变成解析、定位、检索、grounding 和 claim 级验证。

最稳健的生产架构通常不是“用一个万能多模态模型替换所有组件”，而是：

> 保留原始证据，以结构化解析和专用索引保证精度，以共享向量和视觉检索补充跨模态召回，以多模态模型完成理解与重排，再用来源、坐标和时间戳约束生成结果。

当文本已经足够时，不必强行使用视觉；当答案依赖布局、图表、声音或动作过程时，也不能假装一段 OCR、caption 或字幕已经保留了全部信息。多模态 RAG 真正追求的不是“支持更多文件类型”，而是让系统在面对不同信息形态时，仍然能够找到**最小、充分、可核验的证据集合**。

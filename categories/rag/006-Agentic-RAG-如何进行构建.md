## 一、先讲最简单、最高效的构建方式


> 目前构建 Agentic RAG 最省力、上限也很高的方式之一

但需要区分两件事：

- **做出效果很好的原型或个人工具**：你的公式基本成立。

- **做成稳定、可评测、多人使用的生产系统**：仅靠 Runtime + Prompt + Skill + MCP 还不够。

可以把它理解成：
```
Agent Runtime
├── Prompt：定义目标、策略、边界
├── Skills：沉淀可复用的方法和工作流
├── MCP/Tools：连接搜索、数据库、文件、浏览器
├── Memory：保存跨步骤、跨会话状态
└── Model：负责理解、规划、判断和生成
```

传统 RAG 通常是一条固定流水线：
```
问题 → 向量检索 → 拼接上下文 → 生成答案
```

而 Agentic RAG 更像一个动态调查过程：
```
理解问题

  → 决定查什么

  → 选择数据源

  → 多轮检索

  → 判断证据是否充分

  → 必要时改写查询或调用其他工具

  → 汇总并引用证据
```

TRAE、Codex、Claude Code 这类 Runtime 已经替你提供了最难搭的一部分：

- 工具调用循环
- 任务规划
- 文件和代码搜索
- 上下文管理
- Skill 加载
- MCP 接入
- 错误恢复
- 多步骤执行

所以现在做 Agentic RAG，很多时候确实不需要先写一个复杂框架。<u style="text-decoration-color: #e63946">一个目录、一组高质量 Skill、几个搜索或数据库 MCP，再加严格的提示词，就能达到很不错的效果</u>。

不过，效果好的关键不是“接上了 MCP”，而是下面这些能力：

> 1. Agent 知道<u style="text-decoration-color: #e63946">何时检索、查哪里、何时停止</u>。
>
> 2. Skill 包含`领域方法论`，而不只是工具说明。
>
> 3. 检索结果有来源、时间和可信度信息。
>
> 4. Agent 能识别<u style="text-decoration-color: #e63946">证据冲突和信息不足</u>。
>
> 5. 有真实问题集来<u style="text-decoration-color: #e63946">评测</u>召回率、正确率和引用准确率。

真正进入生产环境后，还需要补齐：

- 权限隔离与敏感信息控制
- Prompt Injection 防护
- 检索质量评测
- 调用链可观测性
- 延迟、Token 和费用控制
- 失败重试与确定性降级
- 数据更新和索引同步
- 答案引用与事实核验

所以我的结论是：

> Agent Runtime + Prompt + Skills + MCP，已经成为 Agentic RAG 最合理的“系统底座”。它不是玩具方案，甚至很可能比自己搭一套 Agent 框架效果更好。

但它解决的是“智能执行层”。生产级 Agentic RAG 的真正壁垒，会逐渐转移到：

> 领域知识如何组织、工具如何设计、检索如何评测、权限如何控制，以及系统如何证明自己的答案可靠。

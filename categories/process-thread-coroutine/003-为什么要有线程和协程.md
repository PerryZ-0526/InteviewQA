# 为什么要有线程？为什么要有协程？

## 题目

为什么要有线程？为什么要有协程？

## 面试直接答

> 线程诞生是因为进程"创建切换贵、通信贵"，无法经济地支撑"一份数据多个执行流"的并发需求；协程诞生是因为线程"内核调度成本高、栈内存大、锁竞争复杂"，在海量 IO 并发下浪费严重。两者的演进动机一致——用更低的单位成本承载更多的并发，区别是线程把并发粒度从进程缩到执行流，协程把调度权从内核收到用户态。

先回答为什么要有线程。进程模型有两大缺陷。第一，创建和切换昂贵：切换进程要换页表、TLB 失效、CPU 缓存冷启动，成本在微秒到毫秒级；第二，进程间通信昂贵：管道要拷贝、套接字要序列化，而很多并发场景——比如一个服务器同时服务一万个客户端，或者一个程序同时做界面渲染和后台计算——天然需要多个执行流共享同一份数据。线程正是为此而生：同一进程内的多个线程共享地址空间，直接读写共享内存，通信成本几乎为零；线程切换不需要换地址空间，成本降到微秒级；创建线程只是分配一个栈和任务结构，比 fork 加 exec 轻量得多。所以线程的本质答案是：**在保持共享内存便利的前提下，把并发的最小单位从进程缩小到执行流**，让"多任务 + 共享数据"变得经济可行。

再回答为什么有了线程还要有协程。线程在海量并发下有四个硬伤。第一，**内核调度开销**：每次线程切换要陷入内核、保存恢复上下文、由调度器裁决，1 到 10 微秒一次，十万个连接的高频切换下，光调度开销就吃掉可观的 CPU；第二，**栈内存**：Linux 线程默认栈 8MB，一万线程就是 80GB 虚拟地址空间，虽然物理内存惰性分配，但地址空间、内核线程数据结构、调度队列长度都是实打实的约束，线程数很难突破数万级；第三，**锁与竞争**：共享内存并发必须加锁，锁竞争带来阻塞、唤醒和额外的上下文切换风暴，编程复杂度高；第四，**切换时机不可控**：线程随时可能被内核抢占，切换点对程序员不可见，让并发逻辑难以推理。协程针对性地解决了全部四点：切换是用户态函数调用，几十纳秒，不经过内核；栈按需分配，几 KB 起步，单机承载百万协程；单线程内协作式执行，共享状态无需锁；切换点由 `await`、`yield` 显式标记，程序在哪些位置可能交错一目了然。

更深一层看，协程解决的本质问题是"**阻塞等待的浪费**"。高并发服务里线程的大部分生命周期都在等 IO——等网络包、等磁盘、等锁，真正执行的时间占比极低。与其让内核在线程之间空转调度，不如把调度权交给应用程序：IO 等待期间主动让出，事件循环立刻切换到下一个有活干的协程。所以协程从来不是孤立存在的，它必须和非阻塞 IO、事件循环配套——asyncio、epoll、io_uring 是同一套体系的不同层次。

当然也要讲边界。协程不创造并行：单线程协程无法利用多核，CPU 密集任务用协程毫无收益；协作式调度要求程序里不能有阻塞调用，否则整个循环卡死。正因为如此，现代工业界的主流答案是把两者结合——Go 的 goroutine、Java 的虚拟线程都是 **M:N 模型**：运行时维护少量内核线程，把海量用户态任务复用到其上，用户态任务阻塞时运行时自动把它搬走，既保留了协程的低成本切换，又获得了内核线程的多核并行能力。总结来说：线程回答"如何让共享数据的并发更便宜"，协程回答"如何让海量 IO 并发更便宜"，M:N 运行时则是两个答案的合流。

## 详细解析

### 1. 并发模型的演进脉络

```
单进程阻塞模型          一次只服务一个连接，其余排队
  │ 问题：吞吐 = 1 / 单个请求耗时
  ▼
多进程（prefork）       每连接 fork 一个进程
  │ 优点：隔离性好、简单；缺点：创建切换贵、内存大、通信靠 IPC
  ▼
多线程（thread-per-conn）每连接一个线程，共享内存
  │ 优点：通信便宜、切换较快；缺点：内核调度开销、8MB 栈、锁竞争
  │（C10K 问题：一万并发线程已吃力）
  ▼
线程池 + 非阻塞 IO      复用少量线程处理海量连接（epoll 等）
  │ 优点：线程数可控；缺点：编程模型退回回调/状态机，复杂度高
  ▼
事件循环 + 协程         单线程内协作式调度，每连接一个协程
  │ 优点：百万级并发、同步写法；缺点：单核、阻塞调用致命
  ▼
M:N 运行时              内核线程池 + 用户态调度（goroutine / 虚拟线程）
  优点：多核并行 + 低成本切换 + 同步写法，当前工业界收敛答案
```

### 2. 线程与协程的成本对比表

| 维度 | 内核线程（pthread） | 用户态协程（asyncio 类） |
|------|--------------------|-------------------------|
| 创建成本 | 分配 8MB 栈 + 内核数据结构，约 10~100µs | 分配协程对象，约 100ns~1µs |
| 切换成本 | 1~10µs（陷入内核、调度裁决） | 几十 ns（保存寄存器、换栈） |
| 栈 | 默认 8MB（Linux，虚拟内存预留） | 按需增长，KB 级起步 |
| 调度器 | 内核抢占式，切换点不可控 | 用户态协作式，切换点显式（await/yield） |
| 并行性 | 天然多核 | 单线程内无并行，需多进程/多循环 |
| 同步原语 | 锁、条件变量（必须） | 单线程内共享无需锁 |
| 上限 | 万级（受栈地址空间与调度开销限制） | 百万级（受内存与事件循环吞吐限制） |
| 阻塞影响 | 仅阻塞自身 | 阻塞调用卡死整个循环 |

### 3. 面试追问

**追问 1：线程栈 8MB 是虚拟内存预留、物理页惰性分配，为什么还说它是瓶颈？**

因为瓶颈不只是物理内存。第一，**地址空间**：8MB × 一万线程 = 80GB 虚拟地址，在 32 位时代直接不可能，64 位下虽不紧张，但内核为每个线程维护的 task_struct、内核栈（通常 16KB）、调度队列节点都是真实分配；第二，**调度器复杂度**：可运行线程越多，调度器的开销与延迟越高，runqueue 遍历与负载均衡随线程数增长；第三，**实际使用中物理页确实会被摸到**：高并发下栈页交换、缺页中断同样消耗。协程栈独立于内核，按需增长、可小至几 KB，且不进入内核调度体系，才把上限推到百万级。地址空间、页表与惰性分配的底层细节可参考 [002-从OS底层到语言层的内存管理全景](../os/002-从OS底层到语言层的内存管理全景.md)。

**追问 2：协程优势这么大，为什么操作系统内核不直接提供协程？**

内核确实探索过类似方向（如 Scheduler Activations 学术模型），但有三个结构性障碍。其一，**信任模型不同**：内核不能信任用户程序，必须抢占式调度以防恶意或 bug 程序独占 CPU；协程的协作式前提与内核的安全职责冲突。其二，**语义复杂**：把"阻塞调用自动让出"做到内核级需要改造全部系统调用语义，工程量巨大且破坏兼容性。其三，**收益错位**：协程的价值主要在应用层 IO 编排，内核只关心"什么时候有数据"，这正是 epoll、io_uring 等异步接口的定位——内核提供异步原语，把调度编排留给用户态。Go、Java 选择的 M:N 路线（运行时 + 少量内核线程）就是这种分工的产物：内核保证抢占与公平，运行时保证低成本切换。

**追问 3：协程和回调（callback）是什么关系？为什么不直接用回调写异步？**

回调是异步编程的底层原语：发起 IO 时注册一个函数，IO 完成后调用。回调的问题有三：**回调地狱**——多层嵌套的异步依赖让代码从线性变成锯齿形；**栈丢失**——异常堆栈、局部变量上下文在回调边界断裂，调试困难；**控制流破碎**——循环、条件、异常处理都无法用语言原生结构表达，需要手工状态机。协程在实现上就是"语言帮你维护的状态机"：`async def` 编译成状态机对象，每个 `await` 是一个状态迁移点，`await` 之后的代码就是挂起时保存的**续延（continuation）**。换句话说，回调是"手动管理续延"，协程是"语言级续延"——同一套异步机制的两种编程界面，协程赢在让异步代码保持同步写法。

**追问 4：M:N 模型下，用户态任务阻塞了怎么办？它不是应该让出吗？**

这正是 M:N 与纯协程的关键差异（1:1、1:N、M:N 三种映射模型的总览见 [001-进程线程协程的理解](001-进程线程协程的理解.md) 追问 3）。纯协程（asyncio）里阻塞调用会卡死整个线程，必须全程非阻塞；M:N 运行时（Go、虚拟线程）检测到用户态任务阻塞在内核调用上时，会**把这个任务连同它的执行载体（goroutine 或虚拟线程载体）从内核线程上卸下**，让内核线程去跑别的任务，阻塞解除后再重新挂回——Go 运行时称之为"handoff"。代价是这次切换要经过内核（载体线程真的阻塞了），但换来的是：普通同步代码（哪怕是调用 C 库）无需改造就能享受高并发。这正是虚拟线程声称"百万线程"的同时保持同步编程模型的底气，也是它相对 asyncio 的核心竞争力。

**追问 5：为什么说协程体系里"无锁"？难道协程之间不共享数据吗？**

准确说法是"**单线程协程之间共享数据不需要锁，而不是没有竞争**"。锁要防的是"任意时刻被抢占导致交错"；协程的切换点只有显式的 `await`，两个 `await` 之间的一段代码是原子的——事件循环不可能在其中插入其他协程。所以纯内存操作天然安全。但有两个例外：其一，协程与线程池交互（`asyncio.to_thread`）时，跨线程共享的数据必须加锁；其二，"原子段"内做了 `await`，比如先检查再修改之间挂起了一次，恢复时状态可能已被别的协程改掉——这是协程版的 TOCTOU 问题，解法是检查与修改放在同一原子段内。

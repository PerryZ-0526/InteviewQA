<!-- interviewqa:section question -->
请解释什么是 IDL（Interface Definition Language）。它在分布式系统中解决了哪些问题，与序列化格式、传输协议和 RPC 框架有什么区别？
<!-- interviewqa:end -->

<!-- interviewqa:section answer -->
> IDL，也就是接口定义语言，是一种用<u style="text-decoration-color: #e63946">语言无关、机器可解析</u>的方式描述`跨进程接口契约`的声明式语言。它定义服务有哪些方法、请求和响应包含哪些字段、字段的类型与编号，以及错误、注解等约束；编译器再据此生成多语言的数据模型、客户端桩和服务端骨架。IDL 解决的是`异构系统`如何`共享同一份接口事实并安全演进`的问题，但它本身通常不负责网络连接、请求调度和业务逻辑。

IDL 的核心不是减少几行 DTO 代码，而是把原本散落在服务端实现、客户端实现和文档中的接口约定，提升为一份`可以被工具链消费的单一事实源`。例如 Java 服务向 Go 客户端提供查询用户接口时，双方不再分别手写 `User`、`GetUserRequest` 和方法签名，而是在 `.proto` 等 IDL 文件中定义一次。<u style="text-decoration-color: #e63946">不同语言的生成器会把统一的抽象类型映射成各自语言的类、结构体和调用接口</u>，从而降低字段名写错、类型不一致、文档过期和样板代码重复等问题。

一份典型 IDL 会描述数据类型、字段、枚举、服务、方法以及请求和响应之间的关系。更完整的 IDL 还可以表达流式调用、错误模型、鉴权标记、HTTP 路由、校验规则和弃用信息。IDL 只描述“接口是什么”，一般不描述“业务如何实现”：它可以声明 `GetUser` 接收 `GetUserRequest` 并返回 `GetUserResponse`，但不会实现数据库查询、缓存策略或权限判断。

在 Apache Thrift 中，这份契约通常保存在 `.thrift` 文件中，文件内可以定义 `struct`、`enum`、`exception` 和 `service`。Thrift 编译器读取文件后生成目标语言的数据类型、序列化代码、客户端代理和服务端接口。若项目使用 Blade 构建系统，则可以在 `BUILD` 文件中声明 `thrift_library`：Blade 负责追踪 IDL 与生成代码之间的依赖并调用 Thrift 编译器，随后继续编译和链接生成的 C++ 源码。严格来说，代码生成能力来自 Thrift 编译器，Blade 承担的是构建编排工作。

<span style="background-color: #ffe3e3">IDL 进入构建流程后，解析器先把文本转成抽象语法树或语义模型，再进行名称解析、类型检查和兼容性检查，最后由代码生成插件产生目标语言代码。</span>客户端生成物通常包含数据类型和 stub，<span style="background-color: #fff3cd">调用 stub 时看起来像调用本地方法</span>；<span style="background-color: #fff3cd">服务端生成物通常包含接口或基类，开发者需要补充真正的业务实现</span>。运行时框架负责把请求对象序列化、经网络发送、在服务端反序列化并分派到实现代码，因此 <u style="text-decoration-color: #e63946">IDL 是整个链路的契约输入，而不是完整运行时</u>。

IDL、序列化格式和 RPC 框架属于不同层次。IDL 描述`接口模型`；序列化格式规定对象如何编码成 JSON 文本或 Protobuf 二进制字节；传输协议规定这些字节如何在 HTTP/2、HTTP/1.1 或其他连接上传输；RPC 框架则进一步处理<u style="text-decoration-color: #e63946">连接、调用分派、超时、取消、状态码和流式通信</u>。Protobuf 容易造成概念混淆，是因为它既提供 `.proto` 描述语言，也定义二进制线格式和代码生成工具；gRPC 默认使用 Protobuf 作为 IDL 和消息格式，但 gRPC 本身还包含 RPC 运行时语义。

IDL 的另一项重要价值是`接口治理`。契约进入版本库后，可以在 CI 中执行<u style="text-decoration-color: #e63946">语法检查、风格检查、破坏性变更检测、代码生成和文档生成</u>。以 Protobuf 为例，线上客户端与服务端几乎不可能同时完成升级，所以字段编号一旦发布就不能随意复用；删除字段后应保留其编号和名称，新增字段也要让旧消费者可以忽略。IDL 可以让结构兼容性变得可自动检查，但仍不能保证业务语义兼容，例如把金额单位从“元”改成“分”而保持字段类型不变，工具通常无法发现这种破坏性变化。

常见的使用方式分为 `contract-first` 和 `code-first`。前者先评审并合并 IDL，再生成客户端和服务端代码，适合跨团队、跨语言以及需要严格兼容性治理的系统；后者先写服务端代码或注解，再反向生成接口描述，开发速度更快，也更贴近单体或同语言团队的工作方式，但必须防止生成产物与真实实现漂移。无论采用哪种方式，都应该明确唯一的权威来源，并让生成和兼容性检查进入自动化流水线。

因此，判断一个系统是否需要 IDL，关键不在于是否使用微服务，而在于<u style="text-decoration-color: #e63946">接口是否需要被多个独立演进的消费者稳定复用</u>。`跨语言 RPC`、`公共 SDK`、大规模内部服务和长期维护的 HTTP API 很适合使用 IDL；只在单进程内部调用、接口极少且没有代码生成或治理需求时，引入完整 IDL 工具链的收益可能低于维护成本。

## 一、IDL 在调用链中的位置

`IDL（Interface Definition Language）`是一种面向接口契约的声明式语言。

> 它先建立与具体编程语言无关的接口模型，再由工具把模型<u style="text-decoration-color: #e63946">投影</u>到 Java、Go、Python、TypeScript 等语言中。
```text
                          构建阶段
┌──────────────┐    ┌──────────────┐    ┌─────────────────────────┐
│ IDL 源文件   │ -> │ 解析与语义模型 │ -> │ 校验、兼容性检查、代码生成 │
│ service/type │    │ AST / Model  │    │ protoc / plugins        │
└──────────────┘    └──────────────┘    └────────────┬────────────┘
                                                     │
                      ┌──────────────────────────────┼──────────────────────┐
                      v                              v                      v
                客户端类型与 Stub              服务端接口或骨架          文档/Mock/测试
                      │                              │
                      └───────────┬──────────────────┘
                                  v
                          运行时调用与数据传输
                     序列化 -> 网络 -> 反序列化 -> 分派
```

IDL 的产物不一定只有代码。同一份语义模型还可以生成 API 文档、Mock Server、测试夹具、网关配置和 SDK，也可以输入静态检查器，验证命名规范、字段约束和版本兼容性。

> 这也是 IDL 比一份普通接口说明文档更有工程价值的原因：文档主要供人阅读，IDL 同时供人和机器执行。

## 二、以 Protobuf 和 gRPC 为例

下面的 `.proto` 文件同时定义了消息结构和 RPC 服务：
```proto
syntax = "proto3";

package user.v1;

service UserService {
  rpc GetUser(GetUserRequest) returns (GetUserResponse);
}

message GetUserRequest {
  int64 user_id = 1;
}

message GetUserResponse {
  User user = 1;
}

message User {
  int64 id = 1;
  string name = 2;
}
```

这里的 `message` 是数据契约，`service` 和 `rpc` 是服务契约，字段后的 `1`、`2` 是稳定的 **field number/tag**，不是展示顺序。Protobuf 的二进制线格式使用字段编号而不是字段名标识数据，因此编号属于线上协议的一部分。

`protoc` 解析这份模型后，可以通过不同语言插件生成代码。以 Java gRPC 工具链为例，生成结果大致包括消息类、序列化与反序列化逻辑、客户端 stub，以及供服务端实现的基类。生成器不会替开发者实现“到数据库查询用户”这类业务代码。

一次调用可以概括为：
```text
client.GetUser(request)
        |
        v
生成的 Stub -> Protobuf 编码 -> gRPC/HTTP/2 -> Protobuf 解码
                                              |
                                              v
                                      UserService 实现
```

这说明 `.proto`、Protobuf wire format 和 gRPC 不是同一个概念。`.proto` 提供接口描述，wire format 规定消息字节布局，gRPC 提供远程调用的生命周期和运行时能力。

## 三、Thrift 与 Blade 的实际使用

### 1. 三者的职责

在 Thrift 技术栈中，`.thrift` 是 IDL 文件的常用扩展名，Apache Thrift Compiler 是解析 IDL 并生成目标语言代码的工具，Blade 则是负责依赖分析、触发代码生成以及继续编译和链接的构建系统。

```text
user.thrift
    |
    v
Blade thrift_library
    |
    +-- 调用 thrift --gen cpp ... user.thrift
    |
    +-- 生成 user_types.*、UserService.* 等文件
    |
    +-- 编译生成的 .cpp 文件
    |
    v
C++ Thrift Library
    |
    +-- 被 user_server 依赖
    |
    +-- 被 user_client 依赖
```

公开版 `blade-build` 的 `thrift_library` 当前继承自 C++ 构建目标。它会调用 `thrift_config` 中配置的 Thrift 编译器，并按照 C++ 生成物继续构建；源码中仍保留着支持 Java 生成的 TODO。因此，下面示例以 C++ 为目标语言。企业内部定制版 Blade 是否支持其他语言，需要以对应版本的构建规则为准。

### 2. 项目目录

```text
user-service/
├── BUILD
├── user.thrift
├── user_server.cc
└── user_client.cc
```

### 3. 使用 `.thrift` 定义接口

`user.thrift`：

```thrift
namespace cpp interviewqa

struct User {
  1: required i64 id,
  2: optional string name,
}

exception UserNotFound {
  1: i64 user_id,
}

service UserService {
  User get_user(1: i64 user_id)
    throws (1: UserNotFound not_found),
}
```

这份文件定义了一个 `User` 数据结构、一个业务异常和一个 `UserService.get_user` 方法。字段前的 `1`、`2` 是进入 Thrift 协议的字段 ID，发布后不能随意改号或把旧编号复用于其他语义。`namespace cpp interviewqa` 指定生成的 C++ 类型位于 `interviewqa` 命名空间。

### 4. 使用 `BUILD` 声明生成与编译关系

`BUILD`：

```python
thrift_library(
    name = 'user_thrift',
    srcs = ['user.thrift'],
)

cc_binary(
    name = 'user_server',
    srcs = ['user_server.cc'],
    deps = [':user_thrift'],
)

cc_binary(
    name = 'user_client',
    srcs = ['user_client.cc'],
    deps = [':user_thrift'],
)
```

`thrift_library` 声明 `user.thrift` 是代码生成输入。公开版 Blade 会根据该文件识别其中的结构和服务，预期生成 `user_types.h/.cpp`、`user_constants.h/.cpp` 和 `UserService.h/.cpp`，再将生成的 C++ 源码编译成可供其他目标依赖的库。两个 `cc_binary` 通过 `deps = [':user_thrift']` 获得生成类型、服务接口以及对应的链接依赖。

Blade 默认查找名为 `thrift` 的编译器，实际项目还需要通过 `thrift_library_config` 或项目级配置提供 Thrift 头文件、运行库和必要的生成参数。也就是说，只有写 `thrift_library` 还不够，构建环境中必须存在兼容版本的 Thrift Compiler 与 C++ Runtime。

### 5. 实现服务端 Handler

`user_server.cc`：

```cpp
#include <cstdint>
#include <memory>

#include <thrift/protocol/TBinaryProtocol.h>
#include <thrift/server/TSimpleServer.h>
#include <thrift/transport/TServerSocket.h>
#include <thrift/transport/TTransportUtils.h>

#include "UserService.h"

using apache::thrift::protocol::TBinaryProtocolFactory;
using apache::thrift::server::TSimpleServer;
using apache::thrift::transport::TBufferedTransportFactory;
using apache::thrift::transport::TServerSocket;
using interviewqa::User;
using interviewqa::UserNotFound;
using interviewqa::UserServiceIf;
using interviewqa::UserServiceProcessor;

class UserServiceHandler final : public UserServiceIf {
 public:
  void get_user(User& result, const int64_t user_id) override {
    if (user_id != 42) {
      UserNotFound error;
      error.user_id = user_id;
      throw error;
    }

    result.id = user_id;
    result.name = "Perry";
  }
};

int main() {
  auto handler = std::make_shared<UserServiceHandler>();
  auto processor = std::make_shared<UserServiceProcessor>(handler);
  auto server_transport = std::make_shared<TServerSocket>(9090);
  auto transport_factory = std::make_shared<TBufferedTransportFactory>();
  auto protocol_factory = std::make_shared<TBinaryProtocolFactory>();

  TSimpleServer server(
      processor, server_transport, transport_factory, protocol_factory);
  server.serve();
}
```

`UserServiceIf` 和 `UserServiceProcessor` 都来自 `user.thrift` 的生成代码。开发者只实现 `get_user` 的业务逻辑；请求读取、响应写入、方法分派和 Thrift Binary Protocol 编解码由生成代码与运行时完成。

### 6. 使用生成的客户端

`user_client.cc`：

```cpp
#include <iostream>
#include <memory>

#include <thrift/protocol/TBinaryProtocol.h>
#include <thrift/transport/TSocket.h>
#include <thrift/transport/TTransportUtils.h>

#include "UserService.h"

using apache::thrift::protocol::TBinaryProtocol;
using apache::thrift::transport::TBufferedTransport;
using apache::thrift::transport::TSocket;
using interviewqa::User;
using interviewqa::UserServiceClient;

int main() {
  auto socket = std::make_shared<TSocket>("127.0.0.1", 9090);
  auto transport = std::make_shared<TBufferedTransport>(socket);
  auto protocol = std::make_shared<TBinaryProtocol>(transport);
  UserServiceClient client(protocol);

  transport->open();

  User user;
  client.get_user(user, 42);
  std::cout << user.id << ": " << user.name << '\n';

  transport->close();
}
```

客户端没有手写消息编码或 RPC 报文，只需构造生成的 `UserServiceClient` 并调用 `get_user`。对于返回 `struct` 的方法，Apache Thrift 的 C++ 生成代码使用引用参数承接返回对象，因此示例写成 `client.get_user(user, 42)`。

### 7. 构建与调用链

```bash
blade build :user_server :user_client
```

构建期间，Blade 发现两个二进制目标依赖 `:user_thrift`，先执行 `.thrift` 到 C++ 的代码生成，再编译生成代码和手写代码，最后完成链接。启动服务端后，客户端调用链为：

```text
client.get_user(user, 42)
        |
        v
UserServiceClient
        |
        v
TBinaryProtocol 序列化
        |
        v
TSocket / TBufferedTransport
        |
        v
UserServiceProcessor
        |
        v
UserServiceHandler::get_user
```

因此，“Blade 能否使用 IDL 生成代码”的准确回答是：**可以，但 Blade 是代码生成的构建入口和编排者，实际解析 `.thrift` 并产出源代码的是 Thrift 编译器；Blade 再负责把生成代码纳入正常的依赖、编译和链接流程。**

## 四、几个容易混淆的概念


| 概念         | 主要回答的问题            | 典型例子                                     | 是否负责实际网络调用      |
| ---------- | ------------------ | ---------------------------------------- | --------------- |
| IDL / 接口描述 | 服务暴露什么能力，输入输出是什么   | Protobuf IDL、Thrift IDL、Smithy、OpenAPI   | 否               |
| 数据 Schema  | 一份数据具有什么结构与约束      | JSON Schema、Avro Schema、Protobuf message | 否               |
| 序列化格式      | 对象如何编码为可传输或存储的字节   | JSON、Protobuf binary、CBOR                | 否               |
| 传输协议       | 字节如何在两端之间传递        | HTTP/1.1、HTTP/2、QUIC                     | 是，但不负责完整 RPC 语义 |
| RPC 框架     | 如何完成远程调用、分派和生命周期管理 | gRPC、Apache Thrift Runtime               | 是               |


这些集合存在交叉，而不是严格互斥。Protobuf 同时覆盖 IDL、数据 Schema、二进制编码和代码生成；OpenAPI 是面向 HTTP API 的语言无关接口描述规范，除数据模型外还描述路径、HTTP 方法、参数、响应和安全方案；Smithy 则刻意把抽象服务模型与具体线上协议分开，同一个模型可以映射到不同协议。

JSON 本身不是 IDL，因为它只是一种数据表示格式，不说明有哪些服务方法、字段是否必需或请求应该发到哪里。JSON Schema 可以补充数据结构与约束，但单独使用时通常仍不等于完整的服务接口描述。OpenAPI 把 JSON Schema 风格的数据模型放进 HTTP 操作模型中，因此能描述一套较完整的 HTTP API。HTTP 方法语义可继续参考 [GET 和 POST 的区别](002-GET-%E5%92%8C-POST-%E7%9A%84%E5%8C%BA%E5%88%AB.md)。

## 五、IDL 具体解决什么问题


| 问题      | 没有统一 IDL 时             | 引入 IDL 后            |
| ------- | ---------------------- | ------------------- |
| 跨语言类型映射 | 各团队手写 DTO，类型和空值语义容易不一致 | 由生成器按统一模型映射目标语言类型   |
| 客户端调用   | 手写 URL、方法名、编码和错误处理胶水   | 生成类型安全的 client/stub |
| 服务端接入   | 手写解析、校验和路由分派           | 生成接口或骨架，由框架完成基础分派   |
| 文档同步    | 文档与实现分别维护，容易过期         | 从同一契约生成文档           |
| 接口演进    | 依靠人工评审发现破坏性变更          | CI 比较新旧模型并执行兼容性检查   |
| 多团队协作   | 口头约定字段含义与发布时间          | 契约可评审、可版本化、可发布      |


IDL 并不会自动解决所有分布式系统问题。它不能替代超时、重试、幂等、限流、认证、可观测性和服务发现，也不能证明服务端实现符合业务语义。它解决的是**接口结构可表达、可生成、可验证、可演进**，而不是网络调用的全部可靠性问题。

## 六、接口演进为什么是 IDL 的核心价值

分布式系统中的生产者和消费者会出现**版本偏差**：新服务端可能面对旧客户端，新客户端也可能在服务端回滚后调用旧实现。因此接口兼容性不能建立在“大家同时发布”的假设上。

以 Protobuf 二进制格式为例，消息由字段编号、wire type 和载荷组成。旧解析器遇到不认识的新字段时，可以根据 wire type 跳过它，这为新增字段提供了基础。但是“二进制能够解析”只代表 wire-compatible，不代表业务一定兼容。


| 变更          | 一般结论     | 原因或处理方式                    |
| ----------- | -------- | -------------------------- |
| 新增可选语义的字段   | 通常兼容     | 旧消费者可忽略，新消费者必须接受字段缺失       |
| 删除字段        | 需谨慎处理    | 删除后用 `reserved` 保留编号和名称    |
| 复用已发布的字段编号  | 不兼容      | 旧数据或旧程序会把新字段误认成旧字段         |
| 修改字段编号      | 不兼容      | 线上编码身份发生变化                 |
| 修改字段类型      | 通常不安全    | 即使少数类型在线格式上兼容，也可能改变取值语义    |
| 只修改字段名      | 二进制可能兼容  | 生成代码 API、JSON 映射或文本格式可能被破坏 |
| 改变金额单位但不改类型 | 结构检查无法发现 | 属于语义破坏，需要版本设计和业务评审         |


稳妥的删除方式如下：
```proto
message User {
  reserved 3;
  reserved "nickname";

  int64 id = 1;
  string name = 2;
}
```

兼容性应至少分为 wire compatibility、source compatibility 和 semantic compatibility 三层。IDL 工具最擅长检查前两层中的结构变化；第三层需要清晰命名、注释、版本策略、契约测试和人工评审共同保证。

## 七、Contract-first 与 Code-first


| 模式             | 权威来源     | 优势                | 主要风险                         |
| -------------- | -------- | ----------------- | ---------------------------- |
| Contract-first | IDL 文件   | 先稳定边界，适合跨团队和跨语言协作 | 需要维护生成流程，开发者要理解契约演进规则        |
| Code-first     | 服务端代码或注解 | 上手快，与实现代码距离近      | 容易以单一语言模型绑架公共契约，生成结果可能发生意外变化 |


Contract-first 的典型流水线是“修改 IDL → lint → 与基线做兼容性检查 → 评审 → 生成代码 → 发布版本 → 服务实现”。生成代码应由构建系统稳定地产生，通常不应让各客户端手工复制并修改。

Code-first 并不天然错误。对于单团队维护、以 HTTP/JSON 为主且服务端框架能够稳定导出 OpenAPI 的系统，它可以降低起步成本。关键仍然是明确哪一份内容是唯一事实源，并在 CI 中验证导出的契约没有出现未经评审的破坏性变化。

## 八、常见面试追问

### 1. Protobuf 和 IDL 是什么关系？

Protobuf 是一套具体技术，不是 IDL 这个抽象概念的同义词。它提供 `.proto` 接口描述语言、编译器、生成代码运行库以及二进制线格式。`.proto` 中的 `message` 可以只用于结构化数据序列化，也可以通过 `service` 和 `rpc` 描述服务接口。

### 2. 使用了 IDL，客户端和服务端就一定兼容吗？

不一定。IDL 和兼容性检查可以发现字段删除、编号复用、类型变化等结构问题，却很难发现单位变化、枚举语义变化、默认行为变化和错误码含义变化。生产系统还需要版本偏差测试、契约测试、灰度发布以及明确的废弃周期。

### 3. 为什么不能删除 Protobuf 字段后复用它的编号？

字段编号是二进制线格式中的身份标识。历史日志、缓存、消息队列和尚未升级的程序仍可能包含旧编号；如果将同一编号赋给新含义，解析器可能把旧数据解释成新字段。正确做法是删除字段后将编号和名称标记为 `reserved`。

### 4. IDL 能否替代 API 文档？

IDL 可以成为生成参考文档的权威输入，但不能完全替代面向人的说明。字段类型无法充分表达业务背景、调用前置条件、幂等策略、限流规则、示例场景和故障处理方式。理想状态是结构信息从 IDL 自动生成，业务语义在契约附近维护并参与评审。

### 5. OpenAPI 算不算 IDL？

广义上算。OpenAPI 官方将其定义为面向 HTTP API、与编程语言无关的接口描述，它能够描述路径、操作、参数、请求体、响应和安全方案，并可用于生成文档、客户端和服务端代码。与 Protobuf IDL 相比，OpenAPI 更贴近 HTTP 资源与报文模型，而 Protobuf 加 gRPC 更贴近强类型 RPC 方法与消息模型。

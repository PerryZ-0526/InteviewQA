## 面试直接答

> HTTPS 本质上是 HTTP + TLS。TLS 握手主要完成三件事：`协商加密算法`、`验证服务器身份`、通过非对称加密或密钥交换`生成会话密钥`；之后真正的 HTTP 数据使用`对称加密传输`，兼顾安全性和性能。

### 一、HTTPS 的整体加密思路

HTTPS 并不是直接使用 RSA 之类的非对称加密来加密所有 HTTP 数据，而是采用“非对称加密 + 对称加密 + 数字证书”的组合方案。

原因是<u style="text-decoration-color: rgb(230, 57, 70)">非对称加密安全但计算开销较大，对称加密速度快，适合大量数据传输</u>。所以 TLS 握手阶段主要负责`身份认证`和`密钥协商`，双方得到相同的会话密钥后，后续 HTTP 请求和响应就使用 AES、ChaCha20 等对称算法进行加密。

> HTTPS 中非对称密码学主要用于`身份认证`和`密钥协商`，对称加密用于真正的数据传输；证书则负责把服务器身份和服务器公钥绑定起来。TLS 握手阶段比较“贵”，建立连接之后就切换成高性能对称加密，这就是三者组合的核心逻辑。

### 二、TLS 握手的大致过程

> TLS 全称是 **Transport Layer Security**，中文通常译为 **传输层安全协议**。

客户端访问 `https://` 网站时，首先向服务器发送 Client Hello，其中包含客户端支持的 TLS 版本、加密套件、随机数等信息，比如支持哪些密钥交换算法和对称加密算法。

服务器收到后会返回 Server Hello，从客户端提供的能力中选择 TLS 版本和加密套件，同时返回服务器随机数，并把自己的数字证书发送给客户端。证书中包含服务器域名、公钥、证书有效期以及 CA 的数字签名等信息。

<u style="text-decoration-color: rgb(230, 57, 70)">客户端拿到证书后，会验证证书是否可信</u>。例如检查证书是否过期、域名是否匹配、证书签名能否通过可信 CA 的公钥验证，以及证书链是否最终能够连接到操作系统或浏览器信任的根 CA。<u style="text-decoration-color: rgb(230, 57, 70)">这个过程解决的是“我现在连接的服务器是不是真正的目标服务器”，从而防止中间人伪装服务器。</u>

### 三、会话密钥如何生成

身份验证完成之后，客户端和服务器需要<span style="background-color: rgb(255, 243, 205)">协商一个共同的会话密钥</span>。

早期 TLS 中比较典型的是 RSA 密钥交换，客户端生成一个随机数，使用服务器证书中的 RSA 公钥加密后发给服务器，服务器通过自己的私钥解密，<span style="background-color: rgb(255, 243, 205)">然后双方根据这些随机数生成会话密钥</span>。

现在更常见的是 ECDHE，也就是临时椭圆曲线 Diffie-Hellman。<u style="text-decoration-color: rgb(230, 57, 70)">客户端和服务器分别生成</u>`临时公私钥`<u style="text-decoration-color: rgb(230, 57, 70)">，并交换公钥，然后双方通过自己的私钥和对方的公钥计算出相同的</u>`共享秘密`<u style="text-decoration-color: rgb(230, 57, 70)">，再进一步派生出会话密钥</u>。

ECDHE 的一个重要优势是支持`前向保密`，即使服务器未来的私钥泄露，攻击者通常也无法解密以前抓到的 HTTPS 流量。

> 所谓“前向保密”，关键在于 **ECDHE 用来计算会话密钥的是每次连接临时生成的密钥对，而不是服务器证书里的长期私钥**：
>
> 比如攻击者今天把你和服务器之间的 HTTPS 流量全部抓包保存下来，但他当时不知道客户端和服务器各自的 ECDHE 临时私钥，所以算不出这次连接的会话密钥；连接结束后，这些临时私钥通常也会被销毁。哪怕过了一年，服务器证书对应的长期私钥泄露了，攻击者虽然获得了服务器的“身份私钥”，但仍然拿不到当年那次连接已经销毁的 ECDHE 临时私钥，因此无法重新计算当年的会话密钥，也就<u style="text-decoration-color: rgb(230, 57, 70)">无法解密之前保存的历史流量</u>，这就是“前向保密”。
>
> 相反，如果是早期 RSA 密钥交换，客户端会把会话密钥相关材料直接用服务器长期 RSA 公钥加密发送，攻击者只要先抓包、以后再拿到服务器 RSA 私钥，就可能回头解密过去的流量，所以它不具备这种能力。

### 四、握手完成后的数据传输

> 双方生成相同的会话密钥以后，会互相发送 `Finished 消息`，<u style="text-decoration-color: rgb(230, 57, 70)">确认前面的握手过程没有被篡改</u>。握手成功之后，TLS 安全连接就建立完成。

之后客户端发送的 HTTP 请求，例如 URL、请求头、Cookie、请求体等，<u style="text-decoration-color: rgb(230, 57, 70)">会经过 TLS 使用会话密钥进行对称加密</u>；服务器返回的 HTTP 响应同样如此。因此网络上的攻击者即使抓到了数据包，一般也只能看到加密后的密文。

> 如果面试官继续追问 TLS 1.3，可以补充：TLS 1.3 对握手进行了简化，删除了 RSA 静态密钥交换等旧算法，主要使用 ECDHE，正常情况下只需要 1-RTT 就可以完成握手，还支持会话恢复时的 0-RTT，因此安全性和性能都比 TLS 1.2 更好。
>
> TLS 1.3 之所以从 TLS 1.2 常见的 2-RTT 降到 1-RTT，核心是把密钥交换需要的信息提前放进第一次 Client Hello 中，减少了一轮“服务器先返回参数、客户端再进行密钥交换”的交互。


## HTTPS 组合加密思路中的非对称加密部分


> 非对称加密主要用在 <u style="text-decoration-color: #e63946">TLS 握手阶段</u>，而不是用来加密后续 HTTP 数据。它主要承担两件事：证明服务器身份，以及安全地协商出双方共同的对称密钥。

### 第一层：为什么要“组合”

可以把 HTTPS 理解成一个分工明确的组合：数字证书解决“你是谁”，非对称密码学解决“怎么安全建立密钥、怎么证明身份”，对称加密解决“后续大量数据怎么高效加密”。

因为非对称加密，比如 RSA、ECC，<u style="text-decoration-color: #e63946">计算比较慢，不适合把整个网页内容都加密一遍</u>；而 AES 这类对称加密非常快，但<span style="background-color: #fff3cd">问题是客户端和服务器一开始并没有共同的密钥</span>。

> 所以 TLS 握手最核心的目标之一，就是<u style="text-decoration-color: #e63946">安全地产生一个只有客户端和服务器知道的</u>`对称会话密钥`。

### 第二层：非对称加密到底用在哪里

如果看早期 TLS 的 RSA 握手，非对称加密非常直观。

服务器先把证书发给客户端，证书里面有服务器的 RSA 公钥。客户端验证证书后，生成一个叫 Pre-Master Secret 的随机数，然后：`客户端：随机数 → 用服务器公钥加密 → 发给服务器`

服务器收到后：`服务器：密文 → 用服务器私钥解密 → 得到随机数`

攻击者即使抓到这个包，因为没有服务器私钥，也解不开。随后客户端和服务器根据这个随机数等信息计算出相同的对称会话密钥。

所以在这种模式下，可以直接说：**服务器公钥用于加密密钥材料，服务器私钥用于解密密钥材料。**

### 第三层：现在的 HTTPS 其实不太一样

现在 TLS 1.2/1.3 更常见的是 ECDHE，而不是直接用 RSA 加密会话密钥。

> ECDHE 中文全称是**椭圆曲线临时迪菲-赫尔曼密钥交换**（Ephemeral Elliptic Curve Diffie-Hellman），一句话来说：**客户端和服务器通过交换**`临时公钥`**，在不直接传输密钥的情况下<u style="text-decoration-color: #e63946">计算出相同的共享密钥</u>，并具备前向保密能力。**

客户端和服务器分别生成<u style="text-decoration-color: #e63946">一对临时密钥</u>：

`客户端：Client Private Key + Client Public Key`

`服务器：Server Private Key + Server Public Key`

双方交换公钥，但私钥永远不发送。客户端通过：`客户端私钥 + 服务器公钥`计算出一个 Shared Secret；

服务器通过：`服务器私钥 + 客户端公钥`也能算出完全一样的 Shared Secret。

攻击者虽然能看到两个公钥，但由于椭圆曲线离散对数问题，<u style="text-decoration-color: #e63946">无法轻易推导出这个共享秘密</u>。

然后<span style="background-color: #fff3cd">双方再从 Shared Secret 中派生出真正用于 AES 或 ChaCha20 的对称密钥</span>。

这里严格来说并不是“公钥把对称密钥加密后传过去”，而是**利用非对称密码学完成密钥交换**。

### 第四层：证书里也用到了非对称密码学

还有一个非常重要的地方是身份认证。

服务器证书中包含服务器公钥，同时 CA 会用自己的私钥对证书进行数字签名。浏览器使用 CA 的公钥验证签名，从而确认：
```
这个公钥确实属于 www.xxx.com，而不是黑客伪造的。
```

在现代 TLS 中，服务器还会使用自己证书对应的私钥，对握手中的部分数据进行`数字签名`。客户端使用服务器公钥验证签名，以证明服务器确实拥有对应的私钥。

---

**HTTPS 中非对称密码学主要用于身份认证和密钥协商，对称加密用于真正的数据传输；证书则负责把服务器身份和服务器公钥绑定起来。**

也就是说，TLS 握手阶段比较“贵”，建立连接之后就切换成 AES、ChaCha20 这种高性能对称加密，这就是三者组合的核心逻辑。

## TLS 握手 RTT


> RTT 是“往返时延”，表示<u style="text-decoration-color: #e63946">一条消息从客户端到服务器再返回客户端所需的时间</u>。TLS 1.3 能做到 1-RTT，是因为客户端第一次发消息时就把密钥协商所需的信息一起带上了。

RTT 的英文是 **Round Trip Time，往返时间/往返时延**。比如客户端发送一个请求给服务器需要 50ms，服务器的响应再传回来需要 50ms，那么可以粗略认为 RTT 是 100ms。这里关注的不是服务器处理业务用了多久，而主要是网络上一来一回的耗时。所谓 TLS 握手需要几个 RTT，本质上就是<span style="background-color: #fff3cd">在真正发送加密的 HTTP 数据之前，客户端和服务器必须来回通信几轮</span>。

TLS 1.2 为什么通常需要 **2-RTT**，可以简单理解为它很多关键信息是“看到对方上一条消息以后，才能决定下一条消息发什么”。第一轮，客户端发送 Client Hello，服务器返回 Server Hello、证书以及密钥交换相关信息，这就消耗了 1 个 RTT。客户端此时才能验证服务器，并根据服务器给出的参数生成自己的密钥交换信息，然后再发送 Client Key Exchange、Finished 等消息，服务器再返回 Finished，又需要一次往返，所以握手大约需要 2-RTT。之后客户端才能比较放心地发送真正的 HTTP 请求。

TLS 1.3 的关键优化是：**客户端在第一次 Client Hello 中，就提前把 ECDHE 密钥协商需要的客户端临时公钥发过去了**，这个字段通常叫 Key Share。服务器收到 Client Hello 后，不需要再问客户端“你的密钥交换公钥是什么”，它可以直接使用客户端的 Key Share，再结合自己生成的临时密钥计算共享密钥，然后一次性返回 Server Hello、自己的 Key Share、证书、签名、Finished 等消息。

所以过程变成了：

`客户端 → Client Hello + 客户端ECDHE公钥`

`服务器 → Server Hello + 服务器ECDHE公钥 + 证书 + Finished`

到客户端收到服务器这次响应时，双方实际上已经可以计算出相同的密钥，因此只经历了**一次完整的网络往返，也就是 1-RTT**。客户端随后就可以发送加密的 HTTP 请求。

面试中可以这么概括：**TLS 1.3 之所以从 TLS 1.2 常见的 2-RTT 降到 1-RTT，核心是把密钥交换需要的信息提前放进第一次 Client Hello 中，减少了一轮“服务器先返回参数、客户端再进行密钥交换”的交互。**

至于 **0-RTT**，它主要用于以前已经连接过该服务器的会话恢复场景。客户端可以利用上一次连接保存的密钥材料，在第一次 Client Hello 发出去时就顺便发送加密的 HTTP 数据，因此理论上不需要等待服务器响应就开始传业务数据。不过 0-RTT 存在重放攻击风险，所以并不是所有请求都适合使用。

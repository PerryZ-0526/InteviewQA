# 确定性 workflow 在 agent 时代还剩下什么位置

## 题目

agentic workflow 收敛为 agent loop 之后，确定性 workflow 在 agent 时代还剩下什么位置？

## 面试直接答

> 任务级 workflow 式微之后，确定性编排的位置在基础设施层：评测管线、审批与合规链、数据流水线、框架内把关链——它们的共同特征是逻辑必须可审计、可重放、可证伪，不能交给模型的运行时判断；判断标准从「任务流程图能否提前画出」变为「这层逻辑是否承担不可谈判的确定性责任」。

先给结论定调：死掉的是「任务编排」这个位置，不是「确定性」这个属性。2024 年的 workflow 试图让确定性代码同时承担两件事——决定任务怎么走、保证执行守规矩；前者被更强的模型夺走，后者恰恰是模型最不该碰的部分。所以 agent 时代剩下的不是 workflow 的残骸，而是它本来就更胜任的那一半。

第一个存活位置是评测管线。生成与评判必须分离：如果让完成任务的那个模型自己评自己，就是自利偏差加评测污染；评测协议必须固定，同一批任务每次跑同样的条件，否则结果不可比；轨迹要可重放，复现一次失败需要逐事件回放。这些要求叠加起来，eval harness 天然是 workflow——固定的任务集、固定的评判器、固定的通过门槛，Hermes 自进化项目里的约束门（大小限制、语义保持、缓存兼容）就是典型：这些门不可被平均分抵消，必须是硬编码的确定性检查。dsh 的会话日志支持回放，也是因为「模型可见即已记录」这条确定性不变量在兜底。

第二个存活位置是审批与合规链。权限把关、人工审批、审计留痕必须无条件发生——Claude Code 的 hooks 在 PreToolUse 时同步拦截，不依赖模型「记得先问」；dsh 的 tools/pre-execute 到 post-execute 是 waterfall 流水线，策略监听器可以短路拒绝；LangGraph 的 interrupt() 让流程在工具调用边界停住，等人工批准后从断点恢复。这些机制的共同点是：它们是框架保证的确定性路径，模型无法绕过。任何把合规检查做成「模型可选的工具调用」的设计，都是在把审计责任交给概率。

第三个存活位置是数据流水线。ETL、文档解析、索引构建、批量标注这类任务的分支可枚举，LLM 只是管道里的变换算子。RAG 的预处理链路——切分、清洗、嵌入、入库——每一步的输入输出契约明确，失败可重试，吞吐可预算。这类任务用 agent loop 反而有害：模型会「思考」每一步是否值得做，产生不可预测的 token 成本和延迟，而流水线要的是确定性的成本模型和可预测的批处理行为。

第四个存活位置是框架内把关链。重试策略、超时、降级、回滚这些执行保障必须是确定性代码，因为它们守护的正是模型的不确定性。当代每个 agent 框架都是这个结构：loop 在内、workflow 在外——dsh 的插件树用类型化事件做确定性调度，Claude Code 的 harness 用 checkpoints 与权限规则约束模型行为，LangGraph 用超步执行与状态持久化保证可恢复。模型自由决策的范围越大，外面那层确定性骨架就越重要。

判断标准也随之更新。旧标准问「任务流程图能否提前画出」；新标准问三个问题：这层逻辑是否需要审计重放？分支是否可枚举？失败是否可容忍？三问全否则用 workflow，任一为是则考虑 agent。工程实践里两者几乎总是混合：外层确定性 workflow 管合规与预算，内层 agent 节点做开放任务，这正是「workflow vs agent」旧二分被「任务层 vs 基础设施层」新二分取代的含义。总结来说，agent 时代的 workflow 不是退场而是换岗：从「替模型做任务决策」换成「为模型的决策兜底」，位置从产品层下沉到框架层，这个判断能同时说清两个方向上的错误——既不能拿 workflow 回潮论去逆历史，也不能因为 loop 主流就删掉权限、审批、评测这些确定性路径。

## 详细解析

> 公开信息核验日期：2026-08-16。框架机制描述基于各项目官方文档（dsh 架构文档、Claude Code hooks 文档、LangGraph 文档）。

### 一、存活位置总览


| 位置     | 确定性责任        | 为什么不能交给模型              | 典型实现                                       |
| ------ | ------------ | ---------------------- | ------------------------------------------ |
| 评测管线   | 协议固定、可复现、可重放 | 自利偏差、评测污染              | eval harness、约束门（Hermes 自进化）               |
| 审批与合规链 | 无条件发生、可审计    | 「记得先问」是概率不是保证          | CC hooks、dsh tools 流水线、LangGraph interrupt |
| 数据流水线  | 契约明确、成本可预算   | loop 引入不可预测的 token 与延迟 | RAG 预处理、ETL、批量标注                           |
| 框架内把关链 | 重试/超时/回滚确定性  | 守护的正是模型的不确定性           | checkpoint、权限规则、超步执行                       |


### 二、结构对比：任务层与基础设施层
```text
2024 任务层 workflow（已式微）：
  输入 → [步骤A] → [步骤B] → [步骤C] → 输出
         （每个步骤都是 LLM 调用，工程师画拓扑）

2026 基础设施层 workflow（存活）：
  ┌────────────────────────────────────┐
  │  确定性骨架：权限裁决 / 审批断点 /   │
  │  重试超时 / checkpoint / 审计日志   │
  │  ┌──────────────────────────────┐ │
  │  │   agent loop（模型自由决策）   │ │
  │  │   思考 → 工具 → 观察 → 循环    │ │
  │  └──────────────────────────────┘ │
  └────────────────────────────────────┘
```

### 三、LangGraph interrupt 的审批链示例（1.0 语义）
```python
from langgraph.types import interrupt, Command

def approval_node(state):
    # 在工具调用边界暂停，返回人工审批请求；批准后从断点恢复
    decision = interrupt({"action": "approve_deploy", "context": state["plan"]})
    if decision.get("approved"):
        return {"stage": "deploy"}
    return {"stage": "aborted"}

# 恢复：graph.invoke(Command(resume={"approved": True}), config)
```

审批是确定性路径的典型：interrupt 由框架强制，模型没有「跳过审批」的选项；恢复语义从 checkpoint 精确续跑，不重放已执行部分。

### 四、面试追问

**追问一：审批链为什么不能用「让模型记得先问」代替？**

两个层面的错误。语义层面：模型调用审批工具是「可选择的行为」，模型可能因为上下文压缩丢失、提示词冲突或推理失误而不调用；hooks、interrupt 这类机制是「无条件发生的路径」，框架保证其执行。审计层面：合规要求的是可证明性——「每一次高风险操作都经过了审批」必须由代码路径保证，而不是由模型行为事后推断。安全性不能建立在概率上，这条原则在 Claude Code 的权限设计与 dsh 的流水线设计里是同一逻辑：模型建议与真实执行分离，确定性代码裁决。

**追问二：评测管线为什么必须 workflow 化，agent 化评测有什么问题？**

评测的价值在可比性：同一任务集、同一评判器、同一门槛，才能说 A 改动比 B 改动好。agent 化评测引入三重污染：生成与评判同模型的**自利偏差**；评判器行为随上下文漂移导致**协议不固定**；路径多样性让**结果不可复现**。所以即使被测对象是 agent，评测外部仍是 workflow——固定采样、固定 judge、固定指标、多次运行报均值与方差。Hermes 自进化项目把约束门做成独立于奖励的硬门槛，dsh 用事件日志支持轨迹回放，都是同一原则的体现。

**追问三：数据流水线里 LLM 只是变换算子，为什么还要编排框架而不是手写脚本？**

单机小批量手写脚本没问题；规模上来后，编排框架提供的是确定性工程能力：批处理断点续跑（一万条记录从第 5321 条恢复）、重试与幂等（部分失败不重复不遗漏）、观测与成本归因（每个节点的 token 与延迟可见）、与人工审核点的衔接。这些正是 LangGraph 这类框架 checkpoint 机制的用武之地——它解决的不是「怎么调用 LLM」，而是「长流程怎么可靠地跑到头」。是否上框架的判断标准是流程长度与失败代价，不是「有没有 LLM」。

**追问四：「三问」判断标准在真实项目里怎么落地？**

先回答三问：逻辑是否需要审计重放（合规、评测——是）；分支是否可枚举（数据清洗——是；故障排查——否）；失败是否可容忍（推荐重排——是；资金操作——否）。然后按答案分层：三否的环节做确定性 workflow，任一为是的环节做 agent，最后组合成混合架构——外层 workflow 管预算与审批，内层 agent 节点做开放任务，层与层之间用显式接口衔接。关键纪律是定期复查：模型能力变化后，原本必须 workflow 的环节可能不再需要，反过来 agent 自由度的扩大也可能要求新增确定性闸门。判断标准是活的，不是一次定终身。

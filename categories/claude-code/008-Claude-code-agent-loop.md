> Claude Code 在交互会话中执行一次典型开发任务的完整链路

# 一、整体流程

一次任务可以抽象为：⭐

> *启动或恢复会话*
> ↓
> *加载配置、权限、项目规则和扩展*
> *↓*
> *接收用户输入*
> *↓*
> *执行输入扩展和 UserPromptSubmit Hook*
> *↓*
> *组装本轮完整上下文*
> *↓*
> *调用 Claude 模型并流式接收结果*
> *↓*
> *模型输出：*
> *├─ 文本回答*
> *├─ 扩展思考*
> *├─ 工具调用*
> *├─ 子智能体委派*
> *└─ 用户询问*
> *↓*
> *若调用工具：*
> *参数校验*
> *→ Hook*
> *→ 权限判断*
> *→ 用户确认*
> *→ 沙箱执行*
> *→ 结果处理*
> *→ 写回上下文*
> *↓*
> *再次调用模型*
> *↓*
> *搜索、读取、修改、测试、纠错循环*
> *↓*
> *模型判断任务完成*
> *↓*
> *执行 Stop Hook*
> *├─ 不通过：把反馈写回上下文，继续循环*
> *└─ 通过：输出最终结果*
> *↓*
> *保存会话、检查点和可能的长期记忆*

真正循环的是：`模型决策 → 工具执行 → 观察结果 → 模型重新决策`

而不是传统程序中的：预先生成完整计划 → 严格按计划逐步执行

Claude Code 官方将其描述为智能体循环：每次工具结果都会成为下一步决策的新信息。

# 二、第一阶段：Claude Code 进程启动

> 如果用户已经位于一个运行中的 Claude Code 会话，这一阶段不会为每条消息重新完整执行；如果是新启动、恢复会话或切换工作目录，则需要执行。

## 1. 解析`启动参数`

- 例如：
  > *claude*
  > *claude "修复登录问题"*
  > *claude --resume*
  > *claude --continue*
  > *claude --permission-mode plan*
  > *claude --model opus*
- Claude Code 首先确定：
  > *是交互模式还是一次性打印模式；*
  > *新建会话还是恢复会话；*
  > *使用哪个模型；*
  > *使用哪个服务提供方；*
  > *当前权限模式；*
  > *当前工作目录；*
  > *是否使用 Git 工作树；*
  > *是否加载额外目录、插件或 MCP 配置；*
  > *是否启用扩展思考及其强度。*
- 这些参数不一定都直接写入模型上下文。有些只是控制 Claude Code 运行时，例如权限模式、请求路由和终端显示。

## 2. 认证与模型路由

- 运行时需要确定请求发送到哪里：
  > *Anthropic 官方接口；*
  > *Claude 订阅账户；*
  > *Amazon Bedrock；*
  > *Google Cloud；*
  > *Microsoft Foundry；*
  > *企业内部的大模型网关。*
- 随后读取相应凭证、工作区信息、模型别名和请求头。
- Claude Code 会把模型名称、推理强度、扩展思考配置、上下文窗口、最大输出长度等转化为请求配置。当前支持`自适应推理`的模型会根据任务步骤决定是否思考以及思考多少，用户设置的推理强度负责调整总体倾向。

## 3. 识别项目环境

- Claude Code 根据当前目录建立`项目状态`，包括：
  > *当前工作目录；*
  > *是否位于 Git 仓库；*
  > *仓库根目录；*
  > *当前分支；*
  > *当前工作树；*
  > *未提交变更；*
  > *可访问目录；*
  > *项目对应的会话存储位置；*
  > *项目对应的自动记忆目录。*
- 会话通常按项目目录组织。对话中的每条消息、工具调用和工具结果会持续写入`本地 JSONL 会话文件`，而不是等任务结束后一次性保存。

## 4. 合并多层配置

- Claude Code 的配置不是来自一个文件，而是多个作用域叠加：
  > *组织托管配置*
  > *项目共享配置*
  > *项目本机配置*
  > *用户配置*
  > *环境变量*
  > *命令行参数*
  > *会话内临时设置*
- 配置内容可能包括：
  > *权限白名单和黑名单；*
  > *默认权限模式；*
  > *Hook；*
  > *环境变量；*
  > *插件；*
  > *MCP 服务；*
  > *模型和推理强度；*
  > *沙箱配置；*
  > *是否启用技能、子智能体；*
  > *企业强制策略。*
- 不同设置有各自的优先级，组织托管配置通常用于设置不可由普通用户绕过的边界。

# 三、第二阶段：发现项目规则和扩展能力

## 1. 加载 CLAUDE.md

- Claude Code 会发现当前项目适用的 CLAUDE.md、CLAUDE.local.md 和规则文件，其中可能包含：
  > *项目架构；*
  > *构建命令；*
  > *测试命令；*
  > *编码规范；*
  > *禁止修改的目录；*
  > *公开接口兼容要求；*
  > *提交规范；*
  > *任务执行约定。*
- 需要注意，当前官方文档明确说明：CLAUDE.md 的内容在接口请求中以`用户上下文消息`的形式传递，而不是拥有不可违背的系统提示词权限。因此它是高优先级项目指导，但不是强制安全边界。真正需要强制执行的约束应该放到权限系统或 Hook 中。
- 项目根目录的规则一般会在启动时加载；`子目录中的 CLAUDE.md` 和带路径范围的规则可能按需加载：
  > *Claude 读取 backend/auth/service.py*
  > *↓*
  > *发现 backend/auth/CLAUDE.md*
  > *↓*
  > *将该目录规则加入当前对话历史*
  > \*↓ \*
  > *触发 InstructionsLoaded Hook*
- 这使 Claude Code 不必在启动时把整个大型仓库的所有模块规范都塞入上下文。

## 2. 加载`自动记忆索引`

- 当前 Claude Code 的自动记忆保存在项目对应的 Markdown 目录中。启动时会加载 `MEMORY.md 的前 200 行或前 25KB`，以先达到者为准。<u style="text-decoration-color: rgb(230, 57, 70)">更详细的信息可放在其他主题文件中，Claude 需要时再通过文件工具读取</u>。
- 自动记忆可能记录：
  > *项目使用 pnpm，而不是 npm*
  > *集成测试需要本地 Redis*
  > *认证模块的入口位于 src/auth*
  > *用户倾向先写测试再改实现*
  > *某个测试在 Windows 下存在已知问题*
- 这不是模型权重中的记忆，而是本地文件内容被重新注入上下文。

## 3. 发现技能

- Claude Code 在启动时通常只把`技能的名称和简短描述`提供给模型。例如：
  > *code-review：执行代码审查*
  > *debug：系统化定位故障*
  > *deploy：执行项目部署流程*
  > *database-migration：创建和验证数据库迁移*
- 完整 SKILL.md 不会全部预加载。只有用户主动调用，或者模型判断技能相关时，技能正文才进入上下文。这样能够减少常驻 token 消耗。
- 因此，技能主要扩展的是：
  > *模型知道如何完成某类任务*
- 而不是直接扩展：
  > *模型能够访问什么外部系统*
- 后者通常由工具或 MCP 提供。

## 4. 发现`子智能体`

- Claude Code 会加载可用子智能体的名称、描述、模型和工具权限，例如：
  > *Explore：只读搜索和代码理解；*
  > *Plan：生成实施方案；*
  > *general-purpose：通用执行；*
  > *用户自定义代码审查智能体；*
  > *用户自定义数据库分析智能体。*
- 主智能体根据描述判断何时委派。普通子智能体拥有独立上下文，不自动继承主会话完整历史，只收到一条由主智能体整理的`委派说明`；完成后通常只向主会话返回摘要。

## 5. 连接 MCP 服务

- Claude Code 初始化已配置的 MCP 服务，获得外部能力，例如：
  > *GitHub；*
  > *数据库；*
  > *浏览器；*
  > *工单系统；*
  > *内部知识库；*
  > *云平台；*
  > *监控系统。*
- 为了避免所有 MCP 工具定义常驻上下文，当前 Claude Code 默认支持按需工具发现。模型开始时可能只看到工具名称或索引，真正需要时再通过 ToolSearch 加载完整参数定义。

## 6. 注册 Hook

- Claude Code 读取所有适用 Hook，并注册到生命周期事件：
  > *SessionStart*
  > *InstructionsLoaded*
  > *UserPromptSubmit*
  > *UserPromptExpansion*
  > *PreToolUse*
  > *PermissionRequest*
  > *PostToolUse*
  > *PostToolUseFailure*
  > *PostToolBatch*
  > *SubagentStart*
  > *SubagentStop*
  > *Stop*
  > *StopFailure*
  > *PreCompact*
  > *PostCompact*
  > *SessionEnd*
  > *……*
- Hook 可以是本地命令、HTTP 服务、提示词型检查器或智能体型检查器。它们属于确定性运行时机制，不依赖主模型是否“记得执行”。

## 7. 触发会话启动事件

- 初始化完成后触发 SessionStart。该 Hook 可以：
  > *检查依赖；*
  > *注入当前环境信息；*
  > *设置环境变量；*
  > *读取项目状态；*
  > *输出需要放入 Claude 上下文的内容。*
- 每当 CLAUDE.md 或规则文件实际载入上下文时，还可以触发 InstructionsLoaded

# 四、第三阶段：接收用户输入

用户在终端、IDE、桌面端或远程界面输入：

> *例：修复登录接口中的空指针问题，不修改公开接口，完成后运行相关测试。*

底层智能体循环在不同界面上基本相同，区别主要是输入输出呈现方式以及代码实际运行的位置。

## 1. 区分本地命令与模型任务

- Claude Code 先识别输入属于哪一类。
- `本地固定命令`，这类命令可能由 Claude Code 本地代码直接处理，不必调用模型。
  > */help*
  > */clear*
  > */context*
  > */status*
  > */config*
- `提示词型技能或命令`，其中一部分会扩展成更长的内部提示词，然后交给模型执行。
  > */code-review*
  > */debug*
  > */compact*
- `普通自然语言任务`，作为新用户消息进入智能体循环。

## 2. 用户输入扩展

- 如果用户调用技能，或者输入中包含需要展开的命令，Claude Code 会先构造扩展后的提示词。
- 此时，可以触发 `UserPromptExpansion` Hook，Hook 可以允许或阻止该扩展。
  > *用户输入 /deploy*
  > *↓*
  > *找到 deploy 技能*
  > *↓*
  > *展开 SKILL.md 和动态参数*
  > *↓*
  > *UserPromptExpansion Hook 检查*
  > *↓*
  > *形成最终用户提示*

## 3. `UserPromptSubmit` Hook

- 自然语言输入准备提交给 Claude 之前，触发 UserPromptSubmit。它可以：
  > *1）阻止某类任务；*
  > *2）检查提示是否包含工单编号；*
  > *3）注入当前分支或需求信息；*
  > *4）附加安全要求；*
  > *5）把外部状态补充到上下文。*
- 例如企业可以规定：
  > *如果请求修改生产配置，但没有变更单编号，则阻止提交。*
- 此时任务甚至还没有进入模型。

## 4. 写入`会话日志（追加式状态记录）`

- 用户消息被追加到`当前会话的 JSONL 记录`中。会话日志是`追加式状态记录`，后续用于：
  > *1）恢复会话（resume）*
  > *2）回退对话；*
  > *3）分叉会话；*
  > *4）调试；*
  > *5）审计。*

# 五、第四阶段：组装本轮模型上下文

模型本身没有跨请求状态。每次调用 Claude 接口时，Claude Code 都要重新发送当前有效上下文。`提示词缓存`只减少重复处理成本，不代表模型真的保存了上一轮状态。

一次请求大致包含：

> *1）系统提示词*
> *2）工具定义*
> *3）项目规则和自动记忆*
> *4）已调用技能*
> *5）对话历史*
> *6）旧工具结果*
> *7）Hook 注入内容*
> *8）本轮用户要求*

## 1. 系统提示词⭐

> *系统提示词由许多*`条件片段`*组合而成；*

- 通常涉及：
  > *1）Claude Code 身份；*
  > *2）基本行为规范；*
  > *3）安全规则；*
  > *4）输出风格；*
  > *5）文件操作约定；*
  > *6）工具调用约定；*
  > *7）Git 使用约定；*
  > *8）当前执行环境；*
  > *9）模型能力；*
  > *10）当前权限模式相关要求；*
  > *11）子智能体和团队协作说明；*
  > *12）当前启用功能的附加说明。*
- 从 v2.1.88 source map 的分析看，它不是单一固定字符串，而是<u style="text-decoration-color: #e63946">由大量静态和动态片段拼装而成</u>。当前提示词提取仓库也显示，Claude Code 包含主提示词、工具说明、子智能体提示词、压缩提示词和各种功能型提示词数百项。

## 2. 工具定义

- 模型需要知道工具名称、用途和参数模式，例如：
  > *Read(file\_path, offset, limit)*
  > *Grep(pattern, path)*
  > *Edit(file\_path, old\_string, new\_string)*
  > *Bash(command, timeout)*
  > *Agent(description, prompt, subagent\_type)*
- `核心工具的完整定义常驻请求`；较少使用的工具和 MCP 工具可以按需加载。工具定义本身也占用上下文，因此 Claude Code将工具发现做成了类似“虚拟内存”的机制。

## 3. 项目持久上下文

- 包括：
  > *1）根目录 CLAUDE.md；*
  > *2）当前适用的规则；*
  > *3）自动记忆索引；*
  > *4）输出风格；*
  > *5）当前已调用技能正文；*
  > *6）当前环境信息。*

## 4. 对话历史

- 包括当前有效历史中的：
  > *1）用户消息；*
  > *2）Claude 文本；*
  > *3）工具调用请求；*
  > *4）工具执行结果；*
  > *5）权限拒绝；*
  > *6）测试输出；*
  > *7）子智能体返回摘要；*
  > *8）压缩后的历史摘要。*
- 不是所有本地会话日志都一定重新进入模型。会话日志是完整持久记录，而模型上下文可能已经经过工具结果清理或压缩。

## 5. 本轮用户消息

> *用户的新要求位于上下文末端，使其成为最新指令*。

## 6. `提示词缓存`

- Claude Code <u style="text-decoration-color: #e63946">尽量让请求前缀保持稳定</u>：
  > *稳定系统提示词*
  > *→ 稳定项目配置*
  > *→ 旧对话历史*
  > *→ 新增消息和工具结果*
- 每一轮只在尾部追加内容，接口便可以复用前缀缓存。<span style="background-color: #fff3cd">切换模型、压缩会话或改变部分工具集合会破坏缓存</span>；普通代码编辑通常不会直接破坏已有前缀缓存。

# 六、第五阶段：`冻结本轮请求配置`

从 v2.1.88 源码分析看，智能体循环在一次模型调用前会构建一个相对稳定的`请求配置快照`，其中包括：

> *1）当前模型；*
> *2）提供方；*
> *3）扩展思考配置；*
> *4）推理强度；*
> *5）工具集合；*
> *6）模型输出限制；*
> *7）测试性功能头；*
> *8）当前会话状态。*

其目的是<span style="background-color: #fff3cd">防止一次正在进行的模型调用过程中，用户突然切换模式或配置，导致同一次请求使用一半旧配置、一半新配置</span>。配置变化通常在后续请求边界生效。该细节属于版本实现，不应视为永久公开接口。

# 七、第六阶段：第一次调用模型

Claude Code 将组装好的请求发送给模型，并流式接收响应。

模型可以输出几类内容。

## 1. 普通文本

- 例如：我先检查登录接口及其调用链。
- 这部分可以边生成边显示在终端。

## 2. 扩展思考块

- 在支持扩展思考的模型上，Claude 可以在当前步骤进行更深入推理，例如：
  > *用户要求不改变公开接口，因此应该优先检查内部空值处理，*
  > *不能通过修改返回类型解决。*
- 它属于当前模型决策过程，不等于持久任务计划。下一次工具结果返回后，模型还可以重新思考。

## 3. 工具调用块

- 例如模型输出结构化请求：
  > *{*
  > *"name": "Grep",*
  > *"input": {*
  > *"pattern": "login",*
  > *"path": "src"*
  > *}*
  > *}*
- 模型并没有自己执行搜索。它只是生成“希望调用哪个工具、使用哪些参数”的结构化意图。

## 4. 多个工具调用

- 模型也可能在同一次响应中要求读取多个相互独立的文件。Claude Code 可以并发处理适合并行的只读操作，但涉及写入和依赖顺序的操作需要保持顺序，否则后续读取可能看不到前一步编辑结果。
- source map 分析显示其执行器采用了类似读写锁的思想：<span style="background-color: #fff3cd">只读工作可重叠，存在副作用的操作保持序列化</span>。

## 5. 直接结束

- 如果任务只是解释代码，模型可能不调用工具，直接给出答案并以 end\_turn 结束。
- 对于“修复代码”任务，第一轮通常会请求搜索或读取工具。

# 八、第七阶段：工具调用进入执行管线

假设第一次调用是：

> *Grep(pattern="login", path="src")*

工具不会立即执行，而是经过`完整运行时管线`。

## 1. 参数结构校验

- Claude Code 根据该工具的参数定义检查：
  > *1）工具名称是否存在；*
  > *2）必填参数是否完整；*
  > *3）类型是否正确；*
  > *4）路径格式是否合法；*
  > *5）数值是否超限；*
  > *6）输入能否被标准化。*
- 如果模型生成了错误参数，工具不会盲目执行，而是<u style="text-decoration-color: #e63946">产生参数错误结果返回给模型</u>。

## 2. 工具注册表解析

- 运行时根据工具名称查找实际实现：
  > *Read → 本地文件读取实现*
  > *Edit → 精确替换实现*
  > *Bash → shell 子进程实现*
  > *mcp\_x\_y → MCP 远程工具代理*
  > *Agent → 子智能体生命周期实现*
- 这一步<u style="text-decoration-color: #e63946">把模型输出的抽象工具名映射到真实程序</u>。

## 3. PreToolUse Hook

- 在工具实际执行前触发。Hook 可以：
  > *1）允许；*
  > *2）拒绝；*
  > *3）要求进入正常权限判断；*
  > *4）修改部分输入；*
  > *5）追加上下文；*
  > *6）把工具调用推迟到后面。*
- 例如：
  > *Claude 请求：*
  > *Bash("rm -rf build")*
  > *PreToolUse Hook：*
  > *检查命令*
  > *→ 允许删除 build*
- 例如：
  > *Claude 请求：*
  > *Bash("rm -rf /")*
  > *PreToolUse Hook：*
  > *返回 deny*
  > *→ 工具不执行*
- 官方 Hook 生命周期将 PreToolUse 定义为每次工具调用执行前的拦截点

## 4. 权限规则判断

- 如果 Hook 没有直接给出最终结论，Claude Code 根据当前`权限策略`判断。
- 可能的结果是：
  > *1）ALLOW：直接允许*
  > *2）DENY：直接拒绝*
  > *3）ASK：询问用户*
- 判断依据包括：
  > *当前权限模式；*
  > *工具类型；*
  > *目标路径；*
  > *命令内容；*
  > *项目和用户权限规则；*
  > *组织强制策略；*
  > *是否访问工作目录外；*
  > *是否涉及网络或外部副作用。*
- 例如：
  > *Read(src/auth.ts)*
  > *通常属于低风险读取，可能直接允许。*
  > *Edit(src/auth.ts)*
  > *是否询问取决于当前模式。*
  > *Bash("npm test")*
  > *可能因为已加入允许规则而自动执行。*
  > *Bash("git push origin main")*
  > *由于外部副作用，通常需要更严格判断。*
- 当前权限模式包括：手动确认、自动接受编辑、规划模式和自动模式等；具体可用模式及名称随版本变化。

## 5. 自动模式安全分类

- 在自动模式下，工具操作还可能经过后台安全判断，重点分析：
  > *是否符合用户原始要求；*
  > *是否跨越重要安全边界；*
  > *是否可能受到仓库中恶意文本的诱导；*
  > *是否对远程系统产生副作用；*
  > *是否属于危险删除、发布、上传或部署；*
  > *目标是否为模型和用户已经识别的系统。*
- 被自动模式分类器拒绝时，可以触发 `PermissionDenied Hook`；Hook 能决定是否允许模型调整参数后重试。

## 6. 用户确认

- 如果运行时无法自动决定，就弹出确认界面。用户可以：
  > *1）本次允许；*
  > *2）以后允许匹配操作；*
  > *3）拒绝；*
  > *4）拒绝并向 Claude 提供原因。*
- 拒绝不是直接让整个会话崩溃。通常会形成一个工具错误或拒绝结果回到模型，例如：
  > *用户拒绝了该命令，因为不能修改生产数据库。*
- 模型随后可以换用安全方案。

# 九、第八阶段：检查点、沙箱和真实执行

1. `文件检查点`

- 在 Claude 修改文件前，Claude Code 会保存`受影响文件的当前内容`。这样用户可以回退 Claude 造成的本地文件修改。
- 检查点与 Git 不同：
  > *检查点：面向当前 Claude Code 会话的快速撤销*
  > *Git：面向项目正式历史的版本管理*
- 检查点不会恢复（对外部系统造成的影响）
  > *1）数据库写入；*
  > *2）已发送邮件；*
  > *3）已调用外部接口；*
  > *4）已经部署的服务；*
  > *5）已经推送的 Git 提交；*
  > *6）云平台资源操作。*
- 因此，远程副作用通常比本地文件编辑需要更严格的权限确认。

2. `沙箱约束`

- 如果启用了沙箱，Bash 等工具会在`操作系统级边界`中运行，限制：
  > *1）可读取目录；*
  > *2）可写入目录；*
  > *3）网络目标；*
  > *4）子进程行为；*
  > *5）系统资源；*
  > *6）敏感路径。*
- 权限系统回答的是：这个工具调用是否应该被执行？
- 沙箱回答的是：`即使执行，它最多可以影响什么范围？`
- 两者并不是同一个机制。

3. 超时和输出限制

- Bash 工具通常具有：
  > *1）默认超时；*
  > *2）最大允许超时；*
  > *3）输出大小限制；*
  > *4）进程终止处理；*
  > *5）后台任务处理；*
  > *6）完整输出转存文件机制。*
- 当输出过长时，当前 Claude Code 可以把完整输出写入文件，只向模型返回路径和短预览，避免几十万字符日志直接挤满上下文。

4. 真实工具执行

- 直到这一阶段，操作才真正作用于环境：
  > *Read → 从磁盘读取*
  > *Grep → 调用搜索实现*
  > *Edit → 修改文件*
  > *Bash → 启动子进程*
  > *MCP → 调用外部服务*
  > *Agent → 创建子智能体*
- 在此之前的模型推理、权限判断和 Hook 都只是控制过程。

# 十、第九阶段：工具执行后的处理

## 1. 成功结果：工具成功后触发 `PostToolUse`

- 工具成功后触发 PostToolUse。例如编辑完成后，Hook 可以：
  > *1）运行代码格式化；*
  > *2）执行静态检查；*
  > *3）**检查禁止模式**；*
  > *4）更新生成文件；*
  > *5）记录审计日志；*
  > *6）向下一轮模型注入提示。*

## 2. 失败结果：工具抛出错误时触发 `PostToolUseFailure`

> *错误不会被隐藏。它会被格式化成工具结果，模型在下一轮看到后决定如何处理。*

- 工具抛出错误时触发 `PostToolUseFailure`，例如：
  > *1）文件不存在*
  > *2）旧字符串匹配到多个位置*
  > *3）命令超时*
  > *4）测试进程退出码非零*
  > *5）MCP 连接失败*
  > *6）用户权限不足*

## 3. 工具批次完成

> *如果同一轮并行调用了多个只读工具，全部结束后可以触发*`PostToolBatch`*，让 Hook 对整个批次结果做统一处理。*

## 4. `结果格式化`

- 工具的原始输出会转化为模型能读取的 `tool_result` 消息，例如：
  > *{*
  > *"type": "tool\_result",*
  > *"tool\_use\_id": "tool\_123",*
  > *"content": "src/auth/controller.ts:42: const user = ..."*
  > *}*
- 失败时会标记为错误。

## 5. `截断和外置`

- 如果结果太大，运行时可能：
  > *1）截断中间部分；*
  > *2）只保留开头和结尾；*
  > *3）返回匹配数量；*
  > *4）*`写入临时文件并返回路径`*；*
  > *5）提示模型使用更精确的范围重新读取。*
- 例如模型第一次搜索整个仓库得到三万行结果，下一轮可能调整为：
  > *只搜索 src/auth 目录*
  > *只读取 30～90 行*
  > *只匹配 loginHandler 函数*

## 6. 追加到会话和模型历史

- 处理后的结果同时进入：⭐
  > *1）本地会话 JSONL 状态记录；*
  > *2）当前有效对话历史；*
  > *3）下一轮模型请求上下文。*
- 至此，模型才真正“知道”工具做了什么。

# 十一、第十阶段：智能体循环重新开始



工具结果被写回后，Claude Code再次调用模型。

现在模型看到：

> - 用户目标
> - 项目规则
> - 搜索请求
> - 搜索结果

模型可能推断：

> *登录入口在 controller.ts，*
> *但空指针来源可能在 sessionService.ts，*
> *需要继续读取调用链。*

于是输出第二个工具调用：

> *Read(src/auth/controller.ts)*

读取结果回来后，再输出：

> *Read(src/auth/sessionService.ts)*

然后发现：

> *const userId = session.user.id;*

而 session.user 在匿名会话中可能为空。

接着它会考虑约束：

> *不能改变公开接口*

因此不会简单修改函数返回类型，而可能选择内部空值判断：

> *const userId = session.user?.id;*
> *if (!userId) {*
> *return unauthorizedResponse();*
> *}*

这不是 Claude Code 本地程序硬编码出来的修复方案，而是模型在当前上下文中生成的决策。

# 十二、模型何时会使用`规划模式`

Claude Code 并不是每个任务都自动经过一个`独立 Planner`。

普通模式下：主模型一边理解，一边搜索，一边修正计划

规划模式下：

> *允许搜索和读取*、*禁止直接修改源码*、*要求先形成方案*

因此规划模式本质上首先是权限状态，不是完全不同的模型架构。

复杂任务中，Claude 还可能调用 `Plan 子智能体`，由其<u style="text-decoration-color: #e63946">在独立上下文中研究后返回方案</u>。主智能体再决定是否执行。

典型流程是：⭐

> *主智能体判断任务复杂*
> *↓*
> *调用 Plan 或 Explore 子智能体*
> *↓*
> *子智能体搜索仓库*
> *↓*
> *返回结构化结论*
> *↓*
> *主智能体整合结论*
> *↓*
> *请求用户批准或进入实现*

Explore 和 Plan 等`内置子智能体`有独立工具限制；例如 Explore 主要是只读搜索。

# 十三、`子智能体委派`的完整过程

假设问题涉及多个模块，主模型可能调用：

> *Agent(*
> *subagent\_type="Explore",*
> *prompt="分析登录请求从路由到数据库的完整调用链，*
> *找出可能解引用空用户的所有位置，只返回结论和文件行号。"*
> *)*

此后发生：

> *1）触发 SubagentStart；*
> *2）创建*`独立上下文`*；*
> *3）加载该子智能体系统提示词；*
> *4）加载*`允许的工具`*；*
> *5）构造主智能体的*`委派消息`*；*
> *6）子智能体独立运行搜索—读取—分析循环；*
> *7）子智能体可能经历自己的上下文压缩；*
> *8）完成后形成*`摘要`*；*
> *9）触发 SubagentStop；*
> *10）摘要作为*`Agent 工具结果`*返回主会话。*

普通子智能体不会自动看到：

> *1）主会话完整对话；*
> *2）主会话已经读取的文件全文；*
> *3）主会话已调用技能正文；*
> *4）主会话自动记忆。*

它依赖主智能体写清楚委派内容。特殊的 fork 子智能体可以继承父上下文；需要文件隔离时，还可以配合`独立 Git 工作树`。

子智能体的主要价值不只是`并行`，而是<u style="text-decoration-color: #e63946">防止大量搜索结果污染主上下文</u>。

# 十四、需要用户补充信息时

如果模型发现关键信息无法从项目中得到，例如：

> *“登录失败”是应该返回 401，还是重定向到登录页？*

它可以调用 `AskUserQuestion`，暂停当前任务并等待用户选择。

用户回答后：

> *用户答案*
> *→ 作为工具结果写入上下文*
> *→ 模型继续执行*

这不是结束旧任务再创建新任务，而是智能体循环中的一次观察。

用户也可以随时主动中断 Claude：

> *1）按 Esc 停止当前生成或操作；*
> *2）追加约束；*
> *3）纠正方向；*
> *4）要求撤销；*
> *5）切换权限模式。*

后续模型调用会看到新消息，并据此调整计划。

# 十五、上下文如何在执行过程中增长

每一轮都会增加内容：

> *用户消息*
> *Claude 文本*
> *扩展思考块*
> *工具调用*
> *文件内容*
> *搜索结果*
> *测试日志*
> *错误信息*
> *子智能体摘要*
> *技能正文*
> *路径规则*

由于模型每轮都需要看到当前有效历史，长任务的主要资源约束不是磁盘，而是上下文窗口。官方当前说明，部分模型和方案支持 100 万 token 上下文，但更大的窗口仍然有限，压缩机制依然存在。

## 1. 工具级输出控制

- 首先<u style="text-decoration-color: #e63946">控制单个工具结果</u>：
  > *1）限制搜索条数；*
  > *2）限制读取行数；*
  > *3）截断超大输出；*
  > *4）把完整日志保存到文件；*
  > *5）要求模型重新进行更窄查询。*

## 2. 优先清理旧工具输出

> *上下文接近限制时，Claude Code 优先清理*`较旧且可重新生成的工具输出`*，例如旧日志和旧搜索结果。*

## 3. 会话压缩

- 如果仍不足，则执行压缩：
  > *PreCompact Hook*
  > *→ 选取需要压缩的历史*
  > *→ 模型生成*`结构化任务摘要`
  > *→ 用摘要替换旧历史*
  > *→ 重新注入持久上下文*
  > *→ PostCompact Hook*
  > *→ 继续原任务*
- 压缩后：
  > *1）系统提示词保持；*
  > *2）*`根目录 CLAUDE.md`*重新注入；*
  > *3）自动记忆重新注入；*
  > *4）已调用技能按配额重新注入；*
  > *5）路径规则需要再次读取匹配文件才能重载；*
  > *6）旧工具原始输出可能不再存在于模型上下文。*

4. `压缩抖动保护`

> *如果某个文件或工具结果本身就巨大，导致每次压缩后上下文立即再次满载，Claude Code 不会无限压缩，而会在若干次后停止并报告错误。*

# 十六、Claude 如何判断任务完成

模型可能在以下情况下决定结束当前轮次：

> *1）用户问题已经回答；*
> *2）代码已经修改；*
> *3）相关测试已通过；*
> *4）没有剩余待办；*
> *5）后续步骤需要用户决定；*
> *6）遇到无法解决的阻塞；*
> *7）用户要求停止。*

此时模型输出最终文本，并把停止原因设置为结束当前轮次。

但 Claude Code 不一定立即接受。

`Stop Hook`

模型准备停止时触发 Stop。Hook 可以检查：⭐

> *1）是否修改了源码却没有测试；*
> *2）是否留下未格式化文件；*
> *3）是否存在未完成任务；*
> *4）是否违反分支规则；*
> *5）是否生成了迁移却没有验证；*

如果 Hook 返回阻止信息：

> *检测到修改了 src/auth，但没有运行 auth 测试。*

该信息会重新进入上下文，智能体循环继续：

> *模型看到 Stop Hook 反馈*
> *→ 调用测试*
> *→ 分析结果*
> *→ 再次尝试结束*

因此 Stop Hook 是一种`外部收敛判定器`，能够补足模型自我判断不可靠的问题。官方将 Stop 定义为每个回答结束时触发的 Hook；异常结束则触发 StopFailure。

> 为了避免 Stop Hook 自身造成无限循环，实际系统需要有重入或次数保护。v2.1.88 源码分析显示其确实存在相应防护。

# 十七、任务结束后保留什么

需要区分“本轮任务结束”和“整个会话退出”。

1. 会话仍然存在

- Claude 输出最终回答后，交互会话通常继续保持。用户可以继续说：“再给这个修复补一个集成测试”。
- 再给这个修复补一个集成测试。

2. `会话日志`已经持久化

- 以下内容已经陆续写入 JSONL：
  > *-用户提示；*
  > *-Claude 响应；*
  > *-工具调用；*
  > *-工具结果；*
  > *-错误；*
  > *-*`压缩边界`*；*
  > *-子智能体结果*

3. `检查点`保留

- Claude 修改过的文件可以通过检查点回退。检查点在恢复会话后仍可使用，但只覆盖受支持的本地文件修改。

4. 自动记忆可能更新

- 在执行过程中，Claude 可能把`可复用知识`写入`项目自动记忆`，例如：
  > *认证测试命令是 pnpm test tests/auth*
  > *匿名会话的预期返回码为 401*
- 不是所有任务细节都应该进入长期记忆。临时 bug、一次性路径和短期状态通常只保留在会话中。

5. Git 不会自动等同于完成

- 文件已修改并不代表：
  > *-已经 git add；*
  > *-已经提交；*
  > *-已经推送；*
  > *-已经创建拉取请求；*
  > *-已经部署。*
- 这些需要用户明确要求，或者由项目技能和流程约定规定。由于提交、推送和部署具有更明显的边界与外部副作用，通常会经历额外权限判断。

6. 退出时触发 `SessionEnd`

- 只有用户真正退出、关闭或终止会话时，才触发 SessionEnd，可用于：⭐
  > *1）清理临时资源；*
  > *2）结束后台任务；*
  > *3）记录会话摘要；*
  > *4）删除临时工作树；*
  > *5）上传审计信息。*

# 十八、恢复会话时发生什么

用户以后运行：`claude --resume`，Claude Code 会：

> *找到对应项目会话；*
> *读取*`JSONL 历史`*；*
> *重新读取当前设置文件；*
> *恢复允许恢复的会话状态；*
> *重新检查当前文件系统和 Git 状态；*
> *触发 SessionStart，其来源为恢复；*
> *后续请求重新建立提示词缓存。*

对于历史较短的会话，Claude Code 可以直接加载<u style="text-decoration-color: rgb(230, 57, 70)">原始消息，包括用户要求、模型回复、工具调用以及工具结果</u>，让模型从上次停止的位置继续工作。但如果会话已经很长，包含大量文件内容、搜索结果和测试日志，将全部历史重新发送给模型会占用大量上下文窗口，同时增加请求延迟和输入 token 成本。因此，在部分版本或使用场景中，Claude Code 会提供两种恢复方式。

## 第一种是`完整恢复`

- 系统尽可能保留原始对话历史和工具结果，使模型能够看到`此前讨论过的细节`、`方案比较`、`错误排查过程`和`用户约束`。
- 这种方式的信息损失较少，适合需要`继续复杂调试`、`恢复细粒度设计决策`，或者检查早期讨论内容的场景。但它也会快速占用上下文窗口，恢复后的每一次模型调用都需要携带较长历史，可能很快再次触发上下文清理或压缩。

## 第二种是`摘要恢复`

- Claude Code 先对旧会话执行一次上下文压缩，将原始历史整理成结构化任务摘要，通常保留<u style="text-decoration-color: rgb(230, 57, 70)">任务目标、关键约束、已修改文件、重要决策、测试结果、当前问题和下一步计划</u>。随后，新会话主要使用这份摘要继续执行，而不是把全部原始消息重新放入模型上下文。
- 摘要恢复能够明显减少上下文占用和后续调用成本，也更适合已经接近上下文上限的长期任务。但它属于`有损恢复`：原始会话仍可能保存在本地日志中，模型却不会自动看到摘要中未保留的细节。例如某个方案被否决的完整原因、一次中间测试的具体错误信息，或者用户较早提出的细粒度限制，都可能在压缩过程中被弱化或遗漏。

因此，完整恢复和摘要恢复的区别并不是本地会话文件是否还存在，而是下一次模型请求实际携带哪些历史内容：

> *完整恢复：本地会话记录→ 尽可能重建原始消息历史→ 模型继续执行*
>
> *摘要恢复：本地会话记录→ 生成结构化摘要→ 用摘要代替大部分旧历史→ 模型继续执行*

无论选择哪种恢复方式，Claude Code 都需要重新读取当前项目环境，例如 CLAUDE.md、自动记忆、当前 Git 状态和实际文件内容。

因为会话记录描述的是`上次停止时模型所知道的状态`，而代码仓库在会话中断期间可能已经被用户、其他智能体或外部程序修改。恢复后的 Claude 不应只依赖旧摘要，而应通过 git status、git diff、重新读取关键文件和运行必要测试，确认当前项目的真实状态。

# 十九、哪些部分由模型决定，哪些由运行时决定


| 环节               | 主要决定者           |
| ---------------- | --------------- |
| 理解用户需求           | Claude 模型       |
| 判断需要读取哪些文件       | Claude 模型       |
| 形成修复方案           | Claude 模型       |
| 生成代码修改内容         | Claude 模型       |
| 判断下一步工具          | Claude 模型       |
| 判断是否委派子智能体       | Claude 模型       |
| 工具参数结构是否合法       | Claude Code 运行时 |
| 工具是否存在           | Claude Code 运行时 |
| 操作是否允许           | 权限系统、Hook、用户    |
| 命令实际如何运行         | 工具实现和操作系统       |
| 文件修改前是否建立检查点     | Claude Code 运行时 |
| 超大输出如何处理         | Claude Code 运行时 |
| 上下文何时压缩          | Claude Code 运行时 |
| 压缩摘要内容           | Claude 模型       |
| Stop Hook 是否要求继续 | Hook            |
| 最终如何总结           | Claude 模型       |
| 会话如何保存           | Claude Code 运行时 |


因此 Claude Code 不是完全由模型自由控制，也不是一个写死流程的自动化程序，而是：`概率性的任务决策` + `确定性的执行框架` + `可配置的安全控制` +`可恢复的状态管理`⭐

# 二十、几个容易产生的误解

误解一：启动后会扫描整个代码仓库

> *不会。Claude Code能够访问整个项目，不等于启动时把整个项目全部读入上下文。它通常通过“*`Glob → Grep → Read`*”**逐步发现和读取相关代码**。*

误解二：先生成完整计划，再机械执行

> *不一定。默认情况下，**计划通常在智能体循环中动态形成，并随工具结果不断调整**。*
>
> *只有*`规划模式`*、*`Plan 子智能体`*或*`特定技能`*会显式强化“先规划后执行”。*

误解三：模型直接操作文件和终端

> *模型只生成结构化工具调用。**真正的文件、命令、网络和外部系统操作由 Claude Code 运行时完成**。*

误解四：模型记得上一轮结果

> *模型本身<u style="text-decoration-color: rgb(230, 57, 70)">无状态</u>。Claude Code 将上一轮工具结果再次放进下一次接口请求，模型才表现为“记得”。*

误解五：压缩后模型仍然拥有完整历史

> *压缩是<u style="text-decoration-color: rgb(230, 57, 70)">有损的</u>。完整历史可能仍在本地会话记录中，但下一轮模型只获得压缩后的有效上下文。*

误解六：Claude 说“测试通过”就一定运行过测试

> *只有上下文中存在真实 Bash 工具调用及其测试结果，才能说明测试实际运行过。*
> *最可靠的做法是使用 Stop Hook 或验证技能强制检查。*

误解七：检查点能撤销所有操作

> *检查点主要撤销本地文件修改，**不能撤销外部系统副作用**。*

# 二十一、架构本质

一次 Claude Code 任务的核心并不是“模型生成了一段代码”，而是：`Claude Code 持续为模型构造当前任务状态`，<u>模型基于状态选择下一项行动</u>，`运行时在权限和 Hook 控制下执行行动`，再把真实结果返回模型；这一过程不断循环，直到模型和外部停止检查共同认为任务已经完成。

> Claude Code 的上下文压缩，本质上不是“把聊天记录截断”，而是一次`由模型参与的有损状态重建`：当上下文即将耗尽时，Claude Code 清理低价值内容，把已有对话压缩成`结构化摘要`，再将项目规则、记忆和必要技能重新注入，随后基于这个新上下文继续执行任务。

# 一、为什么必须压缩？

## Claude 模型本身是`无状态的`

Claude Code 每进行一轮交互，都需要重新向模型发送：⭐

> *1）系统提示词和工具定义；*
> *2）CLAUDE.md、规则文件和自动记忆；*
> *3）用户与 Claude 的历史对话；*
> *4）已读取的文件内容；*
> *5）命令输出、测试日志和工具调用结果；*
> *6）当前用户的新指令。*

## `Claude Code 上下文`
```
系统层
├── Claude Code 系统提示词
├── 工具定义
└── 安全规则

项目知识层（长期）
├── CLAUDE.md
├── MEMORY.md ← 主索引文件（核心入口）
└── memory/*.md ← 主题化记忆文件（补充内容）

任务状态层（短期）
├── 当前对话
├── 工具调用结果 ← 结构化 tool result
├── 测试输出
└── 压缩摘要

运行环境层
├── 当前文件系统
├── Git 状态
└── 外部服务状态
```

因此，Claude Code 连续运行时间越长，每轮请求携带的历史越多。尤其是测试日志、代码搜索结果、大文件读取结果，会迅速占满上下文窗口。

Claude Code 使用`提示词缓存`减少重复处理成本，但缓存只降低重复计算和费用，并不会减少上下文本身占用的容量。

# 二、压缩是如何触发的？

> Claude Code 有两种压缩触发方式。

## 1. `自动压缩`

> *默认情况下，当上下文使用率接近容量上限时，Claude Code 自动执行压缩。当前官方文档给出的默认触发点约为上下文容量的 95%。主智能体和子智能体都使用类似机制。*

- 可以通过环境变量提前触发：
  > `export CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=70`
- 表示在上下文使用约 70% 时开始自动压缩。只能调低触发比例，设置得高于默认阈值通常不会产生效果。
- 还可以人为指定压缩计算所依据的容量：
  > `export CLAUDE_CODE_AUTO_COMPACT_WINDOW=120000`
- 这并不会改变模型真实的上下文窗口，而是让 Claude Code 把 120000 个 token 当作自动压缩容量来计算。

## 2. `手动压缩`

> *用户可以直接执行：/compact*
> *也可以\*指定压缩重点*：\*`/compact 保留当前实施方案、修改过的文件、测试结果和剩余问题`

- 后面的文字会作为本次压缩的额外指令，使摘要更倾向于保留指定内容。(Claude)

自动压缩的弱点在于，模型只能自行判断哪些内容重要；手动压缩则允许用户主动定义任务状态。

# **三、压缩时内部发生了什么？**

> *上下文增长*
> *→ Microcompact 清理*`可重建内容`
> *→ 到达阈值后调用*`摘要模型`
> *→ 按*`固定结构`*提取任务状态*
> *→ 用摘要替换指定历史区间*
> *→ 恢复技能、规则、文件引用等*`持久上下文`
> *→ 继续智能体循环*

从 Claude Code 的行为上，可以将压缩过程理解为以下几个阶段。

## 第一阶段：清理旧工具输出（低风险）

Claude Code 会优先清理较早的工具输出，例如：

> *1）大段测试日志；*
> *2）已经使用过的搜索结果；*
> *3）文件读取结果；*
> *4）构建输出；*
> *5）终端命令输出；*
> *6）已经完成用途的中间信息。*

官方说明的顺序是：先清理旧工具结果，仍不足时再压缩对话。

这一步类似“低风险删除”，因为工具输出通常可以重新生成，而用户需求、设计决策和代码修改状态更难恢复。

## 第二阶段：发起单独的摘要请求

如果清理工具结果后仍需要释放上下文，Claude Code 会发起一次专门的模型请求，对历史消息进行摘要。

因此，压缩并不是纯代码实现的字符串裁剪，也不是简单保留最近若干轮，而是由模型理解整个任务历史后生成一份`结构化摘要`。

> *自 Claude Code 2.1.198 起，如果当前会话启用了*`扩展思考`*，压缩请求也会继承这一配置；扩展思考只影响摘要生成过程，不会改变压缩后的会话设置。[CC扩展思考](https://mubu.com/docBB-ofLWbE0)*

Claude Code 使用了`相对固定的结构化摘要模板`，而不只是笼统要求模型“总结对话”。

### 1）普通上下文压缩要求保留五类信息⭐

> *1）Task Overview：用户核心请求、成功标准、约束；*
> *2）Current State：已完成工作、修改或分析过的文件、产物；*
> *3）Important Discoveries：技术约束、关键决策及理由、错误及解决方法、失败方案；*
> *4）Next Steps：待完成动作、阻塞项、优先顺序；*
> *5）Context to Preserve：用户偏好、领域信息、向用户作出的承诺。*

提示词还明确要求：`宁可多保留一些能够避免重复劳动、重复错误的信息，并将摘要包装在特定标签中`。

因此，更准确的描述应该是：Claude Code 使用`预定义字段`指导模型生成`任务状态摘要`，但每个字段具体保留哪些内容，仍由模型进行语义判断。

---

### 2）`部分压缩`还有另一套模板

> *压缩较早的一段历史，但后面仍会拼接未压缩的新消息*

较新的 Claude Code 还存在“部分压缩”提示词，它比普通压缩详细得多，包含九个区块：⭐

> *1）用户主要请求；*
> *2）关键技术概念；*
> *3）文件与代码段；*
> *4）错误及修复；*
> *5）问题解决过程；*
> *6）所有用户消息；*
> *7）待办任务；*
> *8）已完成工作；*
> *9）后续继续任务所需上下文。*

其中甚至要求保留文件名、函数签名、重要代码片段，以及用户提出的安全约束。

这说明 Claude Code 至少存在两种压缩目标：

> *1）完整压缩：将当前长会话替换为简洁、可继续执行的任务快照*
> *2）部分压缩：*`压缩较早的一段历史`***，***`但后面仍会拼接未压缩的新消息`*，因此需要更完整地解释前序对话；*

## 第三阶段：用摘要替换历史消息

> *后续发送给模型的有效上下文中，旧历史由摘要代替。*

摘要生成后，原来的长对话不再完整进入后续模型请求，而是由压缩摘要代替。

可以近似理解为：压缩前上下文 = 系统信息 + 项目信息 + 完整历史 + 当前消息，变成：`压缩后上下文 = 系统信息 + 重新加载的项目信息 + 压缩摘要 + 当前消息`

> 因此，压缩后的 Claude 并不是“仍然记得所有细节，只是显示得更短”，而是真的<u style="text-decoration-color: #e63946">只获得摘要中保留下来的历史信息</u>。

## 本地会话记录 &amp; 当前模型上下文⭐

> `本地会话记录`和`当前模型上下文`是两个概念

会话文件可以继续记录`压缩边界`及相关历史，但后续模型调用使用的是`压缩后的有效消息序列`，而不是重新读取全部原始记录。子智能体的日志中也会记录压缩触发方式和压缩前 token 数量。⭐

- `/compact` 所说的“用摘要替换历史”，主要指的是：后续发送给模型的有效上下文中，旧历史由摘要代替。
- 并不意味着它一定会从磁盘上的 JSONL 中物理删除原始记录。官方将 /compact 描述为“用摘要替换历史”，同时<u style="text-decoration-color: #e63946">会话转录仍存储在同一个 JSONL 中</u>。
- 从 Claude Code v2.1.220 的实际会话记录可以观察到，一次压缩附近会出现类似序列：
  > *此前的原始用户消息、Claude 回复和工具结果*
  > *↓*
  > *一条包含压缩摘要的合成 user 消息*
  > *↓*
  > `一条 system / compact_boundary 记录`
  > *↓*
  > `“Compacted”界面提示记录`
  > *↓*
  > *压缩后的\*\*新对话继续追加*
- 实际问题报告中的 JSONL 记录显示：
  > *type=user*
  > *"This session is being continued from a previous conversation*
  > *that ran out of context..."*
  >
  > *type=system*
  > *subtype=*`compact_boundary`
  >
  > *type=user*
  >
  > *Compacted (ctrl+o to see full summary)*
- 其中第一条合成用户消息携带的正文就是压缩后的任务摘要。
- 因此磁盘上的结构可以近似表示为：
  > *session.jsonl*
  > *│*
  > *├─ 原始消息 1*
  > *├─ 原始工具调用 1*
  > *├─ 原始工具结果 1*
  > *├─ 原始消息 2*
  > *├─ 原始工具调用 2*
  > *├─ 原始工具结果 2*
  > *│*
  > *├─ 压缩摘要消息*
  > *├─ compact\_boundary*
  > *├─ Compacted 状态提示*
  > *│*
  > *├─ 压缩后的新消息*
  > *├─ 新工具调用*
  > *└─ 新工具结果*
- 原始数据仍然位于摘要之前，压缩摘要则作为新的记录追加进去。
  > *需要注意：官方明确警告 JSONL 格式属于内部实现，版本之间可能变化。因此某些版本可能使用不同字段、顺序或记录类型，不能长期依赖“摘要一定是 type=user”这样的固定规则。*

# 四、压缩后哪些内容会保留？

> 不同上下文来源的处理方式不同。


| 内容来源             | 压缩后的行为               |
| ---------------- | -------------------- |
| 系统提示词、输出风格       | 不属于普通消息历史，保持不变       |
| 项目根目录的 CLAUDE.md | 从磁盘重新注入              |
| 不带路径限制的规则        | 从磁盘重新注入              |
| 自动记忆             | 从磁盘重新注入              |
| 对话中的用户要求         | 依赖摘要是否保留             |
| 旧文件读取结果          | 通常被清理或摘要             |
| 旧命令和测试输出         | 通常被清理或摘要             |
| 子目录中的 CLAUDE.md  | 暂时丢失，重新读取相关目录文件时再次加载 |
| 带 paths: 的规则     | 暂时丢失，读取匹配文件时再次加载     |
| 已调用的技能正文         | 重新注入，但受到 token 配额限制  |
| Hook             | 本身是外部执行代码，不作为上下文保留   |


已调用技能重新注入时，每个技能最多保留约 5000 个 token，总量最多约 25000 个 token；超过限制时，较早调用的技能可能被整体丢弃。技能文件截断时优先保留开头，因此关键约束应放在 SKILL.md 前部。

这里有一个关键区别：

> *1）写在对话里的要求：可能被摘要遗漏；*
> *2）写在根目录 CLAUDE.md 里的要求：压缩后重新读取；*
> *3）写在代码、测试、Git 和设计文档里的状态：可以从外部环境重新验证。*

所以 Claude Code 的可靠长期运行并不只是依赖摘要，而是依赖“上下文摘要 + 项目文件 + Git 状态 + 测试结果”共同恢复任务状态。

# 五、压缩摘要存在于哪里？

> 它同时存在于三个层次。

## 1. 磁盘层：当前会话的 JSONL

> *把摘要和压缩边界追加进<u style="text-decoration-color: #e63946">原会话转录</u>*

- 最主要的持久化位置仍然是：
- `~/.claude/projects/<project>/<session-id>.jsonl`
- 一般不会为每次压缩单独创建：
  > *summary.md*
  > *compact.json*
  > *session-summary.json*
- 而是<u style="text-decoration-color: #e63946">把摘要和压缩边界追加进原会话转录</u>。
- 所以它不是自动写进：
  > *CLAUDE.md；*
  > *MEMORY.md，主索引文件（核心入口）*
  > *自动记忆文件，*`memory/*.md`*，主题化记忆文件（补充内容）*
  > *项目任务文档。*
- 这些属于<u style="text-decoration-color: #e63946">另外的持久上下文体系</u>。

## 2. 运行时层：`当前有效会话上下文`

- 压缩完成后，Claude Code 在内存中重建当前有效历史。概念上由：
- 压缩前：`系统上下文 + 原始消息 1～N + 当前新消息`
- 压缩后：`系统上下文 + 重新加载的项目规则 + 压缩摘要+ 压缩后产生的新消息`
- 此时旧消息仍在 JSONL 中，但通常不再逐条发送给模型。
- 也就是说，存在两个不同视图：
  > *持久会话视图：原始历史 + 压缩摘要 + 后续历史*
  > *模型有效视图：压缩摘要 + 后续历史*
- 这正是容易混淆的地方。

## 3. Hook 层：`PostCompact.compact_summary`

- 压缩完成后，Claude Code 会把摘要作为 PostCompact Hook 的输入字段传出：
  > *{*
  > *"session\_id": "abc123",*
  > *"transcript\_path": "/Users/.../.claude/projects/.../session.jsonl",*
  > *"hook\_event\_name": "PostCompact",*
  > *"trigger": "manual",*
  > *"compact\_summary": "Summary of the compacted conversation..."*
  > *}*
- 官方明确说明，compact\_summary 就是本次压缩生成的会话摘要。
- 但这个 Hook 参数本身只是事件输入，不是另一套永久存储。<u style="text-decoration-color: #e63946">只有用户配置 Hook 主动将它写入其他位置时，才会形成额外副本</u>，例如：
  > *1）.claude/audit/compactions.jsonl*
  > *2）docs/tasks/current-state.md*
  > *3）外部数据库*
  > *4）日志系统*

# 六、压缩为什么会导致“失忆”？四种信息损失

> 压缩是`有损的`，主要有四种信息损失。

## 1. 早期细粒度要求被弱化

例如用户最初说：

> *不要修改数据库结构；*
> *不要引入新依赖；*
> *错误码必须与旧版本保持一致。*

经过几十轮开发后，摘要可能只剩下：

> *保持向后兼容。*

`语义方向还在，但约束粒度已经下降`。官方也明确提示，早期对话中的详细指令可能在压缩时丢失，因此<u style="text-decoration-color: #e63946">持久约束应放入 CLAUDE.md。</u>

## 2. 被否决方案重新出现

如果对话中详细比较了方案 A、B、C，最终因为某个隐蔽原因否决方案 B，而摘要只记录“选择方案 A”，那么压缩后 Claude 可能再次提出方案 B，因为它不知道 B 被否决的完整原因。

## 3. 中间因果链断裂

例如：

> *测试失败*
> *→ 怀疑缓存*
> *→ 排除缓存*
> *→ 发现是事务隔离级别*

摘要可能只记录最终结论，不再保留排查路径。后续遇到类似故障时，Claude 可能重复已经排除过的步骤。

> *可以沉淀为 skill，这样之后遇到类似故障，可以根据 skill 来避免重复排查；*

## 4. 当前代码状态与摘要不一致

摘要是<u style="text-decoration-color: #e63946">某一时刻生成的静态文本</u>。压缩后如果外部脚本、用户或其他智能体修改了代码，摘要不会自动同步。因此压缩后 Claude 仍需重新检查：

> *git status*
> *git diff*
> *运行关键测试*

不能把压缩摘要当成项目真实状态的唯一来源。

# 七、压缩前后的 Hook 生命周期

> Claude Code 提供了专门围绕压缩的 Hook

## `PreCompact`，在压缩开始前运行

> 适合在这里执行
> *1）保存当前 git status；*
> *2）导出任务进度；*
> *3）*`将未完成事项写入状态文件`*；*
> *4）记录压缩发生时间；*
> *5）*`备份关键上下文`*。*

- 在压缩开始前运行，区分：
  > *manual：用户执行 /compact；*
  > *auto：系统自动压缩。*
- Hook 输入中包括：
  > *{*
  > *"trigger": "manual",*
  > *"custom\_instructions": "保留接口变更和测试结果"*
  > *}*
  > *// 其中 custom\_instructions 是用户在 /compact 后附加的说明；自动压缩时通常为空。*
- PreCompact 可以阻止压缩。但如果压缩是为了从上下文溢出错误中恢复，阻止压缩会直接使当前请求失败。

## `PostCompact`，压缩完成后运行

> 适合用于：
> *1）审计压缩摘要；*
> *2）将摘要保存到外部日志；*
> *3）分析摘要是否遗漏关键信息；*
> *4）建立<u style="text-decoration-color: #e63946">跨会话任务状态</u>。*

- 压缩完成后运行，输入中包含：
  ```
  {
      "trigger": "manual",
      "compact_summary": "Summary of the compacted conversation..."
  }
  ```
- 它可以读取并记录最终生成的摘要，但不能修改或阻止已经完成的压缩。

## `SessionStart 的 compact 来源`

- 压缩后进入新的上下文阶段时，SessionStart Hook 可以收到：
  > *{*
  > *"source": "compact"*
  > *}*
- 该 Hook 输出到 stdout 的文字可以被重新注入 Claude 上下文。

因此可以设计一套更稳健的恢复链路：
```
PreCompact
    ↓
将进度、约束、Git 状态写入外部状态文件
    ↓
执行压缩
    ↓
PostCompact：记录生成的摘要
    ↓
SessionStart(source=compact)：重新读取状态文件并注入关键内容
```

这比完全依赖 Claude 自己生成的摘要更可靠。

# 八、压缩与另外三种机制的区别

## 压缩 &amp; 提示词缓存

- 提示词缓存解决的是重复计算和费用问题，不减少上下文长度。
- 压缩解决的是容量问题，会改变消息历史。压缩后，由于历史前缀被替换，原有对话层缓存会失效；系统提示词和未变化的项目上下文仍可能继续命中缓存。

## 压缩 &amp; 记忆

- 压缩摘要是当前会话的`临时连续性状态`。
- CLAUDE.md 和自动记忆（MEMORY.md）属于`跨压缩、跨会话的持久信息`，会从磁盘重新加载。
  > *CLAUDE.md 更适合存放规则和架构约束，自动记忆更适合存放 Claude 在使用中发现的构建命令、调试经验和项目模式。*

## 压缩 &amp; 子智能体⭐

- 压缩是在`上下文已经膨胀后做有损治理`。
- 子智能体是在`膨胀发生前进行上下文隔离`。子智能体拥有独立上下文，只把最终摘要返回主会话，因此大规模搜索、日志分析和代码探索不会直接污染主上下文。
- 从上下文工程角度，优先级通常是：
  > *先隔离 → 再控制输入 → 最后压缩*

而不是把所有内容都塞进主会话，等待自动压缩。

# 九、实际开发中的合理用法

对于持续时间较长的编码任务，建议建立三层状态。

第一层是不可丢失规则，放入根目录 CLAUDE.md：
```
# Architecture constraints
- 不修改已有公开接口。
- 禁止直接提交到 main 分支。
- 数据库变更必须生成迁移脚本。
-修改完成后必须运行单元测试和类型检查。

# Compact instructions
压缩时必须保留：
- 当前任务目标；
- 已修改文件；
- 关键设计决策及否决原因；
- 测试结果；
- 尚未解决的问题；
- 用户明确提出的限制。
```

第二层是任务状态，写入项目文件，例如：`docs/tasks/current-task.md`；记录目标、方案、进度、变更文件、测试状态和后续步骤。

第三层是真实执行状态：

> *git status、git diff、pytest*

压缩摘要负责告诉 Claude“之前在做什么”，项目文件负责告诉它“为什么这样做”，Git 和测试负责告诉它“现在真实是什么状态”。

# 十、如何判断应该用 `/compact` 还是 `/clear`

继续处理同一个任务，只是上下文过长时，使用：

> */compact 保留当前方案、代码改动、测试结果和待办*

已经切换到完全无关的新任务时，使用：`/clear`

/compact 会携带旧任务摘要，因此仍然存在历史噪声；/clear 会建立空白对话，但项目级 CLAUDE.md 和记忆仍会重新加载。

官方也建议<u style="text-decoration-color: #e63946">在任务边界清理上下文</u>，而不是长期在一个会话里混合多个无关任务。

---

总体而言，Claude Code 的压缩机制可以概括为：⭐
```
上下文监测
→ 清理旧工具输出
→ 模型生成结构化摘要
→ 用摘要替换对话历史
→ 重载 CLAUDE.md、记忆和部分技能
→ 通过 Hook 补充外部状态
→ 继续智能体循环
```

它解决的是`“有限上下文下如何继续工作”`，但<u style="text-decoration-color: #e63946">不能保证所有历史细节无损保留</u>。

> 真正稳定的长任务，需要<u style="text-decoration-color: #e63946">把关键状态从对话迁移到文件、Git、测试、记忆和 Hook 中</u>，让上下文只承担工作记忆，而不是承担唯一的项目状态。

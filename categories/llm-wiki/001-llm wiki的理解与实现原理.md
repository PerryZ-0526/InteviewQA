# LLM Wiki 的理解与实现原理

## 题目

你如何理解 LLM Wiki？它与传统 RAG 有什么区别，应该如何实现？

## 面试直接答

> LLM Wiki 是 Karpathy 在 2026 年 gist 中提出的<span style="background-color: #fff3cd">知识库组织模式：Agent 按 schema 把不可变原始资料增量编译成一层可浏览、可 lint、可重建的 Wiki</span>，解决传统 RAG 每次查询临时拼碎片、知识无法积累的问题，适用边界是中小规模、以综合阅读为主的个人或团队知识库。

首先说它要解决什么问题。传统 RAG 的流程是把文件上传后切块索引，查询时检索相关片段、现场生成答案。这种方式能用，但模型在每一个问题上都从零重新发现知识：问一个需要综合五份文档的细节问题，每次都要重新找到并拼装相关片段，没有任何积累。LLM Wiki 反其道而行——当新来源加入时，Agent 不是只把它索引起来等检索，而是读取它、抽取关键信息、整合进已有 Wiki：更新实体页面、修订主题总结、标注新数据与旧论断的矛盾，知识被编译一次然后持续保鲜，而不是每次查询重新推导。Karpathy 的原文把这一点概括为 persistent, compounding artifact：交叉引用已经就位、矛盾已经被标注、综合已经反映了读过的所有内容，Wiki 随每个新来源和每个新问题不断变厚。

其次讲三层结构。第一层 Raw Sources 是精选的原始资料，论文、文章、图片、数据文件，只读不可变，Agent 只能读不能改，它是事实的最终依据；第二层 Wiki 是 Agent 生成的 markdown 页面目录，包括总结页、实体页、概念页、对比页、索引页和日志，Agent 完全拥有这一层，负责创建页面、更新内容、维护交叉引用和一致性，人只负责读；第三层 Schema 是告诉 Agent 页面结构和维护约定的配置文件，在 Claude Code 里是 CLAUDE.md、在 Codex 里是 AGENTS.md，它是把 LLM 从通用聊天机器人变成有纪律的 Wiki 维护者的关键配置，并且随使用过程由人和 Agent 共同演化。Karpathy 本人的实践是 Agent 开在一边、Obsidian 开在另一边，Obsidian 相当于 IDE、LLM 是程序员、Wiki 是代码库。

第三讲三个核心操作。Ingest 是摄取新来源：Agent 读取来源、写总结页、更新索引、更新相关实体页和概念页、在日志追加条目，一个来源可能触碰 10 到 15 个页面，可以逐个摄取并保持人工参与，也可以批量摄取减少监督。Query 是问答：先读索引定位相关页面，再下钻具体页面，综合出带引用的答案，有价值的回答还可以写回 Wiki，形成知识复利。Lint 是定期体检：查页面间的矛盾、被新来源取代的过时论断、没有入链的孤儿页、提到却没有独立页面的重要概念、缺失的交叉引用，Agent 还会主动建议值得研究的新问题和新来源。索引文件在中等规模——约百个来源、数百页面——下足够支撑查询，不需要嵌入向量基础设施。

第四讲与传统 RAG 的区别。区别不在于有没有预处理——RAG 同样有摄取、清洗、切分、索引——而在于知识是否被编译沉淀：RAG 在查询时临时检索片段并生成答案，LLM Wiki 在摄取阶段就把知识编译进持久页面，查询是对已积累综合的读取。两者可以组合：Wiki 页面和原始资料都可以成为检索源，gist 里提到规模变大后可以引入 qmd 这类本地混合检索（BM25 加向量加 LLM 重排，同时提供 CLI 和 MCP 接口），但这只是可选工具，不是模式本身的要求。

第五讲实现不是唯一的。gist 明确声明它是抽象的 idea file 而非产品规格，目录结构、页面格式、工具选型都取决于领域和所用的 Agent。开源实现 jackwener/llm-wiki 的形态是 CLI 加四套 Agent skills（ingest、query、lint、research），核心原则是工具本身不调用 LLM，只提供符合 Agent Skills 规范的 SKILL.md 文件，让 Claude Code、Codex 等任何 Agent 来操作 Wiki，Obsidian 作为人类浏览界面。向量库、知识图谱、静态站点都只是可选组件，不是 LLM Wiki 的定义。

最后讲质量与边界。事实可信度来自可追溯引用和原文回查，不来自模型自报置信度，因为置信度通常未校准；冲突也不能简单按「新来源覆盖旧来源」处理，要考虑权威性、生效版本和适用范围。增量更新省成本，但长期在旧生成文本上改写会累积错误，所以系统要保留从原始来源和 schema 重建 Wiki 的能力。这一思想可以追溯到 Vannevar Bush 1945 年的 Memex——关联路径与文档本身同样重要，当年无法解决「谁来承担维护成本」的问题，现在由 LLM 承担了。

## 详细解析

> 版本核验：2026-08-16 直接查证 Karpathy gist 原文与 jackwener/llm-wiki README（main 分支）。

### 一、整体架构图

```text
┌──────────────────────────────────────────────┐
│                Schema / 规则层                 │
│   CLAUDE.md / AGENTS.md：页面结构、命名约定、    │
│   引用规则、Ingest / Query / Lint 工作流        │
└──────────────────────┬───────────────────────┘
                       │ 约束 Agent 的读写行为
┌──────────────────────▼───────────────────────┐
│             Generated Wiki 层（派生物）         │
│  总结页 · 实体页 · 概念页 · 对比页               │
│  index.md（分类索引）· log.md（追加式日志）      │
│  Agent 生成、维护交叉引用、随来源持续更新        │
└──────────────────────┬───────────────────────┘
                       │ 只读，永不修改
┌──────────────────────▼───────────────────────┐
│          Raw Sources 层（真相源，不可变）        │
│  论文 · 文章 · 播客笔记 · 数据文件 · 图片        │
└──────────────────────────────────────────────┘
```

### 二、三层职责表

| 层 | 作用 | 关键约束 |
|---|---|---|
| Raw Sources | 权威原文，事实的最终依据 | 不可变，Agent 只读；来源、时间可追溯 |
| Generated Wiki | 主题化综合页面，人类阅读入口 | 由 Agent 维护；区分事实与推断；可从原文重建 |
| Schema | 页面结构、命名、工作流规则 | 与 Agent 共同演化；决定维护质量 |

### 三、三个核心操作（对应 gist 原文）

**Ingest**：读取来源 → 与用户讨论要点 → 写总结页 → 更新 index → 更新相关实体/概念页 → 追加 log。gist 原文明确「单个来源可能触碰 10~15 个页面」，Karpathy 本人偏好逐个摄取并保持参与（读摘要、检查更新、引导侧重点），也支持批量摄取减少监督，具体工作流由用户在 schema 里固化。

**Query**：先读 index 定位相关页面，再下钻具体页面，综合出带引用的答案；答案形式可以是页面、对比表、幻灯片（Marp）、图表（matplotlib）等。关键洞察是「好的答案可以写回 Wiki」，查询本身也成为知识来源，形成复利。

**Lint**：gist 原文列出的体检项——页面间矛盾、被新来源取代的过时论断、无入链的孤儿页、重要概念缺少独立页面、缺失的交叉引用、可通过检索填补的数据缺口；Agent 还会主动建议值得研究的新问题和新来源。

**索引与日志**：index.md 按类别组织（实体、概念、来源），每次 ingest 更新，查询时先读索引再下钻；gist 明确说这在中等规模（约 100 来源、数百页面）下意外好用，可以避免嵌入式 RAG 基础设施。log.md 是追加式时间线，条目用固定前缀（如 `## [2026-04-02] ingest | Article Title`）时可用 `grep "^## \[" log.md | tail -5` 这类 Unix 命令直接解析。

### 四、与 RAG 的对比

| 维度 | 传统 RAG | LLM Wiki |
|---|---|---|
| 知识沉淀时机 | 查询时现场拼装 | 摄取时编译进页面 |
| 跨文档综合 | 每次重新发现 | 一次性编译、持续保鲜 |
| 可浏览性 | 无（只有检索接口） | 人类可直接读、双向链接成网 |
| 查询路径 | 向量/关键词召回 chunk | 先读索引页，再下钻，必要时回原文 |
| 维护成本 | 索引重建 | 页面级增量更新 + lint 体检 |
| 规模假设 | 大量文档 | 中小规模（约百来源）优先 |

两者可以组合：Wiki 页面与原始资料都可入检索源，Wiki 页面作为「已综合的知识单元」比原文切块更适合语义召回。

### 五、社区实现 jackwener/llm-wiki（源码级）

形态：npm 全局 CLI（`@jackwener/llm-wiki`）+ 四套 Agent skills。核心原则：**工具本身不调用 LLM**，只提供 skill 文件让任何 AI Agent（Claude Code、Codex 等）操作 Wiki，Obsidian 作为人类界面，没有自建 GUI。

Vault 结构：

```text
my-wiki/
├── CLAUDE.md / AGENTS.md        # Agent 启动引导（会话开始自动加载）
├── wiki-purpose.md              # Wiki 范围与受众
├── wiki-schema.md               # 页面类型、命名、frontmatter 规则
├── wiki-log.md                  # 追加式操作日志
├── wiki/                        # AI 维护的页面（Obsidian 兼容）
├── sources/YYYY-MM-DD/          # 不可变原始资料，按日期归档
├── .claude/skills/{ingest,query,lint,research}/SKILL.md
├── .agents/skills/{ingest,query,lint,research}/SKILL.md
└── .llm-wiki/config.toml + sync-state.json
```

四个操作：`/ingest <path>` 读来源→抽实体→用 wikilink 创建/更新页面；`/query <question>` 检索→综合→把有价值洞察写回（知识复利）；`/lint` 健康检查（断链、孤儿页、矛盾、过时内容），安全项自动修复；`/research <topic>` 联网检索→保存来源→ingest→综合报告。CLI 补充命令有 `search`（BM25，配置后叠加 DB9 向量检索）、`graph`（wikilink 图分析：社区、枢纽、孤儿页）、`sync`（mtime + SHA256 变更追踪）。Skills 遵循 Agent Skills 规范（`skills/<name>/SKILL.md` + YAML frontmatter），规范兼容的 Agent 可独立发现。

### 六、面试追问

**追问一：既然摄取时已经把知识编译进页面，为什么查询还要回到原始来源？**

Wiki 页面是「综合层」，价值在压缩与关联，不是替代原文。当问题涉及精确数字、原文措辞、适用条件，或需要验证某个论断时，页面级总结可能丢失细节或混入模型推断，必须下钻原文核对。gist 的 Query 设计正是「先索引后下钻、答案带引用」；这也是 LLM Wiki 与「用模型记忆替代文档」的本质区别——原文永远可回查，Wiki 只是派生物，两者之间必须保持引用边。

**追问二：Wiki 页面全部由模型生成，如何防止幻觉污染知识库？**

三层防线。第一是引用约束：关键断言必须能追溯到 Raw Sources 的具体位置，页面内区分「来源明确的事实」「跨来源归纳」和「模型推断」；第二是 Lint 自动化检查无来源断言、页间矛盾、过时论断，但 lint 只能发现规则化缺陷，不能证明事实正确，高价值页面需要人工抽检和真实查询任务评测；第三是可重建性：Wiki 是派生物，任何可疑页面都可以从原始来源和 schema 重新生成，幻觉造成的污染不是永久性的。本质是把「模型输出」降级为「待验证的候选内容」，最终裁决权留给原文和人工。

**追问三：Karpathy 为什么说中等规模下读索引就够了，什么规模需要换检索方案？**

因为 Wiki 页面已经把知识压缩成主题化单元，索引按实体、概念分类组织，查询先读索引再下钻，路径清晰且上下文干净；在约百个来源、数百页面的规模下，这比「向量召回 chunk 再让模型拼装」更可靠，还省掉了嵌入基础设施。规模膨胀到索引读不完、或需要模糊语义召回时，才引入 qmd 这类 BM25 加向量的本地混合检索；注意此时检索对象变成了 Wiki 页面而非原始 chunk，语义质量比原文切块更高，这是 Wiki 层的额外收益。

**追问四：增量更新省成本，为什么还要保留全量重建能力？**

每次 ingest 只改受影响页面，但模型每次改写都可能引入微小偏差——措辞漂移、上下文丢失、旧错误被沿用——长期累积后 Wiki 与「从原文直接重建」的结果会出现系统性偏离。重建能力是纠偏机制：定期或按需从 Raw Sources 加 schema 重新生成部分或全部页面，与增量版本 diff，发现漂移就修复。gist 没有强制规定重建频率，但「增量更新 + 可重建」缺一不可，只增量不重建的知识库最终会变成模型的自我引用循环。schema 或生成器升级时同理：记录哪些页面仍是旧版本，按访问热度和风险分批迁移，而不是一次性重写全部页面。

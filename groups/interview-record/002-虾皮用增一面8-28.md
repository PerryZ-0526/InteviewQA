## 部分题目解析

### 1、什么情况下用多智能体

> 多智能体不是为了“多”，而是<u style="text-decoration-color: rgb(230, 57, 70)">在任务存在明显的职责分解、上下文隔离、并行执行或权限隔离需求时使用</u>。如果一个智能体能够稳定、低成本地完成任务，就没有必要为了架构复杂度再拆多个智能体。

### 我判断是否使用多智能体，首先看任务能不能形成`几个相对独立的认知单元`

比如做一个复杂研究任务，可能同时需要查论文、分析代码、检索行业数据，最后再综合判断。这几个<u style="text-decoration-color: #e63946">子任务需要的工具、提示词和关注点明显不同</u>，那么可以分别交给研究智能体、代码智能体和检索智能体，最后由一个协调者汇总。这里拆分的核心不是“领域名字不同”，而是每个子任务是否具有<u style="text-decoration-color: #e63946">相对独立的输入、执行过程和可验收输出</u>。

> 如果几个所谓智能体实际上始终共享同一份上下文、使用同样的工具、做高度耦合的推理，那拆开通常只是形式上的多智能体。

### 第二种重要场景是`上下文隔离`

复杂 Agent 最容易出现的问题之一就是上下文污染。例如代码检索过程中可能读取几十个文件，在线研究可能产生大量网页内容。如果全部塞进主智能体，上下文会迅速膨胀，而且大量中间过程最终并不需要保留。可以让子智能体在自己的上下文里完成探索，只把“结论、证据和产物”返回主智能体。这样多智能体本质上承担了一部分上下文管理作用。

### 第三种情况是`并行性`

如果几个任务不存在前后依赖，比如同时调查三个技术方案，就可以让多个智能体并发工作，把端到端耗时从三个任务之和降低到接近最慢那个任务的耗时。但如果任务高度串行，例如必须先确定数据库结构才能写接口，再根据接口写前端，那么拆成多个智能体并不会产生真正的并行收益。

### 另外还有一个很重要但经常被忽略的原因，就是`权限和能力隔离`

比如一个研究智能体只允许 Web Search，一个代码审查智能体只允许 Read/Grep，一个执行智能体才具有 Write、Bash 或数据库写权限。<u style="text-decoration-color: #e63946">此时多智能体不仅是任务拆分，也是安全边界</u>。

所以我不会以“任务复杂”作为唯一判断标准。我的判断一般是：这个任务是否存在独立子目标、不同上下文、不同工具权限，或者可以获得明显并行收益。如果这些条件都没有，优先单智能体；只有拆分能够降低复杂度，而不是把复杂度从模型内部转移到系统编排层，我才会使用多智能体。

### 2、多智能体效果一定比单智能体更好吗

> 不一定。多智能体提升的是<u style="text-decoration-color: rgb(230, 57, 70)">复杂任务的组织能力</u>，而不是模型本身的智力。它可能提高覆盖率、并行度和上下文利用率，也可能引入通信损耗、错误传播、重复推理和额外成本，因此必须通过任务评测决定是否值得拆分。

#### 多智能体最容易产生的误解，就是认为多个模型一起工作等价于“能力叠加”

实际上，如果几个智能体使用的是同一个模型，它们并没有凭空获得更强的基础推理能力，只是<span style="background-color: rgb(255, 243, 205)">把一次复杂推理<u style="text-decoration-color: rgb(230, 57, 70)">重新组织</u>成</span>`多次相对独立的推理`<span style="background-color: rgb(255, 243, 205)">。</span>

> 它<u style="text-decoration-color: rgb(230, 57, 70)">真正可能带来的收益</u>主要来自`任务分解`、`上下文隔离`、`角色专业化`、`并行探索`以及`交叉验证`，而不是 Agent 数量本身。

例如一个复杂调研问题，让单智能体同时查十几个来源、比较方案、做最终判断，<u style="text-decoration-color: rgb(230, 57, 70)">很容易因为上下文过长而遗漏信息。</u>拆成三个研究智能体分别调查不同方向，再由主智能体汇总，覆盖率可能明显提高。但如果只是一个简单数据库查询，却先让规划智能体分析、再让数据库智能体查询、再让审核智能体验证、最后让总结智能体回答，那么原本一次模型调用能够完成的问题变成四五次调用，质量未必提高，延迟和成本却明显增加。

#### 更麻烦的是，多智能体会产生`新的系统性误差`

单智能体的错误主要发生在一次推理内部，而<u style="text-decoration-color: rgb(230, 57, 70)">多智能体还增加了任务拆分错误、信息传递损失、状态不一致和错误级联</u>。例如第一个智能体产生了错误事实，第二个智能体把这个事实当成可信输入继续推理，最后协调者可能因为多个智能体表面上“意见一致”而更加确信错误结论。因此生产系统中不能把子智能体输出默认视为事实，最好保留来源和证据，由上层进行验收。

#### 从工程角度，我更倾向于采用`“最小充分架构”`

先用单智能体建立基线，如果发现问题主要来自上下文过长、跨领域任务混杂、工具权限冲突或者存在可并行的独立任务，再逐步拆分。拆完以后不能凭主观感觉说效果更好，而应该比较任务成功率、答案正确率、工具调用正确率、端到端延迟、Token 成本以及失败恢复能力。

所以面试中如果问我“多智能体是不是高级架构”，我的回答会是否定的。单智能体和多智能体不是简单的上下级关系，而是两种任务组织方式。对于边界清晰、工具较少、流程较短的任务，单智能体往往更稳定；只有当拆分带来的专业化、隔离和并行收益大于协调成本时，多智能体才真正有价值。

### 3、在线信息检索的 ReAct，再一次检索怎么判断

> ReAct 是否继续检索，本质上是在<u style="text-decoration-color: rgb(230, 57, 70)">每轮 Observation 后判断“现有证据是否足够回答问题”</u>。
>
> 生产环境不能只依赖模型一句“我觉得够了”，通常会结合`信息覆盖度`、`来源质量`、`时效性`、`冲突情况`和`最大检索轮数`共同决定。

ReAct 的基本过程是<u style="text-decoration-color: rgb(230, 57, 70)">模型根据当前状态决定 Action</u>，例如发起一次 Search，拿到搜索结果作为 Observation，然后再进行下一轮判断。所以所谓“第二次检索什么时候触发”，并不是预先规定一定检索几次，而是模型发现当前 Observation 无法充分支持最终回答时，再生成新的 Search Action。

#### 我一般会<span style="background-color: rgb(255, 243, 205)">把“信息是否充分”拆成几个判断维度</span>

1. 首先是`问题覆盖度`。假设用户问“LangGraph 和 Claude Agent SDK 在状态管理、权限控制和多智能体方面有什么区别”，第一次搜索只找到了 LangGraph 的状态管理文档，那么虽然已经有相关信息，但问题的三个核心维度没有覆盖完整，因此应该继续检索。
2. 其次看`证据质量`，如果第一次只搜到博客、论坛或者搜索摘要，而问题涉及官方 API 行为，那么应该继续寻找官方文档。
3. 第三是`时效性`，例如用户问“目前 Claude Agent SDK 的权限机制”，结果却来自一年以前的 Claude Code SDK 文档，也需要重新检索。

#### 还有一个很重要的触发条件是`信息冲突`

如果两个来源给出的结论不同，不能简单选择一个，而应该<span style="background-color: rgb(255, 243, 205)">继续搜索更权威或者更新的来源进行裁决</span>。另外，第一次搜索可能发现原始 Query 写得不好，这时第二次并不是机械重复搜索，而是 `Query Rewrite`。例如第一次搜索“Claude Skill permission”，发现真正需要确认的是“Skill 中 allowed-tools 与 Agent SDK allowedTools 的区别”，那么<u style="text-decoration-color: rgb(230, 57, 70)">下一轮 Query 应该针对这个缺口进行定向搜索</u>。

#### 生产系统里我通常不会完全依赖 ReAct 自己无限循环，而会增加一个`显式的检索充分性判断`，可以由规则加 LLM 完成

让模型输出当前已经确认了什么、还缺什么、已有证据是否足够。如果缺少关键事实，就生成下一轮查询；如果已经满足问题覆盖、来源可信和时效要求，就进入 Answer。同时设置最大检索轮数，例如三到五轮，避免因为模型不断追求“更多证据”造成无限搜索。

> 因此在线检索 ReAct 的<u style="text-decoration-color: rgb(230, 57, 70)">退出标准不是“搜索到了内容”，而应该是“搜索到的证据已经足以支持回答</u>”。这是两件完全不同的事情。一个成熟的检索 Agent 应该`以信息缺口驱动下一次搜索`，而不是简单按照固定次数搜索。

### 4、LangGraph 和 Claude Code SDK 的差异

> LangGraph本质上是`显式的智能体编排运行时`，而原 Claude Code SDK、现在的 `Claude Agent SDK`，更接近一套已经实现好的 Agent Harness。前者强调“你怎么组织智能体”，后者强调“直接获得一个成熟智能体运行环境”。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview?utm_source=chatgpt.com "LangGraph overview - Docs by LangChain"))

首先需要纠正一下名称。

Claude Code SDK 在 2025 年已经正式更名为 `Claude Agent SDK`，因为它已经<u style="text-decoration-color: rgb(230, 57, 70)">不再局限于代码场景</u>。它把 Claude Code 中成熟的 Agent Loop、文件操作、Bash、上下文管理、Session、Subagent、Hook、MCP 和权限系统以 Python/TypeScript SDK 的形式暴露出来。也就是说，你调用 SDK 后，<u style="text-decoration-color: rgb(230, 57, 70)">并不需要自己重新实现一个“LLM → Tool Call → Observation → LLM”的完整循环</u>。([Claude](https://code.claude.com/docs/en/agent-sdk/migration-guide?utm_source=chatgpt.com "Migrate to Claude Agent SDK - Claude Code Docs"))

LangGraph解决的问题不一样。

官方把它定位成面向`长时间、状态化智能体`的`低层编排运行时`，核心是 State、Node、Edge、条件分支、持久化、可恢复执行以及 Human-in-the-loop。也就是说，LangGraph不会替你规定 Agent 应该怎么思考，你需要自己设计图：<u style="text-decoration-color: rgb(230, 57, 70)">什么时候调用规划节点，什么时候进入某个 ReAct 子图，什么条件返回 Supervisor，什么条件结束</u>。它给你的核心能力是“控制”。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview?utm_source=chatgpt.com "LangGraph overview - Docs by LangChain"))

所以两者最重要的区别是抽象层不同。

用 LangGraph，我可以明确设计 `context_builder → orchestrator → domain_agent → reviewer → answer`，每一个节点输入输出什么 State、什么时候循环、什么时候 checkpoint 都可以控制。这非常适合业务流程复杂、需要状态持久化、故障恢复和可解释编排的系统。但代价是工程量比较大，Agent Loop、状态结构和退出条件需要自己设计。

Claude Agent SDK 更像直接给我一个`经过大量工程优化的 Agent Harness`。

比如我要做一个`代码研究 Agent`，可以直接开放 Read、Glob、Grep、Bash，让 Claude 自己完成多轮工具调用，而且权限、Hooks、Skills、Subagents 和上下文管理已经存在。官方 SDK 本身就支持通过 allow/deny、permission mode 和 hooks 控制执行。([Claude](https://code.claude.com/docs/en/agent-sdk/permissions?utm_source=chatgpt.com "Configure permissions - Claude Code Docs"))

因此我不会简单说哪个更好。

如果我要构建一个`复杂业务工作流`，比如教育智能体，需要多个领域 Agent、显式状态、审核、重规划和人工介入，我更倾向 LangGraph；如果我要<u style="text-decoration-color: rgb(230, 57, 70)">快速构建一个具有很强自主工具使用能力的研究 Agent</u>、Coding Agent 或自动化 Agent，Claude Agent SDK 的开发成本明显更低。

甚至两者也可以组合：LangGraph负责`顶层业务编排`，每个复杂执行节点内部运行一个成熟的 `Agent Harness`。它们本质上解决的是两个层次的问题。

### 5、Skill 中脚本的权限

> Skill 本身不是一个独立安全沙箱。脚本最终通常通过 Bash 等工具运行，所以<u style="text-decoration-color: rgb(230, 57, 70)">真正控制执行权限的是 Agent 的工具权限系统和底层操作系统权限</u>。
>
> 尤其要区分 Claude Code 与 Claude Agent SDK，两者对 Skill 的 `allowed-tools` 处理不同。

Claude Code 的 Skill 本质上是一个 `SKILL.md` 加上一些可选资源文件，可以包含 reference、examples，也可以在 `scripts/` 下放 Python、Shell 等脚本。Skill 告诉 Claude“什么时候以及怎样执行这套能力”，<u style="text-decoration-color: rgb(230, 57, 70)">真正运行脚本时仍然需要借助 Bash 等执行工具</u>。例如一个 Skill 要执行 `python3 scripts/analyze.py`，实际上就是调用 Bash，因此 Bash 是否允许才是第一层权限控制。

> 官方也明确支持在 Skill 的 `allowed-tools` 中声明诸如 `Bash(git *)` 这样的权限。([Claude](https://code.claude.com/docs/en/slash-commands?utm_source=chatgpt.com "Extend Claude with skills - Claude Code Docs"))

这里很容易理解错：`allowed-tools` 的含义是<u style="text-decoration-color: rgb(230, 57, 70)">“Skill 激活期间，这些工具可以免确认执行”</u>，而不是“Skill 只能使用这些工具”。没有写在里面的工具仍然可能被调用，只不过继续按照全局 permission 配置进行判断。所以真正想禁止某些操作，需要配置 `deny rule`，而不能只依赖 allowed-tools。比如允许 `Bash(git status *)`，同时明确禁止 `Bash(git push *)`。官方权限规则支持按具体 Bash 命令进行模式匹配。([Claude](https://code.claude.com/docs/zh-CN/skills?utm_source=chatgpt.com "使用 skills 扩展 Claude - Claude Code Docs"))

这里还有一个非常值得面试时主动讲的差异：如果是 Claude Agent SDK，`SKILL.md` 里面的 `allowed-tools` 当前并不会作为 SDK 的权限控制生效。SDK 场景应该通过外层 `allowedTools`、`disallowedTools`、permission mode 或 `canUseTool` 来控制。官方甚至明确说明，SDK 的 Skill 列表主要是上下文和可发现性过滤，并不是安全沙箱。即使某个 Skill 没暴露给模型，它的文件如果仍在磁盘上，也可能通过 Read 或 Bash 被访问。([Claude](https://code.claude.com/docs/en/agent-sdk/skills?utm_source=chatgpt.com "Agent Skills in the SDK - Claude Code Docs"))

再往下一层，即使 Agent 允许执行 Bash，脚本也不是无限权限。它仍然<u style="text-decoration-color: rgb(230, 57, 70)">受运行进程本身的操作系统权限、容器、文件系统挂载、网络策略和云凭证权限限制</u>。

> 因此生产环境最好形成两层甚至三层防护：Agent 层限制“模型允许调用什么工具”，<span style="background-color: rgb(255, 243, 205)">运行环境限制“即使调用了这个工具，它实际上能够访问什么资源”。</span>

所以我的理解是，Skill负责封装能力和工作流，而不应该承担最终安全边界。安全边界应该放在 Skill 外部，由工具权限、Hooks、容器和基础设施共同保证。

### 6、Agent 的权限控制是怎么做的

> Agent 权限控制不能只靠提示词说“不要做危险操作”，而应该<u style="text-decoration-color: rgb(230, 57, 70)">在模型之外建立强制执行边界</u>。我通常从工具暴露、调用规则、参数范围、资源权限、沙箱、人工审批和审计七个层面做最小权限控制。

#### 首先最基础的一层，是<u style="text-decoration-color: rgb(230, 57, 70)">决定模型究竟能看到哪些工具</u>

如果一个 Agent 只负责知识查询，就根本没有必要给它数据库写入、Shell 或文件修改能力。相比于“给所有工具，然后告诉模型不要乱用”，直接不暴露危险工具要可靠得多。这属于能力层面的`最小权限原则`。

#### 第二层是工具调用权限

即使暴露了 Bash，也不代表所有 Bash 命令都应该允许。例如 Claude Agent SDK 支持 allow、deny 和 permission mode，权限判断还可以结合 Hooks 与 `canUseTool`。可以允许 `git status`、`pytest`，禁止 `rm`、`git push`，对于没有匹配规则的操作再请求用户确认。官方当前的权限顺序中，Hooks 和 deny 可以在真正执行前阻断操作。([Claude](https://code.claude.com/docs/en/agent-sdk/permissions?utm_source=chatgpt.com "Configure permissions - Claude Code Docs"))

#### 第三层要做到`参数级权限`，而不是只控制工具名

例如数据库工具可以开放 `query_user_profile`，但不<u style="text-decoration-color: rgb(230, 57, 70)">能让 Agent 自由拼任意 SQL</u>；文件读取可以限制工作目录；<u style="text-decoration-color: rgb(230, 57, 70)">Web 工具可以限制允许访问的域名</u>；付款工具可以限制金额和目标账户。

> 也就是说，我更希望把一个“大权限工具”拆成若干语义明确的小工具。

#### 第四层是基础设施权限

这一点非常重要，因为 <span style="background-color: rgb(255, 243, 205)">Agent 层的权限永远不应该成为最后一道防线</span>。即使模型成功调用 Bash，进程也应该运行在容器或受限账户中，只挂载必要目录，只提供必要环境变量，<u style="text-decoration-color: rgb(230, 57, 70)">数据库账号只具有对应表的最小权限</u>。这样即使 Prompt Injection 或 Agent 判断错误突破了模型层，影响范围仍然有限。Anthropic 的安全文档也明确建议对敏感数据和操作采用最小权限和沙箱隔离。([Claude Platform Docs](https://docs.anthropic.com/ko/docs/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks?utm_source=chatgpt.com "탈옥 및 프롬프트 인젝션 완화 - Claude Platform Docs"))

#### 再往上是`高风险操作的人机协同`

例如发送邮件、支付、删除数据、发布代码这类不可逆操作，我通常设计成“Agent负责生成 Action Plan，人负责 Approve，Executor 才真正执行”，而不是让模型同时拥有决策权和执行权。

#### 最后是审计

所有工具调用至少应该记录 Agent、工具名、参数、时间、结果以及授权方式。Hooks 很适合做这一层，因为它可以在工具执行前校验，在执行后记录。([Claude](https://code.claude.com/docs/en/agent-sdk/agent-loop?utm_source=chatgpt.com "How the agent loop works - Claude Code Docs"))

> 所以如果让我概括，我认为 Agent 权限控制的关键原则是：提示词只负责告诉模型“应该做什么”，真正的权限系统负责决定模型“实际上能做什么”。安全边界必须位于模型之外。

### 7、CLAUDE.md 中放什么

> CLAUDE.md 应该放“`Claude 每次进入这个项目都应该知道的稳定事实和规则`”，例如`项目结构`、`开发命令`、`代码规范`和`关键架构约束`，而不是把所有项目文档、临时任务和复杂操作流程全部塞进去。

#### 我一般把 CLAUDE.md 理解成`项目级的长期工作说明`，而不是知识库

因为 Claude Code 每次会话都是新的上下文，CLAUDE.md 的作用就是<u style="text-decoration-color: rgb(230, 57, 70)">把那些每次都需要重新解释的信息自动加载进来</u>。官方建议放入项目架构、构建和测试命令、编码规范、命名约定以及常见工作流，例如“后端使用 FastAPI”“运行测试使用 `pytest tests`”“业务代码禁止直接访问数据库，必须经过 repository 层”这种稳定约束。([Claude](https://code.claude.com/docs/en/memory?utm_source=chatgpt.com "How Claude remembers your project - Claude Code Docs"))

我判断一条信息要不要进入 CLAUDE.md，有一个很简单的标准：如果换一个新的 Claude Code 会话，我<u style="text-decoration-color: rgb(230, 57, 70)">是否还希望它从第一分钟就知道这件事</u>。如果答案是肯定的，就比较适合。例如项目有哪些`核心目录`、哪个模块是`入口`、修改数据库模型以后必须生成 migration、<u style="text-decoration-color: rgb(230, 57, 70)">提交之前必须执行哪些测试</u>，这些都属于长期稳定信息。

#### 反过来，CLAUDE.md 不适合放大量详细文档

因为它会进入上下文，本质上占 Token，而且内容越长，模型对每条规则的遵循效果反而可能下降。官方目前建议尽量保持简洁，<u style="text-decoration-color: rgb(230, 57, 70)">目标可以控制在约 200 行以内</u>。

- 对于只在特定目录生效的规则，可以放到 `.claude/rules/`；
- 对于一个`完整的多步骤操作流程`，比如“如何发布服务”“如何执行数据库迁移并验证”，更适合做成 Skill，让 Claude 真正需要的时候再加载。([Claude](https://code.claude.com/docs/en/memory?utm_source=chatgpt.com "How Claude remembers your project - Claude Code Docs"))

#### 另外还要区分 CLAUDE.md 和自动记忆

CLAUDE.md 是`开发者主动定义的规范`，而 Auto Memory 是 Claude 在使用过程中积累的经验，例如“这个项目运行集成测试之前必须启动 Redis”“这个模块曾经出现过某种调试问题”。官方现在就是把两者作为互补机制：

- CLAUDE.md 管人为规定的稳定规则，Auto Memory 管`运行过程中逐渐发现的经验`。([Claude](https://code.claude.com/docs/en/memory?utm_source=chatgpt.com "How Claude remembers your project - Claude Code Docs"))

> 所以我通常不会在 CLAUDE.md 里写“整个项目是怎样实现的”，而是写`“为了正确修改这个项目，你必须长期知道什么”`。它应该更像给一个新加入项目的高级开发者准备的`一页工作约定`，而不是一份几十页的项目百科。

### 8、MCP Client 和 MCP Server 间的通信方式是什么？

> MCP 在协议层使用 `JSON-RPC` 2.0 定义消息格式，在传输层主要支持 stdio 和 Streamable HTTP。前者适合本地进程通信，后者适合远程服务。面试时要把“消息协议”和“传输方式”区分开。

### MCP Client 和 MCP Server 的通信可以分成两层来看

第一层是协议层，MCP 本身使用 JSON-RPC 来描述请求、响应和通知，例如 Client 调用 Server 暴露的某个 Tool，本质上会发送一条带有 method、params 和 id 的 JSON-RPC Request，Server 执行后再返回对应 id 的 Response。所以 MCP 并不是自己重新设计了一套二进制 RPC 协议，而是在 JSON-RPC 上定义了工具发现、资源读取、提示词获取等语义。([Model Context Protocol](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports?utm_source=chatgpt.com "Transports - Model Context Protocol"))

第二层才是传输层。目前标准的两种主要 Transport 是 stdio 和 Streamable HTTP。stdio 主要用于本地 MCP Server，由 Client 启动 Server 子进程，然后 Client 往 Server 的 stdin 写 JSON-RPC 消息，Server 从 stdout 返回消息。比如 Claude Code 启动一个本地 Python MCP Server，就非常适合这种方式。它的优势是实现简单、不需要监听端口，而且进程生命周期天然由 Client 管理。([Model Context Protocol](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports?utm_source=chatgpt.com "Transports - Model Context Protocol"))

如果 MCP Server 是独立部署的远程服务，则通常使用 Streamable HTTP。Client 通过 HTTP POST 向 MCP Endpoint 发送 JSON-RPC 请求，Server 可以直接返回普通 HTTP Response，也可以通过 SSE 进行流式响应；必要时 Client 还可以通过 GET 建立 SSE 通道接收 Server 主动发送的通知。这里需要注意，早期 MCP 的标准传输叫 HTTP+SSE，而现在已经由 Streamable HTTP 取代，因此面试中最好不要只回答“stdio 和 SSE”。([Model Context Protocol](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports?utm_source=chatgpt.com "Transports - Model Context Protocol"))

### 通信开始后还有一层 MCP 自己的生命周期协议

Client 首先 initialize，与 Server 协商协议版本以及双方支持的能力，然后再调用 `tools/list`、`resources/list` 等接口发现能力，之后才执行 `tools/call` 等操作。因此我会把 MCP 理解为：JSON-RPC 负责消息格式，stdio/Streamable HTTP 负责消息怎么送过去，而 MCP Specification 负责双方具体能够说什么、按照什么生命周期交互。

### 9、LangGraph 适合做 ReAct 吗？

> 适合，而且 ReAct 本身就是 LangGraph 非常典型的应用，但如果只是最基础的 ReAct，没有复杂状态和流程控制，现在直接使用 LangChain 的 `create_agent` 更合适；复杂 ReAct 再下沉 LangGraph。

ReAct 本质上是一个循环：模型根据当前上下文进行判断，决定调用某个 Tool，获得 Observation 后重新交给模型判断，直到模型认为信息足够并产生 Final Answer。从结构上看，它天然就是一个带条件边的状态图，因此 LangGraph 很适合表达这种过程。官方对 Agent 的描述也是模型不断在“LLM 决策—工具调用—结果反馈”之间循环，直到满足退出条件。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/workflows-agents?utm_source=chatgpt.com "Workflows and agents - Docs by LangChain"))

如果自己用 LangGraph 实现，通常会有一个 Agent Node 调 LLM。如果模型产生 `tool_calls`，就通过条件边进入 Tool Node；工具执行结果写回 messages，然后重新进入 Agent Node；如果没有 tool\_call，就走 END。这实际上就是最基础的 ReAct Loop。

> LangGraph 的优势在于这个循环并不是黑盒，你可以控制 State、循环次数、工具执行、Checkpoint、人机审批以及异常恢复。

不过这里有一个比较新的版本变化值得面试时提出来。

LangGraph 1.0 以后，原来的 `langgraph.prebuilt.create_react_agent` 已经被弃用，官方推荐使用 LangChain 的 `create_agent`，而 `create_agent` 底层仍然运行在 LangGraph 上。也就是说，如果我要的只是标准的“模型 + Tools + ReAct Loop”，我不会再自己搭一张 LangGraph 图，而是直接使用 `create_agent`。([Docs by LangChain](https://docs.langchain.com/oss/python/migrate/langgraph-v1?utm_source=chatgpt.com "LangGraph v1 migration guide - Docs by LangChain"))

真正需要直接使用 LangGraph 的场景，是 <u style="text-decoration-color: rgb(230, 57, 70)">ReAct 外面还有更复杂的控制</u>。例如我要让一个检索 ReAct 执行完以后进入 Reviewer，Reviewer 发现证据不足再返回 ReAct；或者工具执行前需要人工审批；或者不同领域使用不同 ReAct 子图；再比如执行到一半需要持久化状态，服务重启以后继续执行。这时候 LangGraph 的 State、Conditional Edge、Checkpoint 和 Interrupt 才真正体现价值。

所以我的判断不是“LangGraph 能不能做 ReAct”，而是“这个 ReAct <u style="text-decoration-color: rgb(230, 57, 70)">是否复杂到值得显式建图</u>”。简单 ReAct 用高层 Agent API，`复杂的、有状态、有审批和多阶段编排的 ReAct` 再直接使用 LangGraph，这样工程复杂度会比较合理。

### 10、谈谈你对 Agent 沙箱的了解

摘要：Agent 沙箱的核心不是告诉模型“不要执行危险操作”，而是在操作系统或容器层给 Agent 划定真实的执行边界，限制文件、网络、进程、凭证和资源，即使模型被提示注入，也无法越过这层边界。

Agent 一旦拥有 Bash、Python、文件读写甚至浏览器工具，就已经不再只是生成文本，而是在执行真实代码。这时候仅靠 Tool Permission 是不够的。Permission 解决的是“模型是否允许调用 Bash”，Sandbox 解决的是“即使 Bash 已经运行，它实际能够碰到什么”。我认为这是理解 Agent 沙箱最关键的区别。

最典型的沙箱是给每个 Agent 任务创建一个隔离执行环境，可以是 Container、轻量虚拟机或者基于操作系统 Namespace 的隔离环境。文件系统方面，只挂载当前 Workspace，并设置只读和可写目录，例如允许修改 `/workspace`，但不能读取 SSH Key、浏览器 Cookie 或宿主机配置。网络方面默认限制外部访问，只允许访问 GitHub、公司 API 等白名单域名，避免 Prompt Injection 成功以后把敏感文件上传到攻击者服务器。

再进一步还要限制进程能力和系统资源。例如禁止 privileged、限制系统调用、限制 CPU、内存、磁盘和最长执行时间，同时对 Secret 做最小化注入。Agent 如果只是需要访问一个数据库，就只给一个低权限短期 Token，而不是把整个云账号 Access Key 放进环境变量。对于高风险 Agent，我还倾向于任务结束后直接销毁 Sandbox，下一次任务重新创建，从而避免不同任务之间的状态污染。

Claude Code 的实现就是一个很典型的例子。它的 Sandbox 同时做文件系统和网络隔离，在 macOS 使用 Seatbelt，在 Linux/WSL2 使用 bubblewrap，而且这种限制作用于 Bash 创建出来的所有子进程。官方也明确区分了 Permission 和 Sandbox：Permission 先决定某个 Tool 能不能运行，Sandbox 再从 OS 层限制运行以后能够访问的资源。([Claude](https://code.claude.com/docs/en/sandboxing?utm_source=chatgpt.com "Sandboxing - Claude Code Docs"))

所以我的安全模型通常是“Permission + Sandbox + IAM + Human Approval”。模型权限负责第一层工具控制，Sandbox 限制执行环境，基础设施 IAM 限制真实资源权限，不可逆操作再增加人工审批。这种设计的价值就在于，即使 Agent 判断错误或者遭遇 Prompt Injection，也只能在一个有限的爆炸半径内出错。

### 11、怎么做 Agent 评测？

> Agent 评测不能只看最终答案，而应该同时评价`任务结果`、`执行过程`和`工程指标`。我一般采用离线数据集回归加线上监控，从任务成功率、工具调用、轨迹质量、安全性、延迟和成本几个维度综合评价。

传统 LLM 的评测往往是 Input 到 Output，但 Agent 中间还存在规划、检索、工具调用、状态修改等过程。所以我首先会把评测分成两层：Outcome Evaluation 和 Trajectory Evaluation。Outcome 解决“最后任务有没有完成”，Trajectory 解决“任务是不是用正确、可靠的方式完成”。例如一个邮件 Agent 最后确实生成了正确回复，但是过程中错误调用了五次搜索、访问了无关邮箱甚至尝试执行发送，这个 Agent 仍然不能算表现良好。

离线评测首先要建立具有代表性的 Dataset。里面除了正常 Case，还应该覆盖边界情况、工具异常、多轮任务、信息不足、Prompt Injection 等失败场景。如果任务有明确答案，可以使用 Exact Match、规则函数或者业务系统返回结果；对于开放回答，可以用人工评分或者 LLM-as-a-Judge，评价正确性、完整性和事实一致性。Agent 具有随机性，所以重要 Case 最好重复执行多次，看成功率而不是只跑一次。

第二类是工具和执行指标，例如 Tool Selection Accuracy、参数正确率、任务成功率、无效调用率、重试次数和循环率。如果一个 Agent 最终答案正确，但是原本两次 Tool Call 能完成，却调用了十五次，也要在效率指标中被惩罚。同时还要记录端到端延迟、Token 消耗和工具调用成本，因为线上 Agent 最终一定是效果、延迟和成本的综合优化问题。

第三层是安全评测，例如 Agent 是否越权调用工具、能否抵抗 Prompt Injection、遇到高风险操作是否正确触发审批、工具失败之后是否安全退出。对于生产系统，这些指标往往比“回答听起来好不好”更重要。

最后我会形成“离线评测—上线—线上 Trace 监控—收集失败样本—重新加入 Dataset”的闭环。Langfuse 当前的评测思路也是类似的：生产 Trace 可以被评分，典型失败样本沉淀成 Dataset，再通过 Experiment 对新模型、新 Prompt 或新 Agent 版本做回归测试。([Langfuse](https://langfuse.com/docs/evaluation/overview?utm_source=chatgpt.com "Evaluation of LLM Applications - Langfuse"))

所以 Agent 评测的核心并不是寻找一个统一总分，而是建立一组与业务失败模式对应的指标，最终回答三个问题：任务完成了吗、完成方式正确吗、完成代价是否可以接受。

### 12、怎么测 Agent 的执行轨迹？

摘要：轨迹评测评价的不是模型隐藏的思维过程，而是可观察的执行行为，包括调用了什么工具、参数是什么、先后顺序怎样、是否重复调用、状态如何变化，以及这些步骤是否合理高效。

我首先会明确一个概念：Agent Trajectory 不应该理解成模型内部 Chain of Thought，而是系统真正能够记录的外部执行轨迹。例如 `用户请求 → search → search result → read_document → result → generate_answer`，以及每一次 Tool Call 的工具名、参数、返回结果和状态变化。我们评测的是这些可观察行为。

最简单的方法是 Reference Trajectory，也就是为一个测试 Case 给出期望执行路径，然后与实际路径进行匹配。对于严格业务流程，例如“查询余额之前必须先身份验证”，可以要求严格顺序匹配。但很多 Agent 任务存在多条正确路径，因此不能所有任务都做 Exact Match。例如查一个信息，Agent 可以先 Search A 再 Search B，也可以反过来，这时候更适合只检查关键工具是否都调用了。

目前 AgentEvals 就提供了几种典型思路，包括 strict、unordered、subset 和 superset。strict 要求调用序列完全一致，unordered 只要求工具集合相同，subset 可以判断 Agent 有没有调用参考范围之外的无关工具，superset 则可以验证几个必要工具是否至少都调用过。([Docs by LangChain](https://docs.langchain.com/langsmith/trajectory-evals?utm_source=chatgpt.com "How to evaluate your agent with trajectory evaluations - Docs by LangChain"))

但只比较工具名称还是不够，因为 `search("正确关键词")` 和 `search("完全错误的关键词")` 虽然 Tool 一样，质量差别很大。因此更完整的 Trajectory Eval 还要检查 Tool Arguments、Observation 使用情况、重复调用次数和状态转移。我通常会定义几个指标，例如必要工具召回率、无关工具调用率、参数正确率、平均步骤数、循环次数和失败恢复成功率。

对于开放式 Agent，我不会强制指定 Reference Path，而是用 LLM-as-a-Judge 把完整的可观察轨迹交给 Judge，询问它几个具体问题：每一步是否有必要、工具选择是否合理、是否遗漏关键步骤、是否存在明显重复、最终结论是否由前面的 Observation 支撑。官方的 Agent 轨迹评测也把确定性轨迹匹配和 LLM Judge 作为两种主要方式。([Docs by LangChain](https://docs.langchain.com/langsmith/evaluation-approaches?utm_source=chatgpt.com "Application-specific evaluation approaches - Docs by LangChain"))

因此我认为最合理的是三层结合：硬性安全规则用程序判断，确定性 Workflow 用 Reference Trajectory，开放任务用 LLM Judge。这样既不会把 Agent 限死在唯一执行路径上，又能真正发现“结果碰巧正确，但执行过程其实很差”的问题。

### 13、谈谈你对 Langfuse 的了解，怎么使用？

> Langfuse 可以理解成`面向 LLM/Agent 的可观测性和评测平台`。我主要用它记录完整执行 Trace，分析模型调用、工具调用、耗时和成本，再通过 Dataset、Score 和 Experiment 建立 `Agent 的离线与线上评测闭环`。

### Langfuse 最基础的价值是 `Observability`

传统后端有日志和 APM，但 Agent 的一次请求可能包含多次 LLM、检索、Tool Call 和子 Agent 调用，只看普通日志很难恢复完整过程。Langfuse 的数据模型主要是 Session、Trace 和 Observation。

一个用户会话可以是 Session，一次 Agent 请求可以是一条 Trace，Trace 下面的模型调用、检索、工具调用等具体步骤就是 Observation，而且 Observation 可以嵌套，因此能够还原<u style="text-decoration-color: #e63946">整个 Agent 执行树</u>。([Langfuse](https://langfuse.com/docs/observability/data-model?utm_source=chatgpt.com "Concepts - Langfuse"))

> 如果我用 LangGraph，接入成本并不高。可以通过 Langfuse 的 `LangChain CallbackHandler` 把 callback 放到 graph 的 `invoke config` 里面，<u style="text-decoration-color: #e63946">此后 LangGraph 节点、LLM 调用和 Tool Call 就可以自动形成 Trace</u>。现在 Langfuse 甚至能根据这些 Observation 自动展示 Agent Graph，对多 Agent 和复杂 LangGraph 调试比较方便。([Langfuse](https://langfuse.com/integrations/frameworks/langgraph?utm_source=chatgpt.com "Open Source Observability for LangGraph - Langfuse"))

### 接入后我第一阶段通常不是立刻做复杂 Eval，而是先用 Trace 排障

例如一个请求为什么耗时 12 秒，可以直接看到是检索用了 2 秒、第一次模型调用 4 秒、第二次 Tool 重试又用了 3 秒；如果 Token 成本异常，也可以定位是哪一个 Agent 或 Prompt 导致上下文膨胀。

> 这一步主要解决“Agent 到底做了什么”。

### 第二阶段才是评测

Langfuse 有统一的 Score，可以把正确性、相关性、用户点赞、工具正确率等评分挂到 Trace 或具体 Observation 上。Score 可以<u style="text-decoration-color: #e63946">来自人工标注、业务代码、用户反馈</u>，也可以通过 LLM-as-a-Judge 自动生成。([Langfuse](https://langfuse.com/docs/evaluation/scores/overview?utm_source=chatgpt.com "Overview - Langfuse"))

### 第三阶段是建立 Dataset 和 Experiment

比如我<u style="text-decoration-color: #e63946">从生产环境里挑出 200 个典型 Query，再加 50 个历史失败 Case 建成 Dataset</u>。修改 Prompt、模型或者 Agent 架构以后，就用同一个 Dataset 跑一遍 Experiment，对比`任务成功率`、`Judge Score`、`成本和延迟`。如果某个版本明显退化，就不能上线。这就把原来“我感觉新 Prompt 好像更好”变成了可重复的回归测试。([Langfuse](https://langfuse.com/docs/evaluation/core-concepts?utm_source=chatgpt.com "Concepts - Langfuse"))

所以如果把前面三题（10、11、12）串起来，我会说：Agent 执行过程中先通过 Langfuse Trace 把轨迹记录下来；基于 Trace 做 Outcome 和 Trajectory Evaluation；线上发现的失败轨迹再沉淀到 Dataset；每次修改模型、Prompt、Tool 或 Graph 后重新跑 Experiment。这样 Langfuse 就不仅是一个“看日志的工具”，而是连接 Agent 可观测性、调试、评测和持续迭代的一整套工程基础设施。

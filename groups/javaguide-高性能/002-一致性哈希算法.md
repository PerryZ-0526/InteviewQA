# ✅一致性哈希算法

> 一致性哈希主要用于分布式缓存、分布式存储、分片系统、分库分表、负载均衡等场景，核心目标是：**当节点增加或删除时，<u style="text-decoration-color: #e63946">只让少量数据重新映射，而不是让几乎所有数据都失效</u>。**

一致性哈希会把整个哈希空间组织成一个首尾相连的`“哈希环”`，例如范围可以理解为 `0 ~ 2^32-1`。首先对服务器节点做哈希，把各个节点映射到环上的不同位置；然后对请求的 Key，比如用户 ID、缓存 Key，也做相同的哈希映射到环上。<span style="background-color: rgb(255, 243, 205)">某个 Key 最终会分配给从它所在位置开始，**顺时针遇到的第一个服务器节点**</span>。

例如：
```text
        Node A
       /      \
   Key1        Node B
      \        /
        Node C
```

普通取模哈希通常是：
```text
hash(key) % N
```

一旦服务器数量 `N` 发生变化，大量 Key 的计算结果都会改变，<u style="text-decoration-color: rgb(230, 57, 70)">导致大量缓存失效</u>。而一致性哈希中，如果新增一个节点，只会影响这个新节点与它前一个节点之间的一小段 Key；删除节点时，也只需要把原本属于该节点的数据迁移到下一个节点，因此数据迁移量明显更小。

一致性哈希还有一个常见问题：如果服务器节点在哈希环上分布不均，可能导致`数据倾斜`。实际项目中通常会引入**虚拟节点**，<u style="text-decoration-color: rgb(230, 57, 70)">让一台真实服务器对应多个哈希位置，从而让数据分布更加均匀</u>。

> 虚拟节点是为了解决一致性哈希中**真实节点分布不均导致的数据倾斜问题**。如果一台真实服务器在哈希环上只对应一个位置，那么节点数量较少时，不同节点之间负责的哈希区间可能差异很大，某些服务器会承担更多数据和请求。引入虚拟节点后，一台真实服务器会通过不同的虚拟节点名称或编号，多次进行哈希，从而映射到哈希环上的多个位置，例如 `ServerA#1`、`ServerA#2`、`ServerA#3` 都属于同一台真实服务器。
>
> 这样每台服务器就能分散到哈希环的多个区域，<u style="text-decoration-color: rgb(230, 57, 70)">Key 仍然按照顺时针找到最近虚拟节点，再由虚拟节点定位到对应真实服务器。随着虚拟节点数量增加，各真实节点负责的哈希区间会更加均匀，负载也更平衡</u>。
>
> 除此之外，节点扩容或下线时，受影响的数据会分散到多个小区间中，不会集中迁移到某一台服务器。因此可以概括为：**虚拟节点本质上是给一台真实服务器在哈希环上创建多个映射位置，用空间换均衡性，从而降低数据倾斜并提升扩缩容时的负载稳定性。**

所以面试中可以概括为：**一致性哈希通过哈希环<u style="text-decoration-color: rgb(230, 57, 70)">减少节点扩缩容时的数据迁移范围</u>，并通过虚拟节点改善负载不均问题，适合动态扩缩容的分布式系统。**

---

> **没有虚拟节点时，一台服务器在环上只有一个“大地盘”，服务器上下线时容易整块迁移；有虚拟节点以后，一台服务器的地盘被切成很多小块并散布在整个哈希环上，所以扩容或下线时，<u style="text-decoration-color: rgb(230, 57, 70)">这些小块会分别交给不同服务器，数据迁移和压力自然就被分散了</u>。**

可以把它想象成“**一个老板在商场里开了很多个小柜台**”，这样最好理解。

假设没有虚拟节点，一台真实服务器在哈希环上只有一个位置：
```text
A -------- B -------- C
```

如果 B 下线，那么原本属于 B 的那一整大片数据，按照一致性哈希“顺时针找下一个节点”的规则，可能会**全部转移给 C**。

也就是说：
```text
B 的数据
  ↓
全给 C
```

这样 C 会突然接收大量数据和请求，压力可能一下子变得很大。

引入虚拟节点以后，一台真实服务器不再只占一个位置，而是分散成很多个“虚拟节点”：
```text
A1 -- B1 -- C1 -- A2 -- C2 -- B2 -- A3 -- B3 -- C3
```

其中：
```text
A1、A2、A3 → 真实服务器 A
B1、B2、B3 → 真实服务器 B
C1、C2、C3 → 真实服务器 C
```

现在假设服务器 B 下线，那么不是环上某一大块区域消失，而是：
```text
B1 消失
B2 消失
B3 消失
```

这三个位置本来负责的数据，会分别交给它们**顺时针后面的虚拟节点**。

例如：
```text
B1 后面是 C1 → 一部分数据给 C

B2 后面是 A3 → 一部分数据给 A

B3 后面是 C3 → 一部分数据给 C
```

于是 B 原来的数据就不是：
```text
全部 → C
```

而更像：
```text
一部分 → A
一部分 → C
一部分 → 其他节点
```

所以压力被分散了。

扩容也是同样的道理。

假设新增服务器 D，如果没有虚拟节点，D 只插入哈希环的一个位置，那么它通常只会从某一台服务器那里接走一整段数据。

但使用虚拟节点之后：
```text
D1、D2、D3、D4...
```

会散落在哈希环不同位置，<span style="background-color: #fff3cd">每一个 D 虚拟节点只从它附近的原有节点“接走一小段数据”</span>。

例如：
```text
A → 分一点给 D1
B → 分一点给 D2
C → 分一点给 D3
A → 再分一点给 D4
```

最终就变成`大家各拿出一点给新服务器`，而不是某一台服务器突然迁移一大批数据。

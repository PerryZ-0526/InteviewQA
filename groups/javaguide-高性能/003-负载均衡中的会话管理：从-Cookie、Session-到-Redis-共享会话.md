# 负载均衡中的会话管理：从 Cookie、Session 到 Redis 共享会话

可以把这句话拆成 5 个概念来理解：**会话 Session、Cookie、负载均衡、会话粘滞、Redis 共享会话**。它们其实是在解决同一个问题：

> **用户连续访问一个网站时，后端怎么知道“这几次请求都是同一个人发的”？**

我从零开始讲。

## 1. 什么叫“会话 Session”

HTTP 本身有个特点：**它天然不记得你是谁。**

比如你登录某个网站：
```text
第 1 次请求：我登录了，用户名 abc，密码 xxx
第 2 次请求：我要看“我的订单”
```

从服务器视角看，这其实是两个独立的 HTTP 请求。

如果什么机制都没有，第 2 次请求来的时候，服务器会一脸茫然：
```text
你是谁？
你刚刚登录过吗？
```

所以服务器需要一种机制，记住“这个用户已经登录了”。

这就叫**会话，Session**。

可以简单理解为服务器给你建了一个“小档案”：
```text
session_id = A8F7X9

对应的信息：
user_id = 10086
username = xiaoming
is_login = true
```

所以 Session 本质上就是：

> **服务器为了记住某个用户的状态，而保存的一份数据。**

除了登录状态，它还可能保存：
```text
购物车
验证码状态
临时权限
用户偏好
登录时间
```

不过现代系统一般不会把太多业务数据塞进 Session。

## 2. Cookie 又是什么

现在还有一个问题。

服务器里面有很多 Session：
```text
Session A -> 小明
Session B -> 小红
Session C -> 小王
```

那么用户下一次访问的时候，服务器怎么知道：
```text
你应该找 Session A
```

呢？

这时候就轮到 **Cookie** 出场了。

Cookie 是：

> **浏览器帮网站保存的一小段数据，每次请求这个网站时，可以自动带给服务器。**

比如你第一次登录成功后，服务器返回：
```text
Set-Cookie: session_id=A8F7X9
```

浏览器看到之后，会把：
```text
session_id=A8F7X9
```

保存起来。

之后你再访问：
```text
GET /my-orders
```

浏览器会自动带上：
```text
Cookie: session_id=A8F7X9
```

服务器一看：
```text
哦，A8F7X9。

查一下 Session。

A8F7X9 -> user_id=10086

原来是小明。
```

于是你不用访问一个页面就重新登录一次。

所以可以记成一句话：

> **Session 通常存在服务器端，Cookie 通常存在浏览器端。Cookie 里可以保存一个 Session ID，用来告诉服务器“我是谁”。**

注意，这只是非常常见的一种模式，不是说 Cookie 只能拿来保存 Session ID。

---

## 3. 那负载均衡为什么会让事情变复杂？

如果你只有一台服务器：
```text
用户
  |
  v
服务器 A
```

Session 放服务器 A 的内存里，没什么问题。

例如：
```text
服务器 A

Session:
ABC -> 小明已登录
```

小明下一次请求还是访问 A：
```text
Cookie: session_id=ABC
```

A 查一下：
```text
ABC -> 小明
```

正常。

但生产环境一般不能只有一台服务器。

因为一台服务器可能：

- 扛不住流量；
- 宕机；
- 升级；
- 重启。

所以一般会部署很多台：
```text
              ┌──> 服务器 A
用户 -> 负载均衡 ├──> 服务器 B
              └──> 服务器 C
```

负载均衡器，比如 Nginx，会负责决定：

> 这个请求到底交给 A、B 还是 C？

比如：
```text
请求 1 -> A
请求 2 -> B
请求 3 -> C
请求 4 -> A
```

问题就来了。

假设小明第一次登录的时候：
```text
小明
 |
 v
负载均衡
 |
 v
服务器 A
```

服务器 A 保存：
```text
Session ABC
user_id = 10086
is_login = true
```

浏览器 Cookie：
```text
session_id=ABC
```

下一次小明请求“我的订单”。

负载均衡器一分配：
```text
小明
 |
 v
负载均衡
 |
 v
服务器 B
```

小明浏览器还是会发送：
```text
Cookie: session_id=ABC
```

但是 B 一查：
```text
ABC？

我的内存里没有这个 Session 啊。
```

于是 B 可能认为：
```text
你没有登录。
```

用户就会出现一种很诡异的现象：
```text
刚登录成功
↓
点一下“我的订单”
↓
怎么又让我登录？
```

这就是多节点环境里经典的 **Session 问题**。

---

# 4. “会话粘滞”是什么意思？

既然 Session 在 A 上，那有人想到一个非常直接的解决办法：

> **那以后这个用户所有请求，都让它去 A 不就好了？**

对，这就是：

**Sticky Session / Session Affinity**

中文通常叫：

- 会话粘滞；
- 会话保持；
- Session 粘性。

比如：
```text
小明 ──────> A
小明 ──────> A
小明 ──────> A
小明 ──────> A

小红 ──────> B
小红 ──────> B
小红 ──────> B
```

虽然前面有负载均衡器：
```text
          ┌── A
LB ───────┼── B
          └── C
```

但是负载均衡器会想办法记住：
```text
小明 -> A
小红 -> B
小王 -> C
```

所以叫“粘”在某台服务器上。

---

## 5. Cookie 粘滞是什么？

负载均衡器可以给浏览器一个 Cookie，例如：
```text
SERVER=A
```

以后浏览器访问时带上：
```text
Cookie: SERVER=A
```

负载均衡器看到后：
```text
哦，你之前是 A 处理的。

那这次继续送 A。
```

于是：
```text
浏览器
Cookie: SERVER=A
      |
      v
负载均衡器
      |
      v
服务器 A
```

这叫：

> **基于 Cookie 的会话粘滞。**

注意这里可能存在两种 Cookie：
```text
session_id=ABC
SERVER=A
```

它们用途完全不一样。
```text
session_id=ABC
```

是应用服务器拿来识别用户 Session 的。

而：
```text
SERVER=A
```

可能是负载均衡器拿来决定：

> 把你送去哪个服务器。

这是初学时很容易混淆的一点。

---

# 6. IP Hash 又是什么？

还有一种办法叫：

**IP Hash**

意思是负载均衡器根据用户 IP 算一下：
```text
hash(用户IP)
```

然后决定把用户送去哪台机器。

比如：
```text
1.2.3.4 -> A
5.6.7.8 -> B
9.10.11.12 -> C
```

只要：

- 用户 IP 没变化；
- 后端服务器列表没变化；

那同一个 IP 通常就会被送到同一台服务器。

例如：
```text
小明 IP = 1.2.3.4

请求1 -> hash(1.2.3.4) -> A
请求2 -> hash(1.2.3.4) -> A
请求3 -> hash(1.2.3.4) -> A
```

于是 Session 放在 A 本地也能工作。

---

# 7. 那为什么生产环境说“避免依赖会话粘滞”？

因为它虽然简单，但有很多坑。

最关键的问题是：

> **你的用户状态和某一台服务器绑定了。**

这样服务器就不再是“随便哪台都能处理请求”。

---

## 问题一：节点挂了怎么办？

比如：
```text
小明 -> A
小红 -> B
小王 -> C
```

小明 Session 全在 A：
```text
A:
Session ABC -> 小明已登录
```

结果 A 突然宕机：
```text
A ❌
```

负载均衡器只能把小明送去 B：
```text
小明 -> B
```

但 B：
```text
没有 Session ABC。
```

结果就是：
```text
用户被踢下线
```

或者购物车、临时状态丢失。

所以你原来的那句话说：

> “节点故障时要评估用户影响。”

说的就是这个。

---

# 8. 问题二：扩容时可能发生什么？

假设原来有：
```text
A
B
C
```

突然流量变大，开始扩容：
```text
A
B
C
D
E
F
```

如果你用的是某些 Hash 算法，服务器数量一变化：
```text
hash(IP) % 3
```

变成：
```text
hash(IP) % 6
```

很多人的映射都会发生变化。

本来：
```text
小明 -> A
```

扩容后可能变成：
```text
小明 -> E
```

问题又来了：
```text
Session 还在 A
```

E 不知道小明登录过。

所以大量用户可能：
```text
突然掉登录
```

这就是原话中的：

> **“扩缩容时要评估用户影响。”**

---

# 9. 缩容同样有问题

比如现在：
```text
A B C D
```

服务器 D 上有 1 万个用户的 Session。

现在低峰期想省钱：
```text
把 D 下掉
```

那么原本：
```text
用户 -> D
```

的人会被重新分配：
```text
用户 -> A/B/C
```

可是他们的 Session 数据还在 D。

于是可能集体掉登录。

所以有状态服务器的扩缩容通常会比无状态服务器麻烦很多。

---

# 10. IP Hash 本身也不是特别可靠

因为“一个用户 = 一个 IP”这个假设并不稳定。

例如你的手机：

在家：
```text
Wi-Fi
IP = A
```

出门切成 5G：
```text
IP = B
```

IP 变化了。

于是：
```text
之前 -> 服务器 A
现在 -> 服务器 C
```

Session 又可能找不到。

反过来也存在一个问题。

公司里可能有：
```text
1000 个员工
```

但是访问互联网时，通过同一个 NAT 出口：
```text
公网 IP 都是 1.2.3.4
```

负载均衡器一算：
```text
hash(1.2.3.4) -> Server A
```

结果：
```text
1000 个人全跑 A 去了
```

于是：
```text
A：CPU 95%
B：CPU 20%
C：CPU 18%
```

负载均衡都不怎么“均衡”了。

---

# 11. 所以更推荐 Redis，Redis 在这里干什么？

核心思路特别简单：

> **不要把 Session 放在某一台业务服务器自己身上，而是放到所有服务器都能访问的公共地方。**

比如 Redis。

原来是：
```text
A
Session ABC -> 小明

B
没有 ABC

C
没有 ABC
```

改造以后：
```text
                 ┌── 服务器 A
用户 -> LB ──────┼── 服务器 B
                 └── 服务器 C
                       |
                       |
                 ┌─────v─────┐
                 │   Redis   │
                 │           │
                 │ ABC->小明 │
                 └───────────┘
```

A、B、C 都不自己保存 Session。

统一去 Redis 查。

---

## 比如第一次登录

请求被送到 A：
```text
用户
 |
 v
LB
 |
 v
A
```

登录成功之后，A 往 Redis 写：
```text
session:ABC
    user_id = 10086
    is_login = true
```

浏览器得到 Cookie：
```text
session_id=ABC
```

---

下一次请求，LB 这次随便把用户送到 C：
```text
用户
Cookie: session_id=ABC
        |
        v
       LB
        |
        v
        C
```

C 自己没有 Session，没关系。

它去 Redis：
```text
GET session:ABC
```

Redis 返回：
```text
user_id=10086
is_login=true
```

于是 C 知道：
```text
哦，是小明。
```

正常处理请求。

下一次送 B：
```text
B -> Redis
```

也正常。

所以最终变成：
```text
请求1 -> A -> Redis
请求2 -> C -> Redis
请求3 -> B -> Redis
请求4 -> A -> Redis
```

哪台服务器都能处理。

---

# 12. 这就是“无状态服务”

这是后端架构里非常重要的一个词：

**Stateless，无状态。**

不是说系统完全没有状态，而是说：

> **业务服务器自己不保存“只有它自己知道”的用户状态。**

例如：
```text
服务器 A
服务器 B
服务器 C
```

最好设计成：
```text
A 挂了？
没事，B 能接。

B 扩容？
没事，新机器马上能接请求。

C 重启？
没事，状态不在它本地。
```

因为状态放在：
```text
MySQL
Redis
对象存储
其他共享存储
```

业务服务器本身就变成“可以随时替换”的机器。

这种架构对：

- Kubernetes；
- Docker；
- 自动扩缩容；
- 云服务器；
- 滚动发布；

尤其友好。

# 13. 用一个现实生活的比喻

可以把服务器想象成银行柜员。

### 会话放服务器本地

假设你第一次去银行：
```text
1号柜员
```

他拿自己的小本子记录：
```text
这个客户已经验证过身份证了。
```

然后你去办理下一个业务。

银行经理说：
```text
去 3 号窗口吧。
```

3号柜员：
```text
你是谁？

重新验证身份证。
```

你说：
```text
我刚才明明验证过啊！
```

问题就是：
```text
信息只存在1号柜员自己的小本子里。
```

---

### 会话粘滞

银行想了个办法：
```text
既然这样，这个客户今天所有业务都去1号窗口。
```

这就是 Sticky Session。

但是：
```text
1号柜员突然请假了。
```

麻烦来了。

---

### Redis 共享 Session

更好的办法是：
```text
所有柜员都查银行中央系统。
```

1号柜员录入：
```text
客户10086：
身份已验证。
```

然后你去 3 号窗口。

3号柜员查中央系统：
```text
哦，验证过了。
```

正常办理。

这里的：
```text
中央系统 ≈ Redis
柜员 ≈ Web服务器
经理 ≈ 负载均衡器
你手里的号码 ≈ Cookie里的Session ID
```

这个类比基本可以贯穿整个概念。

---

# 14. Cookie、Session、Redis、负载均衡之间的完整关系

把所有东西串起来，就是这样：
```text
① 用户登录

浏览器
   |
   | 用户名 + 密码
   v
负载均衡器
   |
   v
服务器 A
   |
   | 创建 Session
   v
Redis

session:abc123
user_id = 10086
```

然后服务器告诉浏览器：
```text
Cookie:

session_id=abc123
```

之后：
```text
② 用户查看订单

浏览器
Cookie: session_id=abc123
        |
        v
     负载均衡
        |
        | 随便选择一台
        v
     服务器 C
        |
        | session_id=abc123
        v
       Redis
        |
        | user_id=10086
        v
     服务器 C
        |
        v
   返回小明的订单
```

所以服务器 A/B/C 谁收到请求都没关系。

---

# 15. 现在再来看你原来那句话

原文是：

> **避免会话粘滞依赖：如果必须使用 Cookie 或 IP Hash 固定会话，扩缩容和节点故障时要评估用户影响。更推荐把会话放到 Redis 等共享存储中。**

现在可以翻译成大白话：

> 最好不要让“某个用户必须访问某一台服务器”。
>
> 因为一旦那台服务器挂了、重启了，或者系统扩容缩容导致用户被分配到另一台服务器，用户原来的登录状态可能就找不到了。
>
> 更好的办法，是把登录状态等 Session 数据存在 Redis 这样的公共存储里。
>
> 这样无论负载均衡把用户请求分配给 A、B 还是 C，任何服务器都能从 Redis 找到用户的 Session。

---

## 你目前可以先记住这张“关系图”
```text
                 Cookie
                   ↓
               浏览器
                   |
                   | HTTP请求
                   v
             +-----------+
             | 负载均衡器 |
             +-----------+
               /    |    \
              /     |     \
             v      v      v
           Web A  Web B  Web C
              \     |     /
               \    |    /
                v   v   v
               +-------+
               | Redis |
               +-------+
                   |
            Session 存这里
```

其中：


| 概念         | 先这么理解就够了                |
| ---------- | ----------------------- |
| Cookie     | 浏览器保存并在请求时带给网站的一小段数据    |
| Session    | 服务器记录“这个用户当前是什么状态”的数据   |
| Session ID | 找到某个 Session 的编号        |
| 负载均衡       | 把用户请求分配给多台服务器           |
| 会话粘滞       | 强行让某个用户一直访问同一台服务器       |
| IP Hash    | 根据用户 IP 决定访问哪台服务器       |
| Redis      | 多台服务器共同访问的高速数据存储        |
| 无状态服务      | Web 服务器自己不保存必须依赖本机的用户状态 |


如果你刚开始学后端，**最值得真正搞明白的不是 Redis 的命令，而是“为什么 HTTP 无状态 → 为什么需要 Cookie/Session → 为什么多服务器会产生 Session 问题 → 为什么要把状态抽出去”这条逻辑链**。后面你再学 Nginx、Spring Session、Redis、JWT、Kubernetes，很多东西会一下子串起来。

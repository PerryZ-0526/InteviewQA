## 一、审查口径与范围

### 1.1 审查范围

纳入 `categories/**/三位数字-*.md`，共 22 篇。`00-index.md`、标签页、README、项目管理文档和 `mobile/dist` 构建副本不作为独立题目重复审阅；但索引、链接和构建副本是否与源文档一致，列入结构检查。

### 1.2 严重程度

- **高**：核心概念、事实、公式或当前产品能力明显错误，可能导致面试中被直接追问击穿。
- **中**：结论有条件却写成普遍规律，论证片面，或只罗列方法而没有解释机制和边界。
- **低**：赘述、重复、格式、命名、链接和可维护性问题，不一定造成事实性失分，但明显影响表达质量。

### 1.3 判断原则

- 百分比、延迟、阈值、准确率、成本倍数等数字，如果没有实验条件、数据集、模型、提供商和时间版本，统一视为“示例或经验值”，不能写成普遍事实。
- 产品和框架能力以 2026-08-10 可核验的官方资料为准；私有实现细节无法核实时，不把推测写成架构事实。
- “面试直接答”优先判断是否能在较短篇幅内形成明确论点、机制、边界和取舍，而不是看覆盖术语的数量。

## 二、总览与优先级

### 2.1 结论摘要

22 篇均发现至少一处值得处理的问题。其中应优先重写或大修的文档有 8 篇：

1. `claude-code/002-Claude Code与Codex架构区别.md`：对 Codex 当前形态和能力的描述大面积过时，且将未公开的内部架构当成事实。
2. `mutil-agent/003-G-Memory多智能体的共享与进化记忆.md`：没有回答同名论文中的 G-Memory，核心定义和层级结构均被替换成通用记忆设计。
3. `hermes/001-Hermes自进化机制.md`：把路线图或可设想机制写成已经上线的自动生产闭环，与公开实现的人工审查护栏冲突。
4. `harness/001-harness工程的理解.md`：没有先消歧，主要回答了评测 Harness，而当前 Agent 语境中的 Harness 通常首先指模型外部运行时/脚手架。
5. `agent/006-agent长时间循环的注意事项.md`：累计 Token 表的数量级计算错误，并误述 Lost in the Middle 的结论。
6. `os/001-python与C++内存管理.md`：把 CPython 当作 Python 通用语义，PyMalloc 阈值前后矛盾，Arena 大小也已不适用于当前 64 位 CPython。
7. `os/002-从OS底层到语言层的内存管理全景.md`：TLB、进程隔离、`mmap`、Rust 默认分配器等多处表述过度绝对或错误。
8. `agent/001-如何降低agent的运营成本.md`：关键成本公式有算术错误，大量节省比例缺乏适用条件，“指数增长”也混淆了单轮上下文和累计成本。

其余文档多数具备可用骨架，但普遍需要删掉无依据数字、压缩重复答案、增加失败边界，并把“方法清单”提升为“机制—指标—约束—验证”的回答。

## 三、跨文档共性问题

### 3.1 把经验数字包装成稳定规律（高频、中风险）

多篇文档出现“节省 30%～50%”“命中率 80%”“固定 3 轮”“相似度 0.85”“抽样 1%～5%”“200 条用例”“2 小时灰度”等数字，却没有说明来源、模型、数据集和业务分布。这类数字只能作为演示参数。面试时更稳妥的表达是：先定义可观测指标，再说明用离线基线、线上实验或历史分位数确定阈值。

### 3.2 把框架 API 和产品行为写成永恒事实（高频、中高风险）

Claude Code、Codex、AutoGen、CrewAI、LangGraph、OpenAI/Gemini 缓存等内容变化快。文档没有标注版本日期，有些 API 看起来是示意代码，有些则已经与当前官方能力不符。建议所有产品题在标题区记录“核验版本/日期”，示意 API 明确写“伪代码”。

### 3.3 用“共识、置信度、LLM Judge”替代外部正确性（高频、高风险）

多个 Agent/多 Agent 文档把模型自报置信度、语义相似度、投票或更强模型裁决当成真值。这些信号只能用于调度，不能证明正确。根本上的验证顺序应是：确定性环境状态和业务不变量优先，其次是有金标校准的人评/模型评，最后才是自洽性、投票和置信度等弱代理信号。

### 3.4 把“上下文、消息、共享状态、长期记忆”混为一谈（高频、中高风险）

上下文是本轮模型可见输入，消息是传输载体，共享状态是协作事实源，长期记忆是跨会话持久信息。压缩、检索、黑板、向量库和摘要分别解决不同问题。当前多篇文章混用这些概念，导致一致性、权限、生命周期和可追溯性没有被回答。

### 3.5 只讲理想成功路径，没有回答“不确定结果”（高频、高风险）

不少流程文章提到了幂等，却没有处理最棘手的情形：外部工具已经执行成功，但进程在记录结果前崩溃。此时既不能安全重试，也不能简单标记失败。高质量答案应区分“未执行、已执行、执行结果未知”，并说明幂等键、查询确认、补偿、人工介入和恢复点。

### 3.6 答案重复，且“直接答”失去直接性（高频、低到中风险）

多篇文档同时保留终版、首版、修改版、详细解析和附录，观点重复但口径并不总是一致。面试材料不应靠篇幅制造完整感；建议保留一版 60～120 秒直接答，细节只围绕高概率追问展开。

## 四、逐篇审查结果

### 4.1 `agent/001-如何降低agent的运营成本.md`

1. **[高｜不正确] 重试成本公式算错。** 文中称 20% 任务需要一次重试会让成本上升约 40%。如果每次重试成本与首次相同，且只有 20% 的任务恰好重试一次，期望倍数是 `1 + 20% = 1.2`，即增加 20%；如果每次成功率为 80% 并持续重试到成功，期望次数是 `1/0.8=1.25`。除非还有更长上下文或额外调用，否则不能得到 40%。
2. **[高｜概念混淆] “多轮工具调用使 Token 指数增长”不准确。** 若每轮新增固定长度且每次重发完整历史，单次上下文长度通常线性增长，累计输入 Token 近似二次增长；并非指数增长。工具输出本身增长、分支复制和多 Agent 广播会改变曲线，但必须单独建模。
3. **[中｜片面] Prompt Cache 被写成低风险且几乎普适的首选。** 缓存只降低符合条件的重复输入部分，不降低输出 Token；还存在最小前缀、前缀稳定性、缓存写入费用、TTL、命中波动和隐私/保留策略等条件。不同供应商和模型的读写计价也不同。
4. **[中｜无依据数字] 30%～50%、50%～90%、95% 路由准确率、100ms、50 Token 等没有基线。** 建议全部改成“示例”，并给出测量公式：可缓存输入占比 × 命中率 × 读写价格差，以及路由误判带来的重试/质量损失。
5. **[中｜根因不足] 工具结果缓存忽略了正确性条件。** 文件、API 和搜索结果并不天然幂等或稳定；必须绑定输入规范化、数据版本、用户权限、TTL、失效事件和负缓存策略。
6. **[低｜赘述] 前半部分和“深入解析”多次复述同一组手段。** 建议将直接答收敛为“减少调用次数、减少每次有效输入、选择合适模型、控制失败重做”，其余作为追问。

### 4.2 `agent/002-降低llm调用成本最有效的手段.md`

1. **[高｜片面] 将 Prompt Caching 断言为“最有效手段”不成立。** 它只在重复且足够长的稳定前缀占比高时占优；一次性短请求、输出成本占主导、工具调用占主导或命中率低的场景，模型路由、批处理、减少调用和缩短输出可能更有效。
2. **[高｜误导] “节省 50%～90% Token/整体降到十分之一”混淆 Token 与费用。** 缓存通常不减少模型看到的逻辑 Token 数，只改变符合条件的输入计价和可能的延迟；输出仍按输出价计费。当前 OpenAI 部分模型还区分 cache write 与 cached input read。
3. **[中｜过时] “OpenAI 自动缓存、用户无需配置”已不完整。** 当前模型文档存在显式与隐式缓存语义，并公开了缓存写入、读取和命中用量字段；必须按具体模型说明。
4. **[中｜无依据数字] “容易达到 80% 命中率”、路由节省 30%～50%、微调/蒸馏节省 70%～90% 都缺少前提。** 微调与蒸馏也是两种不同手段，成本结构和质量风险不能合并成一个比例。
5. **[中｜边界缺失] 只用 `cached_tokens / total_tokens` 作为目标会误判。** 分母应至少区分可缓存输入、不可缓存输入、输出和缓存写入；还要观察命中率、首 Token 延迟、质量与单位成功任务成本。
6. **[低｜格式] 成本对比表 Markdown 已塌缩成单行，影响阅读。**

### 4.3 `agent/003-agent效果的定义.md`

1. **[高｜不正确] “传统 Benchmark 对 Agent 三个维度都没有衡量”过于绝对。** HumanEval 等至少衡量了可执行正确性的一部分；问题在于它们不能完整覆盖工具使用、长程状态、恢复和业务价值，而不是“完全不测”。
2. **[中｜不可操作] “规划步数与理论最优步数之比”通常无法获得理论最优解。** 更现实的是与可验证基线、专家轨迹、成本下界或 Pareto 前沿比较。
3. **[中｜误因归因] “参数错就是提示词问题、路径错就是规划问题”等映射过于机械。** 参数错误也可能来自工具 schema、序列化、状态陈旧或模型能力；必须基于轨迹证据定位，不能按错误表象直接归因。
4. **[高｜验证不足] 把 LLM Judge 写成生产评测的必要组成不成立。** 只要任务有可执行断言、环境状态、业务规则或金标，就应优先使用确定性验证；Judge 应经过人类标注校准，并防止同源模型偏差、位置偏差和提示注入。
5. **[中｜不正确] `temperature=0` 不等于系统完全确定性。** 服务端实现、并发、工具环境、检索结果和模型更新都可能引入非确定性。
6. **[中｜无依据阈值] 50～100 条样本、Kappa > 0.7、线上抽样 1%～5%、差距 10% 等不能作为通用标准。** 评分是序数还是类别也会影响应该使用普通 Kappa、加权 Kappa、相关系数还是校准误差。
7. **[低｜严重赘述] 第 161 行附近开始的 `ChatGPT_v2` 几乎是第二篇完整答案，使全文达到 872 行。** 建议合并为一个评测框架，删去重复定义和重复指标表。

### 4.4 `agent/004-agent上下文压缩策略.md`

1. **[中｜概念混淆] 将外部记忆、检索与上下文压缩混在同一层。** 外部化是减少即时上下文的手段，但持久记忆还涉及写入策略、检索、权限、冲突和生命周期，不能等同于压缩。
2. **[高｜复杂度表述] “Token 成本线性增长”只描述了单轮上下文。** 完整历史每轮重发时，累计输入通常近似二次增长；有缓存、滑窗或摘要后才会改变。
3. **[中｜错误优先级] “用户约束永久保留且权重 10”忽略约束可被撤销、覆盖或限定作用域。** 应保存来源、版本、有效范围和冲突解决规则，而不是永久固定权重。
4. **[中｜机制不足] LRU 加重要性评分不足以保证任务正确。** 当前目标、验收标准、已完成步骤和外部操作结果应作为结构化任务状态，不应与闲聊片段共用淘汰算法。
5. **[中｜质量风险] 摘要会丢失否定、条件、未决事项和证据不确定性。** 应保留源指针、结构化约束和可回查原文，并以任务测试验证压缩后行为，而不只比较语义相似度。
6. **[低｜无依据参数] 三层 Token 配额、轮数和重要性权重均应标为示例配置。

### 4.5 `agent/005-agent从接收需求到完成工作的完整流程.md`

1. **[中｜赘述] 1190 行对于一道流程题明显过长。** 文档把最小可用循环、生产控制面、分布式执行、监控、人工审批和恢复全部当成统一必备流程，反而削弱主线。建议分成“最小闭环”和“高风险生产增强”。
2. **[高｜恢复缺口] 伪代码没有真正解决外部副作用的不确定结果。** 工具执行成功后、幂等记录或 checkpoint 前崩溃，恢复时可能重复扣款/发送/写入；需要操作级幂等键、结果查询、outbox/事务边界、补偿和 `UNKNOWN` 状态。
3. **[高｜状态机不闭合] `WAITING_APPROVAL` 的暂停被返回，但没有展示审批后如何恢复到 `RUNNING`，也没有明确重新验证计划和上下文版本。**
4. **[中｜异常路径不足] 预算检查、工具异常、持久化失败、校验器失败没有在伪代码中形成一致的捕获和状态落盘语义。** 文字讲了恢复，核心代码却只覆盖顺利路径。
5. **[中｜过度绝对] “每个工具结果都必须验证”不区分风险。** 读取本地静态文本与付款、删除、发信需要不同级别的前置确认和后置核验；应采用风险分级。
6. **[中｜根因可更深] 流程真正的核心不是步骤数量，而是三条边界：意图是否足够明确、外部状态变化是否可安全提交、完成是否由可验证证据定义。** 当前文档列举大量组件，却没有用这三条主线统领。

### 4.6 `agent/006-agent长时间循环的注意事项.md`

1. **[高｜算术错误] 累计 Token 表数量级错误。** 若每轮新增 1000 Token 且每轮重发完整历史，累计输入约为 `1000 × n(n+1)/2`：10 轮 5.5 万、50 轮 127.5 万、100 轮 505 万、500 轮 1.2525 亿、1000 轮 5.005 亿；原表的 1.5 万、10 万、25 万、150 万、300 万严重低估。
2. **[高｜自相矛盾] 文中先说 1000 轮每轮 1000 Token 是 100 万生成量，随后又把“Token 数量 O(n²)”混写。** 应区分生成输出总量、某一轮上下文长度、累计输入计费量和模型注意力计算量。
3. **[高｜论文结论误述] Lost in the Middle 的经典结果是相关信息位于长上下文中部时表现往往最差，开头和结尾通常更好；原文把“早期约束和中期信息容易忽略”并列为论文结论，不准确。
4. **[低｜计数错误] 声称有六类问题，实际列出了七类。
5. **[中｜检测片面] 用当前输出与初始目标的语义相似度判断目标漂移会误伤正常的子任务分解和改写。** 应检查结构化目标、不变量、验收条件和未完成项。
6. **[中｜中止边界不足] 达到硬限制不能只 `return`。** 需要先持久化恢复点，标记已发生的外部副作用，产出可交接状态，并区分失败、暂停和需要人工决策。

### 4.7 `claude-code/001-Claude Code子智能体类型与vibe-coding场景.md`

### 4.8 `claude-code/002-Claude Code与Codex架构区别.md`

### 4.9 `design-patterns/001-代码设计范式与共性问题.md`

1. **[中｜概念混用] 将编程范式、SOLID 原则、GoF 设计模式和架构模式都称为“设计范式”。** 面试中应先分层，否则容易被追问“范式、原则、模式、架构有什么区别”。
2. **[中｜过度归纳] “所有原则本质都是解耦”“修改成本指数增长”过于绝对。** 设计还要处理内聚、局部性、一致性、性能、认知负担和变更频率；解耦过度也会增加间接层。
3. **[中｜片面] 开闭原则被简化为“只新增、不修改”。** 真正目标是让高频变化落在稳定扩展点；原有实现、契约和迁移仍可能需要修改。
4. **[中｜表述错误] “依赖注入等于不能 `new` 或静态调用”属于教条化。** 判断标准是依赖边界和可替换性，而不是语法禁令。

6. **[中｜片面] Observer 与消息队列仅在发布订阅形态上相似。** 持久化、确认、顺序、重试、跨进程和投递语义完全不同，不能作为等价关系。
7. **[低｜赘述] `我的作答` 后追加约 400 行模式教程，严重超出题目主线。
8. **[低｜占位符] 文末链接 `002-xxx` 指向不存在的文档。

### 4.10 `engineering-practice/001-高质量代码的标准.md`

1. **[中｜片面] 将高质量代码收敛为正确性、可读性和“设计优雅”不够完整。** 至少还需按场景讨论安全、性能和资源、可观测性、兼容性、可部署/可恢复、可测试与变更成本；“优雅”本身不可验证。
2. **[高｜示例有竞态] 转账示例在事务外检查余额，存在 TOCTOU 竞态。** 并发下两个请求都可能通过检查；应在事务内使用条件更新或加锁，并说明隔离级别。
3. **[高｜一致性缺口] 事务提交后单独写审计日志，审计失败会形成“钱已转但审计缺失”。** 需要事务内审计、outbox 或可恢复补偿，不应把它作为完整正确性范例。
4. **[中｜过度绝对] “每条异常路径都必须有降级”不成立。** 对不可继续或可能破坏一致性的错误，fail fast 和阻断比降级更正确。
5. **[中｜深度不足] 文档以规则清单为主，没有给出质量属性冲突。** 例如可读性与极致性能、抽象与局部理解、兼容性与清理成本，需要说明按风险和变更模式取舍。
6. **[低｜格式/残句] 对比表塌缩，结尾“旧代码、弃用 API”等内容不成完整论证。

### 4.13 `hermes/001-Hermes自进化机制.md`

1. **[高｜与公开实现冲突] 文档把 Hermes 描述成在线收集反馈、自动归因、生成改进并直接合入生产的成熟闭环。** 当前公开的 Hermes Agent Self-Evolution 仓库以 DSPy + GEPA 做候选搜索，已实现重点在技能文件，工具描述、系统提示、代码和持续循环仍分阶段推进；最佳变体通过 PR 交给人工审查，而不是直接提交生产。
2. **[高｜安全错误] “自动合并生产配置”“分钟级反馈”“不会退化”均不可信。** 自优化系统必须允许无改进和回滚，且应防止评测集过拟合、奖励投机、灾难性回归和数据污染。

5. **[中｜无依据实现] 两级聚类、置信度曲线、5% 灰度、2 小时窗口、自动迁移等更像作者设想，没有标注“推演方案”。
6. **[中｜风险判断错误] “长尾影响小，所以可以更激进”忽略低频高损的安全事故。** 风险应由影响 × 概率 × 可恢复性评估，而不是仅看频率。
7. **[中｜概念片面] 微调并不等于简单“改变理解能力”，技能/提示/工具优化与参数更新也不只是成本层面的区别，应比较可逆性、数据需求、泛化和安全边界。

### 4.14 `llm-wiki/001-llm wiki的理解与实现原理.md`

1. **[高｜来源定位不准] 原始概念来自 Karpathy 2026 年的 gist/设计提案，不宜笼统称为“博客”。** 原设计重点是不可变原始资料、LLM 生成的 Wiki、schema/指令三层，以及 Ingest、Query、Lint 三类核心操作。

8. **[中｜冲突策略错误] “新来源优先”不是通用规则。** 权威性、适用版本、生效时间、地域和证据级别比抓取时间更重要。

### 4.15 `mutil-agent/001-多agent系统如何实现共享记忆.md`

1. **[中｜定义错误] “共享记忆就是多个 Agent 读写同一份持久化状态”过窄。** 共享任务状态可以是临时的；长期记忆才强调跨会话持久化。
2. **[高｜概念混淆] 文档把消息通信、共享状态和长期记忆放进同一对比表。** 消息是传输机制，不等于记忆；三者应分别讨论一致性、生命周期、所有权和回放。
3. **[中｜错误绝对化] 黑板模式不必然是内存态、单点或不能跨会话；外部存储也不自动具备高一致性和高扩展性。** 这些取决于部署和协议。
4. **[高｜代码问题] `MemoryEntry` 使用 `time`、`uuid4` 却未导入；写操作加锁而读操作未加锁，不能保证并发一致快照。
5. **[中｜选型风险] 向量数据库不应承担权威可变任务状态。** 它适合相似检索，约束、决策、操作状态应存于有版本和并发控制的结构化存储。
6. **[中｜框架脆弱] LangGraph 示例用普通 `operator.add` 合并消息过度简化；当前框架通常需要能处理消息 ID、更新和删除语义的专用 reducer。
7. **[中｜不正确] 将 RAG 说成只处理静态只读知识不成立。** RAG 的语料可以动态更新，共享记忆也可以使用检索；区别不在“静态/动态”二分。

### 4.16 `mutil-agent/002-多agent讨论如何终止.md`

1. **[高｜代理指标错误] 共识、语义相似度和自报置信度不能证明讨论已经正确完成。** 多个 Agent 可能共享同一错误；终止应优先绑定可执行验收标准、覆盖目标和剩余不确定性。
2. **[中｜过度结论] “结构化 JSON 后语义就可以客观量化”不成立。** 结构化只便于解析，不会自动使主张真实或置信度校准。
3. **[中｜无依据] “仲裁 Agent 是当前最有效实践”没有证据。** 仲裁者仍是概率模型，会继承偏差并成为单点；对可验证任务，环境验证通常更可靠。
4. **[中｜任意阈值] 0.85、3 轮、0.05、1.5 倍预算等只能是示例配置，需要由任务和历史数据校准。
5. **[高｜停止逻辑不完备] 三个信号使用 AND 可能永远无法满足，尤其是本来就无共识的开放问题。** 必须有预算硬上限、无共识退出和将分歧显式交付的状态。
6. **[中｜类比失真] 多 Agent 终止不等于分布式系统共识。** Agent 不是保存同一日志的确定性副本，讨论目标也不总是唯一决定值。
7. **[中｜根因浅] “LLM 天生想继续说”是拟人化描述。** 更根本的原因是控制器持续调用、提示缺少终止动作、完成条件不外显和奖励目标只鼓励继续产出。

### 4.17 `mutil-agent/003-G-Memory多智能体的共享与进化记忆.md`

### 4.18 `mutil-agent/003-多智能体记忆管理与防爆策略.md`

1. **[高｜自相矛盾] 开头称上下文会“指数级膨胀”，给出的公式却是 `N × K × T` 线性关系。** 实际增长取决于广播拓扑、每轮是否复制完整历史、摘要和分支，常见累计输入可呈二次增长，但不能笼统称指数。
2. **[高｜不正确] “摘要和持久化信息不占上下文”错误。** 摘要和被检索回来的记忆同样消耗上下文 Token；外部存储本身不占，读取结果会占。
3. **[中｜压缩风险] 持续在旧摘要上增量摘要会累积信息损失和错误。** 应定期从权威原始记录重建，保存结构化任务状态和来源指针。
4. **[中｜排序错误] 用户消息和工具结果默认高优先级并不安全。** 用户内容可能闲聊或恶意，工具结果可能过时或错误；优先级应基于任务角色、来源、验证状态和时效。
5. **[高｜代码丢信息] `SemanticDeduplicator` 对每条已有消息重复计算 embedding，复杂度近似 O(n²)；合并时追加片段，但 `get_compressed_messages` 只返回 `group[0]`，新增信息没有真正进入输出。
6. **[中｜字段误导] `len(group)` 被写为来源 Agent 数，实际上只是消息数量，同一 Agent 多条消息会被误计。
7. **[中｜并发缺口] 异步压缩若与下一轮读取并发，没有版本或原子切换，会让 Agent 读到不一致的旧/新上下文。
8. **[中｜成本计算不闭合] 压缩一次的输入、输出和未来复用节省被混在同一算式中，且 1000 Token 摘要与“输出 100/200 Token”前后不一致。** 应按压缩成本 + 后续每轮节省 × 复用次数计算盈亏平衡点。
9. **[中｜框架/API 可疑] AutoGen/CrewAI 示例类型和回调需要按具体版本核验，当前看起来更像伪代码，必须明确标注。

### 4.19 `mysql/001-MySQL的底层数据结构.md`

1. **[中｜过度简化] “千万级数据最多 3 次磁盘 IO”把 B+Tree 高度等同于物理 IO 次数。** 根页和内部页可能在 Buffer Pool，叶页也可能命中缓存；行大小、页填充、聚簇/二级索引回表都会改变访问次数。
2. **[高｜过时] “自适应哈希索引用户不能干预”错误。** MySQL 8.4 中 `innodb_adaptive_hash_index` 可动态启停，且默认值为 OFF；其构建虽由 InnoDB 自适应决定，但功能开关可控。
3. **[中｜不准确] AHI 不是把整个 B+Tree 查询普遍变成 O(1)。** 它对频繁访问的索引键前缀/页建立哈希，只有符合模式的查询受益，并可能引发争用。
4. **[中｜概念混淆] “Redo Log 是循环写入缓冲区”混淆内存中的 log buffer 与磁盘 redo log files。** 还应区分逻辑 undo 与面向页修改的 redo 语义。
5. **[中｜过度简化] Undo 不一定保存“完整旧行”，而是保存足以回滚或重建旧版本的信息。
6. **[高｜锁语义片面] Next-Key Lock 不是所有查询防幻读的统一机制。** 一致性读主要依赖 MVCC；锁定读/写及范围条件使用记录锁、间隙锁或 next-key lock，唯一等值命中等情况还会退化为记录锁。
7. **[中｜不准确] “每一行都挂一把锁”不符合 InnoDB 实现。** 行锁是索引记录级语义，内部常按页和 heap number 位图管理。
8. **[低｜失效链接] 下一题 `002-一条SQL语句的执行流程` 不存在。

### 4.20 `os/001-python与C++内存管理.md`

1. **[高｜范围错误] 全文把 CPython 的实现细节直接称为 Python 内存管理。** 应明确 CPython；PyPy、Jython、IronPython 等在对象布局、GC 和释放时机上不同。
2. **[高｜自相矛盾] 前文写 PyMalloc 管理小于等于 256B，后文写小于等于 512B。** 当前 CPython 官方文档的阈值是 512B。
3. **[高｜过时] Arena 写成统一 256KB。** 当前 CPython 文档说明 32 位平台为 256KiB、64 位平台为 1MiB；自由线程构建还使用 mimalloc。
4. **[中｜版本脆弱] “三代 GC”必须绑定 CPython 版本。** Python 3.14 曾移除 generation 1，3.14.5 又为兼容恢复；这说明不能把代际数量写成永久语言规范。
5. **[中｜片面] 并非所有对象都由循环 GC 跟踪；CPython 主要依靠引用计数及时回收，循环 GC 处理容器引用环。
6. **[中｜无依据] “95% 对象生命周期短”“Jython/IronPython 停顿更大”“高并发常关闭 GC”等结论没有数据，且最后一条可能导致循环垃圾长期积累。
7. **[中｜C++ 绝对化] “编译期决定每块内存释放、开发者完全控制”不成立。** 动态所有权、`shared_ptr`、自定义分配器、异常路径和未定义行为都使释放时机和正确性更复杂。
8. **[中｜并发细节] `shared_ptr` 的控制块共享操作通常线程安全，但对同一个 `shared_ptr` 对象并发非 const 访问仍需同步或 `atomic<shared_ptr>`，不能笼统说“线程安全”。

### 4.21 `os/002-从OS底层到语言层的内存管理全景.md`

1. **[高｜不正确] “TLB 命中零延迟”错误。** TLB 查找有成本，只是通常很低并可与流水线重叠；未命中还需页表遍历。
2. **[中｜平台绝对化] x86-64 页表不应统一写成四级。** 现代平台可能启用五级页表，页大小和 TLB 容量也依微架构变化。
3. **[高｜不正确] “一个进程永远看不到另一个进程的内存”错误。** 共享内存、共享映射、调试/进程访问权限以及内核机制都是明确例外；隔离是默认权限边界，不是绝对不可见。
4. **[中｜Swap 片面] 内存不足时并非所有页都写入 Swap。** 干净的文件映射页可直接丢弃后从文件重载，匿名脏页才通常需要交换空间。
5. **[高｜过时] Rust 默认使用 jemalloc 的说法错误。** 当前标准库默认使用平台/系统提供的全局分配器，程序可以用 `#[global_allocator]` 替换。
6. **[中｜不准确] `mmap` 不等于“绕过内核缓冲”。** 它仍通过页缓存和缺页处理，只是避免显式 `read/write` 路径和部分用户态拷贝。
7. **[中｜条件缺失] `malloc(1GB)` 立即成功且不占物理内存依赖 OS、overcommit、提交限制和分配器；不能作为通用事实。
8. **[中｜过度承诺] Rust 的所有内存安全检查并非都“零运行时成本”。** 边界检查、`RefCell` 借用检查等可能在运行时发生；应说所有权/借用的核心规则主要在编译期验证。
9. **[低｜无依据数字] 固定 TLB 容量、周期数和优化收益均应注明具体 CPU 或删除。

### 4.22 `vibe-coding/001-vibe-coding经验与AI生成高质量代码.md`

1. **[高｜概念偏移] 文档把 vibe coding 重新定义为严格规格、测试、审查的工程流程。** Karpathy 最初使用该词时强调“顺着感觉接受 AI 输出、甚至不再细看代码”；本文描述的其实更接近 disciplined AI-assisted/agentic coding。建议先承认术语原义，再说明生产环境为何必须超越纯 vibe coding。
2. **[中｜根因不足] 将 AI 比作“初级工程师”便于沟通但过于浅。** 更根本的风险是模型按概率补全、没有稳定世界状态、会共享提示中的错误假设，并且输出没有天然责任主体。
3. **[中｜过度流程化] 每次改动都要求分支、完整测试、扫描和第二模型复审，不适用于所有风险等级。** 应按改动范围、可逆性、数据/权限和外部副作用分级。
4. **[中｜伪独立] 同一模型换上下文复审可以减少锚定，但不等于独立审查，仍可能共享训练偏差和盲区。
5. **[中｜概念绝对化] 把 Spec 称为“唯一事实源”会忽略可执行合同、测试、数据库约束、运行状态和正式决策记录。** 规格应与这些证据保持同步，而非单方面替代。
6. **[中｜安全示例薄弱] “密码至少 8 位 + bcrypt”不应当作通用现代认证答案。** 密码策略、哈希参数、MFA、撞库防护和标准要求依系统威胁模型及当前规范决定。
7. **[低｜严重赘述] 同一主题先后出现终版、首版+修改、个人经验、详细解析和附录，318 行中大量重复。** 建议只留一段直接答和一套风险分级流程。

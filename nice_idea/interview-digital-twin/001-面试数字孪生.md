# 面试数字孪生

## 1. Idea 概述

面试数字孪生不是简单记录“某道题会不会”，而是在持续练习过程中建立一个可更新、可解释、带不确定性的个人能力模型。

系统将题目拆成细粒度概念节点，结合用户的正确率、回答质量、信心值、反应时间、提示次数和遗忘速度，持续估计用户对每个概念的掌握程度。随后，系统不再随机选择下一题，而是优先选择能够最大程度降低认知不确定性、暴露潜在薄弱点或提升目标岗位覆盖率的问题。

最终它需要回答三个比“今天有几道题待复习”更有价值的问题：

1. 我真正掌握了哪些能力，证据是什么？
2. 下一道题问什么，最能帮助系统理解或提升我的能力？
3. 如果明天参加目标岗位面试，我最可能在哪些知识点上失败？

一句话定位：

> 用概率模型维护一个会随练习演化的“个人面试能力镜像”，再用主动学习决定最值得练习的下一题。

---

## 2. 为什么值得做

### 2.1 普通题库的问题

普通题库通常只有以下状态：

- 看过或没看过；
- 收藏或未收藏；
- 自评“不会、困难、一般、简单”；
- 基于题目级 FSRS 计算下一次复习时间。

这些状态无法回答：

- 两道题是否在考察同一个底层概念；
- 用户答错是概念不懂、记忆衰退，还是表达失败；
- 用户对某个领域掌握度高，但系统为什么仍然不确定；
- 哪道题最值得现在提问；
- 一个知识缺口会影响多少其他题目；
- 用户的自信是否与真实能力匹配。

### 2.2 与 FSRS 的关系

FSRS 解决的是：

> 一张已学习卡片应该什么时候再次出现？

数字孪生解决的是：

> 用户具备哪些能力、系统还不知道什么、下一次观察什么最有价值？

二者不是替代关系：

- FSRS 继续负责题目级记忆调度；
- 数字孪生负责概念级能力估计和全局选题；
- 最终调度器综合“记忆到期程度、信息增益、岗位权重和知识依赖”选择下一题。

---

## 3. 产品目标与边界

### 3.1 产品目标

1. 建立概念级而非题目级的掌握度模型。
2. 给每个估计附带置信区间，避免伪精确。
3. 使用主动学习选择信息增益最大的下一题。
4. 识别“高信心但低正确率”的危险盲区。
5. 预测近期面试风险，并给出可追溯证据。
6. 与现有 Markdown 题库、随机练习和 FSRS 平滑集成。

### 3.2 非目标

首期不追求：

- 用单个分数定义用户的综合面试水平；
- 在数据很少时声称模型预测准确；
- 完全由 LLM 决定概念图和评分结果；
- 取代人工对答案、题目标签和评分标准的审核；
- 做跨用户排名或招聘筛选。

数字孪生首先是个人学习工具，不是人才测评系统。

## 4. 核心概念

### 4.1 Concept：概念节点

概念节点表示可被独立观察和更新的最小知识单元，例如：

```text
Python 垃圾回收
├── 引用计数
├── 循环引用
├── 分代回收
├── 标记清除
├── gc 模块
└── __del__ 与对象生命周期
```

一个概念节点至少包含：

```ts
interface Concept {
  id: string;
  name: string;
  aliases: string[];
  description: string;
  domain: string;
  prerequisites: string[];
  relatedConcepts: string[];
  sourceDocuments: string[];
  importanceByTarget: Record<string, number>;
}
```

### 4.2 Question-Concept Mapping：题目与概念映射

一道题可以观察多个概念，但每个概念的权重不同：

```ts
interface QuestionConceptEdge {
  questionId: string;
  conceptId: string;
  weight: number;          // 该概念在本题中的占比
  discrimination: number;  // 题目区分不同能力水平的能力
  required: boolean;       // 缺失时是否构成关键错误
  evidenceAnchors: string[];
}
```

映射来源分为三层：

1. 确定性规则：标题、标签、章节和显式 Wiki Link。
2. LLM 候选：从“面试直接答”和“详细解析”抽取概念。
3. 人工确认：对新概念、关键边和权重进行审核。

LLM 只生成候选，不直接成为事实来源。

### 4.3 Observation：学习观测

每次作答产生一条不可变观测事件：

```ts
interface AnswerObservation {
  id: string;
  userId: string;
  questionId: string;
  startedAt: string;
  submittedAt: string;
  answerMode: 'self-rating' | 'text' | 'voice';
  score: number;             // 归一化到 0~1
  confidence: number;        // 作答前或作答后自评，0~1
  responseTimeMs: number;
  hintCount: number;
  conceptEvidence: Array<{
    conceptId: string;
    score: number;
    evidence: string[];
    evaluatorConfidence: number;
  }>;
  evaluatorVersion: string;
}
```

观测事件不能被后续模型更新覆盖。模型状态可以重算，原始证据必须保留。

### 4.4 Belief State：能力信念状态

系统保存的不是“用户一定会”，而是：

```ts
interface ConceptBelief {
  conceptId: string;
  masteryMean: number;
  masteryVariance: number;
  lastObservedAt: string | null;
  evidenceCount: number;
  forgettingRate: number;
  confidenceCalibrationGap: number;
  modelVersion: string;
}
```

`masteryMean` 表示当前掌握度估计，`masteryVariance` 表示模型的不确定性。没有足够证据时，系统应展示“未知”，而不是默认“不掌握”。

## 5. 能力模型设计

### 5.1 第一阶段：可解释的启发式模型

第一阶段先构建可调试基线，避免直接进入复杂概率模型。

概念掌握度由近期观测加权得到：

```text
observation_weight
= question_concept_weight
 × evaluator_confidence
 × time_decay
 × response_quality
 × no_hint_factor
```

同时单独维护：

- 正确性均值；
- 回答稳定性；
- 平均反应时间；
- 信心校准偏差；
- 最近一次成功和失败时间；
- 证据数量与来源题目数。

该版本的价值是提供可解释基线，也为后续概率模型准备训练和回放数据。

### 5.2 第二阶段：Time-aware Bayesian Knowledge Tracing

BKT 为每个概念维护隐变量 `L`，表示用户是否掌握该概念：

- `P(L0)`：初始掌握概率；
- `P(T)`：一次练习后学会的概率；
- `P(G)`：未掌握但猜对的概率；
- `P(S)`：掌握但失误的概率。

每次观测后通过贝叶斯更新掌握概率。为了适配面试场景，需要扩展：

1. 将二元正确/错误改为分段或连续得分；
2. 引入时间衰减，模拟长时间未复习后的遗忘；
3. 引入回答模式，区分自评、文字和语音证据强度；
4. 使用题目与概念权重拆分多概念题的观测；
5. 将提示次数和反应时间作为观测质量修正项。

示意：

```text
prior mastery
  ↓ time-aware forgetting
decayed mastery
  ↓ answer likelihood
posterior mastery
  ↓ learning transition
next mastery
```

### 5.3 第三阶段：IRT 题目参数估计

IRT 用于分离“用户能力”和“题目难度”。以 2PL 模型为例：

```text
P(correct | ability, item)
= sigmoid(discrimination × (ability - difficulty))
```

核心参数：

- `ability θ`：用户在某个领域或概念上的能力；
- `difficulty β`：题目难度；
- `discrimination α`：题目区分不同能力水平的程度；
- 可选 `guessing c`：猜对概率。

单用户本地系统无法可靠地从极少数据中同时估计全部参数，因此采用以下策略：

1. 题目难度初值来自人工或 LLM 候选；
2. 区分度先使用统一先验；
3. 用户数据足够后才进行个性化校准；
4. 参数始终展示样本数和不确定性；
5. 不把题目参数包装成客观真值。

### 5.4 推荐的混合模型

最终采用分层混合方案：

```text
FSRS
负责题目级记忆到期程度

BKT
负责概念级掌握状态更新

IRT
负责题目难度与用户能力分离

Knowledge Graph
负责前置依赖与风险传播
```

不建议第一版同时实现所有模型。正确顺序是：

```text
可解释启发式基线
→ BKT
→ 信息增益选题
→ 数据足够后再引入 IRT
```

## 6. 概念图谱

### 6.1 节点与边

概念图包含以下边类型：

| 边类型 | 含义 | 示例 |
| --- | --- | --- |
| `prerequisite_of` | 前置知识 | 引用计数 → Python GC |
| `part_of` | 组成关系 | 标记清除 → 循环垃圾回收 |
| `contrasts_with` | 对比关系 | CPython GC ↔ JVM GC |
| `often_confused_with` | 易混淆 | 并发 ↔ 并行 |
| `applied_in` | 应用场景 | 一致性哈希 → 负载均衡 |
| `evidenced_by` | 观测来源 | 概念 → 题目 |

### 6.2 图谱的作用

图谱不是为了做一个漂亮的可视化，而是参与以下计算：

- 前置知识未掌握时，降低上层概念的可信掌握度；
- 一个核心概念薄弱时，向相关题目传播风险；
- 选题时避免连续提问语义重复的问题；
- 为风险报告生成“为什么”的解释路径；
- 在数据稀疏时，通过相邻节点提供弱先验。

### 6.3 风险传播

某个概念的面试风险可以由以下部分组成：

```text
concept_risk
= weakness
 × target_importance
 × graph_centrality
 × uncertainty
 × recency_factor
```

必须区分：

- `weakness` 高：已有证据表明掌握不足；
- `uncertainty` 高：系统没有足够证据；

前者应安排巩固，后者应安排诊断题。

## 7. 信息增益选题

### 7.1 核心目标

系统选择下一题时，不只考虑“最该复习”，还要考虑“回答之后我们能学到多少关于用户的新信息”。

候选题效用函数：

```text
utility(question)
= w1 × expected_information_gain
 + w2 × overdue_score
 + w3 × target_job_relevance
 + w4 × prerequisite_value
 + w5 × weakness_repair_value
 - w6 × repetition_penalty
 - w7 × fatigue_cost
```

### 7.2 期望信息增益

对每道候选题，模型预测不同回答结果的概率，并计算回答前后信念熵的期望变化：

```text
EIG(question)
= H(current belief)
 - Σ P(outcome) × H(belief after outcome)
```

直观解释：

- 一道过于简单的题，无论答对还是答错概率都极端，信息量低；
- 一道过于困难的题，大概率只能确认“不会”，信息量也有限；
- 难度接近当前能力、同时覆盖高不确定概念的题，信息量最大。

### 7.3 调度策略

提供三种模式：

| 模式 | 主要目标 |
| --- | --- |
| 诊断模式 | 最大化信息增益，快速建立能力画像 |
| 学习模式 | 平衡薄弱点修复、FSRS 到期和知识依赖 |
| 冲刺模式 | 最大化目标岗位高频知识的通过概率 |

用户应知道当前为什么收到这道题，例如：

> 选择本题是因为“循环引用”和“分代回收”的掌握度不确定，同时它们影响 7 道 Python 相关问题。

## 8. “明天最可能挂在哪里”预测

### 8.1 预测对象

预测结果不是一个笼统的“通过率”，而是一组带证据的风险项：

```ts
interface InterviewRisk {
  conceptId: string;
  riskScore: number;
  uncertainty: number;
  targetImportance: number;
  reasons: string[];
  supportingObservations: string[];
  recommendedQuestions: string[];
}
```

### 8.2 风险来源

风险综合以下因素：

- 近期连续答错；
- 长时间未复习导致的遗忘；
- 高信心但低得分；
- 回答正确但反应时间显著偏长；
- 必要概念遗漏；
- 前置概念薄弱；
- 目标岗位高频要求；
- 估计不确定性过高；
- 只在一道题上成功，缺乏迁移证据。

### 8.3 输出示例

```text
高风险：Python 循环引用处理

风险：0.78
不确定性：中

原因：
- 最近两次回答都遗漏 gc.collect 的适用边界
- 对“引用计数能否处理环”给出了高信心错误答案
- 该概念同时影响 Python GC、内存泄漏排查两类问题

建议：
- 先回答“引用计数为什么无法回收环”
- 再完成一题包含弱引用与 __del__ 的迁移题
```

页面必须展示“预测依据”和“不确定性”，禁止只展示一个看似精确的百分比。

## 9. 用户交互

### 9.1 首次诊断

首次进入时，用户选择：

- 目标岗位；
- 面试日期；
- 重点技术栈；
- 自评水平；
- 每日可用时间。

系统从不同领域、难度和概念簇中挑选少量高区分度题目，快速构建初始画像。

### 9.2 作答前

展示题目，但隐藏答案。记录：

- 开始时间；
- 作答前信心值；
- 是否请求提示；
- 选择文字或语音模式。

作答前信心非常重要，它能发现“错误但自信”的危险盲区。

### 9.3 作答后

系统输出：

1. 总体评分与评估置信度；
2. 命中的概念；
3. 遗漏和错误概念；
4. 用户原话对应的证据；
5. 标准答案中的对应位置；
6. 能力模型发生了什么变化；
7. 为什么推荐下一道题。

### 9.4 数字孪生看板

看板建议包含：

- 概念掌握度图；
- 高风险与高不确定性分栏；
- 信心校准曲线；
- 掌握度随时间变化；
- 目标岗位覆盖率；
- 今日最有价值的三道题；
- 模型证据数量和最近更新时间。

避免用单一雷达图掩盖不确定性。

## 11. 数据存储

### 11.1 Local-first 原则

项目当前是本地 Markdown 知识库，数字孪生也应优先保持本地可用：

- 原始回答和能力画像默认只保存在本机；
- 模型调用前明确展示发送范围；
- 支持仅使用本地模型；
- 支持导出、删除和完整重算；
- 不将未经同意的语音、逐字稿或评分上传第三方。

### 11.2 推荐存储结构

早期可使用 JSONL：

```text
admin/twin/
├── concepts.json
├── question-concepts.json
├── observations.jsonl
├── belief-snapshots.jsonl
└── model-config.json
```

当事件数量增加后迁移到 SQLite：

- 事务和索引更可靠；
- 可以按概念、题目和时间高效回放；
- 便于执行模型版本迁移；
- 仍然保持单机、零服务依赖。

### 11.3 Event Sourcing

能力状态是观测事件的派生结果：

```text
observations + model version + parameters
→ deterministic replay
→ current belief state
```

这样可以：

- 修复算法后重算历史；
- 对比不同模型版本；
- 解释某个掌握度为何发生变化；
- 避免一次错误更新永久污染用户画像。

## 12. 评估体系

### 12.1 不能只看用户是否喜欢

至少需要评估四个层面：

| 层面 | 指标 |
| --- | --- |
| 预测质量 | Brier Score、Log Loss、AUC、校准曲线 |
| 选题价值 | 单位题目带来的熵下降、薄弱点发现率 |
| 学习效果 | 延迟测试正确率、迁移题正确率、遗忘速度变化 |
| 产品效果 | 完成率、复习留存、诊断耗时、推荐接受率 |

### 12.2 离线回放

用历史观测进行时间切分：

1. 使用时间点 `T` 之前的数据构建画像；
2. 预测 `T` 之后的作答结果；
3. 比较启发式、BKT、IRT 和混合模型；
4. 禁止把未来观测泄漏到训练数据；
5. 按概念样本量分别报告结果。

### 12.3 评分器评估

LLM 评分器必须单独建设评测集：

- 同一答案多次评分的一致性；
- 与人工评分的一致性；
- 对答案长度和表达风格的偏差；
- 对错误但流畅回答的识别率；
- 引用证据是否真的来自用户答案；
- 模型升级前后的回归测试。

## 13. MVP

第一版不需要完整 BKT、IRT 和图神经网络。MVP 只验证三件事：

1. 概念级画像是否比题目级记录更有用；
2. “为什么推荐这道题”的解释是否可信；
3. 风险报告是否能发现用户自己忽视的盲区。

### 13.1 MVP 范围

- 选择一个分类，例如 Python；
- 人工整理 30~50 个概念节点；
- 为现有题目建立带权概念映射；
- 记录正确率、信心、反应时间和提示次数；
- 使用可解释的加权贝叶斯或 Beta-Bernoulli 模型；
- 实现诊断模式和信息增益选题；
- 输出高风险、高不确定性和高信心错误三个榜单；
- 与 FSRS 到期题混合调度。

### 13.2 MVP 成功标准

- 推荐理由可以定位到具体观测和概念；
- 用户能理解掌握度与不确定性的区别；
- 自适应选题比随机选题更快发现已知薄弱点；
- 重放同一事件序列能得到相同画像；
- 模型参数和评分器版本可追踪。

## 14. 分阶段路线

### Phase 0：数据基础

- 定义 Concept、Observation、Belief Schema；
- 建立题目稳定 ID；
- 完成 Python 分类的概念标注；
- 建立事件存储和回放工具；
- 设计人工评分样本集。

### Phase 1：可解释数字孪生

- 接入作答前信心和反应时间；
- 实现概念级掌握度与不确定性；
- 实现风险看板；
- FSRS 与概念画像联合调度；
- 显示每次更新的证据链。

### Phase 2：主动学习

- 实现期望信息增益；
- 增加诊断、学习、冲刺模式；
- 加入题目重复惩罚和疲劳约束；
- 进行离线回放和小规模 A/B 对比。

### Phase 3：概率模型升级

- 引入 Time-aware BKT；
- 数据足够后尝试 IRT；
- 对比模型校准与泛化能力；
- 支持模型版本并行回放。

### Phase 4：岗位预测

- 建立岗位到概念的权重映射；
- 生成明日风险报告；
- 支持面试日期倒计时训练；
- 根据真实面试复盘校准风险模型。

## 15. 技术难点

### 15.1 评分噪声

LLM 对开放式答案评分存在漂移。解决方式：

- 使用结构化 Rubric；
- 要求评分器引用原文证据；
- 对关键概念使用确定性检查；
- 保存评分器模型和 Prompt 版本；
- 低置信度结果进入人工确认；
- 用多次评分或多评委处理高风险样本。

### 15.2 多概念题的归因

一道题答错不能简单让所有关联概念同时降分。需要：

- 将评分落实到答案中的概念证据；
- 对必要概念和补充概念使用不同权重；
- 对无法归因的错误降低更新强度；
- 使用追问进一步定位缺口。

### 15.3 冷启动

初始数据不足时：

- 显示“未知”而不是低分；
- 使用少量高区分度诊断题；
- 使用自评作为弱先验，不作为事实；
- 让用户选择熟悉领域缩小搜索空间；
- 避免过早拟合个体遗忘率和 IRT 参数。

### 15.4 参数不可辨识

单用户、小样本条件下，能力、题目难度、评分器偏差可能互相混淆。必须：

- 固定一部分参数；
- 使用合理先验；
- 报告置信区间；
- 与简单基线比较；
- 数据不足时拒绝升级复杂模型。

### 15.5 图谱错误传播

错误的前置依赖会放大风险。图谱边需要：

- 标记来源和置信度；
- 支持人工禁用；
- 区分强依赖和弱关联；
- 在算法中限制传播深度和衰减；
- 提供图谱变更后的重算机制。

## 16. 可展示的技术亮点

完成后，该 Idea 可以形成一条完整的技术叙事：

1. 将 Markdown 题库解析成概念图谱。
2. 将开放式作答转化为带证据的结构化观测。
3. 用概率模型维护能力信念，而不是静态分数。
4. 使用主动学习最大化下一题的信息增益。
5. 联合 FSRS、BKT、IRT 和图谱完成个性化调度。
6. 使用 Event Sourcing 回放和比较不同模型版本。
7. 用校准误差和延迟测试验证预测，而不是只展示 Demo。
8. 在 UI 中显式呈现不确定性、证据和模型局限。

真正的辨识度不在于用了多少算法名，而在于：

> 每个能力判断都能回到观测证据，每次选题都有可计算的理由，每个预测都承认不确定性。

## 17. 最终形态

最终，用户打开项目时看到的不再是一排分类和一道随机题，而是：

```text
距离目标面试：1 天

当前最危险的三个知识缺口：
1. Python 循环引用：高信心错误，风险 0.78
2. Kafka Rebalance：14 天未验证，风险 0.71
3. Agent 终止条件：证据不足，不确定性 0.69

现在最值得回答：
“引用计数为什么无法解决循环引用？”

选择原因：
- 可同时验证两个高风险概念
- 预计使 Python 内存管理画像的不确定性下降 18%
- 回答后可决定是否需要继续追问 gc 模块
```

这时它才真正从“面试题收藏夹”演化成“个人面试能力操作系统”。

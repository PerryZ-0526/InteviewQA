# 异步链路与断点续跑设计

## 一、背景

Brief 和 Ask 两条管线都是长任务——Brief 一次完整扫描涉及数十次 LLM 调用和多次 Gmail API 请求，Ask ReAct Loop 复杂查询可能迭代 6-15 轮。单次 invoke 有 50 秒超时限制，无法在单次调用中跑完全程。

解决思路：将长任务拆分为离散切片，每个切片执行一部分工作后持久化当前状态（checkpoint），交还控制权给前端；前端轮询状态，连续调用推进直到完成。进程崩溃后，从最近一次 checkpoint 恢复，不丢失已完成的工作。

---

## 二、整体架构
```
┌──────────────────────────────────────────────────┐
│                    前端                           │
│                                                  │
│  startRun(pipeline, params)                      │
│       │                                          │
│       ▼                                          │
│  loop:                                           │
│    run = getRun(run_id)  ← 轮询 (2.5s interval)  │
│    updateUI(run.progress)                        │
│    if run.needs_continue:                        │
│      run = continueRun(run_id)                   │
│    else:                                         │
│      showResult(run.result)                      │
│      break                                       │
└──────────────────┬───────────────────────────────┘
                   │  JSON-RPC (Executa)
                   ▼
┌──────────────────────────────────────────────────┐
│              Executa 后端                          │
│                                                  │
│  MAIL_AGENT_RUNS: dict[str, BaseCheckpoint]      │
│  (in-memory, 进程生命周期)                         │
│                                                  │
│  ┌─ start ──────────────────────────────────┐   │
│  │  创建 BaseCheckpoint                      │   │
│  │  dispatch: Brief → brief FSM              │   │
│  │           Ask   → ReAct Loop              │   │
│  └──────────────────────────────────────────┘   │
│                   │                              │
│  ┌─ continue ───────────────────────────────┐   │
│  │  读取 checkpoint                         │   │
│  │  推进一个切片（brief: 一批, ask: 一轮）     │   │
│  │  写入 checkpoint                         │   │
│  │  返回 needs_continue + progress           │   │
│  └──────────────────────────────────────────┘   │
│                   │                              │
│  ┌─ checkpoint 持久化 ───────────────────────┐   │
│  │  runs/background/<run_id>.json            │   │
│  │  每次切片后同步写入磁盘                     │   │
│  └──────────────────────────────────────────┘   │
└──────────────────────────────────────────────────┘
```

## 三、Checkpoint 状态设计

### 3.1 公共基座

Brief 和 Ask 的执行模型不同（线性游标 vs 对话循环），中间状态结构不可合并。但共享统一的生命周期管理——创建、轮询、推进、清理、恢复。
```
BaseCheckpoint:
  run_id: str
  pipeline: "brief" | "ask"             ← 分发键
  mailbox: str
  status: "queued" | "running" | "done" | "failed"
  progress: dict                        ← 前端轮询用的轻量进度
    { stage: str, current: int, total: int, detail: str }
  warnings: list[str]
  started_at: str
  updated_at: str
  error: str
  needs_continue: bool
```

公共行为：

- `getRun(run_id)` → 返回公共视图（前端无需区分 pipeline 类型）
- `_save_checkpoint(run_id)` → 写入 `runs/background/<run_id>.json`
- `_load_checkpoint(run_id)` → 从磁盘恢复
- `_on_restart()` → 进程启动时扫描未完成的 checkpoint，恢复或标记

### 3.2 Brief 状态（游标式）
```
BriefRunState extends BaseCheckpoint:
  stage: "queued" | "phase1" | "check_replied" | "phase2" | "finalizing" | "done"

  # 扫描结果缓存（Phase1 之前写入，后续阶段复用）
  messages: list[dict]            # 扫描到的所有邮件摘要

  # Phase1 游标
  phase1_cursor: int              # 已分类的消息数，下次从该位置继续
  phase1_batch_size: int          # 每批分类数（默认 20）
  candidates: list[dict]          # 已累积的候选列表
  low_value_items: list[dict]     # 已累积的低价值邮件

  # Phase2 游标
  phase2_cursor: int              # 已评估的候选数
  judgments: list[dict]           # 已累积的评估结果

  # 卡片
  cards_version: int              # 单调递增版本号，前端增量同步
```

恢复逻辑：读取 checkpoint → 当前 `stage` 是 `phase1` → 从 `phase1_cursor` 位置取出下一批未分类的消息 → 调 LLM 分类 → cursor 后移 → 保存 checkpoint。

**不需要重新扫描**：messages 已在 checkpoint 中缓存。**不需要重新分类**：cursor 记录精确的已处理位置。

### 3.3 Ask ReAct 状态（对话快照式）
```
AskRunState extends BaseCheckpoint:
  iteration: int                          # 当前轮次

  # 核心：对话历史即状态
  messages: list[dict]                    # LLM 标准 messages 格式
    [
      {role: "system", content: "基础层 prompt（Round 2+ 不含语义展开引导层）"},
      {role: "user", content: "任务+用户原始请求"},
      {role: "assistant", content: "Think: ...", tool_calls: [...]},    ← Round 1
      {role: "tool", tool_call_id: "1", content: "{total: 23, ...}"},  ← Round 1 结果
      {role: "assistant", content: "Think: ...", tool_calls: [...]},    ← Round 2
      {role: "tool", tool_call_id: "2", content: "{results: [...]}"},  ← Round 2 结果
      ...                                                                 ← 断点在这里
    ]

  # 辅助字段（从 messages 中派生，给前端展示）
  tool_call_history: list[dict]           # 已完成的工具调用及结果摘要
  accumulated_findings: list[dict]        # 部分结果，前端增量展示

  # 策略
  max_iterations: int                     # 最大迭代次数
  plan_version: int | None                # custom run 策略版本

  # Round 1 语义展开是否已完成（决定恢复时是否需要重新注入引导层）
  semantic_expansion_done: bool
```

恢复逻辑：读取 checkpoint → 将 `messages[]` 完整传入 LLM → Agent 看到最后一条 tool 消息的内容就知道自己刚才观察到了什么、下一步该干什么。**恢复是 LLM 多轮对话的原生能力——不需要额外抽象。**

### 3.4 为什么不合并在同一个 State


|            | Brief                                                | Ask ReAct          |
| ---------- | ---------------------------------------------------- | ------------------ |
| **执行模型**   | 线性 FSM，游标推进                                          | 循环，对话驱动            |
| **中间状态结构** | cursor + list                                        | messages\[\]       |
| **恢复单位**   | "从第 N 个候选继续"                                         | "从上一次 Observe 后继续" |
| **恢复所需数据** | cursor 位置 + 已累积候选人                                   | 完整对话历史             |
| **字段交集**   | 很小。强行合并 → union type → 每个使用者都要判断 `pipeline == brief` |                    |


合并成一个 state 意味着 `phase1_cursor` 和 `messages[]` 同时存在但互斥——类型安全丢失、代码可读性下降、每次扩展新字段都要判断对另一端是否有副作用。

**共享基座、各自扩展** 是正确做法：公共部分（生命周期 + 持久化 + 前端接口）一处维护，pipeline 专用部分各自独立演进。

## 四、切分粒度

### 4.1 Brief：按批次

Brief 每批操作保证在 invoke timeout 内完成：
```
continue (stage=phase1):
  从 messages[phase1_cursor : phase1_cursor + batch_size] 取出一批
  调 LLM 分类 (1 次 sampling 调用)
  cursor += batch_size
  保存 checkpoint
  return needs_continue=true (除非 cursor >= len(messages))

continue (stage=phase2):
  从 candidates[phase2_cursor : phase2_cursor + 4] 取出一批
  调 LLM 评估 (4 次并发 sampling 调用)
  cursor += 4
  写入 cards shard
  保存 checkpoint
  return needs_continue=true (除非 cursor >= len(candidates))
```

选择 `batch_size=20`（Phase1）和 `slice=4`（Phase2）是因为：一次 LLM 调用约 5-15 秒，加上 Gmail API 调用开销，单切片在 50 秒 timeout 内稳定完成。

### 4.2 Ask ReAct：按轮次

每轮（一次 Think + 一次 Act + Observe）是一个不可分割的切片：
```
continue:
  1. 从 checkpoint 加载 messages[]
  2. 将 messages[] 发给 LLM
     → 得到 Think 文本 + tool_calls[]
  3. 如果没有 tool_calls（Agent 输出最终答案）:
     → status=done, needs_continue=false, 写入 result
  4. 如果有 tool_calls:
     → 执行所有 tool_calls（独立调用可并行）
     → 将 assistant 消息 + tool 结果追加到 messages[]
     → iteration += 1
     → 保存 checkpoint
     → needs_continue = iteration < max_iterations
```

为什么一轮作为一个切片，而不是一轮中的每个工具调用：

- 一轮中多个并行工具调用之间没有 LLM 推理——断在这里没有价值，恢复后 Agent 还是要等所有并行调用返回才能继续思考
- LLM 调用是耗时瓶颈，一轮的耗时上限约等于 1 次 LLM 推理 + 最长的一次工具调用，在 timeout 内安全
- 切分太细会导致前端轮询次数膨胀，增加总延迟

## 五、崩溃恢复

### 5.1 正常执行路径
```
start → checkpoint(queued)
  → continue → checkpoint(推进)
  → continue → checkpoint(推进)
  → ... 
  → continue → checkpoint(done), needs_continue=false
```

### 5.2 进程崩溃后
```
── 进程重启 ──

前端调 getRun(run_id):
  → _load_checkpoint(run_id)
  → status = "running"（上次保存的）
  → 不再标记为 failed
  → 返回 needs_continue=true, stage=上次的 stage

前端继续调 continueRun(run_id):
  → 读取 checkpoint
  → 根据 pipeline 类型分发:
      brief: 从 stage + cursor 恢复
      ask:   从 messages[] 恢复，作为下一轮 LLM 调用的上下文
  → 继续推进
  → 写入新 checkpoint
```

### 5.3 启动扫描

进程启动时扫描 `runs/background/` 目录：
```
for each checkpoint in runs/background/:
  if checkpoint.status in ["queued", "running"]:
    if checkpoint.updated_at 超过 N 小时未更新:
      → 标记为 failed（可能前端已放弃）
    else:
      → 恢复为 running，等待前端继续轮询
```

### 5.4 Brief 恢复示例
```
崩溃前 checkpoint:
  stage: "phase2"
  phase2_cursor: 8
  candidates: [c1...c25]    ← 共 25 个候选
  judgments: [j1...j8]      ← 已评估 8 个

恢复后第一次 continue:
  读取 checkpoint
  stage=phase2, cursor=8
  取 candidates[8:12] → 评估 c9, c10, c11, c12
  将结果追加到 judgments
  cursor = 12
  保存 checkpoint
```

无需重新扫描、重新分类、重新评估已完成的候选。

### 5.5 Ask ReAct 恢复示例
```
崩溃前 checkpoint:
  iteration: 3
  messages: [
    {role: "system", content: "基础层..."},
    {role: "user", content: "看看有没有等我回复的邮件"},
    {role: "assistant", content: "Think: 先搜索...", tool_calls: [search_emails]}  ← R1
    {role: "tool", ...content: "38封邮件..."},
    {role: "assistant", content: "Think: 批量检查回复状态...", tool_calls: [check×2]} ← R2
    {role: "tool", ...content: "needs_reply: t1,t7,t15,t23,t28"},
    {role: "assistant", content: "Think: 6个线程需要深入...", tool_calls: [read×6]}  ← R3
    {role: "tool", ...content: "t1: Alice询问Q3预算，需要回复..."},  ← 崩溃点
  ]

恢复后:
  将 messages[] 完整传入 LLM
  LLM 看到最后一条 tool 消息的内容，知道 t1/t7/t15/t23/t28 的线程上下文已读完
  → Think: "t7和t28是误判，t1和t15需要回复，查一下联系人记忆"
  → tool_calls: [get_contact_context×2]
  → 继续执行...
```

不需要重新搜索、重新检查回复状态、重新读线程——对话历史完整保留了已完成的每一步。

## 六、前端接口

三条 RPC 方法，Brief 和 Ask 共用：

### `start_mail_agent_run`
```
输入:
  pipeline: "brief" | "ask"
  params:   pipeline 专用参数

输出:
  {
    run_id: "run_7f3a2b",
    status: "queued",
    needs_continue: true,
    progress: { stage: "queued" }
  }
```

### `continue_mail_agent_run`
```
输入:
  run_id: str

输出:
  {
    run_id: "run_7f3a2b",
    status: "running" | "done" | "failed",
    needs_continue: bool,
    progress: { stage: "phase2", current: 12, total: 25 },
    partial: { ... }            # 增量数据，前端合并展示
  }
```

### `get_mail_agent_run`
```
输入:
  run_id: str

输出:
  {
    run_id: "run_7f3a2b",
    status: "running",
    needs_continue: true,
    progress: { stage: "phase2", current: 12, total: 25 },
    cards_added: 4,
    cards_version: 3,
    warnings: [],
    error: ""
  }
```

前端轮询无需区分 pipeline 类型——三种类型共享同一套返回结构。

## 七、对比


|                     | Brief                        | Ask ReAct                    |
| ------------------- | ---------------------------- | ---------------------------- |
| **执行模型**            | 线性 FSM，6 个 stage             | ReAct 循环，动态轮次                |
| **切片单位**            | 一个 batch（20 条分类 或 4 个候选评估）   | 一轮（Think + Act + Observe）    |
| **Checkpoint 结构**   | 游标 + 累积列表                    | 完整对话历史                       |
| **恢复方式**            | 从 cursor 位置继续                | messages\[\] 传入 LLM 继续对话     |
| **单次 continue 耗时**  | \~5-20s（1 次 LLM + Gmail API） | \~5-30s（1 次 LLM + 0-N 次工具调用） |
| **长查询 continue 次数** | \~10-20 次                    | \~5-15 次                     |
| **进程重启恢复**          | cursor 位置保证不重复不遗漏            | 对话历史保证 Agent 上下文完整           |
| **前端接口**            | 统一 `start / continue / get`  | 同上                           |

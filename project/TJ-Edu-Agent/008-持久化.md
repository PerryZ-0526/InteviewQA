# 持久化-draft

你说得对，我前一版把“LangGraph State → Redis”说得过于简单。\*\*如果 State 里包含完整 messages、RAG 文档、Tool 大结果等大字段，把完整 checkpoint 长期塞 Redis 并不是一个合理的生产设计。\*\*我查了 LangGraph、Dify、Letta、Mem0 的开源实现后，我会把你这个系统的存储方案定成下面这样。


| 数据                               | 主存储                  | Redis            | 对象存储               |
| -------------------------------- | -------------------- | ---------------- | ------------------ |
| LangGraph checkpoint 元数据、小 State | MySQL                | 只缓存最新 checkpoint | —                  |
| State 中的大字段                      | MySQL 只存引用           | 可缓存热点值           | **完整数据放 MinIO/S3** |
| 当前会话消息                           | MySQL                | 最近 N 轮缓存         | 超大 Tool/附件可外置      |
| 长期记忆“原子记忆”                       | MySQL + 向量库          | 热点缓存             | —                  |
| 长期记忆的大原始材料                       | MySQL 存索引            | —                | **MinIO/S3**       |
| 用户画像                             | **MySQL**            | 可缓存              | 一般不需要              |
| 文件、网页快照、Tool 大结果、报告              | MySQL 存 metadata/ref | —                | **MinIO/S3**       |


核心原则就是一句话：

> **MySQL 存“状态索引和结构化事实”，对象存储存“大 Payload”，Redis 只承担热数据和运行时加速，不承担大规模长期持久化。**

### 1. LangGraph State / Checkpoint：不要把完整大 State 原封不动塞 Redis

这里首先要区分“逻辑 checkpoint”和“物理存储”。从 LangGraph 当前实现看，逻辑上 checkpoint 确实表示某个 super-step 下完整的 State；官方文档也明确说，默认会保存各 State channel 的完整值，因此长线程、累积型 messages 会产生明显的存储膨胀。LangGraph 现在甚至增加了 `DeltaChannel` 来缓解 append-heavy channel 的重复存储。([GitHub](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/checkpointers.mdx?utm_source=chatgpt.com "docs/src/oss/langgraph/checkpointers.mdx at main · langchain-ai/docs · GitHub"))

但 LangGraph 自己的生产级 PostgresSaver **物理上并不是简单地每次把整份 State 序列化成一个巨大 JSON**。源码中，简单的 `str/int/bool` 可以 inline 在 checkpoint 中，而复杂 channel 会拆到独立的 `checkpoint_blobs` 表，并通过 `(thread_id, checkpoint_ns, channel, version)` 进行版本化存储；只有新版本 channel 才重新写 blob。([GitHub](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/langgraph/checkpoint/postgres/base.py?utm_source=chatgpt.com "langgraph/libs/checkpoint-postgres/langgraph/checkpoint/postgres/base.py at main · langchain-ai/langgraph · GitHub"))

这其实已经告诉我们正确方向：
```text
Checkpoint
   │
   ├── 小字段 → DB
   │
   └── 大字段 → 单独存储，通过版本/引用关联
```

对于你现在 **MySQL + Redis + 对象存储** 的技术栈，我不会硬搬 PostgresSaver，而会做一个自己的 Checkpointer 存储层：
```text
agent_checkpoint
--------------------------------
checkpoint_id
thread_id
checkpoint_ns
parent_checkpoint_id
state_manifest
metadata
status
created_at
```

其中 `state_manifest` 不是完整大 State，而类似：
```json
{
  "query": "......",
  "plan": {...},
  "current_step": 3,

  "messages": {
    "storage": "object",
    "key": "checkpoint/123/messages/v17.json.zst",
    "sha256": "..."
  },

  "search_result": {
    "storage": "object",
    "key": "checkpoint/123/search/v5.json.zst"
  }
}
```

这样 MySQL 保存的是**checkpoint 的结构和引用关系**，真正的大内容放 MinIO/S3。

这不是我自己凭空设计出来的思路。Dify 当前源码已经在做类似的事情：Workflow Node 的 `inputs/process_data/outputs` 如果超过配置大小，会进行 truncation，并把完整 JSON 通过 `FileService` 上传到 Storage，数据库保存截断版本以及对应的 `WorkflowNodeExecutionOffload` 引用；读取时再从 Storage 加载完整内容。([GitHub](https://github.com/langgenius/dify/blob/main/api/core/repositories/sqlalchemy_workflow_node_execution_repository.py?utm_source=chatgpt.com "dify/api/core/repositories/sqlalchemy_workflow_node_execution_repository.py at main · langgenius/dify · GitHub")) Dify 的 Storage 本身支持 S3、Azure Blob、阿里 OSS、Google Storage、腾讯 COS 等对象存储，而且现在还单独提供了 Workflow Run / Conversation 的 S3-compatible archive 配置。([GitHub](https://github.com/langgenius/dify/blob/main/api/extensions/ext_storage.py?utm_source=chatgpt.com "dify/api/extensions/ext_storage.py at main · langgenius/dify · GitHub"))

所以对于你的 Agent，State 中以下字段应该直接外置：
```text
完整 messages 历史
大段 Tool 返回
网页正文
RAG 大规模候选 Documents
文件解析结果
代码/报告
长规划轨迹
大 JSON
```

State 里只留下：
```text
artifact_id
object_key
hash
size
mime_type
schema_version
```

这样 LangGraph 逻辑上仍然拥有完整状态，只不过部分状态通过引用表示，需要时 hydrate 回来。

### 2. Checkpoint 到底存 MySQL 还是对象存储？

我的答案很明确：

> **MySQL 是 checkpoint 的控制面，对象存储是 checkpoint 大数据的数据面。**

不要反过来把：
```text
checkpoint_123.json
checkpoint_124.json
checkpoint_125.json
```

全部直接扔 S3，然后让 S3 充当 Checkpointer。

因为 Checkpointer 不只是“保存一个文件”，它还需要：
```text
thread_id 查询
checkpoint_id 查询
parent checkpoint
latest checkpoint
pending writes
状态版本
运行状态
恢复位置
```

这些查询关系型数据库明显更合适。

所以：
```text
                  MySQL
                    │
       checkpoint_id / thread_id
           state manifest
                    │
             object_key
                    ↓
                 MinIO
             大 State Payload
```

而且建议**按 State channel/字段外置，而不是整份 State 一个对象**。这样 `messages` 没变化而 `plan` 变化时，不需要重新上传几十 MB 的 messages。

甚至可以进一步使用：
```text
object_key =
state_blob/{sha256}.json.zst
```

做内容寻址和去重。

### 3. Redis 在这里到底存什么？

Redis 不应该再被定义成“State 持久化数据库”。

LangGraph 确实官方提供 RedisSaver，而且把它列为可用于生产的 Checkpointer；但“能够存”和“你的大 State 场景适合存”是两回事。([GitHub](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/checkpointers.mdx?utm_source=chatgpt.com "docs/src/oss/langgraph/checkpointers.mdx at main · langchain-ai/docs · GitHub"))

你的 Redis 我会限定为：
```text
最新 checkpoint 热缓存
session 当前状态缓存
分布式锁
Agent task lease
幂等 key
重复调用去重
当前执行节点
流式输出临时数据
用户画像热点缓存
Memory 检索结果缓存
```

例如：
```text
agent:thread:123:latest_checkpoint → cp_456
TTL = 30min

profile:user:123 → compact profile
TTL = 1h

idempotency:operation:xxx → SUCCESS
```

即使整个 Redis 被清空，**系统仍然应该能够依靠 MySQL + MinIO 恢复任务**。

这就是判断 Redis 定位是否正确的一个非常简单的标准。

Dify 自己的 docker-compose 里也直接把 Redis 标注为 cache，同时 DB 和 storage 是独立持久层。([GitHub](https://github.com/langgenius/dify/blob/main/docker/docker-compose.yaml?utm_source=chatgpt.com "dify/docker/docker-compose.yaml at main · langgenius/dify · GitHub"))

### 4. 长期记忆也不能作为“一大坨文本”存

你的第二个关键问题是：

> 长期记忆也可能很大，放哪里？

这里最容易犯的错误是搞一张：
```text
user_memory

user_id
memory LONGTEXT
```

然后一个用户半年以后 `memory` 变成几 MB。

生产系统不会这么设计。

长期记忆应该拆成**原子 Memory Item**：
```text
memory_item
--------------------------------
memory_id
user_id
memory_type
content
summary
importance
confidence
source_type
source_id
created_at
updated_at
valid_status
```

比如：
```text
M001
用户倾向申请人工智能方向研究生

M002
用户更偏向后端/Agent Platform 岗位

M003
用户希望优先考虑北京的实习岗位
```

这些是几百字甚至几十字的小记录，直接放 MySQL。

然后：
```text
memory_id
   ↓
embedding
   ↓
Vector DB
```

向量数据库只负责：

> “从十万条 Memory Item 中找哪些相关。”

MySQL 仍然是事实源。

Mem0 的 OSS 架构就是把 memory retrieval 建立在独立 Vector Store 上，可以配置 Qdrant、pgvector、Redis、Milvus、Weaviate 等，而不是把所谓“长期记忆”当成一个无限增长的 prompt 文本。([GitHub](https://github.com/mem0ai/mem0/blob/main/docs/open-source/configuration.mdx?utm_source=chatgpt.com "mem0/docs/open-source/configuration.mdx at main · mem0ai/mem0 · GitHub"))

Letta 的设计也很有参考意义。它明确区分有限的 Core Memory 和外部 Recall / Archival Memory；当前官方部署直接使用 Postgres + pgvector 作为持久化基础设施。([GitHub](https://github.com/letta-ai/letta/blob/main/letta/schemas/memory.py?utm_source=chatgpt.com "letta/letta/schemas/memory.py at main · letta-ai/letta · GitHub"))

因此：
```text
Long-term Memory
        │
        ├── 原子事实 / 偏好 / 总结
        │         ↓
        │       MySQL
        │         ↓
        │      Vector DB
        │
        └── 大型原始材料
                  ↓
              Object Store
```

例如用户曾经有一段 3 万字的职业规划交流。

你不应该把 3 万字全部作为一条 Long-term Memory。

应该：
```text
Object Storage：
conversation/2026/xxx.json.zst
    ↓
保存完整原始记录

MySQL：
memory_1 = 偏向 Agent 开发岗位
memory_2 = 优先考虑北京
memory_3 = 希望进入推荐 Agent 业务
memory_4 = ...
    ↓
Vector DB：
这些 memory 的 embedding
```

需要审计或重新抽取时，再通过 `source_object_key` 找回原始记录。

### 5. 用户画像和长期记忆也必须分开

用户画像不是长期记忆数据库本身，而应该是**长期记忆加工后的 Materialized View**。

例如：
```text
user_profile
------------------------
user_id
education_stage
major
research_direction
career_goal
preferred_city
skill_tags
profile_version
updated_at
```

放 MySQL。

长期记忆可能有 500 条，但 Agent 每次请求不可能全部加载。

Context Builder 做的是：
```text
MySQL User Profile
        +
最近消息
        +
Vector DB Top-K Memory
        +
当前任务 State
        ↓
     LLM Context
```

所以用户画像应该是**小而稳定、结构化、直接可读**的；长期记忆则是**大而稀疏，需要召回**的。

### 6. 最终我会把你项目设计成这样
```text
                        LangGraph
                            │
                     Runtime State
                            │
             ┌──────────────┼───────────────┐
             │              │               │
          小 State        大 State       Hot State
             │              │               │
             ▼              ▼               ▼
           MySQL        MinIO / S3        Redis
             │
             │
       Checkpoint Manifest
       Thread / Run / Status
       State Blob Reference
             │
             │
       ┌─────┴───────────────┐
       │                     │
       ▼                     ▼
 User Profile           Long-term Memory
    MySQL                   MySQL
                              │
                              ▼
                          Vector DB

原始历史 / Tool 大结果 / 文档 / 报告
                │
                ▼
             MinIO / S3
```

恢复一次 LangGraph 任务时就是：
```text
thread_id
   ↓
MySQL 找 latest checkpoint
   ↓
读取 state_manifest
   ↓
小字段直接恢复
   ↓
根据 object_key
从 MinIO 拉取必要的大字段
   ↓
重建 Runtime State
   ↓
LangGraph resume
```

保存 checkpoint 时反过来：
```text
State
 ↓
识别大字段
 ↓
序列化 + 压缩 + hash
 ↓
先上传 MinIO
 ↓
成功
 ↓
MySQL transaction
写 checkpoint + blob_ref
 ↓
commit
 ↓
更新 Redis latest cache
```

这里顺序也很重要：**先成功写对象，再提交引用它的数据库记录**，否则会产生“数据库已经指向一个不存在对象”的坏 checkpoint。对象上传成功、DB 提交失败产生的孤儿对象，则可以后台 GC。

另外还要做 checkpoint retention。LangGraph 今年的 PostgresSaver 甚至已经出现了专门讨论 checkpoint 无限累积和 prune 的 issue；官方的 ShallowPostgresSaver 则直接选择只保留最新 checkpoint、不保留历史 time travel。([GitHub](https://github.com/langchain-ai/langgraph/issues/8531?utm_source=chatgpt.com "[Feature] Add safe prune support to Postgres checkpoint savers · Issue #8531 · langchain-ai/langgraph · GitHub")) 所以你的系统也不要无限保存每一步：可以保留“最近 N 个 + 关键里程碑 + 未完成任务 checkpoint”，其余过期删除，并对不再被任何 checkpoint 引用的 MinIO blob 做 GC。

最终，如果面试官问我“你们这些数据到底怎么存”，我会直接回答：

> **我们没有把 LangGraph 完整 State 全塞 Redis。Redis 只做运行时热缓存、锁和幂等控制；Checkpoint 的元数据、执行链路和小型状态持久化在 MySQL，大字段采用 out-of-line storage，序列化压缩后放 MinIO/S3，Checkpoint 中只保存对象引用和版本信息。长期记忆同样不是一个大 JSON，而是拆成原子记忆存 MySQL，并建立向量索引用于召回；原始长对话、Tool 大结果和文档等大对象放对象存储。用户画像则作为长期记忆加工后的结构化视图存 MySQL。这样 Redis 丢失不会影响恢复，MySQL 负责一致性和查询，对象存储负责容量，向量库负责语义召回。**

这版我认为才符合你现在这个项目规模下的生产化设计。

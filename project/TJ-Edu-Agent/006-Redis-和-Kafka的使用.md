# Redis 和 Kafka的使用

## 本项目中Redis的使用

- RAG**查询缓存**：复用RAG模块的召回结果：对query做归一化后（清洗、提取核心意图，计算哈希值），计算哈希值，读redis缓存；
- API 限流保护 /chat、RAG、外部搜索、管理端事件接口，控制模型费用和突发流量；
  - 使用 Redis Lua 脚本实现滑动窗口或令牌桶
- Kafka 消费幂等防止同一 event_id 因重复投递而重复执行整个后台 Agent；

## 本项目中Kafka的使用

- 1）多消费者订阅一个事件
  - kafka的价值**在于用一个事件可以被多个下游独立消费**；
  - 其中某个消费者故障不会阻塞其他消费者，恢复后还能继续消费或回放历史事件，生产者也不需要知道具体有哪些下游。
  - 例如 policy.updated 同时触发：
    - RAG 重建政策索引。
    - 后台任务图筛选受影响学生。
    - 通知服务生成提醒。
    - 审计服务保存变更记录。
  - 每类消费者使用独立消费组，互不影响。相比之下，MySQL任务表更适合一个任务由一个 worker 领取。
- 2）流量削峰
  - **突发事件 → Kafka 暂存 → worker 按稳定速率消费**
  - 把瞬时峰值转换成持续、可控的处理流量，保护数据库、LLM和通知渠道。
  - 生产速度和消费速度不一致：例如学校集中发布竞赛通知，短时间产生数万条画像匹配任务。Kafka先保存事件，worker按照自身能力逐步消费，避免请求直接压垮数据库、LLM或通知服务。
  - 要注意：Kafka**只是把压力转化为消息积压**，并没有消除压力。因此必须监控：
    - 消费延迟和积压量。
    - 消息允许等待的最长时间。
    - worker的处理速度。
    - 是否需要增加分区并扩容 worker。
  - 如果任务必须立即完成，不能接受排队等待，那么仅靠削峰并不能解决问题，还需要扩容消费者或优化处理链路。
- 3）可靠传递与故障恢复
  - 标准消费过程：拉取消息 → 执行业务 → 写入数据库 → 提交 offset（消息在某个分区中的顺序编号）
    - 消费者组会记录自己已经消费到哪个 offset。worker 重启后，就能从已提交的位置继续消费。
  - 如果 worker 在写库前崩溃，因为没有提交 offset，恢复后消息会重新处理，不会轻易丢失。
  - 但如果已经写入数据库、还没提交 offset 就崩溃，消息也会重新处理，因此 Kafka 常见语义是“至少一次”，可能重复。

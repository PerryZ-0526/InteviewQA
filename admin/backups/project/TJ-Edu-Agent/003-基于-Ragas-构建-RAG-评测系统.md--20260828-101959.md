# 基于 Ragas 构建 RAG 评测系统

> 基于 Ragas 构建双层 RAG 评测体系：检索评测集维护 query 与条款证据锚点（doc_id、section_path、原文证据片段），端到端评测集维护 query、参考答案及必须引用证据；以 Recall@k、NDCG、Faithfulness、答案正确性和引用覆盖率定位检索与生成问题，并基于失败样本持续优化结构化切块和提示词。

基于Ragas的评测系统：构建两层评测集

- 1）query，source_doc_id + 页码/章节/原文证据片段（相关证据）
  - 评估召回率Recall@k（反映检索的全面性）
  - 精确率Precision@k（反映检索的精准度）
  - 平均倒数排名MRR（关注首个相关结果的位置）
  - 归一化折扣累计收益NDCG（综合考虑相关性等级和排名位置，区分“高度相关”和“沾点边”的文档）
- 2）query，参考答案，证据
  - 生成质量评估：评估检索相关性、答案相关性、可行度

评测数据集构建方法：

- LLM生成、线上日志、人审、人工补困难样本

评测时，再判断新切块结果中是否有 Chunk 覆盖或包含这段证据，而不是要求命中某个固定 Chunk ID。这样更换切块大小、重叠率或父子切块后，原评测集仍可复用。

## 评测集数据模型

```json
{
  "case_id": "e2e_0001",
  "query": "学生申请国家奖学金需要满足什么条件？",
  "reference_answer": "……",
  "required_evidence_ids": ["ev_0001"],
  "evidence": [
    {
      "evidence_id": "ev_0001",
      "doc_id": "policy_2025_001",
      "doc_version": "2025-09-01",
      "document_hash": "sha256:...",
      "normalizer_version": "v1",
      "page_start": 7,
      "page_end": 7,
      "section_path": "第三章 申请条件 / 第十二条",
      "start_char": 3521,
      "end_char": 3816,
      "text": "申请国家奖学金的学生应当……",
      "necessity": "required",
      "relevance_grade": 3
    }
  ]
}
```

// 相应的也要为chunk标注位置：start_char和end_char

## start_char/end_char 应相对于什么计算

- 不能相对于 Chunk 计算，否则重新切块后偏移就失效。
- 应**相对于该版本文档生成的“规范化全文”计算**：

```
原始文档
  → 解析正文
  → 统一换行
  → 统一 Unicode
  → 去除页眉页脚
  → 按确定规则拼接段落
  → canonical_document_text
  → 计算 start_char/end_char
```

## 评测集构建流程

### 1、确定问题分类（构建样本覆盖矩阵）

- 单条款直接回答
- 多条款归纳
- 跨章节问题
- 跨文档问题
- 带条件、例外、否定的问题
- 时效性和版本的问题
- 表格问题
- 带约束条件的问题（检测元数据标注）
- 无答案或信息不足的问题（需要系统拒答）
- 用户表达含糊、口语化、错别字的问题
- 容易被相似条款误导的问题

### 2、收集候选样本

- 线上真实查询日志，40%
- 人工编写，25%
- LLM生成，20%
- 历史错误case和回答反馈，10%
- 人工补充困难样本和对抗样本；5%

Ragas 可以基于知识图谱生成单跳、多跳问题，但官方也建议在生成后筛选适合进入正式测试集的样本

### 3、标注证据

对于llm生成的query样本：

以“证据—事实点—问题—参考答案”为一条完整链路：先从原文确定证据和原子事实，再让 LLM 根据这些事实生成问题和参考答案，最后由独立审核器从问题反推所需证据，检查能否回到最初的证据集合。不过，联合设计不等于让同一个模型自问自答自审，否则容易产生一致性幻觉。生成器和审核器应使用不同提示词、相互隔离的输入，必要时使用不同模型，并由程序校验原文位置，最后通过人工抽样兜底。

对于线上日志抽取、人工补充、bad case等query样本，如何进行证据标注呢？

// 借鉴了claude code的记忆召回机制；

**两阶段证据标注**

```
query 样本
→ 基于概要、标题、元数据和混合检索召回候选文档
→ 基于结构树召回候选章节/条款
→ LLM 选择最小充分证据
→ 程序回填原文位置
→ 独立 LLM 检查证据充分性
→ 高风险和低置信度样本人工复核
→ 写入证据库和评测集
```

首先，为每篇政策文档，总结概要作为元数据；第一阶段：让llm根据概要来圈定文档范围（候选文档集）；第二阶段：在候选文档集中，选取证据片段；

- 首先为每篇政策文档生成概要和结构化元数据（方案1：结合 BM25、向量检索召回候选文档；方案2：借助claude code sdk来召回）；
- 然后利用文档结构树进一步定位候选条款，让 LLM选择能够完整回答问题的最小证据集合。证据的页码和字符范围不由 LLM直接生成，而是由程序根据原文回填。
- 最后使用独立 LLM检查证据充分性，对低置信度、高风险及多文档样本进行人工复核。这样既提高了标注效率，也避免文档概要漏召回或模型自审带来的错误。

### 4、审核

我的审核机制分为**三层**：

- 1）首先使用确定性规则对全部样本做位置、版本和字段一致性校验；
- 2）然后使用独立 LLM 对全部样本检查（打分）证据相关性、完整性和答案忠实度；
- 3）最后将人工审核资源集中在随机抽样和高风险样本上。

两种不同方法生成的问题，有不同的审核侧重点：

- 对于 LLM 生成的问题，因为是先有证据再生成 query，审核重点是问题是否自然、**是否能被证据完整回答**；
- 对于线上真实问题，因为是先有 query 再找证据，审核重点是有没有**找错或漏掉证据**，并通过独立的全库证据搜索进行交叉验证。抽样比例会根据各类样本的实际错误率动态调整。

**LLM 生成 query 的审核方式**

- LLM 生成 query 是“先选证据，再根据证据出题”。因此，它的证据来源通常比较清楚，审核重点不在于重新寻找证据，而在于检查生成的问题是否合格。
- 审核时主要判断：问题是否能够被选定证据完整回答、是否自然地模拟真实用户、是否过于简单地改写原文、是否在问题中泄露答案，以及参考答案有没有超出证据。还可以让独立审核模型只看到 query 和证据，不看到生成过程，重新回答问题；如果它无法仅根据证据回答，说明问题和证据之间存在断裂。
- 这类样本最容易出现的并不是“找错证据”，而是问题不自然、难度虚高或虚低、问题与证据机械绑定。因此，人工抽样时应重点评价真实性和业务价值。

**真实 query 和人工 query 的审核方式**

- 真实 query 和人工补充 query 是“先有问题，再寻找证据”。这类样本的主要风险是漏标证据或错标证据，因为标注模型可能只在第一批候选文档中找到一段看似相关的内容，却遗漏其他章节的限制条件。
- 因此，审核时不能只判断现有证据能不能回答，还要**反向检查“是否还有其他必须证据”**。可以让独立审核模型**重新进行一次更宽松的文档召回和证据搜索，再将它找到的证据与原标注结果比较**。如果两次结果不同，或者重新搜索发现了额外的必要条款，就进入人工审核。
- 对于线上 bad case，尤其不能只在原系统召回的 Chunk 中审核，因为错误原因可能正是正确文档没有被召回。审核器需要从更大的候选文档范围甚至全库重新寻找证据。

三层审核机制

- 第一层是确定性规则校验，覆盖全部样本。这一层不使用 LLM，**主要检查结构和可追溯性**，例如：doc_id 和文档版本是否存在、证据原文能否通过 start_char/end_char 从规范化文档中准确还原、页码和 section_path 是否一致、必须证据是否为空、是否存在重复 query、是否混用了已失效政策等。规则校验失败的样本直接退回，不进入后续评测集。
- 第二层是全量 LLM 审核。审核模型重点判断语义问题，包括：证据能否回答 query、证据是否完整、有没有遗漏限制条件或例外条款、参考答案是否超出证据，以及 query 是否自然、明确。**审核模型应与生成模型使用不同提示词，最好使用不同模型**；同时不要把生成模型的推理过程交给审核模型，避免审核器顺着生成器的结论进行确认。
- 第三层是人工分层审核。人工审核对象由两部分组成：一部分是随机抽样，用于估计整体错误率；另一部分是规则或 LLM 判定的高风险样本。也就是说，即使一个样本没有表现出明显问题，仍有一定概率被随机抽中，防止系统性错误长期无法被发现。

哪些样本容易出问题，以下样本应优先进入人工审核：

- 一个问题需要多个证据、多个章节或多个文档才能回答；
- 包含“不允许”“除非”“不得”“至少”“不超过”等否定、例外或数值限制；
- 涉及申请资格、处分、金额、时间期限等**高风险结论**；
- 同一事项存在新旧版本、失效文件或政策冲突；
- 被标为“知识库无答案”或“证据不足”；
- query 存在指代不明、主体缺失、口语、省略或错别字；
- 证据来自表格、附件、扫描件、OCR 或跨页内容；
- 证据片段过长，或者只覆盖了条款的一部分；
- 候选文档很多、文档召回分数接近，无法明确判断所属政策；
- **证据生成模型与审核模型判断不一致**；
- 同一个 query 多次审核得到不同结果；
- LLM Judge 给出低置信度或认为缺少证据；
- 线上 bad case，尤其是当前检索系统没有召回正确文档的样本；
- 与已有样本高度相似，可能发生重复或测试集泄漏的样本。

此外，LLM 生成的问题还要重点检查是否过于书面化、是否直接复述条款、是否在问题中泄露答案，以及是否只因为与证据字面高度相似才显得容易回答。

如何进行人工分层，可以将样本划分成三档。

- 低风险样本是单文档、单条款、证据位置准确、两个 LLM 判断一致，并且不涉及否定、例外或时效问题的样本。这部分通过自动审核后进入普通评测集，人工只随机抽查，例如从 5%～10% 起步。
- 中风险样本包括多证据问题、口语化真实 query、证据较长或者审核模型置信度一般的样本。这部分提高抽样比例，例如抽查 20%～30%。
- 高风险样本包括政策冲突、无答案判断、否定和例外条件、高风险业务结论、LLM 判断不一致、OCR 证据以及核心回归样本。这部分可以强制人工审核。虽然高风险类别内部是全审，但从全部评测数据来看，人工审核仍然只是经过风险筛选的一部分。

具体比例不需要一开始固定，可以根据每一层的人工审核错误率动态调整。如果某类样本连续发现较多问题，就提高该类样本的抽样比例；如果长期稳定，再逐渐降低。

## 数据闭环和版本准入

每次评测后，将失败样本归入以下类型：

- R1：必要证据没有召回；
- R2：召回了，但排序过低；
- R3：召回内容噪声过多；
- G1：证据充分，但答案遗漏；
- G2：答案产生无依据事实；
- G3：回答正确，但引用错误或缺失；
- G4：回答不够可执行；
- D1：评测标注本身不完整或有争议。

对应优化关系：

| 错误类型 | 优先优化方向 |
| ------- | ---------- |
| R1      | 切块、查询改写、关键词/向量混合召回 |
| R2      | 重排模型、融合权重、元数据过滤 |
| R3      | Chunk 粒度、去重、动态 Top-k |
| G1      | 回答提示词、证据归纳、结构化生成 |
| G2      | 忠实性约束、无证据拒答、逐声明引用 |
| G3      | 引用生成和引用校验 |
| G4      | 领域 Rubric、回答模板、流程信息补全 |
| D1      | 人工复核并升级评测集版本 |

版本发布时建议采用硬门槛：

- 高风险样本不得遗漏 required 证据；
- 核心结论不得出现无证据引用；
- Faithfulness 和 Citation Coverage 不得低于既定基线；
- 新版本不能只提升平均分，同时显著损害某类问题；
- 报告各类型分数、失败数量和置信区间，而不是只报告一个总分。

最终形成：

线上失败样本发现 → 人工确认 → 加入困难集 → 定位检索或生成问题 → 修改切块/召回/提示词 → 全量回归 → 小流量验证 → 进入稳定版本。

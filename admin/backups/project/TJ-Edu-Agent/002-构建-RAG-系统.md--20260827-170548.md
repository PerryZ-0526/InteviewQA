# 构建 RAG 系统

> 构建 RAG 系统：支持多种文档格式导入及复杂表格处理，采用结构感知的父子文档切块以保证政策条目完整及语义连续；根据首轮召回的证据覆盖度动态生成补充查询，自适应选择缺失维度补充、语义扩展、HyDE 等检索策略，提高复杂问题的召回完整性。

## 离线流程

文档预处理 → 多格式解析（pdf、word、excel、html、md） → 政策结构识别 → 父子分块 → 元数据标注→Embedding → SQLite、Elasticsearch、Milvus 三路持久化

### 文档清洗

- 去除页眉页脚、多余空号、噪声符号、无信息封面、无意义分隔符
- 保留对政策结构有意义的信息，避免过度清洗，保留编号前缀，不破坏**结构锚点**：第一章、第一条、一、（一）、1、附件、附表（附件、表格、清单独立处理）

### 政策结构识别

- 恢复政策结构，它会识别：
  - 文档标题；章、节、条、子条、项目；正文；附录；表格行；页眉页脚、页码等噪声；条件、材料、流程、时间、金额、禁止性规定等**语义标签**。
- 最终形成一个政策结构树 PolicyDocumentIR：
- ![政策结构树 PolicyDocumentIR](images/1787739981887-ujryun.jpg)
- 同时保存每个节点的：node_id、层级、标题路径、原始锚点、页码/位置、语义标签、表格信息

### 表格处理

转为markdown格式，保留表格语义结构

标准表格语义层设计：

- 我们的 RAG 模块没有把表格简单地转成纯文本，而是采用“格式解析、标准表格模型、语义恢复、结构化切块”四层处理方式。
- 对于 Word 文档，我们使用 python-docx 获取表格网格和合并单元格关系；旧版 .doc 会先由系统内部调用 LibreOffice 转换成 .docx，再进入相同链路。对于 PDF，我们使用 pdfplumber 获取表格、单元格和坐标信息。
- 不同格式提取出的表格会先转换为**统一的物理表格模型**。
  - 每个单元格不仅保留文本，还会记录起止行列、row_span、col_span、坐标、所属页面和表格编号。
  - 这样可以避免在过早转成二维字符串时丢失横向、纵向合并关系，也方便后续统一处理 Word 和 PDF 表格。
- 在语义恢复阶段，我们会分析多级列表头、行标题、数据单元格、备注和合计，并为每条数据构建**二维上下文**。
  - 例如某个分值不仅保留“10分”，还会同时关联它所属的一级表头、二级表头和纵向分类。
  - 对于合并单元格，我们不会机械填充所有空格，而是根据合并范围，把横向列表头和纵向分组上下文补充到对应数据记录中。
  - 若一张物理表格内部实际包含多个逻辑区域，还会进一步拆成多张逻辑表。
- 进入切块阶段后，表格行被视为不可随意拆开的原子片段，并继续复用现有基于大小的统一 chunker。较小的表格可以整体形成一个可检索块；较大的表格会在保留表格标题、多级表头和行分组上下文的前提下按记录组合切块。这样即使用户只检索某一条数据，返回的 chunk 仍包含理解该数据所需的完整表头和分类信息。
- 同时，我们会保存表格和单元格的来源位置，用于检索结果引用和回溯。如果表格网格不完整、合并范围冲突或出现大量无法解释的空单元格，系统会降低质量评分，并进入降级处理，而不是把错误结构直接写入知识库。

```
PDF
→ pdfplumber
→ PdfTableAdapter
→ PhysicalTable

Word
→ python-docx
→ DocxTableAdapter
→ PhysicalTable，物理标

PhysicalTable
→ TableSemanticNormalizer
→ StandardTable
→ 统一表格 chunker
```

- PhysicalTable 只描述物理结构：

```json
{
  "cells": [
    {
      "text": "培养模块",
      "row_start": 1,
      "row_span": 1,
      "col_start": 0,
      "col_span": 2,
      "source_position": {}
    }
  ]
}
```

- Word 和 PDF 共用同一个 TableSemanticNormalizer，完成：
- 识别表格标题、章节标题；
- 识别多级横向表头；
- 识别纵向行标题；
- 构建横向和纵向上下文；
- 识别备注、合计、说明；
- **将一个物理表拆成多个逻辑表**；
- 生成语义完整的数据行；
- 按统一 size 配置切块，保证不拆单元格和数据行。

**表格语义恢复流程**，标准处理顺序如下：

1. 建立物理网格：根据 PDF 坐标边界或 Word 布局网格生成稳定的行列坐标。
2. 恢复合并范围：为每个实际单元格计算 row_span、col_span。
3. 校验结构：检查越界、重叠、悬空文字和无法定位的单元格。
4. 识别候选标题行：识别横跨多数列、非空单元格较少且具有标题特征的行。
5. 识别表头区域：从逻辑表起始位置向下识别一行或多行列标题。
6. 识别行标题：根据左侧位置、纵向跨度、文本类型和数据分组关系识别行标题。
7. 识别备注与合计：结合跨度、位置和“说明、备注、合计、小计、总分”等语义特征分类。
8. **拆分逻辑表**：遇到新的 section_title 或新的完整表头结构时结束上一逻辑表。
9. 构建二维上下文：为每个数据记录计算表标题、章节、行标题路径和列表头路径。
10. 生成语义记录：只生成语义完整、来源可追踪的 **SemanticRecord**。
11. 执行质量检测：不合格结果进入降级解析或人工复核状态。

### 文档切块

- 项目使用“父块负责上下文，子块负责检索”的策略；
- 检索子块（适合检索的最小完整语义单元），返回父块（保持章节/主题级语义完整性）
- 结构感知+父子文档，不截断单条政策
- 1）Parent chunk：500-900中文字，target约700，根据结构自然浮动；超过1000时，将图一主题下继续拆成多个parent sub-block，避免过长；
  - 对应一个完整章节或相邻结构单元；
  - **保存完整上下文**；
  - searchable=false；
  - 不生成向量，也不进入Elasticsearch。
- 2）Child chunk：120~300中文字，target约220，小于80字的单个条款通常语义不足，不利于召回、
  - 绑定 parent_chunk_id；
  - 内容较短、语义集中；
  - searchable=true；
  - 进入 Embedding、Elasticsearch 和 Milvus。
- 3）Overlap默认0，政策文档优先依赖结构树，而不是sliding window；**长自然段被迫拆分时，才允许少量 overlap**。
- 4）短条款合并

### 元数据标注

- 来源信息：文档id（后续做增量更新）、文档标题
- 结构信息：section_path（文档结构树，便于定位chunk，引用溯源）、页码
- 适用信息：所属学院，适用专业、适用年级；
- 其他信息：version、status、upload_time

标注方法：

- 规则提取 + 人工补全（未文档补元信息，信息传递到chunk元数据）

### 向量化

- Text-embedding-v3，中文效果好，维度可选1024、2048；
- 数据在阿里云国内节点处理，不出境，数据合规

### HNSW，分层可导航小世界网络

- HNSW 构建了一个**多层的图结构**，查询时从高层稀疏图开始找大方向，逐层往下精化，最终在底层找到精确候选。
- 支持增量插入（随时可以插入新数据，不需要重建索引）
- 参数m，每个节点的最大连接数（16）
- 参数ef_construction，构建时的探寻因子（搜索宽度，搜索多少候选领居来决定最终链接）（64）
- 参数ef_search，检索时的探寻因子，控制查询时搜索的候选数量；（40）

## 在线流程

- 用户提问
- 查询处理（query改写、HyDE假设文档嵌入）
- 混合检索-多路召回：向量检索、BM25；RRF倒数排名融合（不看分数只论排名，忽略量纲差异），k=60
- Rerank重排序，cross encoder模型，【查询文本+文档文本】拼在一起计算语义相似度；
- 父块去重
- 上下文压缩，过了掉文档快内部的无关段落
- 拼接prompt，证据引用
- LLM回答，引用溯源

## Evidence ReAct RAG

“最多两轮、证据质量驱动”的内部检索闭环：

- 1）第一轮：基础检索：使用原始问题执行关键词与向量混合召回、融合和 rerank。
- 2）Evidence Reviewer：计算确定性质量指标
  - 初始检索完成后，Reviewer 会计算一个**加权的 quality_score**：
    - 问题关键词覆盖率  34%
    - 问题分面覆盖率    24%
    - 检索/精排分数     24%
    - 证据来源多样性    10%
  - 输出-1：sufficient：结束检索
  - 输出-2：repair：直接输出第二轮并发query计划
    - **自适应并发query策略**：可自适应选择三类分支：
      - 1）缺失 facet 补充
        - 针对条件、材料、流程、截止时间等缺失维度生成 Query。
        - 执行现有 BM25 + 向量 + RRF 混合检索。
      - 2）语义扩展
        - 处理口语、隐式表达、术语不对齐等问题。
        - 同样执行现有混合检索。
      - 3）HyDE
        - 生成政策正文风格的假设文档。
        - 只使用假设文档 embedding 做向量检索。
- 3）第二轮：按需补召回。根据Evidence Reviewer的输出来执行相应的并发query策略分支。
  - 首轮质量充分 → 不执行第二轮
  - 首轮缺少明确 facet → facet Query
  - 首轮存在语义错位 → semantic expansion
  - 语义缺口适合文档化表达 → 可加入 HyDE
  - 精确日期/金额问题 → 通常不使用 HyDE
- 4）统一证据池：多 Query 并发召回后，与第一轮证据合并，并始终使用原始用户问题统一 rerank。
- 5）最终复核：再次评估证据质量，选择质量不低于第一轮的结果进入回答生成。
- 核心约束是：最多两轮、LLM调用都集中在Reviewer中、原始 Query 始终保留、改写文本不作为证据、失败自动降级、不把内部能力拆成多个 Agent Tool。

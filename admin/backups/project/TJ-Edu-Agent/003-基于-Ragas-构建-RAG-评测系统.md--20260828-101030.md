# 基于 Ragas 构建 RAG 评测系统

> <span style="font-size: 12pt">3. 基于 Ragas 构建 RAG 评测系统：维护两套评测集，检索评测集“query+相关条款列表（section\_path）”、端到端评测集“query+参考答案+必须引用的证据”；基于评测反馈建立数据闭环，持续优化切块策略、提示词工程。</span>

下面按二面/业务终面的回答口径组织。每一题都不是追求“定义最标准”，而是让面试官听出你对 Agent 架构、工程约束和业务落地有自己的判断。

## 1. 你为什么这么设计，而不是另一种架构？

我现在这套架构并不是一开始就设计成这样的，而是逐步收敛出来的。最开始我采用的是比较典型的 LangGraph 流程：上下文构建之后先做意图识别，再进入 Planner，之后是 Executor、Reviewer，必要时再 Replan。这个设计的优点是每个阶段职责非常明确，但真正实现以后会发现一个问题：对于大量简单请求，这套流程其实过重了。比如用户只是问一条政策，系统仍然需要经历意图识别、规划、执行、审核，多次调用大模型，不但延迟高，而且很多节点做的是重复判断。

所以后来我把架构收敛成了“上下文组装 → Orchestrator → 领域 Agent → Answer”。其中领域 Agent 按能力边界拆分，比如政策检索、知识图谱、用户画像、外部搜索，每个领域内部是一个独立的 ReAct 子图，有自己的工具、状态和退出条件。Orchestrator 不负责具体完成任务，而是判断当前任务需要哪些领域能力以及它们之间的依赖关系。简单任务实际上只调用一个领域 Agent，复杂任务才会跨多个领域组合。

我没有继续保留一个独立的意图识别节点，是因为在这个系统里，“识别意图”和“决定下一步调用什么能力”本质上高度重合。如果先让一个模型判断这是“政策咨询”，然后再让 Orchestrator 判断应该调用政策 RAG，相当于连续做了两次语义路由。把这部分合并以后，可以减少一次模型调用，也降低意图标签设计对系统能力的限制。

但我也没有把整个系统做成一个超级 ReAct Agent。因为当工具数量不断增加以后，一个 Agent 同时面对 RAG、搜索、图谱、画像、业务办理等十几个甚至几十个工具，模型的工具选择准确率会下降，而且所有领域上下文混在一个窗口里，很容易造成上下文污染。拆成领域 Agent 后，每个 Agent 只看到与自己有关的工具和状态，执行边界更清晰，也方便单独测试和替换。

所以我设计这套架构的核心原则不是“多 Agent 越多越好”，而是两点：\*\*简单任务尽量走最短路径，复杂任务才引入编排；模型负责不确定决策，确定性的流程尽量交给代码和状态机。\*\*我认为这比完全固定的 Workflow 灵活，又比一个无限自主的“大 Agent”更可控，是工程上比较合适的折中。

## 2. 你的 Agent 到底是真 Agent，还是 Workflow？

我不会把 Agent 和 Workflow 完全看成二元对立。实际上大部分能够真正上线的 Agent 系统，本质上都是“Workflow 外壳 + Agent 决策”的混合架构。

如果整个系统从用户输入开始，每一步执行路径都是提前写死的，比如一定先检索、再总结、再生成答案，即使其中每一步用了大模型，我会认为它更接近 Workflow。因为模型只是完成某个固定节点中的内容生成，并没有决定“下一步做什么”。

真正具有 Agent 特征的地方，我认为至少应该包括三个方面：第一，模型能够根据当前状态动态选择工具或者能力；第二，工具执行结果会反馈给模型，模型能够根据结果决定继续、调整还是退出；第三，同一个用户目标可能产生不同的执行轨迹，而不是永远走固定流程。

按照这个标准，我现在的系统并不是一个纯 Workflow。最外层确实是结构化的，比如上下文组装和最终回答是确定性阶段，但进入领域 Agent 后，它是 ReAct Loop。以政策 Agent 为例，模型可能先调用政策检索，发现证据不够以后扩大查询范围，也可能读取具体政策条款以后直接结束；外部搜索 Agent 也可能连续搜索、读取网页、重新组织查询。执行路径不是预定义死的。

但我也不会为了证明它是 Agent，刻意让所有东西都自主化。比如权限校验、工具参数验证、最大调用次数、状态写入、敏感操作审批，这些我反而希望做成确定性的 Workflow。因为这类事情如果交给大模型决定，系统反而不稳定。

所以如果面试官问我“这到底是不是 Agent”，我会回答：**它是一个受约束的 Agent 系统。外部执行骨架是 Workflow，内部不确定决策使用 Agent Loop。**

我觉得真正重要的也不是给系统贴一个“Agent”的标签，而是判断哪些问题值得让模型自主决策。像自然语言任务分解、工具选择、信息不足时是否继续检索，这些适合 Agent；而权限、安全、事务、一致性这些工程问题，不应该因为用了 Agent 就全部交给模型。

如果所有节点都固定，那只是一个 LLM Workflow；如果所有东西都交给一个模型无限循环，又很难生产化。真正能上线的 Agent 通常就在这两个极端之间。

## 3. Orchestrator 为什么这么设计？为什么不是一个 ReAct？

单个 ReAct 最大的优势其实是简单。用户给出任务以后，模型不断执行“思考 → 调工具 → 获取结果 → 再决策”，理论上只要给它足够多的工具，它就能够完成很多复杂任务。所以在工具数量比较少、任务领域比较单一的时候，我反而不会做多 Agent，一个 ReAct 就够了。

问题出现在系统能力不断扩展以后。

假设一个 Agent 同时拥有政策 RAG、知识图谱、画像查询、互联网搜索、业务办理、推荐等二三十个工具，那么模型每一步都需要从大量工具中选择。工具描述本身会占据上下文，而且不同领域返回的数据结构完全不同。一次复杂任务里搜索结果、政策全文、画像信息都混进同一个消息历史以后，上下文会迅速膨胀。

所以我的做法是把工具按照领域能力封装成几个独立 ReAct，而 Orchestrator 面对的不是二三十个底层工具，而只有几个领域能力。例如它只需要决定：“这个任务先调用画像 Agent，再调用政策 Agent。”具体政策 Agent 内部怎么检索、检索几次、什么时候停止，由领域 Agent 自己解决。

它实际上形成了两级决策：

> Orchestrator 解决“由谁做”；
> Domain ReAct 解决“具体怎么做”。

这里还有一个我比较强调的设计：**Orchestrator 不一定需要一个完整的外层循环。**

如果每个领域 ReAct 本身已经有结果验收和退出机制，再在 Orchestrator 外面做一个无限的 Plan→Execute→Review→Replan Loop，很容易形成双层循环。这样既增加模型调用，也容易出现“里面已经完成了，外面又重新检查一遍”的冗余。

因此我更倾向把 Orchestrator 做成一次或有限次编排。对于能够提前确定依赖关系的任务，一次生成执行计划，然后按依赖执行即可。只有出现某个领域 Agent 明确返回“缺少某类能力”或者执行失败时，才触发一次重新调度，而不是默认每个任务都循环规划。

所以选择 Orchestrator 并不是因为“多 Agent 比单 Agent 高级”，而是因为系统已经出现了明显的领域边界。工具规模小时，一个 ReAct 更好；工具和上下文复杂到一定程度以后，引入 Orchestrator 才能把工具空间、上下文和错误传播范围切开。

## 4. 多 Agent 的收益到底在哪里？有没有量化？

我认为多 Agent 最大的问题就是很容易变成架构上的自我感动。所以如果一个系统从单 Agent 改成多 Agent，我不会用“模块更加清晰”来证明它有效，而是要看是否在几个可测指标上获得了收益。

第一个指标是工具调用准确率。

单 Agent 挂载大量工具以后，可以构造一组需要调用不同工具的任务，统计正确工具选择率、错误调用率和无效调用次数。然后和领域 Agent 架构做对照。如果单 Agent 平均每个任务出现 0.8 次无效工具调用，而拆分以后下降到 0.2 次，这就是一个比较明确的收益。

第二个是任务成功率。尤其针对复杂组合任务，比如“根据我的学业画像判断某项政策是否适用，并给出相关资源”，这种任务同时涉及画像和政策两个领域。可以建立固定测试集，对比单 Agent 和 Orchestrator + Domain Agent 的最终任务完成率。

第三个指标是上下文成本。领域拆分之后，一个政策 Agent 没必要看到搜索 Agent 的全部中间轨迹，Orchestrator 也只接收结构化结果而不是整个 ReAct history。因此可以统计平均输入 Token、峰值上下文长度和每个任务的模型调用成本。

第四个是延迟。这里多 Agent 不一定占优势，因为增加编排层本身会增加一次调用。所以我不会说多 Agent 天然更快。它真正可能获得延迟收益的地方，是复杂任务可以把彼此独立的领域调用并行执行。例如一个任务同时需要搜索和画像，两者没有依赖关系，就可以并发。

第五个是可维护性。这虽然不像准确率那么直观，但依然可以测，比如新增一个工具时修改多少模块、回归测试影响范围有多大，以及某个 Agent 出错时是否能够独立定位。

因此在我的设计里，多 Agent 不是默认方案，而应该做消融实验：

> Single ReAct
> 对比
> Orchestrator + Domain ReAct

然后看任务成功率、工具正确率、平均 Token、P95 延迟、无效调用数这些指标。

如果拆完以后成功率只提升 1%，但 Token 增加 50%、延迟翻倍，我会直接退回单 Agent。只有当任务复杂度已经足够高，多 Agent 才值得承担额外的编排成本。

所以多 Agent 对我来说不是一个技术目标，而是一种**控制复杂度的手段**。架构是否合理最终要靠任务级评测，而不是靠 Agent 数量证明。

## 5. 线上如果出现 Agent 无限循环、错误工具调用、上下文膨胀怎么办？

这三个问题我不会单纯依赖 Prompt 解决，因为它们本质上都是运行时治理问题。

首先是无限循环。我会设置多层退出机制。最外层有最大步骤数和最大模型调用次数，比如一个领域 ReAct 最多允许执行 8～10 个步骤；同时设置任务级 Token Budget 和时间 Budget。超过任何一个阈值就强制退出。另外还可以检测重复行为，例如连续多次调用同一个工具，并且参数基本一致、结果没有变化，就认为进入循环，直接触发熔断。

更进一步，可以为 Agent 设置明确的终止状态，例如 SUCCESS、INSUFFICIENT\_INFO、FAILED，而不是要求模型一定给出答案。有时候最正确的行为其实是承认当前证据不足，而不是为了完成任务不断搜索。

第二个问题是错误工具调用。我会把模型的“选择工具”和真正的“执行工具”分开。模型只能产生结构化 Tool Call，执行层会对参数 Schema、权限、资源范围进行校验。对于只读搜索类工具可以自动执行，但像修改画像、办理业务、发送消息这种带副作用的操作，需要额外审批或者策略校验。同时工具执行最好保证幂等，避免模型重复调用造成重复写入。

第三个是上下文膨胀。我不会把所有历史 Tool Result 原样塞回模型。短期策略包括工具结果裁剪、结构化摘要、大文档外置，只保存引用 ID；长期对话则进行上下文压缩，把历史轨迹压缩成目标、已确认事实、未完成事项等结构化状态。不同领域 Agent 之间也不共享完整消息历史，只共享必要结果。

另外，我会把可恢复性考虑进去。LangGraph 这类状态图框架的价值之一，就是关键节点可以做 Checkpoint。如果 Agent 在第六步失败，不需要从第一步重新执行，而是从最近的稳定状态继续。

所以我认为 Agent 上线后最重要的变化是：不能再把它当成“一次 LLM 调用”，而要把它当成一个有预算、有状态、有权限、有生命周期的运行进程。

Prompt 负责告诉模型“应该怎么做”，Runtime 才负责保证“即使模型做错，也不会失控”。

## 6. Agent 的效果怎么评估？

Agent 的评估不能只看最终答案，因为同样一个正确答案，可能一个 Agent 调了两个正确工具得到，另一个 Agent 调了十几个工具最后碰巧得到。如果只评答案，两者看起来一样，但第二个显然没有上线价值。

所以我通常把评估拆成三个层次。

第一层是最终任务结果，也就是 Task-level Evaluation。最核心的是任务成功率，例如用户要求“找到符合条件的政策并判断是否适用”，最终有没有完成。这部分可以通过人工标注测试集、规则校验或者 LLM-as-Judge 做评分。但 Judge 不能完全替代确定性规则，像政策编号、金额、日期这种事实最好直接程序化校验。

第二层是执行轨迹。这里主要看工具选择准确率、工具参数正确率、无效调用次数、任务平均步骤数、是否产生循环、是否遗漏关键工具。例如答案虽然正确，但是本来应该查询用户画像，模型却凭空假设用户年级，这种任务应该判失败。

第三层是系统工程指标，包括平均 Token、模型调用次数、端到端延迟、P95 延迟、失败恢复率以及单任务成本。这些指标决定一个 Agent 能不能规模化运行。

如果进入真实线上环境，我还会增加用户侧指标，例如用户是否继续追问、是否接受推荐、人工纠正率以及任务完成后的满意度。但这类指标会受到很多业务因素影响，所以不能直接等同于 Agent 能力。

测试集本身也很重要。我不会只放正常问题，而会专门加入模糊任务、跨领域任务、信息缺失任务、工具失败、矛盾证据、恶意指令等边界情况。因为 Agent 最大的问题通常不是平均情况下不会回答，而是在异常情况下容易失控。

另外架构发生变化时，我会做回归评测。例如从 Single ReAct 改成 Multi-Agent，不是看 Demo 好不好，而是在同一套测试集上比较：

任务成功率有没有提高？错误工具调用有没有减少？成本是否值得？

我认为 Agent Eval 的核心就是把“感觉这个 Agent 挺聪明”变成一组可以回归、可以比较、可以持续优化的指标体系。

## 7. 如何控制 Agent 的成本和延迟？

我会把成本和延迟看成架构设计问题，而不是最后上线时再优化。

第一步通常是减少不必要的大模型调用。比如我之前的架构里有 Intent Router、Planner、Reviewer，如果一个简单问题都要经过这些节点，实际上大量调用并没有创造新的信息。因此我后来把意图路由合并进 Orchestrator，简单任务直接进入一个领域 Agent。**减少一次模型调用，往往比把单次调用优化 20% 更有效。**

第二个办法是模型分级。并不是所有任务都需要最强模型。例如简单路由、Query Rewrite、结果分类可以使用更轻量模型，而真正复杂的规划和最终回答再使用能力更强的模型。如果系统能够根据任务复杂度动态选择模型，可以明显降低平均成本。

第三个是 Prompt Cache。Agent 多轮调用最大的特点就是系统提示词、工具定义和大量上下文前缀高度重复，因此缓存命中以后，可以显著降低重复输入 Token 的成本。设计上要尽量保证稳定内容位于 Prompt 前部，动态信息放在后面，提高前缀复用率。

第四个是控制上下文。工具搜索结果不能原封不动塞进模型。RAG 应该限制 TopK，对长文档只返回相关段落；多个 Agent 之间传递结构化结果而不是完整轨迹。很多 Agent 的成本其实不是输出，而是几万 Token 的无效输入。

第五个是并行化。例如 Orchestrator 判断一个任务同时需要画像查询和互联网搜索，而且二者不存在依赖，就并行执行，而不是串行等待。对于 I/O 型工具调用，我也会使用异步并发。

另外还需要缓存。确定性高、变化慢的信息，比如政策内容、静态知识图谱查询、用户重复查询，都可以在工具层缓存，而不是每次重新检索和调用 LLM。

最终我会给每个任务设置明确的 Budget，例如最大模型调用次数、最大 Token、最长执行时间。超预算时系统应该降级，例如减少搜索深度、使用已有结果回答，而不是无限追求“最好答案”。

我的原则是：\*\*先从架构层面减少调用，再做模型分级和缓存，最后才是压 Prompt 这种局部优化。\*\*成本优化不能以明显降低任务成功率为代价，所以所有策略最终都应该通过 Eval 做成本—效果曲线。

## 8. 如果把你的方案应用到推荐系统，Agent 应该放在哪一层？

如果让我把 Agent 应用到推荐系统，我不会一上来就让 Agent 替代召回、粗排或者精排模型。因为传统推荐链路本身是一个极其成熟的低延迟系统，核心链路通常要求毫秒级响应，而一个 Agent 动辄需要多轮模型推理和工具调用。如果强行把 ReAct 放进主排序链路，延迟、稳定性和成本都很难接受。

我更倾向把 Agent 放在传统推荐模型的“上层控制面”。

传统推荐模型很擅长根据历史行为预测“用户下一步可能点击什么”，但它不一定擅长理解一个复杂、临时、自然语言表达的用户目标。例如用户突然说：“我最近准备找 Agent 开发实习，希望多推荐一些工程实践，不要再给我基础大模型科普。”这种意图变化如果只依赖长期行为特征，可能需要很多次交互才能反映出来。

Agent 可以先把这种高层需求转化成结构化约束，比如主题是 Agent Engineering，目标是求职，内容深度偏实践，同时降低基础科普权重。然后把这些信号传递给传统推荐链路，而不是自己去给几百万候选内容排序。

第二个位置是复杂推荐任务的编排。例如用户说：“我下个月去东京三天，帮我安排住宿、餐厅和景点。”这已经不是单物品推荐，而是一个多约束、多步骤决策问题。Agent 可以调用住宿、地图、餐厅等多个推荐服务，维护预算和时间约束，再组合成最终方案。底层每一个候选仍然可以由专业推荐模型生成。

第三个位置是推荐后的交互和反馈。传统推荐系统很多反馈是点击、停留、点赞这些隐式信号，Agent 可以通过对话获得显式反馈，例如“不是不喜欢这个作者，而是这篇太基础”。这种反馈的信息密度远高于一次点击，可以转换成短期用户状态。

所以我更认可一种架构：

**Agent 负责理解目标、规划和协调，推荐模型负责大规模候选生成和精确打分。**

也就是说，Agent 更像推荐系统的智能控制器，而不是替代推荐模型本身。

这样既利用了大模型在语言理解、推理和工具编排上的优势，又保留传统推荐系统在大规模计算、低延迟和稳定性上的优势。我觉得这也是 Agent 真正进入推荐业务更现实的一条路径。

---

## 9. 传统推荐是召回→粗排→精排→重排，Agent 到底能改变哪一个环节？

如果严格来看，我认为 Agent 不应该简单理解成“给召回、粗排、精排、重排再加一个第五阶段”。它更可能改变的是整个推荐系统的决策范式，从单次前馈排序变成“理解目标 → 调用推荐能力 → 获取反馈 → 再决策”的闭环。

首先在召回之前，Agent 可以增加一个意图理解层。

传统召回主要依赖用户 ID、历史行为、Query、Embedding 等特征，而 Agent 可以从自然语言和当前上下文里抽取临时目标、约束和负反馈。例如用户说“最近不要再推荐大模型基础教程”，Agent 可以把这个信息转换成显式约束，再影响召回 Query、召回通道权重或者候选过滤。

所以第一个变化其实发生在“召回之前”。

在召回阶段，Agent 可以做召回策略编排。例如传统系统可能有协同过滤召回、Embedding 召回、热门召回、社交召回等多个通道。Agent 不需要自己遍历内容库，而是根据当前任务动态决定调用哪些召回服务以及怎样组合。它更像一个高层路由器。

粗排和精排阶段，我反而认为 Agent 的价值相对有限。这里需要对成千上万个 Item 做高吞吐打分，专门训练的排序模型在成本、延迟和一致性上都远优于通用大模型。因此这两层大概率仍然应该由传统推荐模型主导。大模型可以通过蒸馏、生成特征等方式影响排序模型，但这和在线 Agent 已经不是同一件事情。

Agent 最容易直接介入的是重排之后的 Slate 组织。因为这里候选数量已经比较少，例如几十个，可以考虑更复杂的全局约束：多样性、主题覆盖、用户即时目标、避免重复、解释性，甚至让大模型对小规模候选进行语义级比较。

但我认为更大的改变发生在推荐结果之后。

传统推荐：

> 推荐 → 用户点击 → 收集行为 → 下一次推荐。

Agent 推荐：

> 理解用户目标 → 推荐 → 用户自然语言反馈 → 修改用户当前状态 → 再调用推荐系统。

这样推荐从一个单轮 Ranking 问题变成了一个多轮决策问题。

所以如果让我总结，我会说：**Agent 最可能重点改变“召回之前”和“重排之后”，而不是直接替代中间的粗排和精排。**

召回前，它负责理解高层意图和动态约束；中间的大规模 Ranking 仍然交给传统推荐模型；重排后，它负责全局决策、交互和多轮反馈。

从更长期来看，Agent 真正可能改变的不是某一个阶段，而是把传统推荐系统从“预测用户会点击什么”，逐渐扩展成“理解用户现在想完成什么，并主动组织多个推荐能力帮助他完成这个目标”。

如果你的二面官确实是做“Agent × 推荐”的负责人，我认为**第 8、9 两题非常可能成为你和普通 Agent 候选人拉开差距的地方**：不要回答成“大模型可以理解语义，所以替代推荐算法”，而应该明确表现出你知道传统推荐链路为什么存在，也知道 Agent 的延迟、成本和规模化推理不适合直接取代精排。你要表达的核心观点其实就是一句话：

**让 Agent 做高层决策，让推荐模型继续做它最擅长的大规模预测。**

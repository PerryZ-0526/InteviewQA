# 用户画像与长短期记忆机制

## 简历描述

> 用户画像与长短期记忆机制：画像融合校内结构化事实、LLM 标签及周期性沉淀的稳定偏好，采用常驻摘要 + Tool 按需深读的分层注入策略；短期记忆通过滑动窗口 + 摘要保障会话连续性，长期记忆保存跨会话事件与交互证据，通过向量检索按需召回。

## 一、整体定位

用户画像不应设计成静态标签集合，也不应在服务器上为每个用户维护多份 Markdown 文件，而应设计为：

> 多源、可追溯、动态演化、多视图消费的学生画像系统。

核心链路：
```text
原始数据 / 用户行为
        ↓
   证据与事实
        ↓
规则 / LLM 提取候选画像
        ↓
校验、去重、冲突处理、时效判断
        ↓
   当前有效画像
        ↓
┌────────────┬────────────┐
↓            ↓            ↓
常驻摘要     Tool 深读     推荐圈选视图
```

核心原则：

1. 事实、来源、形成方式、可信度、时效性是不同维度，不混成一个“层级”。
2. LLM 只负责生成候选画像，不直接修改当前有效画像。
3. 画像必须保留来源和证据，能够解释“为什么系统认为学生具有某个特征”。
4. 用户画像表达“这个学生现在是什么样”，长期记忆保存“过去发生过什么”。
5. MySQL 中的`结构化画像`是系统内部统一数据源；面向 LLM 的画像文本在读取阶段动态生成并可缓存在 Redis 中。

## 二、用户画像与长短期记忆的边界

### 1. 短期记忆

短期记忆服务当前会话连续性，本质上是一个`“滑动窗口 + 分层摘要 + 关键状态抽取”`的混合记忆系统，用于在严格 token 预算下维持对话连贯性。
```
最近若干轮原始消息（Sliding Window Buffer）
        +
会话滚动摘要（Session Summary）--- 语义压缩--> 结构化摘要
        +
关键状态快照（Key State Snapshot / Working Memory）--- 结构化状态
```

> 短期记忆是`运行时状态系统`，长期记忆是`跨会话事件系统`

#### 结构化摘要
```
- 当前任务场景（对应教育Agent能力域）
- 当前对话目标 / 用户意图
- 已完成关键决策 / 子任务
- 用户已确认的事实与约束（稳定信息）
- 校内上下文状态（学业/流程/资源/政策相关状态）
- 当前待决问题 / 信息缺口
- 推荐与检索线索（可用于资源/导师/论文/政策召回）
- 下一步行动建议（系统应执行的动作）
```

#### 结构化摘要-示例
```
用户当前处于“学业规划 + 校内资源推荐”场景，目标是确定毕业设计方向并匹配校内导师与项目资源。

当前对话目标：
帮助用户在 LLM Agent 方向中细化毕业设计选题，并给出可落地工程路径。

已完成关键决策：
用户已确定研究方向为 LLM Agent；
已排除纯 CV 方向。

用户已确认的事实与约束：
希望选题具备工程可落地性；
偏好 Agent + RAG + Tool 使用范式；
倾向校内可获得导师与算力支持的方向。

校内上下文状态：
用户为计算机相关专业学生；
当前处于毕业设计准备阶段；
尚未绑定具体导师课题组。

当前待决问题：
RAG 与 Tool-augmented Agent 在毕业设计中的选型；
是否需要结合校内真实业务系统（如教务/流程/资源系统）作为应用场景。

推荐与检索线索：
可推荐校内研究方向匹配“LLM Agent / 知识增强 / 智能问答”的导师；
可检索校内已有相关论文/毕设题目；
可推荐适配的实验室项目或横向课题；
可推荐与 Agent 相关的校内资源（算力/平台/课程）。

下一步行动建议：
1. 推荐3-5个匹配LLM Agent方向的校内导师/课题组
2. 给出RAG vs Tool Agent的工程选型对比方案
3. 提供2-3个可落地毕业设计题目模板
```

#### 预算控制策略

短期记忆的核心约束是：

> 必须在固定 token budget 内最大化有效信息密度

典型分配：
```
Sliding Window:   40%
Session Summary:  40%
Key State:        20%
```

动态调整规则：

- 对话初期：窗口占比更高
- 对话后期：摘要占比提升
- 任务明确后：状态快照占比最高

### 2. 长期记忆

长期记忆偏`“情景记忆”`，保存`值得跨会话复用的历史事件与交互证据`，例如：
```text
2026-08-12：
学生在职业规划对话中明确表示，
就业方向优先考虑 Agent 应用开发，
就业地点目前偏向上海。
```

长期记忆回答：

> 过去发生过什么？

其特点：

- 保留事件上下文、时间和来源；
- 信息较完整，但噪声高于画像；
- 通过向量检索按需召回；
- 不作为每轮对话的常驻内容。

全量历史对话可以作为`原始交互归档`，但不能简单认为“全量对话向量化 = 长期记忆”。长期记忆应是`从历史交互中筛出的高价值、可跨会话复用事件`。

### 3. 用户画像

用户画像偏`“语义记忆”`，是对多源事实与历史交互的进一步抽象：
```text
求职方向：Agent 应用开发
目标城市：上海
研究兴趣：LLM Agent、RAG
```

用户画像回答：

> 这个学生当前是什么样？

因此二者关系是：
```text
原始历史交互
      ↓
可检索长期记忆
      ↓
候选画像属性
      ↓
稳定用户画像
```

同一信息可以同时出现在记忆和画像中，但形态不同：
```text
长期记忆：
7 月 20 日学生表示准备找上海的 Agent 开发岗位。

用户画像：
求职方向 = Agent 应用开发
目标城市 = 上海
```

这不是重复存储，而是“证据 → 当前认知”的关系。

### **4. 用户画像与长期记忆的抽象层级**

> 有一定“来源重叠”（都从历史交互中沉淀内容），但不应该是“存储内容重复”。更合理的设计是把二者看成不同抽象层级；
```
用户画像 = 从长期历史中提炼出的、当前有效的结构化认知；
```
```
长期记忆 = 支撑这些认知的历史事件与证据。
```

比如用户曾经多次表达：

- “我更想做 Agent 应用开发”
- “我不太想做纯算法岗位”
- “我最近主要投上海的岗位”

经过周期性沉淀后，用户画像里可能只保留：
```
求职方向：Agent 应用开发
偏好：工程/Agent > 纯算法
目标城市：上海
```

而长期记忆中可以保留更具体的历史事件：
```
2026-07-30：讨论 AI Platform 后端岗位……
2026-08-06：修改 Anna 邮箱助手实习描述……
2026-08-11：简历求职意向调整为 Agent 应用开发……
```

所以二者回答的问题不同：


|        | 用户画像          | 长期记忆            |
| :------ | :------------- | :--------------- |
| 核心问题   | “这个用户现在是什么样？” | “过去发生过什么？”      |
| 数据形态   | 结构化、压缩后的事实/偏好 | 事件、对话、历史上下文     |
| 更新方式   | 从多个来源提炼、合并、覆盖 | 随交互持续积累         |
| 注入方式   | 高频、常驻或摘要注入    | 按需检索            |
| 信息密度   | 低噪声、高价值       | 信息更完整，但噪声更高     |
| 是否保留来源 | 可记录来源，但不是重点   | 应尽量保留时间、来源和原始证据 |


这样一来，`历史交互 → 长期记忆 → 用户画像`实际上是一条`信息逐渐抽象`的链路，而不是两套系统分别从对话中提取一遍相同的东西。

更准确地说，你这里的“24h 周期性对话沉淀偏好”，本质上就是一个`长期记忆向用户画像晋升/蒸馏的过程`：

> 历史交互 → 提取候选偏好 → 去重/冲突处理 → 稳定性判断 → 写入用户画像

因此我之前建议的“长期记忆从历史交互中提取偏好、事件等高价值信息”确实和你现有的画像设计有些重叠。对于你的架构，应该进一步区分：

**长期记忆偏“情景记忆”，用户画像偏“语义记忆”。**

这两个术语在面试时也很好解释：长期记忆保存“发生过什么”，画像保存“从这些经历中总结出了什么”。

因此，你简历这句话我建议改成：

> **用户画像与长短期记忆机制：画像融合校内结构化事实、LLM 提取标签及周期性从历史交互沉淀的稳定偏好，采用常驻摘要 + Tool 按需深读的分层注入策略；短期记忆通过滑动窗口 + 摘要保障会话连续性，长期记忆保存跨会话历史事件与交互证据，并通过向量检索按需召回。**

如果字数比较紧，可以进一步压成：

> **用户画像与长短期记忆机制：画像融合校内结构化事实、LLM 标签及周期性沉淀的稳定偏好，采用常驻摘要 + Tool 按需深读；短期记忆通过滑动窗口 + 摘要保障会话连续性，长期记忆保存跨会话事件与交互证据，通过向量检索按需召回。**

我更推荐第二版。

另外，原来的“**长期记忆向量化存储全量对话**”不是说技术上不能做，而是概念上容易让人觉得“向量库里的聊天记录 = 长期记忆”。如果你的真实实现确实是全量对话都入库，可以在面试中解释为：

> 底层保留全量历史交互作为原始证据层，在其上构建可检索的长期记忆；高频、稳定的信息进一步沉淀为用户画像。

这样你的整个记忆体系实际上会很清楚：

**原始历史交互 → 可检索长期记忆 → 稳定用户画像**，抽象程度逐层提高。

## 三、画像信息模型

一条画像信息应拆成多个正交维度：


| 维度    | 含义          | 示例                                         |
| ----- | ----------- | ------------------------------------------ |
| 信息内容  | 画像表达什么      | 专业、研究兴趣、职业倾向、资源偏好                          |
| 信息来源  | 原始数据来自哪里    | 教务系统、图书馆、问卷、对话、反馈                          |
| 形成方式  | 画像如何得到      | 直接事实、用户自述、规则统计、LLM 推断                      |
| 来源可靠性 | 原始信息本身是否可靠  | 校内权威数据高、单次弱行为低                             |
| 推断置信度 | 从证据推导结论是否可靠 | 多源一致时提高                                    |
| 时效性   | 信息变化速度      | 稳定、阶段性、短期                                  |
| 证据    | 什么支撑该结论     | 选课、项目、对话、报名记录                              |
| 状态    | 当前是否有效      | candidate / active / superseded / rejected |


需要区分“来源可靠性”和“推断置信度”。

例如：
```text
事实：
选修《机器学习》
来源可靠性：高

推断：
职业兴趣 = 算法
推断置信度：中低
```

而用户明确说：
```text
“我想找 Agent 应用开发岗位”
```

虽然来自对话，但对于“职业偏好”这一维度，它比根据选课记录推断更直接、更可靠。

## 四、总体数据分层

建议划分为四层：


| 层级        | 保存内容            | 示例             |
| --------- | --------------- | -------------- |
| L0 原始证据层  | 校内数据、问卷、对话、行为事件 | 选课记录、一次对话、一次报名 |
| L1 事实与记忆层 | 可确认事实、长期事件记忆    | 专业=计算机、参与某项目   |
| L2 画像认知层  | 当前有效的画像结论       | 研究兴趣=Agent     |
| L3 消费视图层  | 面向不同业务生成的表示     | 常驻摘要、完整画像、推荐标签 |


整体结构：
```text
                  学生数据
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
     校内系统        问卷        用户交互
        │            │            │
        └────────────┼────────────┘
                     ↓
                 Evidence
                     │
        ┌────────────┴────────────┐
        ↓                         ↓
 Structured Fact              Memory
   结构化事实                 长期事件记忆
        │                         │
        └────────────┬────────────┘
                     ↓
             Candidate Claim
                     ↓
      校验 / 合并 / 冲突 / 时效判断
                     ↓
               Active Claim
                     ↓
      ┌──────────────┼──────────────┐
      ↓              ↓              ↓
   常驻摘要       Tool 深读      推荐圈选视图
```

## 五、核心数据模型

### 1. `profile_dimension`：画像维度定义

用于定义不同画像字段的更新规则，避免将逻辑写死在代码中。

核心字段：
```text
dimension_key
dimension_name
category
value_type
cardinality
source_policy
stability
decay_policy
conflict_policy
inject_policy
recommendation_enabled
```

例如：
```text
research_interest
- 多值
- 动态
- 可由问卷、对话、项目、课程、图书馆、反馈共同更新

major
- 单值
- 稳定
- 只允许校内权威系统更新
```

不同画像维度必须采用不同更新规则：

> “学院、专业”不能靠对话覆盖；“研究兴趣、职业偏好”则应允许随行为和对话动态变化。

### 2. `student_fact`：结构化事实

保存画像计算所需的标准化事实，例如：

- 学院、专业、年级；
- 选课记录；
- 科研项目；
- 讲座参与；
- 图书馆借阅；
- 实验室经历。

核心字段：
```text
fact_id
student_id
fact_type
fact_key
value_json
source_system
source_record_id
occurred_at
valid_from
valid_to
created_at
updated_at
```

注意：

> 校内业务系统仍然是原始事实的权威来源，`student_fact` 只是画像系统内部的标准化事实投影。

### 3. `profile_evidence`：统一证据

所有能够支撑画像结论的信息，都统一包装成 Evidence。

证据类型：
```text
SIS_FACT          校内结构化事实
QUESTIONNAIRE     问卷
USER_STATEMENT    用户明确表达
CONVERSATION      普通对话
MEMORY            长期记忆
FEEDBACK          推送反馈
BEHAVIOR          用户行为
```

核心字段：
```text
evidence_id
student_id
evidence_type
source_system
source_ref_id
content
payload_json
occurred_at
source_reliability
created_at
```

Evidence 让画像可以追溯：
```text
research_interest = Agent
        ↓
E1024：本人明确表达
E0931：参与教育智能体项目
E0872：参加大模型相关讲座
E0821：借阅相关图书
```

### 4. `memory_item`：长期记忆

保存值得跨会话复用的历史事件。

核心字段：
```text
memory_id
student_id
memory_type
content
source_conversation_id
occurred_at
importance
validity
embedding_id
created_at
```

存储职责：

- MySQL：完整内容、时间、来源、有效状态等元数据；
- Milvus：向量索引与语义召回；
- Milvus 不承担权威状态管理。

### 5. `profile_claim`：画像结论

`profile_claim` 是真正意义上的当前用户画像。

之所以使用 Claim，而不是简单的 Tag，是因为：

> “用户喜欢 Agent”是系统基于当前证据形成的一条认知结论，并不一定永久成立。

核心字段：
```text
claim_id
student_id
dimension_key
value_json
claim_type
confidence
stability
status
first_seen_at
last_supported_at
valid_from
valid_to
version
supersedes_claim_id
generated_by
created_at
updated_at
```

其中：
```text
claim_type:
fact
self_report
inferred

status:
candidate
active
superseded
rejected
```

### 6. `claim_evidence`：画像与证据关系

Claim 与 Evidence 是多对多关系：
```text
claim_id
evidence_id
relation
weight
```

其中：
```text
relation:
support
contradict
```

画像因此具备：

> **可解释性、可追溯性、冲突检测能力。**

### 7. `feedback_event`：推送反馈

推送反馈先保存成行为事件，不直接修改画像：
```text
feedback_id
student_id
resource_id
event_type
occurred_at
context_json
```

事件包括：
```text
LIKE
DISLIKE
CLICK
VIEW
SAVE
REGISTER
ATTEND
IGNORE
```

不同反馈强度不同：


| 信号        | 强度    |
| --------- | ----- |
| 点赞、明确感兴趣  | 强正反馈  |
| 报名、实际参加   | 强正反馈  |
| 多次查看      | 中等正反馈 |
| 单次点击      | 弱正反馈  |
| 踩、明确不感兴趣  | 强负反馈  |
| 单次忽略      | 极弱信号  |
| 长期同类资源无响应 | 弱负反馈  |


因此：

> **忽略 ≠ 不喜欢。**

正确链路：
```text
Feedback Event
      ↓
Signal Aggregator
      ↓
Evidence
      ↓
Candidate Claim
```

## 六、画像生成与更新机制

### 1. LLM 不直接写 Active Profile

采用两阶段更新：
```text
规则 / LLM
     ↓
Candidate Claim
     ↓
Profile Resolver
     ↓
Active Claim
```

LLM 负责：

> **“这些信息可能意味着什么？”**

程序负责：

> **“这条结论能否进入当前画像？”**

### 2. Candidate Extractor

从事实、长期记忆和行为信号中生成候选画像：
```text
dimension = research_interest
value = robotics
evidence_ids = [E101, E103]
status = candidate
```

LLM 输出必须绑定 Evidence，避免无证据生成画像。

### 3. Profile Resolver

Profile Resolver 负责确定性处理：
```text
Schema 校验
    ↓
Evidence 校验
    ↓
来源是否合法
    ↓
检索同维度已有画像
    ↓
新增 / 强化 / 削弱 / 冲突
    ↓
时效与稳定性判断
    ↓
更新 Active Claim
```

核心职责：

- 去重；
- 合并；
- 证据累积；
- 冲突判断；
- 时间衰减；
- 画像版本管理。

---

## 七、置信度、时间与冲突

### 1. 置信度

置信度不能完全交给 LLM 自己打分，至少考虑：
```text
来源可靠性
+
证据强度
+
多证据一致性
+
信息新鲜度
```

V1 可以先使用：
```text
HIGH
MEDIUM
LOW
```

没有必要强行生成看似精确的 `0.873`。

### 2. 稳定性与时间

不同画像变化速度不同：


| 画像属性   | 稳定性       |
| ------ | --------- |
| 学院、专业  | stable    |
| 职业方向   | medium    |
| 研究兴趣   | medium    |
| 最近关注主题 | transient |
| 推荐资源偏好 | dynamic   |


动态画像至少维护：
```text
first_seen_at
last_supported_at
valid_from
valid_to
stability
```

不能把历史偏好永久作为当前画像。

### 3. 冲突处理

对于单值维度，例如：
```text
原画像：
career_city = 上海

新表达：
“现在准备去杭州。”
```

不直接覆盖，而是：
```text
C101:
career_city = 上海
status = superseded

C144:
career_city = 杭州
status = active
supersedes_claim_id = C101
```

对于研究兴趣等多值维度，则可以共存：
```text
Agent
机器人
医疗 AI
```

因此在 `profile_dimension` 中通过 `cardinality = single / multi` 配置不同冲突策略。

## 八、从对话记忆沉淀画像

周期任务不应该是：
```text
对话 → LLM 总结 → 直接修改画像
```

而应该是：
```text
近期长期记忆
      ↓
提取候选画像
      ↓
与既有画像比对
      ↓
合并 / 强化 / 削弱 / 冲突
      ↓
稳定性判断
      ↓
更新画像
```

画像可以理解为：
```text
即时信号
   ↓
候选偏好
   ↓
稳定偏好
```

例如学生第一次说：

> “最近对机器人方向也挺感兴趣。”

先形成：
```text
research_interest = robotics
status = candidate
```

如果随后出现：
```text
报名机器人讲座
+
持续关注机器人导师
+
参与机器人项目
```

则不断增加支持证据，最终晋升为稳定画像。

因此所谓“24h 周期性沉淀”，本质上是：

> **长期记忆向用户画像的晋升 / 蒸馏过程。**

## 九、多视图消费与分层注入

底层 Active Claims 是画像系统面向下游的统一数据源，在此基础上派生三类视图。

### 1. 常驻上下文摘要

每轮对话只注入高价值、低噪声摘要：
```text
【学生画像摘要】

计算机专业硕士研究生。
当前研究兴趣集中于 LLM Agent 与 RAG。
近期职业方向偏 Agent 应用开发和 AI Platform。
就业地点倾向上海。
```

特点：

- 信息少；
- 稳定；
- 高频使用；
- 控制 Token 开销。

### 2. Tool 按需深读

Agent 需要更完整信息时调用：
```text
get_profile(section="career")
```

返回：
```text
职业方向：
- Agent 应用开发
- AI Platform 后端

就业地点：
- 上海

相关证据：
- 用户明确表达……
- 参与教育智能体项目……
- 近期关注……

历史变化：
- 曾考虑算法方向
- 后逐渐转向 Agent Engineering
```

### 3. 推荐圈选视图

为资源推荐生成结构化 Feature：
```text
student_id
feature_key
value
confidence
updated_at
```

例如：
```text
10001 | interest.agent    | true | HIGH
10001 | interest.rag      | true | MEDIUM
10001 | career.backend    | true | HIGH
```

推荐系统直接基于结构化字段筛选，不需要每次让 LLM 判断哪些学生应该收到通知。

## 十、服务端存储与 LLM 可读视图

系统部署在服务器中，以 Web 方式服务约 500 名用户。画像数据不采用“每个用户对应若干 `.md` 文件”的文件系统持久化方案，而采用：

> **MySQL 结构化持久化 + Redis 热点缓存 + Milvus 语义索引 + LLM 可读文本动态生成。**

500 名用户本身并不会带来明显的容量压力，关键问题在于并发更新、事务一致性、结构化查询以及未来多实例部署。如果直接维护：
```text
profiles/
├── user_001/
│   ├── summary.md
│   ├── academic.md
│   └── interest.md
├── user_002/
└── ...
```

会带来文件写竞争、查询困难、版本和事务管理复杂，以及多实例服务之间本地文件不同步等问题。因此 Markdown 只作为一种**序列化展示格式**，不作为物理存储形式。

### 1. MySQL：画像权威状态

MySQL 保存画像系统内部需要维护的结构化状态：
```text
student
profile_dimension
student_fact
profile_evidence
profile_claim
claim_evidence
memory_item
feedback_event
student_profile_feature
profile_view_snapshot
```

职责：

- 保存结构化事实及其标准化投影；
- 保存 Evidence；
- 保存 Claim、版本和当前状态；
- 保存反馈事件；
- 支持事务、并发更新和结构化查询；
- 为画像摘要、深度读取和推荐圈选提供统一数据源。

需要区分两层“权威性”：

> **校内业务系统是学院、专业、选课等原始事实的权威来源；MySQL 中的 Active Claims 是画像系统面向下游消费的当前有效状态。**

### 2. LLM 可读视图：动态生成，不落地为 Markdown 文件

Agent 不直接读取服务器上的 `profile.md`，而是通过画像 Tool 获取所需视图：
```text
Agent
  ↓
get_profile(student_id, section)
  ↓
Redis Cache
  ↓ miss
MySQL 查询 Active Claims / Evidence
  ↓
Profile Renderer
  ↓
Markdown / Text
  ↓
返回 Agent
```

因此“Markdown”更准确地说是：

> **画像的 LLM 可读序列化格式，而不是画像的持久化格式。**

例如 `get_profile(section="career")` 可以在运行时生成：
```text
// 职业规划

当前方向：
- Agent 应用开发
- AI Platform 后端

就业地点：
- 上海

相关证据：
- 用户明确表达……
- 参与教育智能体项目……
```

这段内容只是一次 Tool 返回结果，可以动态生成，也可以在 Redis 中缓存，不需要对应一个真实的 `profile_career.md` 文件。

### 3. 三类逻辑视图

底层仍然只有一套 Active Claims，不为三种场景分别维护三份画像。
```text
               Active Claims
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
   Summary View   Section View   Feature View
        ↓            ↓            ↓
   常驻上下文      Tool 深读      推荐圈选
```

其中：

#### Summary View

面向实时对话图，保留高价值、低噪声画像摘要。生成后可缓存：
```text
profile:summary:{student_id}
```

#### Section View

面向 Tool 按需深读，根据 `academic / interest / career / preference` 等 section 查询相关 Claim 和 Evidence，再动态组织成 LLM 可读文本。

可按需缓存：
```text
profile:section:{student_id}:{section}
```

#### Feature View

面向资源推荐和学生圈选，保持结构化形式，例如：
```text
student_id
feature_key
value
confidence
updated_at
```

该视图主要用于数据库过滤和推荐逻辑，不需要转换为自然语言。

### 4. Redis：视图与热点数据缓存

Redis 不保存画像的最终权威状态，只缓存可重建结果：
```text
profile:summary:{student_id}
profile:section:{student_id}:{section}
profile:feature:{student_id}
memory:search:{student_id}:{query_hash}
```

典型读取链路：
```text
Agent
  ↓
get_profile(10001)
  ↓
Redis 命中？
  ├─ 是 → 直接返回
  └─ 否
       ↓
     MySQL
       ↓
  Profile Renderer
       ↓
  写入 Redis
       ↓
     返回 Agent
```

画像更新后，不直接修改缓存内容，而是：
```text
Profile Resolver
      ↓
更新 MySQL
      ↓
删除 / 失效对应 Redis Key
      ↓
下次读取重新生成
```

避免数据库状态和缓存视图长期不一致。

### 5. Milvus：长期记忆语义索引

Milvus 主要保存：
```text
memory_embedding
```

必要时也可以保存适合语义检索的画像证据或画像片段索引，但不承担 Claim 当前状态管理。

典型长期记忆读取：
```text
Query
  ↓
Milvus 召回 memory_id
  ↓
MySQL 获取完整 Memory / Evidence
  ↓
按需注入 Agent 上下文
```

### 6. 部署层面的结论

对于当前约 500 名用户的 Web 系统，推荐的画像数据链路是：
```text
                MySQL
         结构化画像权威状态
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
   Active Claim  Evidence   Memory
       │
       └──────────┬──────────┘
                  ↓
           Profile Renderer
                  ↓
        LLM 可读 Markdown/Text
                  ↓
              Redis Cache
                  ↓
                Agent
```

这里最重要的区分是：

> **分层注入 ≠ 分文件存储。**

“常驻摘要 + Tool 按需深读”的分层注入策略仍然成立，只是底层统一从结构化画像生成不同视图，而不是为每个用户维护多份 Markdown 文件。

## 十一、完整更新链路
```text
新数据进入系统
    │
    ├─ 教务 / 图书馆 / 科研数据
    ├─ 问卷
    ├─ 用户对话
    └─ 推荐反馈
          ↓
    原始数据 / Evidence
          ↓
     事实与记忆持久化
          ↓
    Candidate Extractor
      规则 / LLM
          ↓
     Candidate Claim
          ↓
      Profile Resolver
          │
          ├─ Schema 校验
          ├─ Evidence 校验
          ├─ 去重
          ├─ 一致性判断
          ├─ 冲突处理
          ├─ 时间与稳定性判断
          └─ 状态更新
          ↓
       Active Claim
          ↓
┌─────────┼──────────┐
↓         ↓          ↓
画像状态更新完成
          ↓
   相关 Redis 缓存失效

下次读取动态重建摘要 / 深度视图 / 推荐视图
```

## 十二、面试概述

如果面试官问“你们用户画像是怎么设计的”，可以概括为：

> 我们没有把用户画像做成静态标签表，而是设计成证据驱动的动态画像。底层统一接入校内结构化事实、问卷、历史交互和推荐反馈等数据，并保存其来源和证据；规则和 LLM 只负责生成候选画像属性，再由程序完成校验、去重、冲突处理、时效判断和状态更新。最终有效画像作为下游统一数据源，派生出面向 Agent 的常驻摘要、Tool 按需读取的完整画像，以及面向资源推荐的结构化圈选视图。长期记忆负责保存“过去发生过什么”，用户画像负责表达系统对学生“当前是什么样”的稳定认知。

整个体系可以进一步压缩为：

> **数据采集 → 证据管理 → 画像推断 → 画像演化 → 多视图消费**

真正有技术含量的重点不是“让 LLM 生成标签”，而是：

> **可追溯画像、动态画像演化、画像与记忆分层。**

## 面试直接答

可读性确实有主观成分，但它有可操作的判据：以"目标读者能否在预算时间内准确理解并安全修改这段代码"为基准，底层机制是读者的认知负荷，落地上可以拆成命名、局部性、抽象层次、一致性四类可检查的信号。我的观点是，判断一段代码可不可读，不应该停留在"我觉得"的层面，而要用可证伪的指标和可复现的实验来验证，这正是 Google 用可读性认证制度管理这件事的原因。

先解释为什么可读性"主观但可度量"。主观是因为读者背景不同：熟悉领域的人读领域代码毫无障碍，新人读同一段代码可能完全卡住，所以可读性永远要相对"目标读者"定义。可度量是因为理解代码的过程消耗的是工作记忆，而工作记忆的容量是有认知科学研究支撑的：短时记忆大约只能同时容纳四到七个信息块。Felienne Hermans 在《The Programmer's Brain》里系统研究过这个问题——读者在理解一段代码时需要把变量值、控制流、不变量同时装进工作记忆，一旦信息块数量超载，理解就会失败。所以可读性的本质问题就变成了：这段代码要求读者同时在脑子里装多少东西。

由此出发，第一类判据是命名与词汇。好的命名让读者不必回到定义点就能恢复语义，名称长度与作用域匹配——作用域越大、存活越久，名字就该越具体；动词要精确区分 get、fetch、compute、resolve 的语义；更重要的是团队内词汇一致，同一个概念永远用同一个词，这是领域驱动设计里统一语言在代码层的落地。命名不一致的代码，读者每遇到一个新名字就要重新建立一次映射，认知负荷是叠加的。

第二类判据是结构层面的认知负荷，也就是 Google 代码审查指南里对"复杂度"的定义：无法被读者快速理解的代码就是过度复杂。具体信号包括函数长度、嵌套深度、魔法数字、一行里多个决策点，以及变量的定义点与使用点距离——一个变量在文件开头定义、在三百行之后才被使用，读者的工作记忆就被白白占用了几百行。每行代码应该只要求读者做一个决策，每段代码块应该只讲一层故事。

第三类判据是局部性与抽象层次。局部性指修改的局部化程度：改一个需求要动几个文件、几处代码，需求变更的范围越小，说明代码结构越接近业务结构的真实边界。抽象层次一致的意思是，同一个函数内不应该混着业务规则、IO 细节和数据结构操作——单层抽象原则（Single Level of Abstraction）要求函数内所有语句处于同一抽象级别，读者才能顺着一个叙事线读完而不需要在不同层次之间跳来跳去。

第四类判据是可证伪的验证手段。审查时让同事只看代码、不看文档，然后复述这段代码的行为并画出流程，行为对不上就是不可读的客观证据；让新成员尝试在代码里定位并修改一个具体需求，记录卡壳的位置和耗时；用圈复杂度、命名一致性检查这类工具做自动化底线。可读性一旦有了可测量的代理指标，它就从审美争论变成了工程问题。

同事说你的代码难懂的时候，我的处理方式是分三步。第一步是收集证据而不是辩护：具体是哪个文件哪一段、卡在哪个概念上、期望读到什么却没读到，把"难懂"这个整体感受拆成可定位的具体问题——很多冲突在拆解这一步就会消失，因为双方谈论的根本不是同一处代码。第二步是归因：如果是命名或结构问题，直接改，这没有讨论空间；如果是知识差——同事不熟悉这段代码依赖的业务背景或技术选型，那正确的动作是补注释、写设计决策记录，把"为什么这么写"沉淀下来，而不是把代码改得更啰嗦；如果是风格偏好，引入团队规范来仲裁，比如统一风格指南和 lint 规则，让机器执行一致性，人不再为格式吵架。第三步是用改写对比验证：按照对方的建议改一个版本，让团队盲评两个版本，如果对方的版本确实更好，就承认并吸收进团队规范，让这次的争论变成下次的标准。

同时我要守住一个反向的警惕：不要写"聪明代码"。位运算技巧、深继承、元编程、嵌套三元的炫技写法，代价几乎总是可读性，除非有性能剖析数据证明这处优化是必要的，否则一律选择直白的写法。可读性的目标读者是团队平均水平，不是未来的自己——三个月后的自己读现在的代码，和一个普通同事读它的难度没有区别。

边界上我也承认：可读性有时与性能冲突，查表法、SIMD 这些优化天然难读，这种场景需要基准测试背书加详尽的注释；领域代码（数学公式、DSL）的读者是领域专家，可读性标准要向专业读者校准。总结来说，可读性不是玄学，是可以用认知科学解释、用工程手段度量、用团队流程改进的系统工程。

## 详细解析

### 为什么可读性有客观底座：认知负荷模型

理解代码时，读者的大脑同时在处理三类信息（Hermans《The Programmer's Brain》的框架）：变量当前值、控制流位置、以及这段代码试图维持的业务不变量。这些信息竞争**工作记忆**的有限容量——心理学经典结论是短时记忆约 4~7 个信息块。代码越要求读者同时记住更多信息块，理解失败率越高：

```
工作记忆（约 4~7 个块）
├── 变量值 × N（每个活跃变量占一个块）
├── 控制流位置（循环、分支嵌套一层加一个块）
├── 业务不变量（"balance 永不为负"这类隐含约束）
└── 超出容量 → 读者开始猜 → 误解 → bug
```

可读性工程的全部手段，本质都是减少对工作记忆的占用：好命名免去回查定义，短函数免去记忆中间状态，卫语句免去记忆嵌套条件，局部化免去记忆跨文件关系。

### "难懂"的三类归因与应对

| 归因 | 典型信号 | 证据 | 应对 |
|---|---|---|---|
| 结构与命名问题 | 巨函数、误导性命名、嵌套过深、魔法数字 | 读者复述行为失败；定位修改耗时长 | 改代码，无讨论空间 |
| 知识差 | 领域概念陌生、技术选型动机不明 | 解释清楚后读者表示理解 | 补注释与设计决策记录（ADR），不改代码 |
| 风格偏好 | 两种写法都合理，纯属口味 | 双方都说服不了对方 | 团队规范 + lint 仲裁，机器执行一致性 |

### 同一逻辑的两种写法

不可读版本：

```java
if (u != null && u.getLevel() >= 3 && !u.isBanned() && (s = u.getSubscription()) != null && s.isActive() && (System.currentTimeMillis() - u.getLastLoginAt() < 30L * 24 * 3600 * 1000)) {
    d = computeDiscount(o, u.getLevel() == 5 ? 0.2 : 0.1);
} else {
    d = 0;
}
```

可读版本：

```java
private static final long MONTH_IN_MILLIS = 30L * 24 * 3600 * 1000;
private static final int VIP_LEVEL = 5;

public double discountFor(Order order, User user) {
    if (user == null || !eligibleForDiscount(user)) {
        return 0;
    }
    double rate = user.getLevel() == VIP_LEVEL ? 0.2 : 0.1;
    return computeDiscount(order, rate);
}

private boolean eligibleForDiscount(User user) {
    return user.getLevel() >= 3
        && !user.isBanned()
        && hasActiveSubscription(user)
        && loggedInWithin(user, MONTH_IN_MILLIS);
}
```

对比要点：第一版一行五个决策点加两个副作用，读者必须同时追踪所有条件；第二版把决策拆成带名字的谓词，每个方法只回答一个问题，`30L * 24 * 3600 * 1000` 这个魔法数字被命名后意图自明。两版行为等价，工作记忆占用完全不同。

### 面试追问

**追问一：可读性和性能冲突的时候，你会怎么选？**

默认先可读，优化必须有数据背书。流程是：写直白的版本 → 用 profiler 找到真正的热点 → 只对热点做必要的优化 → 优化处用注释解释为什么不能写直白（附基准数据），并用测试锁住行为。大多数"为了性能"的难懂代码在剖析之后都会发现根本不在热路径上，是过早优化。真正的冲突场景（查表法、SIMD、位操作）只占代码库的极小比例，值得用注释成本换取性能收益，其余 99% 的代码没有资格牺牲可读性。

**追问二：新人一眼能懂的代码，和资深工程师觉得啰嗦的代码，怎么平衡？**

先定义目标读者。可读性优化目标是"团队平均水平的成员"，既不是第一天入职的新人，也不是写这段代码的人。新人一眼能懂但资深觉得啰嗦的代码，通常是抽象层次过低——把每个细节都铺开，反而淹没了主线，这种"简单"对所有人都是负担。正确解法是维持单层抽象：公开接口面向领域概念，实现细节收进下层函数，新人读上层就能建立心智模型，需要细节时再下钻。如果新人连上层都读不懂，那是抽象层次过高或命名问题，不是新人的问题。

**追问三：如果"难懂"是因为代码用了不常见的模式——函数式写法、设计模式、DSL——你会改吗？**

先问这个模式在不在为团队买单。不常见的写法如果有明确收益——设计模式约束了不变量、函数式消除了共享状态、DSL 把业务规则交还给业务人员——那该做的是文档和培训，把"不常见"变成"团队常见"。如果模式没有收益，只是为了炫技或个人偏好，那它就是在用全体读者的认知成本为作者买单，应该改成团队的主流写法。判断标准很简单：把这个模式删掉重写，系统会失去什么能力？什么都没失去的话，答案就是删。

**追问四：你怎么衡量可读性改进的实际效果？**

用三个可观察的代理指标。修改局部性：统计典型需求变更触及的文件数和行数，可读性好的代码改动范围收敛；评审与 onboarding 时长：新成员定位、理解、修改一个需求的平均耗时，这是最直接的读者视角数据；缺陷密度：难理解的代码区域 bug 密度显著更高，这是软件工程领域反复验证过的相关性——读者理解错的地方，就是 bug 出生的地方。这三个指标不需要精确到小数，趋势足够支撑决策。

## 面试直接答

审查 AI 生成代码和审查人类代码共享同一套质量底线，但审查重心必须转移：人类代码审查主要防范"人为什么会写错"，AI 代码审查要防范"模型在什么条件下系统性出错"。我的做法是把审查资源优先投向正确性与安全这类**可证伪**的维度，风格与规范问题交给 linter 和 CI 门禁，再用测试、静态分析、agent 交叉审查和人工逐行复核组成多层防线。这个重心转移不是偏好问题，而是由模型的工作方式决定的。

模型生成代码时没有运行时反馈，它对项目约束的理解完全来自 prompt 和上下文，而不是编译错误和测试失败；它倾向于生成"看起来合理但实际错误"的代码，而且信心与正确性不相关。有数据支撑这个判断：DryRun Security 在 2026 年 3 月发布的 Agentic Coding Security Report 里，用三个主流 agent 各自通过连续 PR 构建完整应用，结果 30 个 AI 生成 PR 中有 26 个引入了至少一个安全漏洞，共 143 个问题，比例高达 87%；其中 Codex 表现最好，最终仍遗留 14 个未解决问题。反复出现的漏洞集中在访问控制缺失、缺少速率限制、硬编码 JWT 密钥这些 OWASP Top 10 经典模式上。

所以我审查的第一优先级永远是安全。具体检查点包括：外部输入是否参数化进入 SQL 而不是字符串拼接；密钥、凭证、token 是否硬编码在代码或配置文件里；新增接口是否做了鉴权和授权而不是默认信任；AI 顺手引入的新依赖是什么、版本和来源是否可信——供应链是 AI 代码审查里容易被忽略但风险最高的维度，因为模型倾向于"引入一个库解决问题"而不会评估维护状态。

第二优先级是正确性。AI 代码最常见的正确性问题集中在四类：只覆盖 happy path 而漏掉边界和失败分支；空 catch 块和吞异常；并发场景下共享状态没有同步或事务边界错误；以及幻觉——调用不存在的库函数、写错默认参数、虚构配置项。这类问题肉眼审查效率很低，我的验证手段是可执行的：要求 agent 为每个不变量和反例写测试并实际跑通，类型检查和测试覆盖率是硬门禁，幻觉 API 在编译期就会被发现。

第三是架构一致性，这是 AI 代码和人类代码审查差异最大的地方。AI 有两个相反的毛病：上下文充足时倾向过度设计，比如为一个简单查询引入工厂类、转换层和多组数据对象；上下文不足时又把本该抽象的逻辑直接写死。真正需要检查的不是"用没用设计模式"，而是抽象层次是否与需求复杂度、项目现有架构和未来变化概率匹配。同时要检查它是否违背了项目约定——现在很多仓库有 CLAUDE.md 这类项目规范文件，新代码违反规范说明 agent 没有真正遵循上下文。另外 AI 常常不搜索代码库就重复造轮子，实现一个项目里已经存在的工具函数。

第四层是工具化审查，这是 coding agent 生态里进展最快的部分。Claude Code 内置 `/review` 命令可以审查工作区的暂存和未暂存改动，配套的 Code Review 功能在 PR 上部署专门的审查 agent 集群，把发现去重、分级、验证后以内联评论形式贴到具体行，还支持用 REVIEW.md 自定义严重度定义、跳过规则和验证标准。OpenAI 的 Codex Security Review 是 2026 年 3 月进入研究预览的专项安全审查，四阶段流水线：先为仓库建立可编辑的威胁模型，再结合提交历史扫描，然后在隔离沙箱里实际复现漏洞确认不是误报，最后生成最小化补丁作为 PR 提交给人工评审。独立测试显示它真阳性率 74%，对比 Semgrep 的 20% 和 Snyk 的 28%；测试期间扫描了 120 多万个提交，在 OpenSSH、GnuTLS、Chromium 等大型开源项目里发现了 14 个真实 CVE。

但工具不能替代人工，这是我的明确边界。静态工具和审查 agent 都查不出业务逻辑错误——比如扣款金额的计算公式违反业务规则，这在任何安全扫描器眼里都是"正确"的代码。而且生成代码的模型和审查代码的模型如果是同一个，会存在系统性盲区：同类偏见会同时漏掉同一类问题。所以我的流程是：小批量 PR 让 diff 尽可能小，CI 门禁（lint、typecheck、测试、依赖漏洞扫描）不可跳过，高风险模块用不同模型的独立 agent 交叉审查，关键路径和所有安全补丁必须人工逐行复核并签字。对待 AI 生成的代码，标准应该和审查一个初级外包工程师的代码完全一致，甚至更严，因为它的产出速度意味着错误也会以同样速度累积。

## 详细解析

### 多层审查防线

```
┌─────────────────────────────────────────────────────────────┐
│ 第一层：自动门禁（不可跳过）                                    │
│   lint / typecheck / 单元测试 / 依赖漏洞扫描（SCA）            │
├─────────────────────────────────────────────────────────────┤
│ 第二层：agent 交叉审查                                        │
│   /review（通用）· Codex Security Review（安全专项）           │
│   不同模型交叉验证，避免同模型系统性盲区                        │
├─────────────────────────────────────────────────────────────┤
│ 第三层：人工逐行复核                                          │
│   关键路径、安全补丁、数据库迁移、配置变更 → 必须人工签字       │
│   业务逻辑正确性只能由领域知识判断                              │
├─────────────────────────────────────────────────────────────┤
│ 第四层：生产可观测（兜底）                                      │
│   日志 / 指标 / 告警 / 灰度发布 + 回滚预案                     │
└─────────────────────────────────────────────────────────────┘
```

### 工具对比：三种审查路径

| 维度 | Claude Code /review 与 Code Review | Codex Security Review | 人工审查 |
|---|---|---|---|
| 触发方式 | `/review` 命令；PR 上按需/自动触发 | PR 评论 `@codex security review`；PR 打开或每次 push 自动运行 | 团队流程 |
| 审查重点 | 正确性、bug、风格、规范符合度 | 安全漏洞（威胁建模驱动） | 全部维度，业务逻辑最强 |
| 验证手段 | 结合代码库上下文分析，REVIEW.md 可要求 file:line 证据 | 沙箱实际复现漏洞，过滤误报 | 领域知识与运行时经验 |
| 已知局限 | 同模型盲区；业务规则错误难发现 | 无合规审计报告；大仓库首次扫描慢；补丁质量未充分验证 | 速度与覆盖率有限，成本高 |
| 定位 | 通用审查加速 | 安全专项拦截 | 最终责任与签字 |

### AI 生成代码的典型问题示例

下面这段代码是 AI 生成的典型产物，几乎每个审查维度都有问题：

```java
@Service
public class PaymentService {

    public void processPayment(String userId, String amount) {
        try {
            String sql = "UPDATE accounts SET balance = balance - " + amount + " WHERE user_id = " + userId;
            jdbcTemplate.execute(sql);
            logger.info("payment processed");
        } catch (Exception e) {
            // TODO: handle later
        }
    }
}
```

逐行审查要点：

| 行 | 问题 | 维度 |
|---|---|---|
| `balance - " + amount` | SQL 字符串拼接，注入风险；amount 未做数值校验（负数、NaN、精度） | 安全 + 正确性 |
| `user_id = " + userId` | 同上，且未校验 userId 合法性 | 安全 |
| `processPayment` 无事务注解 | 扣款失败不回滚，无幂等键，重复请求会重复扣款 | 正确性（并发/事务） |
| `catch (Exception e)` 空吞 | 失败无感知、无告警、无补偿，扣款这类操作必须显式失败 | 正确性（失败分支） |
| `TODO: handle later` | AI 生成的占位注释，恰恰是它没处理失败路径的直接证据 | 正确性 |

### 面试追问

**追问一：生成代码和审查代码如果都用同一个模型，系统性盲区怎么破？**

三层手段。第一，交叉验证：生成用 Claude，审查用 Codex 或另一个模型，同类偏见交叉后漏检率显著下降；第二，把审查标准改为可证伪的：不讨论"这段代码好不好"，只验证"这个断言有没有证据"——测试通过没有、类型检查过没有、沙箱里漏洞能不能复现，行为证据优先于模型判断；第三，人工抽查集中在模型最弱的能力上：跨文件语义、业务规则、并发时序，这些恰恰是 agent 审查最不可靠的部分。本质上，盲区的解法不是让模型更聪明，而是让审查链路里至少有一环不依赖模型判断。

**追问二：AI 生成的代码经常"看起来对"，你具体怎么验证？**

核心原则是让验证可执行而不是靠读。类型检查和编译是第一道：幻觉 API、虚构参数在编译期直接暴露。测试是第二道：要求 agent 为业务不变量和反例写测试，测试真实跑通才算数，AI 很擅长写"验证 happy path"的测试，我会额外要求边界值和失败路径的用例。第三道是环境验证：在真实依赖环境里跑起来，而不是只看 diff——很多问题（缺迁移脚本、配置项不存在、端口冲突）只有运行才暴露。最后是 diff 最小化：大 PR 里"看起来对"的代码最难验证，拆小后每个变更的意图清晰，审查密度自然提高。

**追问三：agent 审查的误报怎么管理？会不会审出一堆噪声把团队淹没？**

Claude Code 的 Code Review 用 REVIEW.md 解决这个问题：可以重新定义严重度（比如只有错误逻辑、未加范围的数据库查询、日志泄露 PII 才算 Important，风格问题一律算 Nit）、限制每次审查的 nit 数量、跳过 CI 已覆盖的检查（格式、lint 不需要 agent 再报一遍）、要求每条行为判断附 file:line 证据来压制误报。Codex Security Review 则用沙箱复现来过滤——只有能实际利用的漏洞才报出来，这把它对 Semgrep 的真阳性率从 20% 拉到 74%。所以误报管理不是玄学，是把"什么值得报"写进规则、把"报的到底是不是真的"交给验证。

**追问四：团队里谁对 AI 生成的代码负责？可以让 agent 自动合并修复补丁吗？**

责任在合并者，不在工具。Codex Security Review 生成的补丁明确设计为"只提交 PR 供人工评审，绝不自动应用"，这个设计选择本身就是答案：安全补丁改变了系统行为，必须有人理解它为什么对。我的团队规则是：所有 AI 生成的补丁走正常评审流程，涉及安全、数据库迁移、支付、权限的变更强制人工签字；CI 门禁对 AI 提交和人工提交一视同仁，不允许跳过。这样即使 agent 出错，责任链仍然清晰——合并那个人签字的时候，就是他对代码负责的时候。

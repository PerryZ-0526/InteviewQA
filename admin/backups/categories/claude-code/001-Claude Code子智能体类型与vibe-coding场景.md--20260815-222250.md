# ✅Claude Code 子智能体类型与 Vibe Coding 场景

## 面试直接答

从两个维度分类：第一个维度是它负责什么任务，第二个维度是它如何获得上下文并运行。

### 1. 职责维度

---

先说`职责维度`，Claude Code 最主要的内置子智能体有 `Explore`、`Plan` 和 `general-purpose`。

- Explore 是只读的`代码探索智能体`，主要用于文件定位、符号搜索、`调用链分析`和`代码结构理解`。它不能修改文件，适合回答「认证逻辑在哪里」「这个接口被哪些模块调用」「类似功能是如何实现的」这类问题。它会在独立上下文中读取大量文件，最后只把结论返回主会话，避免搜索结果污染主上下文。
- Plan 也是只读智能体，但主要服务于`计划模式`。它负责在修改代码之前调查现有架构、数据模型、接口和测试结构，为主智能体制定实施方案提供依据。需要注意的是，Plan 更像规划阶段的代码研究员，最终方案仍然由主智能体综合形成。
- general-purpose 是`通用执行型子智能体`，拥有<span style="background-color: rgb(255, 243, 205)">完整的可用工具</span>，适合同时包含代码探索、复杂推理、文件修改和命令执行的多步骤任务。例如跨多个模块统一异常处理、完成一个相对独立的功能、定位并修复测试失败，都可以交给它。

> 除此之外，Claude Code 还有 `statusline-setup`、`claude-code-guide`等辅助型内置智能体，分别用于状态栏配置、回答 Claude Code 自身使用问题。不过日常开发中，真正经常使用的还是 Explore、Plan 和 general-purpose。

Claude Code 还支持`自定义子智能体`。我可以为项目配置代码审查、测试分析、安全审计、数据库迁移等专用智能体，分别设置系统提示词、模型、工具权限、技能和权限模式。这样可以把团队的开发规范和审查流程固化下来，而不是每次临时写一大段提示词。

### 2. 上下文和运行方式维度

---

在这个维度下，子智能体主要分为`命名型子智能体`和`对话分叉型子智能体`。

Explore、Plan、general-purpose 以及`自定义子智能体`都属于命名型子智能体。它们启动时会创建一个新的`独立上下文`，不会继承主会话的完整对话，但会获得自己的系统提示词、工具和模型配置以及`主智能体传递过来的任务描述`；除 Explore、Plan 的精简上下文外，其他子智能体还可能接收项目 CLAUDE.md 和父会话的 Git 状态。

> 它们适合职责明确、可以单独描述、会产生大量中间信息的工作。

对话分叉型子智能体则会继承创建时主会话的完整上下文，包括对话历史、系统提示词、工具和模型。它相当于从当前会话状态复制出一条`执行分支`，因此不需要重新解释之前已经讨论过的需求和决策。不过它后续产生的搜索结果和工具调用仍然保留在自己的上下文中，最终只把结果返回主会话。当前版本可以通过 `/fork` 启动这种分叉。

命名型子智能体强调`「专业化和输入隔离」`，对话分叉型子智能体强调`「继承现有上下文」`。

> - 例如，我想调查一个陌生模块，会使用 Explore；
> - 但如果主会话已经讨论了很长时间的重构方案，现在希望另一个智能体基于已有讨论补测试、做反向审查，或者尝试另一套实现，我会使用对话分叉，因为重新向命名型智能体转述所有背景的成本很高。

### 3. 在 Vibe Coding 中，我一般这样使用。

---

- 让`主智能体`承担需求理解、架构决策、任务协调和最终验收；
- 让`内置子智能体`自主完成代码探索和计划调查；
- 将高输出、独立、可并行的辅助任务隔离出去；
- 通过`自定义子智能体`建立开发、测试和审查之间的`职责与权限边界`；
- 只有在任务需要继承当前完整上下文时才使用分叉，需要并行写代码时再使用`独立工作树`。

子智能体的价值不在于“同时启动多少个 Agent”，而在于上下文隔离、专业分工、权限控制和并行效率是否真正提升了交付质量。

---

所以总结来说，职责维度解决的是「该让谁做」，Explore 负责探索，Plan 负责规划研究，general-purpose 负责复杂执行，自定义智能体负责固定的专业流程；上下文维度解决的是「带着什么背景去做」，命名型子智能体使用干净的独立上下文，分叉型子智能体继承主会话完整上下文。Vibe Coding 的关键不是机械地套用多智能体流水线，而是根据任务特征选择合适的职责、上下文和隔离方式。


## 详细解析

> 功能核验日期：2026-08-10。命令和内置子智能体属于快速变化的产品能力，面试时应说明版本。

### 一、命名型子智能体

Explore、Plan、general-purpose 和自定义子智能体都使用`独立上下文`。

> 主 Agent 应传递完整任务、输出格式、约束和必要证据，不能假设子 Agent 看过主会话。Explore/Plan 使用精简上下文；其他类型还可能读取项目指令和父会话 Git 状态。

独立上下文的价值是`隔离`大量搜索和中间输出，代价是背景转述不完整。
```
- 适合边界清晰、高输出、可独立验收的任务；
- 强依赖隐含讨论的任务不宜直接委派。
```

### 二、对话分叉

通过当前版本的 `/fork` 创建的分叉继承创建点的完整上下文、系统提示、工具和模型，之后独立执行。

它适合<span style="background-color: #fff3cd">让另一路径基于已有长讨论进行审查或尝试替代方案</span>，但不适合重新配置成不同工具或模型的专职 Agent；需要专业化配置时应使用命名型/自定义子智能体。

### 三、Worktree 的真实边界

Worktree 隔离的是工作目录和文件改动，不是完全独立的运行环境。各 worktree 仍共享 Git 对象库和远程仓库，凭据、端口、数据库、缓存及其他外部资源也可能冲突。并行写代码时要给外部资源单独命名，并在合并前处理共同文件冲突。

### 四、选择原则


| 需求          | 选择                       |
| ----------- | ------------------------ |
| 只读搜索、调用链调查  | Explore                  |
| 计划模式中的架构调查  | Plan                     |
| `独立的多步骤执行`  | general-purpose 或自定义子智能体 |
| 固化团队审查/安全规范 | 自定义子智能体                  |
| 完整继承当前长讨论   | 对话分叉                     |
| 并行修改代码      | 独立 Agent + worktree      |


专用 Agent 不一定更准确；效果仍取决于模型、输入证据、提示和验证。

> 主 Agent 应负责拆分、冲突管理和最终验收，子 Agent 的结论仍需用代码、测试或外部状态复核。

### 五、Vibe Coding 的使用边界

主会话负责目标、架构和验收；搜索、测试分析、安全审查等高输出任务可委派。

任务之间尽量减少`共享写入面`，先并行读、后`协调写`。

> 多 Agent 的收益来自上下文隔离和并行，不来自“投票就更正确”。

### 六、`委派任务`的输入与输出契约

- 独立上下文不会自动获得`主会话里的隐含决定`。因此，父会话应传递目标、非目标、允许读写范围、已知事实、验证命令和返回格式。
- 子智能体至少返回结论、证据位置、运行命令、未验证项；负责修改时还要返回文件清单和测试结果。
- 主会话依据 diff、测试或外部状态验收，不能只接受“已完成”。

### 七、并行收益与冲突

并行适合`读多写少、边界稳定、可独立验收的任务`，例如分别调查前端调用链、后端模型和测试覆盖。

不适合多个智能体同时设计同一公共接口、修改同一迁移或共享不可隔离数据库。

> 任务过小时，描述、重复扫描和汇总成本可能超过并行收益。

### 八、Worktree 与外部资源

工作树应使用独立分支，并<span style="background-color: #fff3cd">尽量分配独立端口、临时目录、测试数据库和缓存命名空间</span>。

共享凭据和远程服务时仍可能互相影响。

> 合并前先同步基础分支、处理共同文件冲突，再运行`跨分支不变量相关测试`。

### 九、自定义角色与常见失败

自定义角色应围绕稳定复用的流程建立，工具遵循最小权限。提示词写清成功证据和拒绝边界，比人格描述更重要。

> 常见失败包括遗漏约束、重复探索、把 worktree 当成完全隔离环境、用投票替代测试，以及汇总时只保留结论却丢失证据。

> 选择是否委派，应比较端到端时间、主上下文节省、重复工作、冲突率和验收质量，而不是统计启动数量。

### 十、选择示例

如果主会话只知道“登录失败”：
```
先让 Explore 定位认证入口、配置和相关测试；获得证据后由主会话确定修改范围。

若需要在既定方案下补一组独立测试，可委派 general-purpose 或自定义测试角色。

若主会话已经进行了很长的架构讨论，希望另一条路径从同一背景反向审查，则使用对话分叉更省转述成本。

若两路都要写代码，先按模块分配 worktree 和文件所有权；公共接口由主会话先冻结，最后统一合并验证。
```

> 这里的`选择依据`依次是职责、需要继承多少上下文、是否写共享状态，而不是简单用“复杂任务就多开 Agent”。


## 在 Vibe Coding 中，我如何使用 Claude Code 的子智能体

> 我不会把子智能体理解成需要开发者手动编排的固定流水线。

Claude Code 内置的 `Explore`、`Plan` 和 `general-purpose` 本身会由主智能体根据任务类型自动调用。

因此，我的主要工作不是逐个指定它们做什么，而是<span style="background-color: #fff3cd">把需求、阶段目标、验收标准和并行边界描述清楚</span>，让主智能体能够合理地进行`任务委派`。

> 只有在自动委派不稳定，或者我明确需要`独立审查`、`权限隔离`和`并行执行`时，我才会显式指定或配置子智能体。

---

拿到一个中大型需求后，我首先在主会话中完成需求对齐，明确功能目标、非目标、架构约束、验收标准和允许修改的范围。主会话始终是整个任务的协调者和最终责任主体，它负责维护完整需求、汇总调查结果、决定实施方案，并对最终代码进行验收。子智能体承担的是相对独立的辅助任务，而不是代替主会话掌握整个项目。

在代码库调查阶段，我通常直接要求 Claude 分析相关模块、调用链、数据模型、相似实现和已有测试，不一定显式说“调用 Explore”。当搜索范围较大时，Claude Code会自动将只读调查委派给 `Explore`，把大量文件搜索和阅读过程留在独立上下文中，只将结论返回主会话。这样做的核心价值不是多一个模型并行工作，而是隔离探索过程产生的大量代码、日志和搜索结果，避免主上下文被低价值细节占满。内置 `Explore` 和 `Plan` 当前不会加载项目的 `CLAUDE.md` 与父会话 Git 状态，因此对调查有直接影响的特殊规则，例如“忽略生成目录”或“只分析新版接口”，我会在任务描述中再次明确。

如果需求涉及多个模块、接口变化或者数据迁移，我会进入计划模式，让主智能体先形成文件级实施方案。在这个过程中，Claude Code 会在需要时自动使用 `Plan` 子智能体进行只读调查。最终计划仍由主会话整理和确认，因为主会话拥有完整的需求上下文，能够把不同调查结果组织成修改顺序、依赖关系、验证方式和回滚方案。这里我不会让每个子智能体各自生成一套完整方案，否则容易产生重复分析和相互冲突的架构判断。

进入实现阶段后，我默认由主智能体完成核心链路，特别是多个步骤高度共享上下文时，例如数据模型修改、服务逻辑调整、接口适配和测试更新。这类工作看似可以拆开，但实际存在大量隐式依赖，过度交给多个独立子智能体会增加上下文重建和结果整合成本。Claude Code 官方也更建议把需要频繁交互、多个阶段共享大量上下文的工作留在主会话中，而把独立、可通过摘要交付的任务交给子智能体。

对于真正独立的工作单元，我会让主智能体进行明确委派。例如前端和后端两个改动不存在未确定的共享接口时，可以并行开发；测试套件运行、日志分析、文档检索等会产生大量输出的任务，也适合交给子智能体；一个子智能体还可以专门调查数据库迁移影响，另一个调查接口兼容性，最后由主智能体综合结论。并行拆分的前提是任务之间没有强顺序依赖，并且每个子任务都有明确输入、输出和验收标准，否则并行只会制造更多冲突。

对于反复出现且需要固定检查标准的任务，我不会依赖内置子智能体临时发挥，而是创建项目级自定义子智能体。例如配置只读的代码审查智能体，要求它基于原始需求和代码差异检查架构边界、异常处理、并发、事务、安全和测试有效性；配置测试分析智能体，只允许读取代码和运行测试，不允许直接修改业务代码；配置数据库审查智能体，只允许执行只读查询。自定义子智能体的 `description` 决定 Claude 在什么场景下自动委派，`tools`、`disallowedTools` 和权限模式则用于控制它能执行什么操作，因此我会把职责和权限边界写得非常具体。

实现完成后，我通常采用“开发与审查分离”的协作方式。主智能体先完成实现和基础自检，再调用独立的代码审查子智能体。审查子智能体不直接继承开发过程中的全部判断，而是基于原始需求、实施计划、代码差异和测试结果重新检查。它只输出问题、证据和修改建议，不直接改代码。主智能体再判断审查意见是否成立并完成修复。这样做比让开发模型在原上下文中简单地说“检查一下自己”更可靠，因为审查者有独立的系统提示词、上下文和权限边界。

如果一个旁支任务高度依赖主会话已经积累的背景，我会使用分叉，而不是普通命名子智能体。例如主会话正在实现解析器修改时，可以使用 `/subtask` 从当前完整会话分叉一条支线，让它根据当前设计编写测试，或者分别评估保守修复与重构方案。普通子智能体通常从新的独立上下文开始，只接收主智能体整理的委派说明；分叉则继承当前完整对话、系统提示词、工具和消息历史，更适合“从当前工作状态分出一条支线”。但分叉失去了普通子智能体的输入隔离优势，因此我只在重新传递背景的成本很高时使用。

如果多个子智能体需要同时修改代码，我不会让它们直接操作同一个工作区，而会通过 `isolation: worktree` 为它们创建`独立 Git 工作树`。每个子智能体在自己的代码副本中修改、测试并形成独立差异，最后由主智能体审查和合并。

> 这样可以避免并行写入同一文件、覆盖未提交修改和测试环境相互污染。工作树解决的是文件隔离问题，但不能自动解决架构冲突，因此并行前仍然要明确模块边界、接口契约和最终合并顺序。

我也不会为了展示多智能体能力而过度拆分。

- 修改一个已知函数、修复定位明确的错误，或者补充少量测试时，主智能体直接完成通常更快。
- 因为子智能体需要重新建立上下文，启动和汇总也会产生额外延迟与 Token 成本。

总结来说，我使用子智能体的方式是：

- 让主智能体承担需求理解、架构决策、任务协调和最终验收；
- 让内置子智能体自主完成代码探索和计划调查；
- 将高输出、独立、可并行的辅助任务隔离出去；
- 通过自定义子智能体建立开发、测试和审查之间的职责与权限边界；
- 只有在任务需要继承当前完整上下文时才使用分叉，需要并行写代码时再使用独立工作树。
```
子智能体的价值不在于“同时启动多少个 Agent”，而在于上下文隔离、专业分工、权限控制和并行效率是否真正提升了交付质量。
```

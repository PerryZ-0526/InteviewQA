# 什么情况下用进程，什么情况下用线程，什么情况下用协程？

## 题目

什么情况下用进程，什么情况下用线程，什么情况下用协程？

## 面试直接答

> 选型看三个变量：**负载类型**（CPU 密集还是 IO 密集）、**隔离与稳定性需求**、**并发规模**。CPU 密集或强隔离需求选进程；共享状态高频交互、中等并发选线程；海量网络 IO 选协程。Python 语境下 GIL 把 CPU 密集的答案唯一锁定为多进程，这道题在 Python 面试里实际上是"先判断负载类型，再对照语言约束"的两步决策。

先说什么时候用进程。第一类是 **CPU 密集**任务：在 CPython 里线程无法并行，多进程是唯一能榨干多核的手段，比如数据处理、图像渲染、模型推理预处理；在其他语言里，CPU 密集也可以选线程，进程更多是隔离诉求。第二类是**强隔离与稳定性需求**：一个组件崩溃不能拖垮其他组件——浏览器每个站点一个渲染进程、微服务按进程拆分、主程序拉起不可信插件，都是这个理由。第三类是**权限与资源边界**：需要独立的内存限额、独立的用户权限、或干脆跨语言跑子程序。选择进程的代价是启动慢、通信要序列化、内存占用大，所以频率低、数据量小的并行任务不适合频繁 fork。

再说什么时候用线程。核心判据是**共享同一份内存状态且需要并发**：线程间通信就是读写变量，比进程的 pickle 加管道便宜几个数量级，适合高频交互的共享数据结构——内存缓存、连接池、会话表。典型场景：IO 密集的中等并发（几十到几百连接，线程池足够）；GUI 程序主线程渲染加后台线程计算；C++/Go/Java 里的 CPU 并行（这些语言没有 GIL，线程就是并行单元）。Python 的线程要额外记一条：只对 IO 密集有效，`ThreadPoolExecutor` 配阻塞 IO 是够用的，但连接数上万后线程栈和内核调度开销会先到天花板。

然后说什么时候用协程。判据是**海量 IO 并发、连接数远大于 CPU 核数、业务以 IO 编排为主**：网络网关、爬虫、API 聚合服务、长连接推送、聊天服务。这类负载的共同点是绝大多数时间在等网络，协程把等待时间全部复用起来，单机万级乃至十万级连接。两个前提条件：生态里有所需的异步库（aiohttp、httpx、asyncpg），团队守得住"协程内不调阻塞函数"的纪律。

最后讲混合架构，这是工程里的常态。真实系统几乎都是分层的：**多进程提供多核与隔离，进程内协程提供吞吐**。Nginx 是 master 进程 fork 出多个 worker，每个 worker 内用 epoll 事件驱动处理海量连接；Gunicorn 的 prefork 模型同样可选 gevent 或 asyncio worker；Go 的 goroutine 用 M:N 调度把这两层在运行时内部做掉了。Python 里最实用的组合是：CPU 密集部分丢给大小约等于核数的 `ProcessPoolExecutor`，IO 编排交给单进程内的 asyncio，两者用 `run_in_executor` 衔接。反面案例也要记住：用线程跑 CPU 密集（Python 下反而更慢）、协程里调同步 IO（卡死整个循环）、CPU 密集负载开三倍于核数的进程（切换开销吃掉收益）。一句话口诀：**计算看 CPU 类型，隔离看容错要求，规模看连接数量**——CPU 密集且要隔离用进程，共享状态中等并发用线程，海量 IO 用协程，三者可以按层组合。

### 1. 选型决策树

                 │
        ┌────────▼─────────┐
        │ 负载是 CPU 密集吗？ │

            │            │
   ┌────────▼───────┐   ┌▼──────────────────┐

               ▼ 协程承担 IO 吞吐              └───┬────┘

### 2. 场景决策表

| 典型场景 | 选型 | 关键理由 |
|---------|------|---------|
| Python 数据清洗 / 模型推理 / 图像处理 | 多进程（ProcessPoolExecutor） | GIL 下线程无并行，进程数 ≈ 核数 |
| C++ 渲染引擎 / Go 服务内并行计算 | 多线程 | 无 GIL，共享内存通信最便宜 |
| 浏览器多标签页 | 多进程 | 渲染崩溃隔离 + 站点安全沙箱 |
| 内存缓存服务（共享大表 + 并发读写） | 多线程 + 读写锁 | 共享内存高频访问，IPC 序列化不可接受 |
| GUI 界面 + 后台耗时任务 | 主线程 + 工作线程 | UI 线程不阻塞，结果回投消息队列 |
| API 网关 / 爬虫 / 长连接推送 | 协程 + 异步 IO | 万级连接，线程栈与调度开销撑不住 |
| 既有大量同步阻塞库的老系统 | 线程池 | 生态没有异步版本，改造成本高于收益 |
| 单连接大文件传输 | 线程或进程 | 吞吐瓶颈在磁盘/带宽，异步切换收益低 |
| CPU 密集 + 高并发 IO 混合服务 | 多进程 + 进程内协程 | 进程吃多核、协程吃吞吐，分层组合 |

### 3. 面试追问

**追问 1：一个服务既有 CPU 密集阶段又有大量 IO 等待，怎么组合？**

这是最常被追问的混合场景。标准答案是**分层**：外层用多进程或进程池承担 CPU 密集阶段（大小约等于核数），内层用协程承担 IO 编排。Python 里的具体接法：asyncio 主循环负责全部 IO，遇到 CPU 密集子任务时 `await loop.run_in_executor(process_pool, cpu_func)` 提交给 `ProcessPoolExecutor`，IO 部分继续并发推进。反向结构也可行：multiprocessing 起多个进程，每个进程内跑一个小型 asyncio 循环。选哪种看哪个是主流量：IO 为主用前者，计算为主用后者。Go 生态下这个问题被 M:N 调度自动消解，goroutine 池天然两头兼顾，这也是很多人选 Go 写高并发服务的原因。

**追问 2：线程池和进程池的大小怎么定？**

CPU 密集任务：**等于物理核数**（`os.cpu_count()`），超配只会增加切换开销；有超线程时最多乘 2 并实测验证。IO 密集任务：可用 Brian Goetz 在《Java Concurrency in Practice》中给出的**线程数经验公式**——最优线程数 ≈ 核数 × (1 + 等待时间/计算时间)，等待占比越高，线程数可以越多。两个补充：其一，公式是起点不是终点，必须以压测数据为准；其二，Python 的线程池受 GIL 约束，公式里的"计算时间"应理解为持有 GIL 的执行时间，IO 等待比极高时线程数可以远超核数。协程场景不适用这个公式，因为协程数量由连接数决定而非计算资源。

**追问 3：什么情况下协程反而不如线程？举几个反例。**

三个典型反例。第一，**单连接大吞吐**：大文件下载、流式传输，瓶颈在带宽和磁盘，线程阻塞模型完全够用，协程的切换收益趋近于零，还引入调度开销；第二，**CPU 密集**：单线程协程没有并行能力，`await` 密集的纯计算反而因状态机切换变慢；第三，**生态不配合**：系统依赖大量同步 C 库又无法改造，asyncio 里要么频繁 `to_thread`（退化回线程池），要么承受卡死风险，此时不如直接上线程模型。另外 asyncio 单事件循环本身有吞吐上限——单核执行字节码的极限，真到了瓶颈需要多进程起多个独立 loop。

**追问 4：为什么浏览器选择多进程而不是多线程？它不嫌内存大吗？**

因为浏览器把**隔离与安全**放在内存开销之上。渲染引擎极其复杂，一个网页的恶意或错误代码导致渲染进程崩溃、内存写穿，如果所有标签页共享一个进程，整个浏览器随之崩溃；多进程把故障域限制在单个标签页。安全层面，现代 Chrome 的站点隔离（Site Isolation）把不同来源的页面放进不同进程，配合沙箱与操作系统权限约束，防止跨站数据窃取（Spectre 一类侧信道攻击的防御也依赖进程级隔离）。代价确实存在——Chrome 的内存占用常年被诟病，但这是"用内存买稳定性"的主动取舍。这也印证了选型的第一原则：先定需求优先级，再谈资源成本。

**追问 5：进程间通信这么贵，多进程架构里如何降低通信成本？**

三个层次。第一，**减少通信频率**：把数据分片，每个进程处理自己分片内的数据，只在收尾时合并（MapReduce 思路）；第二，**减少拷贝**：共享内存（`multiprocessing.shared_memory`）让多个进程直接映射同一块物理内存，大数据只传偏移量；避免不必要的 pickle——传 `memoryview` 或 mmap 文件；第三，**异步化通信**：用消息队列解耦生产与消费，通信延迟不再阻塞计算。Python 3.14 的 `concurrent.interpreters` 提供了折中选项：同一进程内多解释器，共享进程地址空间，channel 传对象，比多进程轻、比多线程隔离，适合通信频繁又需要 GIL 隔离的场景（细节与陷阱见 [002-Python中的进程线程协程](002-Python中的进程线程协程.md) 追问 5）。

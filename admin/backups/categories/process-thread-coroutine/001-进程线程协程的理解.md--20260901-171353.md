# 讲讲你对进程、线程、协程的理解

讲讲你对进程、线程、协程的理解？

## 面试直接答

> 进程是操作系统**资源分配**的基本单位，拥有独立的虚拟地址空间；线程是内核 **CPU 调度**的基本单位，共享进程的地址空间；协程是**用户态协作式调度**的执行单元，切换不经过内核。三者的本质差异集中在隔离性、调度权和切换成本三个维度：进程用隔离性换稳定性，线程用共享换通信效率，协程用协作调度换极致并发。

### 首先讲进程

进程是"运行中的程序"，操作系统为它分配<u style="text-decoration-color: #e63946">独立的虚拟地址空间、页表、文件描述符表、信号处理表等资源</u>，这些资源记录在内核的`进程控制块（PCB）`里。进程间彼此隔离，一个进程段错误或者内存写穿，不会污染其他进程，这是操作系统稳定性的基石；代价是进程间<u style="text-decoration-color: #e63946">通信必须走 IPC 管道、共享内存、信号等机制</u>，而且进程切换要切换页表、导致 TLB 失效和 CPU 缓存冷启动，成本在微秒到毫秒级。

> Linux 上创建进程用 fork 加 exec，fork 用`写时复制`优化——子进程先共享父进程的物理页，只有一方写入时才真正复制，所以 fork 本身很快。

### 其次讲线程

线程是`同一个进程内共享地址空间的执行流`，`内核调度的最小单位`，拥有<u style="text-decoration-color: #e63946">独立的栈、寄存器和程序计数器</u>，<u style="text-decoration-color: #e63946">共享堆、全局变量和文件描述符</u>。它解决的核心问题是：同一份数据要并发处理时，多线程直接读写共享内存，通信成本远低于进程间 IPC。线程切换不用换地址空间，只需要保存寄存器、切换栈，成本在微秒级，比进程快一到两个数量级。

但共享带来同步问题——数据竞争、死锁、锁开销，这是多线程编程复杂度的主要来源。

### 第三讲协程

协程是运行在`用户态`的、`由程序自己调度和切换的执行单元`，操作系统完全不知道它的存在。线程的切换要陷入内核、走系统调用、由内核调度器裁决，而协程的切换只是<u style="text-decoration-color: #e63946">保存几个寄存器和栈指针、跳转到另一个协程的代码，是**函数调用级别**的开销</u>，几十纳秒就完成，比线程切换快两个数量级左右。协程的栈也很小，可以按需增长，几 KB 起步，而线程栈默认 8MB，所以单机可以承载百万级协程而线程只能承载几千个。

代价是`协作式调度`：协程必须主动让出 CPU，任何一个协程执行阻塞操作而不让出，整个调度循环就卡住，所以协程必须和异步 IO、事件循环配合使用。

实现上协程大致分两类：

一类是`有栈协程`，每个协程拥有自己独立的栈空间，切换时交换栈指针，Go 的 goroutine 属于这一类，栈还会自动增长；

另一类是`无栈协程`，编译器把 `async` 函数编译成状态机，<u style="text-decoration-color: #e63946">局部变量存放在状态机对象里</u>而不是真实调用栈上，Python 的 asyncio、JavaScript 的 async/await 都是这一类，优点是不需要动态分配栈、切换更快，缺点是不能在普通函数调用链里隐式挂起，必须显式 await。

> 这里顺带区分一个概念：goroutine 严格说是 M:N 调度的用户态线程——由 Go 运行时在少量内核线程上抢占调度、栈自动增长，比纯协程更进一步，兼具了协程的低成本切换和内核线程的多核并行。

### 最后做三层定位总结

进程解决`"隔离与稳定"`：独立地址空间让故障互不传染，适合不同任务之间边界清晰的场景；线程解决`"共享与并发执行"`：同一份数据多个执行流，通信成本最低，适合中等并发与共享状态；协程解决`"海量并发下的调度开销"`：把调度权从内核收回用户态，适合连接数远超核数的 IO 密集服务。

> 面试中把它们串成一条演进主线来讲——资源隔离的需求诞生进程，通信与并发效率的需求诞生线程，高并发下内核调度成本成为瓶颈又催生协程——比孤立地背三个定义更能体现理解深度。


## 详细解析

### 1. 从内核视角看三者的层级关系

进程、线程、协程不是并列概念，而是嵌套的层次结构：进程包含线程，线程之上再叠加协程。
```text
┌─────────────────────────────── 操作系统（内核态）──────────────────────────────┐
│                                                                              │
│   ┌──────────────┐   ┌──────────────┐          ┌──────────────┐             │
│   │    进程 A     │   │    进程 B     │   ...    │    进程 C     │             │
│   │ 独立虚拟地址空间│   │ 独立虚拟地址空间│          │ 独立虚拟地址空间│             │
│   │ 页表/文件表/PCB │   │ 页表/文件表/PCB │          │ 页表/文件表/PCB │             │
│   └──────┬───────┘   └──────────────┘          └──────────────┘             │
│          │ 进程内共享：堆 / 全局数据 / 文件描述符 / 页表                          │
│   ┌──────┴───────────────────────────┐                                       │
│   │ 线程1（私有栈+寄存器） 线程2（私有栈+寄存器）│ ← 内核线程：CPU 调度的最小单位          │
│   │         pthread / clone 创建      │                                       │
│   └──────────────┬──────────────────┘                                       │
└──────────────────┼───────────────────────────────────────────────────────────┘
                   │
        ┌──────────▼──────────────┐
        │     用户态（进程内）        │
        │   ┌────┐ ┌────┐ ┌────┐  │
        │   │协程1│ │协程2│ │协程3│  │ ← 用户态调度，内核完全无感知
        │   └────┘ └────┘ └────┘  │
        │   事件循环 / 调度器（如 asyncio）│
        └─────────────────────────┘
```

### 2. 三要素对比表


| 维度       | 进程                     | 线程                             | 协程                            |
| -------- | ---------------------- | ------------------------------ | ----------------------------- |
| 资源分配单位   | 是（地址空间、文件句柄等）          | 否，共享进程资源                       | 否                             |
| CPU 调度单位 | 是                      | 是（内核抢占式）                       | 否（用户态协作式）                     |
| 地址空间     | 独立，页表隔离                | 共享                             | 共享（且通常在单线程内）                  |
| 通信方式     | IPC：管道 / 信号 / 共享内存     | 共享内存 + 锁                       | 共享内存，单线程内无需锁                  |
| 切换成本     | 高（µs\~ms，TLB 失效、缓存冷启动） | 中（约 1\~10µs）                   | 低（几十 ns，函数调用级）                |
| 默认栈大小    | —（虚拟内存）                | Linux 默认 8MB                   | 可小至几 KB，或按需增长                 |
| 崩溃影响范围   | 仅自身进程                  | 整个进程                           | 整个进程                          |
| 调度器      | 内核抢占式                  | 内核抢占式                          | 用户态协作式（goroutine 为运行时抢占式）     |
| 典型创建接口   | `fork()` / `exec()`    | `pthread_create()` / `clone()` | `async def` + 事件循环 / `go` 关键字 |


### 3. 面试追问

**追问 1：协程切换比线程切换快，具体快在哪几个环节？**

线程切换必须经过内核：触发系统调用 → 陷入内核态（特权级切换）→ 内核调度器选下一个线程 → 保存/恢复寄存器与浮点上下文 → 返回用户态，全程约 1\~10 微秒，且跨核迁移还带来缓存失效。协程切换是用户态函数调用：只保存少量寄存器（调用者保存寄存器）和栈指针，跳到另一个协程继续执行，几十纳秒量级。更关键的差异是**可预测性**：协程在用户代码里显式让出（`await` 点），切换时机由程序决定；线程切换随时可能发生在任意指令之间，导致锁竞争模式无法预判。另一点是**栈的局部性**：协程栈小且常驻缓存，线程栈 8MB、访问跨度大。

**追问 2：既然线程共享地址空间，为什么还需要锁？CPU 不是按指令执行的吗？**

因为共享变量的"读-改-写"不是一条指令。以 `count++` 为例，编译后是三条指令：从内存加载到寄存器、寄存器加一、写回内存。线程 A 加载后还没来得及写回，内核调度切到线程 B，B 完成加一写回，再切回 A 时 A 用旧值写回，B 的更新被覆盖——这就是**数据竞争**。此外还有**内存可见性**问题：多核下每个核有自己的缓存，A 核写的数据不一定立刻对 B 核可见，需要内存屏障或锁保证 happens-before 关系。Python 的 GIL 是个经典反例：GIL 让字节码层面的操作原子化，但 `count += 1` 是四条字节码（LOAD、ADD、STORE），线程可以在其间被切换，所以 CPython 中自增仍需要锁。相关内容可参考 [002-Python中的进程线程协程](002-Python%E4%B8%AD%E7%9A%84%E8%BF%9B%E7%A8%8B%E7%BA%BF%E7%A8%8B%E5%8D%8F%E7%A8%8B.md)。

**追问 3：内核级线程和用户级线程（协程的祖先）的映射模型有哪些？协程属于哪一种？**

三种映射模型：**1:1**——每个用户线程对应一个内核线程，pthread 即如此，并发度受内核线程数限制，但单个线程阻塞不影响其他线程；**1:N**——多个用户线程复用一个内核线程，早期 Java 绿色线程即如此，优点是切换快，缺点是一个线程阻塞全部阻塞、且无法利用多核；**M:N**——Go 的 GMP 模型和 Java 虚拟线程（JEP 444）即如此，运行时把大量 goroutine 复用到少量内核线程上，goroutine 阻塞时运行时把它挪走、换另一个可运行的上去，兼顾了切换成本与多核利用。纯协程属于 1:N 的现代版本——事件循环驱动，阻塞点必须异步化；goroutine 和虚拟线程则是 M:N 的演进形态。

**追问 4：fork 创建进程不是很慢吗？为什么还能很快？**

fork 慢在传统认知里是指"复制整个进程内存"，但 Linux 用\*\*写时复制（COW）\*\*优化：fork 时只复制页表，父子的页表都指向同一批物理页并标记为只读，任何一方写入时触发缺页中断，内核才复制该页。因此 fork 的开销主要是复制页表（几毫秒内），与进程内存大小基本无关。真正昂贵的是后续的进程切换（TLB 冲刷、缓存冷启动）以及 exec 加载新程序映像。这解释了为什么 Nginx 用"master fork 多个 worker"的模式启动代价很低。与内存/地址空间相关的底层细节可参考 [002-从OS底层到语言层的内存管理全景](../os/002-%E4%BB%8EOS%E5%BA%95%E5%B1%82%E5%88%B0%E8%AF%AD%E8%A8%80%E5%B1%82%E7%9A%84%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86%E5%85%A8%E6%99%AF.md)。

### 4. 一个统一的记忆框架

面试时可用"三个问题"来组织答案：**谁拥有资源？**（进程）；**谁被内核调度？**（线程）；**谁被用户自己调度？**（协程）。再沿"隔离性递减、切换成本递减、并发规模递增"的轴线定位三者，任何追问都能落回这个框架。

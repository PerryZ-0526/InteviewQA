# HTTP/2 的多路复用是怎么解决 HTTP/1.1 的队头阻塞问题的？

## 题目

HTTP/2 的多路复用是怎么解决 HTTP/1.1 的队头阻塞问题的？请对比 HTTP/1.0、HTTP/1.1（含 pipelining 与多连接两种折中方案）与 HTTP/2 的并发模型，并说明 HTTP/2 还遗留了哪些层面的队头阻塞、HTTP/3 又是如何进一步解决的。

## 面试直接答

> HTTP/2 用二进制分帧与流多路复用，把 HTTP/1.1 连接级「请求串行排队」改造为流级「并行交错传输」，在应用层消除了队头阻塞；但 TCP 的有序字节流交付仍保留传输层队头阻塞，只有 HTTP/3 基于 QUIC 的流级独立重传才能彻底根治。

首先说 HTTP/1.1 的队头阻塞是怎么产生的。HTTP/1.0 时代一个连接同一时刻只能承载一个请求，响应返回之前不能发出下一个请求；HTTP/1.1 引入持久连接省掉了反复建连的握手开销，但请求在一个连接上依然串行排队，前一个响应不回来，后一个请求就得等着，这就是队头阻塞。后来 HTTP/1.1 又定义了 pipelining，允许客户端不等响应连续发出多个请求，但规范要求服务器必须按请求顺序返回响应，所以只要队首那个响应慢——比如后端处理慢或者响应体大——后面已经算好的响应也发不出去，阻塞依旧存在；再加上早期代理服务器对 pipelining 支持参差不齐、容易把响应顺序搞乱，主流浏览器基本都禁用了它。工程上的折中是开多条连接：早期规范建议每域名两条连接，后来浏览器普遍默认对同一域名开 6 条 TCP 连接，再配合域名分片把资源分散到多个域名下，用连接数换并行度。但每条连接内部仍然存在队头阻塞，而且多连接带来成倍的握手、TLS 和慢启动开销，连接之间无法共享拥塞状态，整体效率不高。

其次说 HTTP/2 的核心解法。HTTP/2 在单个 TCP 连接上引入了流的概念：每个请求-响应对是一条流，流之间逻辑独立；所有数据——头部和正文——都被切成二进制帧，帧头里带着 31 位的流 ID，不同流的帧可以在连接上任意交错发送，接收端按流 ID 把帧重新组装回各自的消息。响应因此可以乱序返回：一条流上的大文件传输慢，完全不影响其他流上的小请求先完成。HTTP/1.1 需要六条连接才能拿到的并行度，HTTP/2 一条连接就实现了，而且连接复用还带来额外收益：TCP 慢启动只需要爬升一次，TLS 握手只需要做一次，HPACK 头部压缩的动态表是连接级共享的，头部越压越小。

第三说多路复用配套的三个机制。一是流量控制：多流并发意味着一条流可能把整条连接的窗口占满，所以 HTTP/2 在流级和连接级各有一套基于 WINDOW_UPDATE 帧的滑动窗口，接收方按窗口发放额度，保证单条流不能饿死其他流；二是优先级：RFC 7540 设计了基于依赖树和权重的优先级方案，让阻塞渲染的 CSS、JS 先发，后来因为实现复杂、各浏览器行为不一致，RFC 9218 把它简化成 urgency 加 incremental 的可扩展优先级；三是取消与重置：RST_STREAM 帧可以随时终止一条流而不影响连接，比 HTTP/1.1 只能粗暴断开连接精细得多。

第四说边界条件——HTTP/2 并没有把队头阻塞彻底消灭。多路复用解决的是应用层的队头阻塞，但 HTTP/2 跑在 TCP 之上，TCP 对应用层暴露的是严格有序的字节流：只要一个 TCP 段在传输中丢失，接收方内核缓冲区就必须等它重传，后续所有段无论属于哪条流都无法向上交付，所有流一起卡住，这是传输层的队头阻塞。在丢包率高的弱网环境下，HTTP/2 单连接可能比 HTTP/1.1 的多连接表现更差，因为六条连接里丢包只拖累一条，单连接一次丢包拖累全部。此外还有实现层面的坑：大帧会延迟同连接上 RST_STREAM、WINDOW_UPDATE 这类控制帧的发送，所以实际实现会限制帧大小并给控制帧优先调度。

第五说彻底解决的方向与实践建议。HTTP/3 把传输层换成基于 UDP 的 QUIC，可靠传输从连接级下沉到流级：每个 QUIC 流独立编号、独立做丢包检测与重传，一条流丢包只阻塞这一条流，传输层队头阻塞随之消除；头部压缩也换成 QPACK，规避了 HPACK 动态表在乱序场景下的队头依赖。实践上，对大多数站点 HTTP/2 通过 TLS 的 ALPN 协商默认启用即可，收益主要来自连接复用和头部压缩；域名分片、雪碧图、文件合并这些为规避 HTTP/1.1 连接限制而生的优化在 HTTP/2 下大多成为反模式，应该移除；弱网或高丢包场景优先评估 HTTP/3。

## 详细解析

> 版本核验：RFC 9113（HTTP/2）、RFC 9112（HTTP/1.1）、RFC 9114（HTTP/3）、RFC 9000（QUIC），2026-08-16 查证。

### 一、HTTP/1.1 的队头阻塞是怎么产生的

**HTTP/1.0 时代**：一条连接同一时刻只能有一个未完成的请求，响应返回前不能发下一个请求。每个资源都要经历建连、请求、响应、断开，页面有几十个资源就要几十次握手。

**HTTP/1.1 持久连接**：连接可以复用，但请求仍然串行排队——这是最纯粹的队头阻塞（Head-of-Line Blocking，HOL）：队首请求的响应不回来，后面所有请求都发不出去。
```
HTTP/1.1 持久连接（串行，无流水线）：
连接 ──[req1]──────等待──────[resp1]──[req2]──────等待──────[resp2]──►
            ↑ 响应回来前 req2 不能发出 → 队头阻塞
```

**HTTP/1.1 Pipelining**：允许客户端不等响应连续发出多个请求，但 RFC 9112 §9.3.2 要求服务器必须按请求顺序返回响应，且响应之间不能交错。队首响应慢，后续响应全部被堵在队里：
```
HTTP/1.1 Pipelining（响应必须按序）：
连接 ──[req1][req2][req3]───────────────────────────────────────────►
      ◄──────[resp1（慢，处理 3s）][resp2][resp3 早已算好但发不出去]
                    ↑ 队首响应慢 → 后续响应全部阻塞
```

pipelining 在实践中失败了：早期代理和服务器实现 bug 多（响应顺序错乱、挂死连接），浏览器纷纷禁用（Chrome 从未默认启用，Firefox 默认关闭，Opera 曾启用后放弃）。所以 HTTP/1.1 时代的真实解法是**多连接**：浏览器对同一域名默认开 6 条 TCP 连接，配合域名分片（domain sharding）换取并行度。但这只是把阻塞分摊到 6 条队列里，每条队列内部队头阻塞依旧，且多连接各自独立握手、独立慢启动，无法共享拥塞状态。

### 二、HTTP/2 多路复用的核心机制

**二进制分帧层**：HTTP/2 在应用层（HTTP 语义）与传输层（TCP）之间插入分帧层，所有消息被切成帧，帧是最小传输单元。帧头固定 9 字节（RFC 9113 §4.1）：
```
HTTP/2 帧头（9 字节）：
+-------------------------------+
|        Length (24 位)          |
+---------------+---------------+
|   Type (8)    |   Flags (8)   |
+-+-------------+---------------+
|R|     Stream Identifier (31)  |
+-------------------------------+
```

- **Length**：帧负载长度，上限由 SETTINGS\_MAX\_FRAME\_SIZE 决定（默认 16384，可协商到 2^24-1）
- **Stream Identifier**：31 位无符号整数，标识帧属于哪条流；0 号流保留给连接级控制帧（SETTINGS、PING、GOAWAY）

**流（Stream）**：一个请求-响应对应一条流。客户端发起的流 ID 为奇数（1、3、5…），服务端发起的流为偶数（2、4、6…，用于服务端推送）；流 ID 必须单调递增，用尽后必须新建连接（RFC 9113 §5.1.1）。不同流的帧可以在连接上任意交错：
```
单连接上的帧交错（响应可乱序）：
流1: [HEADERS][DATA][DATA]──────────────[DATA]   ← 大文件，慢慢传
流3:      [HEADERS][DATA]                        ← 小请求，先完成
流5:           [HEADERS]────[DATA][DATA]         ← 互不阻塞
时间轴 ──────────────────────────────────────►
接收端按 Stream ID 重组，各流独立完成
```

**主要帧类型**：


| 帧类型                         | 作用                         |
| --------------------------- | -------------------------- |
| HEADERS                     | 携带头部块（HPACK 压缩后）           |
| DATA                        | 携带请求/响应正文                  |
| WINDOW\_UPDATE              | 流量控制窗口更新                   |
| RST\_STREAM                 | 立即终止一条流                    |
| SETTINGS                    | 连接级参数协商（连接建立时交换）           |
| PING                        | 连接保活与 RTT 测量               |
| GOAWAY                      | 优雅关闭：不再接受新流，已建立的流继续完成      |
| PUSH\_PROMISE               | 服务端推送预告（Chrome 106 起已移除支持） |
| PRIORITY / PRIORITY\_UPDATE | 优先级声明                      |


**双层流量控制**（RFC 9113 §5.2）：HTTP/1.1 只依赖 TCP 一层流控，多流复用后必须防止单流占满连接窗口。HTTP/2 在连接级和流级各维护一个滑动窗口（初始 65535 字节，可用 SETTINGS\_INITIAL\_WINDOW\_SIZE 调整），接收方通过 WINDOW\_UPDATE 帧发放额度；一条流的窗口耗尽只阻塞该流，不影响其他流。

**HPACK 头部压缩**（RFC 7541）：静态表（61 个高频头）+ 动态表 + 哈夫曼编码。动态表在连接级共享，请求头中重复的字段（如 Cookie、User-Agent）只传索引号。这是 HTTP/1.1 没有的：HTTP/1.1 每个请求都要重复传输完整头部文本，头部冗长还会快速填满初始拥塞窗口，加剧延迟。

**优先级机制**：RFC 7540 §5.3 定义依赖树 + 权重（0-256）的优先级模型，服务器据此调度帧发送顺序。实践中该模型实现复杂，各浏览器生成的依赖树不一致，服务器支持参差不齐，优先级几乎没生效；RFC 9218 将其简化为 urgency（0-7，默认 3）+ incremental 标志，通过 PRIORITY\_UPDATE 帧或 HEADERS 帧携带。

### 三、四代并发模型对比


| 维度      | HTTP/1.0     | HTTP/1.1 持久连接 | HTTP/1.1 多连接（浏览器实践） | HTTP/2         | HTTP/3      |
| ------- | ------------ | ------------- | ------------------- | -------------- | ----------- |
| 并发模型    | 一请求一连接       | 一连接串行排队       | 每域名约 6 连接并行         | 单连接多流交错        | 单连接多流交错     |
| 响应顺序    | —            | 严格按请求顺序       | 连接内按序，连接间并行         | 流内有序，流间乱序      | 流内有序，流间乱序   |
| 应用层队头阻塞 | 有            | 有（最严重）        | 有（分摊到每条连接）          | 无              | 无           |
| 传输层队头阻塞 | 有（每连接独立，影响小） | 有             | 有（丢包只拖累一条连接）        | **有（丢包拖累所有流）** | 无           |
| 头部压缩    | 无            | 无             | 无                   | HPACK（连接级动态表）  | QPACK       |
| 传输层     | TCP          | TCP           | TCP                 | TCP            | QUIC（UDP）   |
| 流控      | 仅 TCP        | 仅 TCP         | 仅 TCP               | TCP + 流级/连接级双层 | QUIC 流级/连接级 |
| 握手      | 每请求建连        | 1 次/连接        | 6×                  | 1×（ALPN 协商 h2） | 1-RTT/0-RTT |


### 四、HTTP/2 遗留的队头阻塞：TCP 层

TCP 保证字节流严格有序交付：接收方内核按序号重组，只有连续的数据才能向上交付给应用。一个段丢失，后续所有段——无论属于哪条 HTTP/2 流——都滞留在接收缓冲区等待重传：
```
HTTP/2 上的 TCP 丢包（所有流一起卡）：
流1: [DATA][DATA][DATA]...
流3:      [DATA]          ← 已经到达，但 TCP 不交付
流5:           [DATA]
TCP 段:  ──[S1]──[S2]──✗丢失──[S4][S5][S6]──►
                        ↑ S2 未重传前，S4/S5/S6 全部滞留内核缓冲区
```

在约 1% 丢包率的弱网下，HTTP/2 单连接上大量并发流的表现可能劣于 HTTP/1.1 的 6 条连接：多连接场景一次丢包只阻塞一条连接的队列，单连接场景一次丢包阻塞全部。这也是 Google 在部署数据中报告的 QUIC 收益来源之一——HTTP/3 把最差那部分用户的体验明显抬升。

另一个实现细节（RFC 9113 §4.2）：过大的帧会延迟同连接上 RST\_STREAM、WINDOW\_UPDATE、PING 等控制帧的处理，因此发送方应限制 DATA 帧大小，让控制帧有机会插入。

### 五、HTTP/3 与 QUIC：彻底消除队头阻塞

HTTP/3（RFC 9114）把传输层换成基于 UDP 的 **QUIC**（RFC 9000）。关键差异是把可靠传输从「连接级有序字节流」改为「流级有序 + 流间独立」：
```
QUIC 丢包（只阻塞所属流）：
QUIC 包: ──[pkt1:流1][pkt2:流3]──✗丢失[pkt3:流1]──[pkt4:流5]──►
                                   ↑ 只影响流1的重组，流3、流5 正常交付
```

- **流级独立恢复**：每个 QUIC 流独立编号（流 ID 最低两位编码方向与发起方），独立做丢包检测与重传，一条流丢包只阻塞该流
- **QPACK（RFC 9204）**：HPACK 的动态表更新必须按序处理，HTTP/2 丢包重传时头部解码也会被连带阻塞；QPACK 把动态表更新放在单向控制流上，并用阻塞上限防止头部解码拖垮整个连接
- **0-RTT 与连接迁移**：QUIC 握手与 TLS 1.3 合并为 1-RTT，恢复连接可 0-RTT；连接用 Connection ID 标识而非四元组，Wi-Fi 切蜂窝网络不断连
- **代价**：QUIC 在用户态实现，CPU 开销高于内核态 TCP，在低丢包高带宽网络下性能可能不如 HTTP/2

### 六、面试追问

**追问一：HTTP/1.1 的 pipelining 不也能在一个连接上并发发请求吗？为什么说它没解决队头阻塞，浏览器为什么不用它？**

pipelining 只解决了「发送」的并发，没解决「响应」的并发：RFC 9112 要求响应严格按请求顺序返回，队首响应慢，后续响应全部卡住，这是队头阻塞的另一种形态。它失败的工程原因有三：一是早期代理和服务器实现 bug 多，响应顺序错乱或连接挂死；二是客户端无法在连接中途取消一个大响应（只能断开连接，代价是已发送的请求全部作废）；三是慢响应不可预测，队头阻塞带来的延迟抖动比串行更不可控。因此浏览器选择多连接而非 pipelining。

**追问二：HTTP/2 是不是完全消除了队头阻塞？**

没有。HTTP/2 只消除了应用层（HTTP 消息级）的队头阻塞，传输层队头阻塞依然存在：TCP 有序交付语义决定了一个段丢失会阻塞所有流的交付。在丢包率高的网络（移动网络、跨国链路）下，HTTP/2 单连接可能比 HTTP/1.1 多连接更差。彻底解决需要 HTTP/3：QUIC 把可靠传输下沉到流级，丢包只阻塞所属流。答题时主动点出这层边界，是区分「会用」和「真懂」的关键。

**追问三：HTTP/2 为什么需要自己的流量控制？HTTP/1.1 为什么没有？**

HTTP/1.1 每条连接只承载一个请求-响应对，TCP 的流控就够了。HTTP/2 单连接上成百上千条流共享一个 TCP 窗口，若只有 TCP 一层流控，一条大文件下载流就能占满窗口，其他流的帧发不出去，等效于新的队头阻塞。所以 RFC 9113 设计了流级窗口（防止单流饿死其他流）加连接级窗口（防止流之和撑爆连接）的双层流控，窗口额度通过 WINDOW\_UPDATE 帧发放；一条流窗口耗尽，只阻塞该流。

**追问四：HPACK 动态表会不会引入新的队头阻塞？QPACK 怎么解决的？**

会。HPACK 编码依赖动态表的当前状态，而动态表随头部按序更新：接收方解码流 N 的头部块之前，必须已处理完所有更新动态表的头部块。HTTP/2 丢包重传导致头部块乱序到达时，后续头部解码全部等待，形成头部层级的队头阻塞。QPACK 的对策是：把动态表更新放到专用的单向控制流（编码器流/解码器流）上传输，数据流上的头部块只引用已确认的表状态，并设置允许阻塞的流数量上限（SETTINGS\_QPACK\_BLOCKED\_STREAMS），超过上限编码器就停止使用会阻塞的表项，保证阻塞可控。

**追问五：HTTP/2 下还需要域名分片、雪碧图、文件合并这些优化吗？**

不需要，而且大多变成反模式。域名分片会拆散连接：每个新域名都要重新 TCP 握手、TLS 握手、慢启动爬坡，还损失 HPACK 动态表共享，头部压缩率下降；雪碧图和小文件合并让缓存粒度变粗——改动一个图标就要让整张雪碧图失效重传，而 HTTP/2 下小文件的额外成本只剩每个流的帧开销，收益不再成立。正确姿势是单域名单连接、资源按模块拆分、利用缓存和优先级。这也解释了为什么很多站点迁移 HTTP/2 后要专门做一轮「去 HTTP/1.1 优化」的清理。

**追问六：既然一条连接就够，服务器为什么还要限制并发流数？**

通过 SETTINGS\_MAX\_CONCURRENT\_STREAMS 协商并发流上限。原因：一是服务器资源保护，每条流都要占用内存（缓冲、流状态、HPACK 上下文），恶意或失控客户端可以用海量流耗尽服务器内存；二是公平性，防止单一客户端占满带宽饿死其他客户端；三是调度可控性，流数过多时优先级调度退化为不可控竞争。客户端超过上限会被服务器以 REFUSED\_STREAM 错误拒绝新流，客户端应排队重试而非断开连接。

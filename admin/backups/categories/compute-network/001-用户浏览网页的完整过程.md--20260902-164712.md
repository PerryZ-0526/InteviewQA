## 面试直接答

> 用户从输入 URL 到看到完整页面，大体可以分成<u style="text-decoration-color: #e63946">网络通信</u>和<u style="text-decoration-color: #e63946">浏览器渲染</u>两个阶段，核心流程是 URL 解析、缓存检查、DNS 解析、建立连接、发送请求、服务器处理、页面渲染以及子资源加载。
>
> 当用户在浏览器输入 URL 并回车后，浏览器首先解析 URL，确定<u style="text-decoration-color: #e63946">协议、域名和端口</u>，同时检查<u style="text-decoration-color: #e63946">本地强缓存</u>，如果缓存命中就直接使用，否则开始网络请求。接着浏览器进行 <u style="text-decoration-color: #e63946">DNS 解析</u>，将域名转换成服务器 IP 地址。
>
> 拿到 IP 后，浏览器与服务器<u style="text-decoration-color: #e63946">建立连接</u>。如果是 HTTPS，一般<u style="text-decoration-color: #e63946">先建立 TCP 连接，再进行 TLS 握手</u>，完成<u style="text-decoration-color: #e63946">证书验证和密钥协商</u>，保证后续通信安全。连接建立后，浏览器<u style="text-decoration-color: #e63946">构造 HTTP 请求</u>，把请求行、请求头、Cookie 等信息发送给服务器。如果前面部署了 Nginx，请求可能先经过<u style="text-decoration-color: #e63946">反向代理和负载均衡</u>，再转发到具体的后端应用服务器。
>
> 后端服务器收到请求后，会执行相应业务逻辑，比如读取缓存、查询数据库、计算数据等，然后<u style="text-decoration-color: #e63946">返回 HTTP 响应</u>，其中包括状态码、响应头以及 HTML 等响应内容。
>
> 浏览器收到 HTML 后开始<u style="text-decoration-color: #e63946">解析并渲染页面</u>。首先解析 HTML <u style="text-decoration-color: #e63946">构建 DOM 树</u>，同时<u style="text-decoration-color: #e63946">解析 CSS 构建 CSSOM 树</u>，两者结合生成<u style="text-decoration-color: #e63946">渲染树</u>，然后经过 Layout 计算元素的位置和尺寸，再经过 Painting 和图层合成把页面显示到屏幕上。解析过程中如果遇到同步 JavaScript，可能会阻塞 DOM 构建。
>
> 与此同时，浏览器还会根据 HTML 中的 CSS、JS、图片等标签继续发起子资源请求，并结合强缓存、协商缓存以及 HTTP 长连接进行优化。等主要资源加载和渲染完成后，用户就可以看到并操作页面。现代 HTTP 通常不会在页面加载完后立即断开连接，而是通过 Keep-Alive 保留连接，以便后续请求继续复用。

从用户敲下回车键到页面完整呈现，浏览器经历了一个极为精密的多环节协作流程。若要用一段系统且专业的话来概括，整个过程可分为`网络通信`与`页面渲染`两大阶段，具体包含以下核心步骤：

### 第一，URL解析与资源定位

浏览器首先解析输入的URL，判断协议（HTTP/HTTPS）和域名，并检查`强缓存`（如本地磁盘缓存），若命中则直接加载，否则进入网络请求。

> 强缓存是浏览器缓存机制的一种，<u style="text-decoration-color: rgb(230, 57, 70)">当浏览器发现本地资源仍在有效期内时，会直接读取本地缓存，不向服务器发送请求</u>。
>
> 它通常由 `Cache-Control` 的 `max-age` 或 `Expires` 控制。强缓存失效后，浏览器才可能通过 ETag 或 Last-Modified 与服务器进行协商缓存。

紧接着进行`DNS域名解析`，依次查询浏览器缓存、操作系统 hosts 文件和本地DNS服务器，若未命中则通过根服务器进行递归/迭代查询，最终将域名解析为目标服务器的IP地址（同时附带端口号）。

### 第二，建立连接与数据加密协商

对于HTTPS协议，浏览器会与服务器建立TCP连接（三次握手），并在TCP之上进行 TLS/SSL 握手（以TLS 1.3为例，仅需1-RTT即可完成密钥协商和证书验证），确保后续数据传输的加密性与安全性。

> 若使用HTTP/2或HTTP/3，还会涉及多路复用或UDP+QUIC协议的优化协商。

### 第三，发送HTTP请求

浏览器`构建符合协议的请求报文`（包含请求行、请求头如Cookie、User-Agent等），通过已建立的连接发送至服务器。

若使用了Nginx等反向代理，请求会先经过代理层进行`负载均衡`，再转发至后端的应用服务器（如PHP-FPM或Java容器）。

> Nginx 可以把不同请求分配到不同服务器，例如第一个请求给 A，第二个给 B，第三个给 C，这就是负载均衡。<u style="text-decoration-color: rgb(230, 57, 70)">这样客户端只需要记住一个域名，后端却可以通过增加服务器来提高整个系统的处理能力。</u>
>
> 除此之外，Nginx 做反向代理时还可以承担 HTTPS 证书处理、静态资源服务、请求限流、缓存、压缩等工作，从而减少后端应用服务器的压力。

### 第四，服务器处理并返回响应

后端服务器执行业务逻辑（访问数据库、计算等），生成`响应内容（`通常是HTML文档），并附带`状态码`（如200、304、404）和`响应头`（包含缓存策略如Cache-Control）返回给浏览器。

### 第五，浏览器解析与渲染页面

这是最关键的一环：浏览器<u style="text-decoration-color: rgb(230, 57, 70)">自上而下解析接收到的HTML字节流，将其转换为 **DOM树**</u>；同时解析`外部CSS及内联样式`构建**CSSOM树**。两者结合生成`渲染树`（Render Tree），接着进行`布局`（Layout） 计算每个节点的几何位置，再通过`绘制`（Painting） 将像素绘制到屏幕上（包含图层合成与栅格化处理）。

> 需要注意的是，解析过程中若遇到`同步JavaScript脚本`，会阻塞 DOM树的构建（直到JS执行完毕），因此现代开发常使用`async`或`defer`属性来优化加载；而CSS加载虽不阻塞DOM解析，但会阻塞渲染树的生成。

### 第六，加载子资源与页面交互

主HTML解析完毕并非结束，浏览器会继续根据页面中的img、script、link等标签，<u style="text-decoration-color: rgb(230, 57, 70)">并行发起</u>数十个乃至上百个对图片、字体、视频<u style="text-decoration-color: rgb(230, 57, 70)">等静态资源的请求</u>（HTTP/1.1受限于6个并发连接，HTTP/2则通过多路复用解决队头阻塞），<u style="text-decoration-color: rgb(230, 57, 70)">直至所有资源加载完成触发</u>`onload`<u style="text-decoration-color: rgb(230, 57, 70)">事件，页面正式进入可交互状态</u>。

> 此外，整个流程中还穿插着`协商缓存`验证（通过 If-Modified-Since 或 ETag 校验资源是否更新）以及浏`览器事件循环机制`（Event Loop）的配合。这一系列步骤从用户输入到首屏展现，通常仅需数百毫秒，其中任何一个环节（如DNS解析过慢、TLS握手延迟、JS执行阻塞渲染）都会影响用户体验，这也是前端性能优化的核心发力点。


## 最后会释放tcp连接吗？什么时候释放

**不一定立即释放，默认情况下会保持一段时间（持久连接）。**

具体什么时候释放，取决于`HTTP协议版本`、`服务器配置`以及`双方的超时策略`。分几种情况详细拆解：

**1. 默认机制：保持连接（Keep-Alive）**

为了优化性能，现代浏览器和服务器<u style="text-decoration-color: rgb(230, 57, 70)">默认不会在页面加载完后立即关闭连接</u>。

- **为什么保持？** 因为一个页面往往包含数十个图片、CSS、JS文件。如果请求完HTML就断开，后续请求这些资源需要\*\*重新经历三次握手 + TLS握手（HTTPS）\*\*，耗时巨大。
- **释放时机（超时时间）**：连接会进入“空闲（Idle）”状态，等待后续请求。服务器端（如Nginx/Apache）通常会配置一个\*\*空闲超时时间\*\*（例如 `keepalive_timeout 65s`），如果该连接在\*\*65秒内\*\*没有新的请求，服务器会主动发起关闭。

> 浏览器端同样有自己的超时限制，通常以服务器配置为准。

**2. 主动释放的触发条件**

除了超时，以下情况会\*\*立即\*\*或\*\*主动\*\*释放TCP连接：

- **服务器主动要求关闭**：如果服务器响应头中包含 `Connection: close`，浏览器读到该字段后会立即关闭连接，不会复用。
- **达到最大请求数**：部分服务器为了负载均衡或防止内存泄漏，规定单个连接只能复用处理\*\*100-1000个请求\*\*，达到上限后会主动释放并新建连接。
- **浏览器标签页/窗口关闭**：用户直接关闭网页标签或浏览器，浏览器进程会终止，底层的TCP Socket会被操作系统回收，主动发送`FIN`包释放连接。
- **网络异常或超时**：网络中断、防火墙拦截或超过`timeout`设置而未收到数据，连接会被强制中断。

**3. 不同HTTP版本的差异（关键）**

- **HTTP/1.0**：默认是“短连接”，请求完后\*\*立即释放\*\*。除非手动设置 `Connection: keep-alive`。
- **HTTP/1.1（主流）**：\*\*默认长连接\*\*。释放时机完全由上述的`超时时间`或`最大请求数`决定。页面加载完通常不释放，保持待命。
- **HTTP/2 和 HTTP/3**：同样使用长连接，且因支持`多路复用`，单个连接极其高效，服务器往往会将超时时间设置得更长，以最大化复用效率。

> 多路复用可以理解为：在同一条网络连接上，同时传输多个 HTTP 请求和响应，而不需要每个请求都单独建立一条连接。
>
> 比如浏览器加载一个页面时，需要同时请求 HTML、CSS、JS、图片等资源，在 HTTP/1.1 中往往需要建立多个 TCP 连接，或者在同一连接中排队发送；
>
> 而 HTTP/2 会<u style="text-decoration-color: rgb(230, 57, 70)">把不同请求拆成多个“流”，让它们在</u>`同一个 TCP 连接中交错传输`，因此多个请求可以并发进行，大大减少建立连接的开销，提高连接利用率和页面加载效率。

**4. 释放的过程（四次挥手）**

无论是浏览器还是服务器主动关闭，都会走`四次挥手（FIN/ACK）`流程。通常是服务器端主动先发FIN包（因为服务器掌握空闲超时计时器），浏览器确认后关闭；如果用户关掉浏览器，则由浏览器主动发起FIN。

---

**总结一句面试标准话术：**

> “现在的浏览器访问完页面后，不会立即释放 TCP连接。<u style="text-decoration-color: rgb(230, 57, 70)">为了复用连接加载后续静态资源，连接会保持空闲状态，直到达到服务器预设的</u>`Keep-Alive超时时间`<u style="text-decoration-color: rgb(230, 57, 70)">（如60秒）或</u>`最大请求数上限`，才会由服务器主动触发四次挥手断开；若用户关闭标签页或发生网络异常，也会触发连接释放。”

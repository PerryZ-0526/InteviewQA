## 面试直接答

> 1）默认端口号；2）安全性；3）协议层；4）证书要求；5）应用场景、6）性能；7）SEO，优先收录

1）默认端口号
http：80；https：443

2）安全性
http：明文传输；
https：①通过（SSL/TLS协议）加密传输，防窃听/篡改；②身份验证（通过数字证书验证服务器身份，防止伪造网站）

3）协议层
1）HTTP 直接工作在`应用层`；
2）HTTPS 在 HTTP 和 TCP 之间添加了`TLS/SSL 加密层`，工作在传输层与应用层之间。

4）证书要求
HTTPS 必须配置 `SSL 证书`（由受信任的证书颁发机构 CA 签发），而 HTTP 不需要证书。

5）应用场景
HTTP：适用于不敏感信息的传输（如新闻网站、静态博客）
HTTPS，强制推荐场景：登录、支付、个人信息提交等敏感操作。

6）性能
https 稍慢，加密开销（已优化，TLS1.3、HTTP/2）

7）SEO搜索引擎优化
https优先收录

**摘要：**用户从输入 URL 到看到完整页面，大体可以分成网络通信和浏览器渲染两个阶段，核心流程是 URL 解析、缓存检查、DNS 解析、建立连接、发送请求、服务器处理、页面渲染以及子资源加载。

当用户在浏览器输入 URL 并回车后，浏览器首先解析 URL，确定协议、域名和端口，同时检查本地强缓存，如果缓存命中就直接使用，否则开始网络请求。接着浏览器进行 DNS 解析，将域名转换成服务器 IP 地址。

拿到 IP 后，浏览器与服务器建立连接。如果是 HTTPS，一般先建立 TCP 连接，再进行 TLS 握手，完成证书验证和密钥协商，保证后续通信安全。连接建立后，浏览器构造 HTTP 请求，把请求行、请求头、Cookie 等信息发送给服务器。如果前面部署了 Nginx，请求可能先经过反向代理和负载均衡，再转发到具体的后端应用服务器。

后端服务器收到请求后，会执行相应业务逻辑，比如读取缓存、查询数据库、计算数据等，然后返回 HTTP 响应，其中包括状态码、响应头以及 HTML 等响应内容。

浏览器收到 HTML 后开始解析并渲染页面。首先解析 HTML 构建 DOM 树，同时解析 CSS 构建 CSSOM 树，两者结合生成渲染树，然后经过 Layout 计算元素的位置和尺寸，再经过 Painting 和图层合成把页面显示到屏幕上。解析过程中如果遇到同步 JavaScript，可能会阻塞 DOM 构建。

与此同时，浏览器还会根据 HTML 中的 CSS、JS、图片等标签继续发起子资源请求，并结合强缓存、协商缓存以及 HTTP 长连接进行优化。等主要资源加载和渲染完成后，用户就可以看到并操作页面。现代 HTTP 通常不会在页面加载完后立即断开连接，而是通过 Keep-Alive 保留连接，以便后续请求继续复用。

## 详细解析

## 版本二：详细解析

**摘要：**HTTPS 并不是一种完全取代 HTTP 的新协议，而是在 HTTP 通信外增加 TLS 安全层。HTTP 解决“数据怎么传”，TLS 解决“数据怎么安全地传”，因此 HTTPS 能够提供机密性、完整性和身份认证。

### 一、先理解本质：HTTPS 到底是什么

HTTP 是应用层协议，它规定浏览器和服务器之间如何组织和交换数据，例如 GET、POST 请求，请求头、响应头、状态码，以及请求体和响应体等。

一个普通 HTTP 请求大致可以理解为：
```text
浏览器
   |
   | HTTP 请求
   v
服务器
```

问题在于，HTTP 本身并不负责加密。如果浏览器发送：
```text
POST /login

username=tom&password=123456
```

如果整个请求通过 HTTP 明文传输，那么从协议角度看，中间能够截获网络数据的人就有可能直接看到用户名和密码。

HTTPS 并没有改变 GET、POST、状态码这些 HTTP 规则，而是在 HTTP 和底层网络传输之间加入了 TLS。

可以粗略理解为：
```text
HTTP：

应用层       HTTP
              |
传输层       TCP
              |
网络层       IP
```

而 HTTPS：
```text
应用层       HTTP
              |
安全层       TLS
              |
传输层       TCP
              |
网络层       IP
```

所以平时常说：
```text
HTTPS = HTTP + TLS
```

这里过去经常使用 SSL 这个名称，所以很多资料会写成“SSL/TLS”，但现代 HTTPS 实际使用的是 TLS。

需要注意，如果是 HTTP/3，底层使用的是 QUIC，而 TLS 1.3 的握手机制被整合进 QUIC 中，但从面试理解上仍然可以认为 HTTPS 的安全能力来自 TLS。

### 二、HTTP 最大的问题：明文传输

如果只使用 HTTP：
```text
浏览器 ------------ HTTP ------------> 服务器
```

中间可能经过：
```text
浏览器
   |
路由器
   |
运营商网络
   |
代理服务器
   |
公网
   |
服务器
```

如果攻击者能够监听其中某一段通信，就可能看到 HTTP 请求中的数据。

例如：
```text
Cookie: session_id=xxxx
Authorization: Bearer xxxx
password=123456
```

因此 HTTP 面临的第一个问题就是“窃听”。

但仅仅防止别人“看到”还不够。

攻击者还可能把：
```text
服务器返回：

转账金额：100元
```

篡改成：
```text
转账金额：10000元
```

这就是数据完整性问题。

另外，还有第三个问题：浏览器如何确定自己连接的服务器真的是 `www.example.com`？

假设攻击者伪装成目标服务器：
```text
浏览器 ------> 攻击者 ------> 真服务器
```

浏览器以为自己在直接访问服务器，实际上攻击者处于通信中间，这就是典型的中间人攻击，也就是 MITM。

因此安全通信至少需要解决三个问题：
```text
数据不能被别人看懂
数据不能被偷偷修改
服务器不能被别人冒充
```

HTTPS 正是围绕这三个问题设计的。

### 三、HTTPS 提供的三个核心能力

HTTPS 的第一个能力是机密性，也就是 Confidentiality。

TLS 会对真正传输的 HTTP 内容进行加密。即使攻击者截获网络数据，看到的也是加密后的内容，而不是直接看到用户名、密码和 Cookie。

可以理解成：
```text
原始数据：

password=123456

        |
        | TLS 加密
        v

密文：

8A7F91B3C2...
```

服务器收到之后，再通过密钥解密。

因此网络中真正传输的是：
```text
浏览器 ---- 加密数据 ----> 服务器
```

而不是直接传输明文。

第二个能力是完整性，也就是 Integrity。

TLS 不仅加密数据，还会对数据进行完整性保护。如果攻击者在网络中修改了数据，例如把：
```text
money=100
```

修改成：
```text
money=10000
```

接收方可以发现数据已经发生改变，从而拒绝这段数据。

第三个能力是身份认证，也就是 Authentication。

浏览器访问：
```text
https://www.example.com
```

不能只是“服务器自己说自己是 example.com”，否则任何攻击者都可以这么说。

因此 HTTPS 引入了数字证书和 CA 体系。

### 四、数字证书是干什么的

当浏览器和 HTTPS 服务器建立连接时，服务器会发送自己的数字证书。

证书中通常包含服务器的域名、公钥、证书有效期、颁发机构等信息。

可以简单理解为：
```text
服务器：

“我是 www.example.com，这是我的证书。”

        |
        v

浏览器：

“这个证书是谁颁发的？”
“证书是否过期？”
“域名是否匹配？”
“签名是否合法？”
```

证书通常由受信任的 CA，也就是 Certificate Authority，证书颁发机构进行签发。

浏览器和操作系统中预置了一些可信的根 CA。

所以验证过程大致是：
```text
浏览器信任
   |
   v
根 CA
   |
   v
中间 CA
   |
   v
www.example.com 的证书
```

这就是所谓的证书链。

如果整条证书链都能够被验证，并且证书中的域名与用户正在访问的域名匹配，那么浏览器就认为：
```text
当前服务器身份可信
```

如果证书过期、自签名且不受信任，或者访问域名与证书不匹配，浏览器就会提示类似：
```text
您的连接不是私密连接
```

因此，HTTPS 中的证书主要解决的是“你到底是不是我要访问的那台服务器”这个问题。

### 五、HTTPS 为什么既有非对称加密，又有对称加密

这是 HTTPS 面试中非常经典的追问。

如果要给数据加密，一般会涉及两类加密方式：对称加密和非对称加密。

对称加密可以理解为：
```text
同一把密钥

客户端：
明文 + Key → 密文

服务器：
密文 + Key → 明文
```

它最大的优点是速度非常快，非常适合大量数据传输。

但是存在一个问题：
```text
这把 Key 怎么安全地告诉对方？
```

如果直接通过网络发送：
```text
客户端 ---- Key ----> 服务器
```

攻击者把 Key 截获以后，加密就失去意义了。

非对称加密则使用一对密钥：
```text
公钥
私钥
```

公钥可以公开，私钥由服务器自己保存。

它可以在身份认证和密钥协商中发挥作用，但非对称密码算法的计算成本通常比对称加密高，不适合直接拿来加密所有 Web 请求中的大量数据。

所以 TLS 的设计思路可以粗略理解成：
```text
握手阶段
        ↓
利用非对称密码体系、密钥交换等机制
完成身份认证和密钥协商
        ↓
得到共享的会话密钥
        ↓
后续通信
        ↓
使用高效的对称加密
```

也就是说：
```text
非对称体系：
解决身份认证和安全协商问题

对称加密：
解决大量数据高效加密问题
```

需要稍微严谨一点的是，现代 TLS 1.3 通常通过 ECDHE 等密钥交换机制协商共享密钥，而不是简单地“客户端生成一个对称密钥，再用服务器公钥加密发过去”。后者更接近早期 RSA 密钥交换的理解。

### 六、一次 HTTPS 连接大概经历什么

假设用户访问：
```text
https://www.example.com
```

浏览器先通过 DNS 得到服务器 IP，然后开始建立连接。

传统 HTTPS 场景可以简化为：
```text
浏览器                         服务器
   |                              |
   |-------- TCP 三次握手 ------->|
   |                              |
   |-------- TLS ClientHello ---->|
   |                              |
   |<------- ServerHello ---------|
   |<------- 数字证书 ------------|
   |                              |
   |      验证服务器证书           |
   |                              |
   |---- 完成密钥协商 ------------>|
   |                              |
   |====== TLS 安全连接建立 =======|
   |                              |
   |---- 加密的 HTTP 请求 -------->|
   |                              |
   |<--- 加密的 HTTP 响应 ---------|
```

其中 TLS 握手最核心的事情可以概括成两件：
```text
确认服务器身份
+
协商通信密钥
```

一旦 TLS 安全连接建立完成，后面的 HTTP 请求和响应都会受到 TLS 的保护。

因此浏览器实际执行的是：
```text
HTTP 请求
    ↓
TLS 加密
    ↓
网络传输
    ↓
TLS 解密
    ↓
服务器处理 HTTP 请求
```

响应方向反过来也一样。

### 七、HTTP 和 HTTPS 在端口和 URL 上的区别

HTTP 默认端口通常是：
```text
80
```

HTTPS 默认端口通常是：
```text
443
```

例如：
```text
http://example.com
```

通常等价于访问：
```text
http://example.com:80
```

而：
```text
https://example.com
```

通常等价于：
```text
https://example.com:443
```

不过端口并不是写死的，服务器也可以配置其他端口。

两者 URL 的协议头也不同：
```text
HTTP：

http://
```

HTTPS：
```text
https://
```

### 八、HTTPS 会不会比 HTTP 慢

从原理上看，HTTPS 确实比 HTTP 多了一些工作。

HTTP 可以粗略理解为：
```text
建立连接
    ↓
发送 HTTP 数据
```

HTTPS 还需要：
```text
建立连接
    ↓
TLS 握手
    ↓
证书验证
    ↓
密钥协商
    ↓
加密通信
```

所以 HTTPS 会产生额外的网络往返和 CPU 加解密开销。

但是现代网络环境下，这个差距已经非常小。

例如 TLS 1.3 简化了握手流程，能够减少建立安全连接所需的网络往返次数；HTTPS 连接还可以通过 Keep-Alive 进行复用，并不是每一个 HTTP 请求都重新 TLS 握手一次。

另外，现代 CPU 对加密算法的处理性能也已经很高。

同时 HTTP/2 提供多路复用、Header 压缩等机制，在主流浏览器环境中通常与 HTTPS 配合使用，因此实际网页访问时，HTTPS 并不能简单理解成“HTTP 加密以后一定明显更慢”。

### 九、HTTP 和 HTTPS 的核心区别怎么记

最终可以把整个知识点压缩成下面这张图：
```text
HTTP

浏览器
   |
   | 明文 HTTP
   v
服务器

风险：
窃听
篡改
冒充
```

而 HTTPS：
```text
HTTPS

浏览器
   |
   |  TLS
   |  ├── 加密
   |  ├── 完整性保护
   |  └── 证书认证
   |
   | 加密后的 HTTP
   v
服务器
```

所以 HTTP 和 HTTPS 最本质的差异并不是端口 80 和 443，而是 HTTPS 增加了 TLS。

HTTP 主要回答：
```text
浏览器和服务器
“按照什么格式交换 Web 数据？”
```

TLS 主要回答：
```text
“怎么保证这些数据
安全地传给正确的服务器？”
```

最后在面试中，可以把整个逻辑收束为一句话：HTTP 本身是明文传输协议，无法解决窃听、篡改和身份冒充的问题；HTTPS 则是在 HTTP 基础上加入 TLS，通过数字证书完成服务器身份认证，通过密钥协商建立会话密钥，再通过对称加密和完整性保护机制保障后续 HTTP 通信，因此能够提供机密性、完整性和身份认证。HTTP 默认使用 80 端口，HTTPS 默认使用 443 端口，而现代 Web 场景基本都应优先使用 HTTPS。

## 面试直接答

> 我对 AI 大模型的理解可以概括为一句话：<span style="background-color: #fff3cd">大模型是能力原材料，工程系统才是产品——模型决定了能力上限，知识接入、记忆与成本工程决定了这套能力在生产环境中实际可用的程度</span>。这句话来自我在三个 AI 项目里的切身经验：同一个模型，被不同系统包裹之后，效果和成本可以差出一个数量级。

首先说我对模型本身的认知。大模型的本质是概率性的知识压缩器：它在海量语料上做 next-token prediction 训练，把世界知识压缩进参数，推理时按条件概率逐 token 生成。Scaling Law 揭示了数据、参数和算力的规模增长会带来可预测的能力提升，甚至涌现出推理能力；但它有三个固有局限决定了模型不能裸用——幻觉，生成的是概率最高而非事实正确的序列；上下文窗口有限，单次对话装不下长期积累的知识；知识有时效，参数冻结在训练截止点，无法感知新信息。所以我的基本判断是：模型是原材料，不是产品，任何严肃的生产系统都必须围绕它构建工程外壳。

在这个认知上，我把工程系统拆成三条线。知识接入线解决「模型不知道什么」的问题：传统 RAG 在查询时临时检索片段、现场拼装答案，能用但没有积累；GraphRAG 引入实体和关系做结构化检索；我目前最认同的是 Karpathy 提出的 LLM Wiki 模式——摄取新来源时就把知识编译进持久化页面，交叉引用和矛盾标注一次性就位，查询变成对已积累综合的读取，知识随使用产生复利。执行线解决「模型怎么干活」的问题：确定性流程用 Workflow，开放任务才用 Agent，判断标准是控制流图能否在模型运行前画出来；生产上我更倾向渐进式混合架构，让两者的边界随需求演进。保障线决定系统能不能长期活着：上下文压缩控制 token 成本，记忆分层区分短期上下文、长期画像与共享记忆，模型分级路由和 prompt 缓存压降成本，最后用评测闭环验证效果，而不是靠感觉调 prompt。

这三条线的判断全部来自我的项目实践。第一个项目 TJ-Edu-Agent 是教育场景的智能问答系统，我用 LangGraph 构建两层编排图，RAG 负责知识接入，用户画像模块维护长短期记忆，再用 Ragas 构建端到端评测系统，让每次改动都能量化验证效果。第二个项目 anna-Inbox 是邮箱智能助手，最有价值的决策是把原来固定六阶段的 Workflow 升级成统一的 ReAct Agent Loop：不做简单/复杂查询的分流，因为简单查询在 Agent Loop 里天然一轮收敛，多维护一条路径只省几百 token 却带来双倍维护成本；同时把语义展开的 few-shot 教学材料只放在第一轮系统提示词里，第一轮结束就移除，六轮复杂查询能省约 40% 的上下文 token。第三个项目就是这个面试知识库本身：它由 Claude Code 配合 CLAUDE.md 规范和 interview-qa skill 维护，本质上就是 LLM Wiki 模式的最小落地——Agent 按 schema 编译内容、维护索引和交叉引用，我负责审核与修正，两百多道题目的知识体系因此能持续积累而不是每次重新检索。

我现在最感兴趣的技术方向有三个。多智能体系统的共享记忆与防爆策略——多个 agent 如何共享一份记忆而不互相污染、记忆膨胀时按什么规则修剪；MCP 协议的无状态化演进——工具生态从有状态服务走向无状态注册对 agent 架构的影响；以及上下文工程——如何把有限的上下文窗口当成稀缺资源来规划。总结来说，我的理解是：大模型的革命性在于把「理解与生成」商品化，工程价值随之迁移到知识、记忆、成本与评测这些系统能力上；对模型原理有敬畏、对工程杠杆有判断、对成本和效果有量化习惯，才是一个合格的 AI 应用工程师。

## 详细解析

> 版本核验：2026-08-16 依据仓库内已完成查证的题目（llm-wiki/001 核验过 Karpathy gist 原文、agent/008 核验过 Ng 的 HumanEval 数据）与 project/ 下项目文档撰写；外部引用沿用题库中已验证的出处。

### 一、认知主线：模型是什么、能力从哪来、局限在哪

**大语言模型**的本质是**概率性知识压缩器**：以 **next-token prediction** 为目标在海量语料上训练，知识被压缩进参数权重，推理时按条件概率逐 token 生成序列。这条认知决定了后面所有的工程判断——模型的输出是「概率最高的续写」而非「事实正确的答案」，幻觉不是 bug，而是这个范式的固有属性。

能力来源上有两条主线。一是 **Scaling Law**：Kaplan 等人在 2020 年的论文中系统量化了模型性能随参数量、数据量和算力规模幂律提升的规律，这也是「大力出奇迹」的理论基础，且后续观察到规模增大后推理、代码等能力**涌现**。二是**推理侧的放大**：思维链、RL 训练与 test-time compute 让模型在推理时投入更多计算换取更高质量的输出，这和工作流设计是同一哲学——用更多 token 换成功率，区别只是发生在训练后还是推理时。

三个固有局限及其工程含义：

| 局限 | 成因 | 工程含义 |
|---|---|---|
| 幻觉 | 生成的是概率最高序列，不保证事实正确 | 关键事实必须靠检索、引用回原文验证，不能信任模型自报置信度 |
| 上下文窗口有限 | 注意力机制的序列建模有窗口上限 | 长期知识必须外置，催生 RAG、记忆分层、上下文压缩 |
| 知识有时效 | 参数冻结在训练截止点 | 新知识必须通过检索/工具实时接入，而非指望模型「学过」 |

结论：**模型是原材料，不是产品**。能力上限由模型决定，实际可用性由系统决定。

### 三、知识接入线：从「查询时拼装」到「摄取时编译」

知识接入方案的演进反映了对「知识如何被系统持有」的理解深化：

| 维度 | 传统 RAG | GraphRAG | LLM Wiki |
|---|---|---|---|
| 知识沉淀时机 | 查询时临时拼装 | 查询时结构化检索 | 摄取时编译进页面 |
| 知识单元 | 原文切块 | 实体/关系/社区摘要 | 主题化页面 + 交叉引用 |
| 跨文档综合 | 每次重新发现 | 图谱查询辅助 | 一次性编译、持续保鲜 |
| 知识积累 | 无（每次从零检索） | 图谱随索引更新 | 复利（查询结果可写回） |
| 适用规模 | 万级文档、点查为主 | 多跳推理、关系密集 | 百级来源、综合阅读 |

LLM Wiki 的核心区分是「知识是否被编译沉淀」——RAG 在查询时现场推导，LLM Wiki 在摄取阶段就把综合、矛盾和交叉引用一次性就位，查询是对已积累知识的读取，详见 [001-llm wiki的理解与实现原理](../llm-wiki/001-llm%20wiki的理解与实现原理.md)。本知识库正是这一模式的最小落地：Claude Code 按 CLAUDE.md 的 schema 编译每道题目、维护索引与标签，人负责审核。

### 四、执行线：Workflow 与 Agent 的边界

Anthropic 在《Building effective agents》中给出的判断标准最实用：**workflow 是预定义的代码路径，控制流图由工程师拥有；agent 是模型在运行时动态决定步骤和工具调用，图由模型拥有**。判断标准可以浓缩为——流程图能否在模型运行前画出来，详见 [008-agentic-workflow的理解](../agent/008-agentic-workflow的理解.md)。

anna-Inbox 的升级过程是这条边界的最佳实践样本：原实现是固定六阶段流水线（Plan → Search → Filter → Context → Answer → Guard），所有查询无论复杂度都走同一批处理路径；升级后改为统一 ReAct Agent Loop，两个关键决策：

一是**不做复杂度分流**。简单查询（如「本月多少发票」）在 Agent Loop 里搜索、观察、回答一轮收敛，不存在多轮浪费；分流省掉的只是首轮一次 LLM 调用（几百 token），代价却是多维护一条完整 Workflow 路径（搜索调用、结果拼装、错误处理、进度推送）与两条路径的一致性风险。

二是**提示词分层**。语义展开的 few-shot 教学材料（约 1800 token，教模型把「求职者」翻译成 ["resume","CV","面试"] 这类搜索词）只注入第一轮系统提示词，第一轮结束后移除，后续轮次只保留基础层（身份 + 工具 + 规则 + 历史，约 1500 token）。六轮复杂查询中，分层比不分层省约 40% 的上下文 token。Guard 作为代码级安全校验保留在循环之外，验证 id 引用、标记风险语言——安全约束不交给模型自评。

### 五、保障线：成本、记忆、评测

**成本**：两条主线是 prompt 缓存与模型分级路由——缓存命中可大幅降低重复前缀的计费，路由则让便宜快速的模型做反思、分类与检索意图判断，强模型只用于关键生成，详见 [002-降低llm调用成本最有效的手段](../agent/002-降低llm调用成本最有效的手段.md)。

**上下文与记忆**：上下文压缩解决「窗口装不下」的问题，方法包括摘要、分层提示词与选择性丢弃，详见 [004-agent上下文压缩策略](../agent/004-agent上下文压缩策略.md)。记忆分层则区分短期上下文（当前会话）、长期画像（用户偏好持久化）与共享记忆（多 agent 之间的协作状态）；多智能体场景下记忆问题从「压缩」变成「治理」——写入校验、来源标注、冲突裁决与防爆阈值，详见 [004-多智能体记忆管理与防爆策略](../mutil-agent/004-多智能体记忆管理与防爆策略.md)。

**评测**：没有量化评测的系统只能靠感觉调 prompt。TJ-Edu-Agent 用 **Ragas** 构建 RAG 评测系统，对检索质量（context precision/recall）与生成质量（faithfulness、answer relevancy）分别打分，让每次改动可验证。这是我把「效果评估」列入保障层而不是可选件的原因。

### 六、三个项目的设计取舍复盘

| 项目 | 解决的问题 | 关键设计 | 可量化的取舍 |
|---|---|---|---|
| TJ-Edu-Agent | 教育场景智能问答 | LangGraph 两层编排图 + RAG + Ragas 评测 + 用户画像长短期记忆 + 异步推送 | 评测闭环让每次模块改动可量化验证 |

三个项目恰好覆盖了三条线的两端：TJ-Edu-Agent 验证「知识接入 + 评测」的价值，anna-Inbox 验证「执行层范式选择」的成本账，interviewQA 验证「编译式知识沉淀」的长期复利。

### 七、面试追问

**追问一：Scaling Law 还在持续兑现，工程优化是不是只是过渡手段，等模型更强了系统就没价值了？**

工程不会消失，理由有二。第一，Scaling 提升的是推理上限，不是消除架构约束——上下文窗口、知识时效、成本结构是系统级约束，模型再强也要在有限窗口内工作，知识仍然需要外置。第二，Ng 的 HumanEval 数据反过来成立：GPT-3.5 零样本 48.1%，套上 agentic workflow 后 95.1%，反超零样本 GPT-4 的 67.0%——工作流是独立于模型能力的杠杆，模型更强时好的系统设计只会放大收益。而且工程范式本身随模型能力进化：RAG 演进到 LLM Wiki、固定工作流演进到 agent loop，系统设计不是静态的，它和模型共同演化。

**追问二：anna-Inbox 为什么不按查询复杂度分流？简单查询也走 Agent Loop 不浪费吗？**

简单查询在 ReAct Loop 里天然一轮收敛——调用 search_emails、观察结果、直接输出答案，不存在多轮浪费；分流唯一省下的是首轮一次 Agent LLM 调用（几百 token），代价却是要多维护一条完整的 Workflow 路径（搜索调用、结果拼装、错误处理、前端进度推送），以及两条路径行为不一致的风险。这是「先证明收益大于成本再引入复杂度」的原则：分流省下的成本远小于双倍维护成本时，统一入口是更优解。如果未来简单查询占比极高且首轮调用成为主要成本，再评估分流也不迟——渐进式混合架构的边界本来就该随数据演进。

**追问三：RAG 和 LLM Wiki 你怎么选型？什么场景你会坚持用传统 RAG？**

规模是第一分界线：百级来源、以综合阅读为主的个人或团队知识库选 LLM Wiki，编译式沉淀的复利在中等规模下最显著；万级文档、以点查为主、内容高频变化的场景必须坚持传统 RAG，因为编译式沉淀的更新成本与一致性维护在那个规模下不可承受。第二是知识形态：结构化、可沉淀、慢变化的知识适合编译；流式、时效性强、用完即弃的内容适合检索。两者也可以组合——Wiki 页面作为「已综合的知识单元」入向量库，语义质量比原文切块更高，检索对象从 chunk 升级为综合页。

**追问四：多智能体共享记忆与单智能体记忆的本质区别是什么？**

单智能体记忆只有一致性问题——自己的短期上下文、长期画像如何分层、压缩与召回；多智能体共享记忆多了权限与污染问题——谁写的、谁能读、记忆膨胀时按什么规则修剪、一个 agent 的错误写入如何不污染其他 agent 的决策。所以共享记忆的设计重心从「压缩」转向「治理」：写入校验、来源标注、冲突裁决、防爆阈值。这也是我对 [004-多智能体记忆管理与防爆策略](../mutil-agent/004-多智能体记忆管理与防爆策略.md) 里那类防爆机制特别感兴趣的原因——单点记忆可以用工程直觉管理，共享记忆必须有制度化的治理规则。

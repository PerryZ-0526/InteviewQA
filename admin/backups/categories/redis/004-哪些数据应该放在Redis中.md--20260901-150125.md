## 面试直接答

> 我一般按“数据是否需要`长期可靠保存`、是否要求`事务一致性`、`访问频率和时效性`”来区分。
>
> - Redis 适合<u style="text-decoration-color: rgb(230, 57, 70)">高频访问、短生命周期、可重建的数据</u>；
> - MySQL 适合<u style="text-decoration-color: rgb(230, 57, 70)">长期持久化、需要强一致性和复杂查询</u>的数据。
>
> 实际系统里两者通常不是二选一，而是 MySQL 做事实源，Redis 做缓存和临时状态。

### 如果让我在项目里做选择，我首先看这个<u style="text-decoration-color: rgb(230, 57, 70)">数据丢了以后能不能接受</u>

像用户账号、订单、用户画像的正式版本、任务记录、业务配置、审批记录这些数据，一旦丢失就会影响业务正确性，而且通常还需要事务、索引、条件查询和审计，所以我会放 MySQL。MySQL 更适合作为`系统的持久化事实源`，也就是`最终可信的数据`应该能够从数据库恢复出来。

Redis 更适合`高频读写但生命周期比较短`的数据。例如<u style="text-decoration-color: rgb(230, 57, 70)">登录 Session、验证码、限流计数器、接口缓存、热点用户信息、分布式锁、任务执行中的临时状态等</u>。这些数据通常要求访问速度非常高，而且很多天然带 TTL，比如验证码 5 分钟失效、Session 几小时失效，因此 Redis 的内存访问和过期机制非常合适。

### 还有一种非常典型的场景是 Redis 和 MySQL <u style="text-decoration-color: rgb(230, 57, 70)">同时保存同一类数据，也就是 Cache Aside</u>

比如用户画像的权威版本存在 MySQL，Agent 每次请求都需要读取画像，如果直接访问 MySQL 会产生较高延迟，就先查询 Redis；缓存命中直接返回，未命中再查询 MySQL，并把结果写入 Redis。更新时通常先更新 MySQL，再删除或者更新 Redis 缓存。

> 这里必须明确，Redis 是`缓存副本`，MySQL 才是`最终事实源`，不能让两个数据库都变成独立的权威来源，否则很容易产生一致性问题。

### 另外还要考虑查询模式

Redis 擅长 Key-Value、Hash、Sorted Set 这类简单高性能访问，比如排行榜、计数器、最近访问列表；MySQL 更适合<u style="text-decoration-color: rgb(230, 57, 70)">多字段筛选、Join、聚合、分页以及事务</u>。例如我要查“过去一个月所有审批失败且属于某个用户的任务”，显然 MySQL 更合适，而不是把这类关系型查询硬塞进 Redis。

> 所以我的判断原则可以概括为：长期、重要、不可丢、需要事务和复杂查询的数据放 MySQL；高频、临时、可过期、可重建的数据放 Redis。工程上最好让 MySQL 保证正确性，让 Redis 提升性能，而不是为了追求速度把所有状态都放进 Redis。

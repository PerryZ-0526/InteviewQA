## 面试直接答

> DeepSeek Harness（dsh）是 DeepSeek 于 2026 年 8 月以 MIT 协议开源的首款 Agent 框架，核心架构是`「一切皆插件」`：
>
> 模型适配器、工具、会话日志、沙箱乃至 agent loop 本身全部是插件，由 vendor 引入的 `Cordis 微内核`负责装载与生命周期管理，<span style="background-color: rgb(255, 243, 205)">插件之间通过 ctx 服务键和类型化事件协同</span>；应用边界是它处于开发者预览阶段，定位是框架而非开箱即用的产品。

### 架构的第一层是 Cordis 插件微内核`/ˈkɔː.diːs/`

Cordis 不承载任何业务功能，只做插件加载、卸载与依赖管理，有五个核心概念：

1. 实现 Service 的对象是`插件`；

> 插件就是一个功能块，它对外提供某种"服务"。比如"Bash 工具"插件提供"执行命令"这项服务

2. Context（ctx）是服务的容器，每个服务占据一个稳定的 `ctx 键`，比如 ctx.tools、ctx.llm、ctx.sessions；

> 系统里有一个公共的"登记簿"，每项服务都有一个固定的名字（ctx.tools、ctx.llm 这些就是名字）。你要用某项服务，就按名字去登记簿里取，不用知道它具体是谁提供的、代码在哪。这就是"标准插座"的含义：插进去的东西可以换，插座编号不变。

> 注意：这里的 Context 是 Cordis 的`运行时服务容器对象`，即`插件的运行环境`。

3. 插件通过 inject 声明`服务依赖`，<span style="background-color: rgb(255, 243, 205)">加载顺序由依赖关系决定</span>而不是手动编排启动序列；

> 每个插件入住时声明"我需要谁谁谁"，系统自动算出先后顺序。你不需要写启动脚本手动安排"先加载 A 再加载 B"，声明了要什么，顺序就出来了。

4. 服务间通过`类型化事件`通信：emit（通知）、waterfall（可拦截的链式传递）、parallel（并行扇出）和 serial（按序执行）

> 插件之间不用互相调用对方的函数，而是广播事件。四种模式就是四种广播方式：
>
> ```
> - emit：喊一嗓子通知大家，说完就走，不管有没有人理；
>
> - waterfall：像传话筒一样挨个传，每个人都可以截住话茬不让往下传（这就是"可拦截"的来源）；
>
> - parallel：分头通知所有人，并行处理；
>
> - serial：排队，一个一个来。
> ```
>
> 用哪种模式，等于在代码里写明`"这件事允许不允许别人插手、插手到什么程度"`。

5. 注册是可逆的，提示词片段、工具 schema、事件监听器都通过 `ctx.effect` 安装，插件卸载时自动撤销注册。

> 插件装上的东西（事件监听器、工具注册、提示词片段）全部被登记在册，卸载时按册子自动全部撤销。类比：租房时押金和物品都登记了，退租时照单清点，不会留下垃圾。这解决了传统插件系统"卸载了但监听器还赖在内存里"的经典问题。

> 这套设计意味着框架里没有特权内核，扩展 dsh 的方式是把插件挂载到其他插件旁边，而不是给某个核心打补丁。

### 第二层是 Profile 与组合包的分层组装

运行中的 dsh 是一棵`插件树`，由启动时按序叠加的各层组合而成。

> 1. `profile` 是存放在 Harness home 中的一份`具名配置`，里面列出"我要用哪些组合包、按什么顺序叠"；
> 2. `组合包`是 Cordis 配置项及其挂载代码的分发格式（配套代码的打包形式），相当于"一个功能的安装包"

层次顺序是：

先按 profile 列出的顺序应用每个组合包，然后应用 profile 自己的 cordis.patch.yml，再是 home 级 patch，最后是命令行 --patch overlay。

一条 patch 按 id 定位某个条目并整体替换其配置，或插入新条目，所以任何一层都可以覆盖下层的任何决定，用 dsh --profile web --dump-config 就能看到实际启动的完整配置树。

> 官方发行版以 dsh-base 为第一层，提供模型适配器、工具、持久化、沙箱与审批策略、设置、凭据和遥测，dsh-web-app 在其上叠加浏览器应用，dsh-headless 叠加一次性运行器且完全不带服务器。

### 第三层是核心包与轮次流程

一个步骤是一次模型请求加上它调用的工具，一个轮次包含零个或多个步骤。轮次开始时，驱动器从 inbox 领取首条输入，agent/pre-step 这个 waterfall 事件让监听器改写或直接拒绝即将进入模型的消息；每个步骤先执行 agent/request，经 llm/stream 流式生成，工具调用依次经过 tools/pre-execute、tools/execute、tools/post-execute 三段把关流水线；步骤结束后，agent/turn-stopping 这个 serial 事件可以终止轮次，最后 turn/end 关闭轮次。这套流程里，模型看到什么、工具如何执行、轮次何时停，全部是可拦截的扩展点。

### 第四层是会话日志与「模型可见即已记录」不变量

会话日志是仅追加的 SessionEvent 事件流，模型看到的上下文以它为单一事实源，deriveMessages 从日志中投影出模型历史。fork、恢复、文本记录、遥测和持久化全部派生自同一条事件流。运行时有一条不变量断言：任何抵达模型请求的内容都必须能从日志重建，所以新增一种模型可见输入就必须新增一个会话事件类型。这条不变量保证了审计、回放和跨会话恢复的一致性，是 dsh 架构上我认为最值得讲的设计。

### 第五层是能力 seam 与 agent preset

一个 seam 是一项可替换能力，由三种角色构成：声明接口的 Service Definition、实现它的 Service Provider、使用它的 Consumer。文件系统与进程提供方共享同一个执行世界，把它们指向远程沙箱，Bash、PTY 和 LSP 就一并搬了过去，不需要每个工具单独 fork。

agent preset 是按会话组合插件集合的机制，工具注册沿 agent、preset、global 的作用域链解析，一个 preset 的挂载实例被多个会话共享，各会话状态互不污染；空会话可以热切换 preset，但产生过输出的会话被网关锁定，防止日志里的工具调用无法用新工具集重放。

### 最后提 Code Mode SDK（PTC模式）

这是媒体报道中被称为 PTC（程序化工具调用）的机制：模型写一段程序，在宿主提供的异步绑定上运行，程序内部的中间数据留在运行环境里，只有最终结果进入模型上下文，从而把多轮工具编排压缩成一次代码执行，显著降低 token 消耗。它的实现也是一个 seam，运行时提供方可以替换，worker-thread 后端是默认实现。

> 为了让你更清晰地理解PTC模式，这里是DeepSeek Harness提供的四种模式对比：


| **模式**    | **核心特点**                           | **适用场景**             |
| :--------- | :---------------------------------- | :-------------------- |
| **标准模式**  | 提供完整的工具组合（文件编辑、Shell、检索等），功能最全面。   | 日常的通用Agent任务。        |
| **PTC模式** | **模型生成代码**来组合多轮工具调用，中间数据在程序内处理。    | 复杂的、多步骤的工具工作流，追求高效率。 |
| **极简模式**  | 仅保留Shell和文件编辑两个最基础的工具。             | 用于模型基础能力的基准测试。       |
| **创造模式**  | 提供一个可以检查和试验插件的运行时环境，甚至能让Agent修改自身。 | 用于创建和调试自定义的Agent预设。  |


总结来说，dsh 的架构贡献是把 agent 框架从「带扩展点的产品」推进到「一切能力皆可替换的元框架」，代价是开发者预览期的兼容性风险与插件生态治理的长期不确定性。

### 通俗易懂版

> 上面那一版里如果「插件树」「微内核」「seam」这些词对不上号，这一版换一个角度讲。dsh 的核心思路其实只有一句话：**它不卖成品，只卖标准插座**。

传统 Agent 框架像精装房——模型调用、工具执行、记忆管理的流程都是`预先装修好的`，你想改其中某一处，要么等官方更新，要么去读源码打补丁。dsh 的做法是把房子的每一面墙都做成`标准插座面板`：模型适配器、工具、沙箱、会话记忆、甚至 AI 思考的主循环，全部做成`可以拔下来换掉的插件`。

> 这也是它敢叫自己`「元框架」`的原因——它是`用来搭框架的框架`，本身不给你任何固定答案。

理解了这一点，再看它的架构就容易了，可以把它想象成一栋楼。最底下是物业公司 Cordis 微内核：物业不干任何业务，只负责三件事——住户（插件）入住登记、退房清理、处理住户之间的依赖（你要用水电，我就保证水电先给你接好）。

它带来两个实际好处：

- 一是插件之间不需要互相 import 代码，各自声明「我需要什么」，加载顺序由依赖关系自动推导，没有手写的启动脚本；
- 二是<span style="background-color: rgb(255, 243, 205)">插件之间的协作走统一的「事件广播」</span>，内置四种语义——普通通知、像流水线一样逐个传话且中途可以截断、并行分头通知、排队依次执行。用哪种模式，等于在代码里就写明白了「这件事允不允许别人拦截」。

第二层是`「组合包 + 补丁」的分层配置`，相当于装修预算单：

- 每次启动 dsh 就是按顺序叠放一堆配置层，<span style="background-color: rgb(255, 243, 205)">后放的层可以覆盖前面任何一层里的任意一个条目</span>——注意是任意粒度，小到一个工具的参数，大到 agent 循环本身，都能用一条 patch 按 id 整体替换掉。
- 同一份底层代码，给内部团队是一套配置，给客户是另一套配置。

第三层是`运行时的流水线`，可以想成餐馆后厨：客人下单（用户消息）先进预处理岗，这里允许被拦截、改写甚至直接拒绝；然后进厨师岗（模型生成）；<span style="background-color: rgb(255, 243, 205)">模型要用的每把工具，都要经过出库前检查、使用、用后登记三道关卡，每一道你都能安插自己的逻辑</span>；

最后还有个`「这单做完了吗」的判断环节`，也可以插话决定继续还是收工。

> 要点是：模型看到什么、工具怎么执行、一轮何时停，全部是可拦截的扩展点，而不是写死在主循环里的固定步骤。

第四层是这栋楼的监控录像——`「模型可见即已记录」`。

模型看到的每一条上下文，必须先写进一份只追加的日志；模型的历史不是单独存在内存里的，而是从这份日志里回放出来的。这条设计值得重点讲，因为审计、断点恢复、数据统计全部共用这一份日志，永远不可能出现「日志里没有、但模型看到了」的东西；代价是以后想给模型加一种新的可见输入，就得先设计它的日志格式和回放方式，扩展成本比直接拼字符串高。

第五层的 seam 就是前面说的「标准插座」的正式叫法：一个可替换的能力，由声明接口、实现、使用三个角色组成。

最漂亮的例子是文件系统和进程共享同一个`执行世界`——把执行世界指向远程沙箱，Bash、终端、LSP 这些工具就整体搬过去了，不需要一个个单独改造。

preset 则是给不同会话配的「工具套装」；为了保证历史日志能原样重放，产生过输出的会话不允许中途换套装，只有空会话可以热切换。

最后是媒体报道里的`PTC（程序化工具调用）`：
```
模型不再一步步调用工具，而是写一段小程序在宿主环境里跑完，中间过程的数据留在程序里，只把最终结果送回模型上下文。
```

就像让秘书出去办完整件事再回来汇报，而不是每跑一个窗口就打电话请示一次——<span style="background-color: rgb(255, 243, 205)">多轮工具编排被压缩成一次执行，token 消耗显著下降</span>。

如果面试官追问「这个架构的代价是什么」，答三件事：

1. 学习与调试成本高（行为散落在各插件的注册副作用里）
2. 开发者预览期兼容性不稳定；
3. 社区插件生态治理存在不确定性——灵活性是用复杂度换来的。


## 详细解析

> 内容基于 2026-08-16 克隆的 `deepseek-ai/deepseek-harness` 仓库源码与官方文档核验。

### 一、整体结构图
```text
┌─────────────────────────────────────────────────────┐
│  启动时按序叠加的插件树（profile + patch 分层）        │
│  dsh-headless / dsh-web-app                          │
│  dsh-base（模型适配器/工具/持久化/沙箱/审批/遥测）     │
├─────────────────────────────────────────────────────┤
│  Cordis 微内核（vendor 引入，只做装载与生命周期）       │
│  · Service 插件 / ctx 服务容器 / inject 依赖声明       │
│  · 类型化事件：emit / waterfall / parallel / serial   │
│  · 可逆副作用：ctx.effect() 注册，卸载自动撤销         │
├─────────────────────────────────────────────────────┤
│  核心包（部分）                                       │
│  core/session   ctx.sessions   仅追加 SessionEvent 日志│
│  core/system-prompt ctx.systemPrompt 提示词片段组装    │
│  core/tools     ctx.tools      作用域化工具注册+把关流水│
│  core/agent     ctx.agents     Agent 接口与活跃注册表  │
│  core/agent-loop ctx.agentLoop 默认驱动器（本身可替换） │
│  llm/llm        ctx.llm        消息词汇表与适配器 seam  │
└─────────────────────────────────────────────────────┘
```

### 二、轮次流程（官方架构文档原文结构）
```text
turn/start
  claim next-step input plus one queued message
  assemble prompt sections + tool schemas
  -> agent/pre-step                   reject | enter(messages)
     step/start
     append entered messages as user/message
     derive model history from the log
     agent/request -> llm/stream -> assistant/chunk* -> assistant/message
     tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
     step/end
  -> agent/turn-stopping
turn/end
```

`turn/*`、`step/*`、`user/message`、`assistant/*`、`tool/*` 是持久会话事件；`agent/pre-step`、`agent/request`、`llm/stream`、`tools/*` 是 waterfall 实时扩展点，监听器必须调用 `next()` 才能委托下去；`agent/turn-stopping` 是 serial 事件，没有 `next()`。

### 三、Cordis 四种事件分发模式


| 模式          | 是否 await | 分发顺序       | 是否有返回值 | 典型用途                          |
| ----------- | -------- | ---------- | ------ | ----------------------------- |
| `emit`      | 否        | 监听器按注册顺序观察 | 否      | 通知（session/event 广播）          |
| `waterfall` | 否        | 环绕中间件，可短路  | 是      | 策略决策（agent/pre-step、tools/\*） |
| `parallel`  | 是        | 所有监听器并行    | 否      | 扇出                            |
| `serial`    | 是        | 按注册顺序执行    | 是      | 汇总（agent/turn-stopping）       |


Waterfall 语义值得单独讲：监听器收到 `(...args, next)`，调用 `next()` 执行下游监听器并拿到下游返回值，可以包装后继续向外返回；不调用 `next()` 直接返回就是短路。单决策事件里短路是设计意图——拥有决策权的策略监听器可以直接给出结论，只做观察的监听器则必须委托。

### 四、配置示例：用 patch 替换任意条目
```sh
# 查看机器实际启动的配置树
dsh --profile web --dump-config
```

profile 的 `cordis.patch.yml` 按 id 定位条目整体替换，例如把某个工具替换成自定义实现：
```yaml
# ~/.dsh/profiles/web/cordis.patch.yml（示意）
- id: dsh-tool-bash
  plugin: my-company:dsh-tool-bash-safer
  config:
    timeoutMs: 30000
```

覆盖顺序：profile 列出的组合包 → profile 的 `cordis.patch.yml` → home 级 patch → `--patch` overlay，后层覆盖前层。与 Claude Code 的 hooks/subagents 这类「预置扩展点」相比，patch 能替换的粒度是任意插件条目——包括 agent loop 本身。

### 五、面试追问

**追问一：Cordis 和常见的 IoC 容器、npm 插件机制有什么区别？**

IoC 容器通常只解决依赖注入，插件生命周期和事件通信要另外搭。npm 包机制没有运行时装配概念，插件之间的协作要靠显式 import 和调用约定。Cordis 把三件事合成一个运行时：服务键查找替代直接 import（插件之间零编译期耦合）、inject 声明决定启动顺序（无需编排代码）、类型化事件带分发模式语义（观察、包装、短路是接口约定的一部分）。它出自 Koishi 生态，被 dsh 以 vendor 方式引入，意味着 dsh 连插件框架本身都是可替换的依赖而不是产品的一部分。

**追问二：「模型可见即已记录」不变量是怎么落地执行的？**

三个层面：类型层面，所有模型可见输入必须扩展 SessionEventMap 类型，新增会话事件类型才能在日志里表达；渲染层面，每个会话事件都必须能从日志渲染回模型上下文，deriveMessages 只从日志投影，不维护旁路状态；运行层面，存在断言性质的检查（官方文档称 runtime invariant），在模型请求组装时校验其内容可由日志重建。这个设计的直接收益是 fork 和恢复不需要单独的序列化格式，转写、遥测、回放共享同一条流；代价是每次新增模型可见输入都要同时设计事件 schema、渲染路径和回放行为，扩展成本高于「拼字符串进上下文」的做法。

**追问三：agent preset 为什么只允许空会话切换？**

切换 preset 等于替换工具集和提示词片段。如果会话已经产生过工具调用，日志里记录的是旧工具集能执行的调用，用新工具集重放这段历史时会出现无法解释的调用——这正是「模型可见即已记录」要求的可重建性被破坏的场景。所以产品规则限定只有未产生任何输出的空会话可以 recompose，网关在协议层返回 agent-preset-locked 错误强制这个约束。子 agent 则通过 composeFrom 绑定父会话的既有组合，而不是重新按 id 挂载，保证子会话与父会话历史在同一个组合代际下重放。

**追问四：一切皆插件的代价是什么？**

三方面。调试成本：行为分散在多个插件的注册副作用里，出错时要从配置树和事件流里还原现场，dsh 提供的 dump-config 和事件映射文档就是为此设计的。治理成本：社区插件没有统一的兼容性保证，官方开发者预览明确承诺破坏性变更，媒体与社区对插件长期可维护性的质疑集中在这里。性能边界：服务键查找、事件分发、作用域链解析都是运行时开销，虽然量级不大，但相对单体 harness 的直接函数调用是真实成本。判断标准是：需要替换核心行为或做多产品复用，收益大于成本；只是加一个工具，插件化与硬编码的差距不大。

## Cordis 插件微内核-简述






**Cordis 是一个“元框架”（Meta-Framework）**，即一个用于构建框架的框架。它源于知名的聊天机器人框架 Koishi，后被 DeepSeek 的 AI Agent 框架 **DeepSeek Harness (dsh)** 采用作为其底层核心，由此进入大众视野。

其核心思想是\*\*微内核架构（Microkernel Architecture）\*\*，致力于解决复杂软件系统中组件动态组合与拆卸的难题。

### ⚙️ “什么都不干”的内核

Cordis 内核极其精简，它本身不提供任何具体的业务功能。它的职责非常纯粹，只做三件事：

\*   **加载 (Load)** 插件

\*   **卸载 (Unload)** 插件

\*   **管理依赖关系 (Dependency Management)**

你可以把它想象成一个极其精简的操作系统内核，它只负责调度和管理，而把文件编辑、网络浏览等所有具体功能都交给应用程序（插件）去实现。

### 🧩 “一切皆插件”的设计

在 Cordis 的设计哲学下，\*\*系统的每一部分都是插件\*\*。以 DeepSeek Harness 为例，以下所有能力都是以插件形式存在，可被自由替换和重组：

\*   **模型适配器**：对接不同的大语言模型（如 DeepSeek, OpenAI, Claude 等）。

\*   **工具注册表**：管理 Agent 可调用的各种工具。

\*   **会话与记忆管理**：处理对话历史和上下文。

\*   **安全沙箱**：提供安全的代码执行环境。

\*   **Agent 循环**：控制智能体的思考与行动主循环。

\*   **用户界面**：甚至是 Web 界面本身也是插件。

这意味着你可以\*\*通过修改配置文件来增删或替换系统的任何功能模块，而无需改动任何核心源代码\*\*。

### ⏳🧩 “时空可组合性”：Cordis 的核心创新

Cordis 的设计精髓被概括为 **“时空可组合性”（Spatiotemporal Composability）** 。它解决了传统插件系统的两大核心痛点：

\*   **时间可组合性 (Temporal Composability)：确保副作用可逆**

    传统插件卸载时，其注册的监听器、创建的文件等“副作用”常常无法被完全清理，导致内存泄漏等问题。Cordis 通过 **“可逆副作用”（Reversible Effects）** 机制解决了这个问题。每个操作都会产生一个对应的“撤销函数”。当插件被卸载时，Cordis 会自动、按顺序地调用这些函数，\*\*完整地撤销该插件产生的所有影响\*\*，确保系统“恢复如初”。

\*   **空间可组合性 (Spatial Composability)：确保依赖可管理**

    插件之间常有依赖关系。当一个插件所依赖的另一个插件发生变化或更新时，Cordis 能够感知并\*\*自动调整依赖它的插件的生命周期\*\*，保证整个系统的稳定运行。

### 🔗 生态系统与应用

Cordis 并非凭空出现，它有着坚实的生态基础：

\*   **起源与作者**：它脱胎于拥有超过 **4000 个插件**的开源聊天机器人框架 Koishi，其核心作者是 **崔添翼**（Koishi 的作者）。

\*   **学术背书**：2026年8月，北京大学与 DeepSeek 联合发表了关于 Cordis 设计理念的学术论文，为其建立了形式化模型。

## PTC 程序化工具调用

近期AI Agent领域的一项重要技术革新。**DeepSeek Harness** 框架提供的四种核心运行模式之一。

### **什么是PTC（程序化工具调用）？**

PTC的全称是 **Programmatic Tool Calling**。它的核心思想是`改变传统AI模型“提问-回答-调用工具-再提问”的串行工作方式`。

- **传统模式**：模型每调用一次工具（如读文件、搜索网页），都需要与外部环境进行一次“往返”通信，并将所有中间结果都保存在对话上下文中。这会导致**高延迟**和**Token消耗巨大**的问题。
- **PTC模式**：模型不再一步步地调用工具，而是根据你的指令，直接**编写一段完整的程序（在dsh中是TypeScript代码）**。
- **执行过程**：这段程序会在一个安全的**沙箱环境**中自动运行。程序内部可以自主、批量地调用各种所需工具，处理所有中间数据。
- **最终结果**：整个程序运行完毕后，只会将**最终的、精炼的结果**返回给模型上下文。正如你所说，“中间过程的数据留在程序里”。

### **在DeepSeek Harness (dsh) 中如何体现？**

在DeepSeek Harness中，PTC模式是作为一项内置能力提供的。

- **工作方式**：模型通过 **Code Mode SDK** 来使用工具，直接生成一个TypeScript程序来组合和执行多步操作。
- **核心优势**：这种方式将“本来要一来一回调十次的工具操作合并成一次执行”，极大地减少了模型与外部环境的交互次数和上下文长度。
- **实际效果**：根据报道，这种模式能**大幅降低Token消耗**，在处理复杂编程任务时表现出“极高的性价比”。

### **与其他模式的区别**

为了让你更清晰地理解PTC模式，这里是DeepSeek Harness提供的四种模式对比：


| **模式**    | **核心特点**                           | **适用场景**             |
| :--------- | :---------------------------------- | :-------------------- |
| **标准模式**  | 提供完整的工具组合（文件编辑、Shell、检索等），功能最全面。   | 日常的通用Agent任务。        |
| **PTC模式** | **模型生成代码**来组合多轮工具调用，中间数据在程序内处理。    | 复杂的、多步骤的工具工作流，追求高效率。 |
| **极简模式**  | 仅保留Shell和文件编辑两个最基础的工具。             | 用于模型基础能力的基准测试。       |
| **创造模式**  | 提供一个可以检查和试验插件的运行时环境，甚至能让Agent修改自身。 | 用于创建和调试自定义的Agent预设。  |


### **总结**

PTC（程序化工具调用）是一个真实存在且正在快速发展的技术方向。它通过让模型“写程序”而不是“打电话”的方式来使用工具，解决了传统工具调用方式在效率和成本上的痛点。DeepSeek Harness是这一理念的积极实践者，将其作为核心模式之一向开发者开放。

## 什么是 Agent Preset

dsh 的 **Agent Preset（智能体预设）**，简单来说就是**一个会话（Session）中，Agent 所拥有的“能力包”或“人格设定”**。

> 它并非一个固定的程序，而是一份`可配置的插件清单`，决定了这个 Agent 可以使用哪些工具、拥有怎样的系统提示词（Persona）以及具备何种能力。

### **Agent Preset 的核心构成**

从技术实现上看，一个 Agent Preset 其实就是一个**包含** `agent.cordis.yml` **配置文件的目录**。这个YAML文件像一张“菜单”，列出了这个 Agent 会“点”的所有插件，主要包括：

- **工具 (Tools)**：Agent 能使用的具体功能，比如执行Shell命令、编辑文件、搜索网页等。
- **提示词 (Persona/Prompt)**：定义 Agent 的角色、行为风格和思考方式。
- **其他能力 (Skills, Sub-agents等)**：更复杂的工作流、计划能力或子Agent。

### **Agent Preset 如何工作？**

它的工作机制可以概括为“**一次挂载，多会话共享**”：

1. **常驻挂载**：当一个 Preset 被系统加载（挂载）后，它会在整个进程中只被加载一次，成为一个常驻的“能力模板”。
2. **会话认父**：每个新的对话会话（Session）在创建时，可以通过“认父”的方式，声明自己使用哪一个 Preset。
3. **视图解析**：Agent 最终的能力视图会按照 `agent → preset → global` 的优先级进行解析，即 Preset 本身的配置会覆盖全局默认配置，而会话内的临时配置又能覆盖 Preset 的配置。这种设计保证了不同会话即使共享同一个 Preset 模板，其内部状态也是相互隔离、互不干扰的。

### **dsh 内置的四种 Agent Preset (运行模式)**

dsh 官方预置了`四种开箱即用的 Agent Preset`，也就是我们通常所说的四种**运行模式**：


| **Preset (模式)**     | **核心特点**                                                    | **适用场景**                          |
| :------------------- | :----------------------------------------------------------- | :--------------------------------- |
| **标准模式 (Standard)** | 功能最完整的编码Agent，支持文件编辑、Shell、检索、Skills、计划、子Agent等全套工具。        | 日常的、复杂的编程与开发任务。                   |
| **PTC模式 (PTC)**     | 具备标准模式的全部能力，但通过 **Code Mode SDK** 让模型编写TypeScript程序来组合多步操作。 | 追求高效率、低Token消耗的复杂任务（你之前提到的PTC模式）。 |
| **极简模式 (Minimal)**  | 仅提供持久的 `bash` (Shell) 和 `str_replace_editor` (文件编辑) 两个核心工具。 | 简单的文件修改、测试最小化Agent或作为基准测试。        |
| **创造模式 (Creative)** | 具备标准模式的全部能力，并额外提供了**运行时检查、插件实验和Preset创作指导**功能。              | **用于创建和调试你自己的自定义 Agent Preset**。  |


### **如何自定义 Agent Preset？**

这是 dsh 灵活性的核心体现，主要有两种方式：

1. **手动创建**：你可以直接复制一个现有的 Preset 目录，然后修改其中的 `agent.cordis.yml` 文件，按需添加、删除或配置插件。这些自定义的 Preset 通常存放在 `~/.dsh/.agent-presets/` 目录下。
2. **使用“创造模式”**：这是官方推荐的更高级方式。你可以启动一个运行在“创造模式”下的 Agent，然后**用自然语言指令让它帮你创建或修改一个新的 Preset**。这实现了“用Agent创造Agent”的理念。

总而言之，Agent Preset 是 dsh 实现“一切皆插件”理念的关键。它让你能像搭积木一样，通过选择和组合不同的插件，为不同的任务“组装”出拥有特定能力和人格的AI Agent。

## Seam（能力接缝）

> 在 dsh（DeepSeek Harness）中，**Seam（能力接缝）** 是其插件化架构的**核心设计模式**。它并非一个具体的功能，而是一种组织代码的方式。
>
> 你可以把它理解为一个**标准化的“插槽”**，用于将某个特定的能力（如执行命令、调用大模型等）插件化，使其可以被自由替换和组合。

### **Seam 的三大角色**

一个完整的 Seam 由三个分工明确的角色组成：

1. **服务定义 (Service Definition)**：制定“插槽”的**标准接口**。它规定了这个能力“长什么样”以及“如何被调用”，但不关心具体如何实现。例如，`dsh-shell` 就定义了执行 Shell 命令的标准。
2. **服务提供方 (Service Provider)**：提供“插槽”的**具体实现**。针对同一个接口，可以有多个不同的实现方案。
  - 例如，`dsh-bash-local` 提供在本地执行命令的实现，而 `dsh-bash-sandbox` 则提供在安全沙箱中执行的实现。
3. **服务消费者 (Service Consumer)**：**使用这个能力**的代码或插件。它只关心接口，不关心具体是谁提供的。
  - 例如，`dsh-tool-bash` 这个工具就是 `dsh-shell` 这个 Seam 的消费者，它通过标准接口来调用命令。

### **Seam 的核心特点**

- **可替换性**：这是 Seam 最重要的价值。由于“定义”和“实现”分离，更换一个 Provider 就能整体替换掉产品的某一块能力，无需修改其他代码。
- **可选性**：许多 Seam 代表的是“可选能力”，它们并不属于 Agent 主循环（loop）的核心。例如，子代理（Subagent）和上下文压缩（Compaction）等功能，都是挂在 Seam 上的可选插件。

### **dsh 中的 Seam 示例**

在 dsh 中，几乎所有核心能力都是通过 Seam 来实现的：

- `ctx.llm` **(LLM Seam)**：大语言模型适配器接口。通过这个 Seam，你可以轻松更换 dsh 背后使用的大模型，官方默认已支持近 40 家模型厂商。
- `ctx.subagents` **(Subagent Seam)**：子代理接口。允许一个 Agent 将任务委派给子 Agent 执行。
- `ctx.compaction` **(Compaction Seam)**：上下文压缩接口。用于在对话历史过长时进行总结压缩。
- `ctx.approval` **(Approval Seam)**：审批接口。用于处理需要人工审批的操作，例如工具调用前的确认。
- **MCP Seam**：用于对接模型上下文协议（MCP）的接口。

### **总结**

总而言之，**Seam 是 dsh 实现“一切皆插件”这一核心理念的基石**。它将一个完整的能力清晰地拆分为“定义”、“实现”和“使用”三个部分，从而实现了高度的模块化和可扩展性。得益于此，dsh 的内核可以做得非常精简，所有功能都以插件的形式，通过这些标准化的“接缝”挂载到系统上。

---

在 dsh 的“一切皆插件”和“能力接缝 (Seam)”架构下，**你可以通过编写插件，来替换掉 subagent、记忆模块和上下文压缩模块等agent的核心设计**。这些都属于挂在 Seam 上的“可选能力”，而非不可变的核心。

### **如何替换三大模块**

#### **1. 替换 Subagent 模块**

Subagent 的替换核心在于 `ctx.subagents` 这个服务接口。

- **实现方式**：你可以开发一个插件，为 `ctx.subagents` 提供一个**全新的 Provider（服务提供方）**。只要新 Provider 遵循既定的执行契约（contract），就能无缝替换掉原有的实现。
- **现有案例**：社区已有 `dsh-plugin-product-subagents` 这样的插件，可将外部的 Agent CLI（如 Claude Code、Codex）作为 dsh 的子代理来使用。

#### **2. 替换记忆模块**

记忆模块的替换可以通过实现一个新的 `ctx.memory` 服务来完成。

- **实现方式**：开发一个插件，注册一个新的 `ctx.memory` 服务，并提供相应的记忆操作工具（如 `memory_save`、`memory_search`）。
- **现有案例**：社区已经涌现了多种记忆插件，例如：
  - `@max-null/dsh-memory`：提供跨会话的明文记忆。
  - `dsh-mnemon`：提供完备的本地记忆系统。
  - `dsh-hermes-memory`：提供 Hermes 风格的跨会话记忆与自主学习能力。

这些插件都无需修改 dsh 源码即可集成，充分证明了该模块的可替换性。

#### **3. 替换上下文压缩模块**

上下文压缩模块的替换同样是可行的。

- **实现方式**：dsh 的上下文压缩能力通过 `compaction/*` 相关的 Seam 实现。替换它需要开发一个插件，为上下文压缩提供新的策略或实现。
- **现有案例**：社区已有 `dsh-ui-preset-enhance` 插件，它通过界面集成了“手动 Compact”（手动压缩）的功能，这展示了通过插件干预和控制压缩流程的可能性。

### **为什么可以做到？**

这种高度的可替换性，源于 dsh 精妙的架构设计：

- **极薄的内核**：dsh 的内核非常精简，本身只包含最基础的骨架。
- <span style="background-color: #fff3cd">**能力接缝 (Seam)**：所有扩展功能都以“能力接缝”的形式存在</span>。一个 Seam 定义了“接口（interface）”、“实现（implementation）”和“消费者（consumer）”三个角色。更换其中的“实现”，就能整体替换掉这块能力。
- **声明式依赖**：插件通过稳定的 key（如 `ctx.subagents`）来声明自己需要什么、提供什么，框架会自动处理依赖关系。

总而言之，dsh 将 Subagent、记忆、上下文压缩等全部设计为“可选能力”，并通过“能力接缝”机制暴露出来。这使得你完全可以编写自己的插件来替换它们，而不需要触碰框架的核心源码。<!-- created: 2026-08-16 01:43:31 -->

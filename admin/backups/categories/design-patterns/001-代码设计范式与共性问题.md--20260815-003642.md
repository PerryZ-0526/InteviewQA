## 面试直接答

### 1. GoF 二十三种设计模式

前人总结的软件设计方法很多，其中最经典的一组是 `GoF 二十三种设计模式`，分为创建型、结构型和行为型三大类，比如单例、工厂、观察者、策略、装饰器等，每种模式针对一类反复出现的结构问题给出了经过验证的解决方案。

> GoF 是 "Gang of Four"（四人组）的缩写，他们合著的《设计模式：可复用面向对象软件的基础》一书，总结了 23 种经典设计模式，该书按用途将模式分为三类：
>
> - **创建型**（如单例、工厂）：关注对象创建机制，提升灵活性和复用性。
> - **结构型**（如装饰器、适配器）：关注类与对象的组合方式，形成更大结构。
> - **行为型**（如观察者、策略）：关注对象间的职责分配与通信协作。
>
> 这套模式针对面向对象设计中反复出现的典型问题，提供了经过验证的通用解决方案，是后续众多设计理论和实践的重要基础。

---

### 2. SOLID五项原则

SOLID 五项原则从更抽象的层面提出了面向对象设计的指导思想：

1. `单一职责`原则，规定一个类应该只有一个引起它变化的原因，即只承担一种职责；
2. `开闭原则`，要求软件实体应当对扩展开放、对修改关闭；
3. `里氏替换`原则，指出子类型必须能够替换其基类型，且不破坏程序的正确性；
4. `接口隔离`原则，建议客户端不应依赖它不需要的接口，应使用多个专门接口而非单一臃肿接口；
5. `依赖反转`原则，则要求高层模块不应依赖低层模块，二者都应依赖抽象，同时抽象不应依赖细节，细节应依赖抽象。

---

### 3. 通用职责分配软件模式、领域驱动设计、整洁架构

除了 SOLID 和 GoF，还有一些同样重要的理论体系。

- 通用职责分配软件模式GRASP 从`职责分配`的角度提出了信息专家、控制器、低耦合、高内聚等九种模式，<span style="background-color: rgb(255, 243, 205)">指导我们在设计阶段如何为类和对象分配合适的职责。</span>
- `领域驱动设计`强调以`业务领域`为核心，通过实体、值对象、聚合根、限界上下文等概念来应对复杂业务场景下的建模难题。
- `整洁架构`则从系统层面把依赖方向收敛到核心领域，外层适配器只能单向依赖内层业务逻辑。

---

### 4. 这些范式和理论所瞄准的共性问题，归纳起来主要围绕以下几个维度。

1. 第一是`耦合问题`，高耦合会让一个模块的改动牵连大量其他模块；很多设计原则都关注降低不必要的耦合，但解耦不是唯一目标。
2. 第二是`内聚问题`，低内聚意味着一个<span style="background-color: rgb(255, 243, 205)">模块内部各成分之间关联松散，职责混乱</span>，导致理解和维护困难，`高内聚、低耦合`通常是良好模块设计的重要目标。
3. 第三是`可复用性`，当重复逻辑确实表达同一变化原因时，好的设计会提取复用；过早抽象也会增加理解和修改成本，DRY 原则正是为此而生。
4. 第四是`可扩展性`，业务需求总是在变化，设计需要<span style="background-color: rgb(255, 243, 205)">预留合理的扩展点</span>，让高频变化尽量落在稳定扩展点；开闭原则并不意味着原有代码永远不能修改。
5. 第五是`可测试性`，紧耦合的代码往往难以进行单元测试，因为无法隔离依赖，所以`依赖注入`和`控制反转`成为现代架构的基础设施。
6. 第六是`可读性与可理解性`，代码被阅读的次数远多于被编写的次数，`命名规范`、`代码分层`、`一致的风格约定`本质上都是在降低认知负荷。
7. 第七是`复杂度管理`，无论是分层架构、微服务拆分、还是限界上下文的划分，都是为了将复杂系统分解为人类大脑可以逐块理解的小单元——这也是分治思想在软件工程中的体现。

总结来说，这些模式、原则和架构方法虽然层级不同，但共同关心一个核心问题：

> 如何让软件`在面对持续变化的需求时，保持低成本的修改能力`。耦合、内聚、复用、扩展、测试、可读和复杂度控制，这七个维度构成了我们评判设计好坏的基本坐标。


## 详细解析

### 一、先分清层级


| 层级      | 回答的问题          | 示例                        |
| ------- | -------------- | ------------------------- |
| 编程范式    | 如何组织计算与程序      | 面向对象、函数式、声明式              |
| 设计原则    | 判断设计的方向性准则     | SOLID、DRY、KISS、YAGNI      |
| 设计模式    | 特定上下文中的可复用协作结构 | Strategy、Adapter、Observer |
| 架构模式/风格 | 系统级边界和依赖组织     | 分层、六边形、事件驱动               |


模式不是必须套用的模板。先确认变化点和约束，再判断模式带来的间接层是否值得。

### 二、真正需要平衡的质量属性

设计不仅处理耦合，还要平衡内聚、认知负担、可测试性、性能、一致性、部署边界和变更频率。微服务与消息队列可以隔离团队或负载，也会增加网络失败、数据一致性和运维复杂度；不能把“拆得更细”自动等同于更好设计。

### 三、几个常见误区

- **开闭原则**：目标是稳定边界，不是禁止修改。扩展点只应为高概率变化建立。
- **依赖注入**：核心是依赖方向和可替换性，不是禁止使用 new 或静态函数。
- **Repository**：通常由内层定义所需端口、外层实现，但接口位置取决于架构分层，不存在唯一目录答案。
- **Observer 与消息队列**：都可呈现发布订阅，但持久化、确认、顺序、重试和跨进程语义不同。
- **Singleton**：进程内唯一实例不等于业务全局唯一；共享可变状态会增加测试和并发风险。
- **DRY**：重复两段看似相似但变化原因不同的代码，强行抽象会形成错误耦合。

### 四、如何回答“为什么用这个模式”

面试中应按四步回答：具体问题是什么；哪些变化需要隔离；模式如何改变依赖；不用它或使用更复杂替代方案会付出什么成本。例如 Strategy 适合多个算法在运行时替换，若算法固定且只有一个实现，引入接口层反而过度设计。

### 五、设计审查清单

1. 模块是否有清晰职责和变化原因。
2. 依赖是否从易变细节指向稳定抽象。
3. 抽象是否已有至少两个真实用例或明确变化证据。
4. 数据一致性、错误和资源边界是否清楚。
5. 测试能否通过公开契约验证行为。
6. 新增间接层是否降低了总体认知成本。

### 六、从变化轴选择设计

先识别哪些内容经常变化、哪些必须稳定。支付渠道增加而结算流程稳定时可用 Strategy；第三方接口变化而领域模型稳定时可用 Adapter；复杂构建需要维护不变量时可考虑 Factory/Builder。只有一个实现且变化概率低时，直接函数往往更好，接口和对象跳转本身也是成本。

### 七、SOLID 的反教条解释

- 单一职责指`主要变化原因`，不是一个类只能有一个方法；
- 开闭原则追求`稳定扩展点`，不是旧代码永不修改；
- 里氏替换要求`前置条件不变强`、`后置条件不变弱`和`不变量保持`。
- 接口过细会增加组合成本，依赖注入只是依赖反转的手段之一。

### 八、耦合、内聚与局部性

把一次业务规则拆到多个服务、事件和配置，源码依赖可能下降，但理解成本可能上升。耦合还包括数据、时间、运行时和组织耦合。消息队列降低同步时间耦合，却增加契约、顺序、重试、幂等和最终一致性问题。

### 九、DDD 与架构边界

限界上下文允许同一术语在不同业务边界拥有不同模型；聚合保护一致性边界，不是把相关表都塞进巨大对象。简单 CRUD 套完整 DDD 可能过度设计。Repository 接口位置取决于契约所有权和依赖方向，不取决于唯一目录命名。

### 十、用变更场景验收设计

提出新增实现、修改规则、替换基础设施三个真实变化，检查影响模块、公共契约、局部测试和迁移风险；再用一个低概率变化检查是否过早抽象。设计质量由真实变更成本、回归缺陷和维护者理解时间验证，不由模式数量验证。

### 十一、案例：从条件分支到 Strategy

当计价模块只有固定的一种算法时，一个清晰函数足够。随着企业价、区域价和促销价出现，而且它们独立发布、需要分别测试，巨大的条件分支开始产生共同变化压力，此时把算法抽成 Strategy 能隔离选择与实现。若又把每个两行公式拆成多层工厂和注册中心，则可能过度设计。

### 十二、案例：Observer 不等于消息队列

进程内 UI 状态变更通知可用 Observer，调用通常同步、失败由当前进程处理。订单事件跨服务传播时，需要持久化、确认、重试、幂等、顺序和死信，这些是消息基础设施的语义。二者都有“发布—订阅”外形，但替换时必须补齐可靠性契约。

### 十三、面试追问回答框架

被问“你用过什么模式”时，不先背定义，而是说明当时的变化点、原设计的具体痛点、采用模式后依赖如何改变、付出的复杂度、以及后来如何通过测试或变更验证。能说明某次没有使用模式的理由，同样体现设计判断。

## 高频使用的 GoF 设计模式精讲（附代码示例）

GoF 的 23 种设计模式中，以下 7–8 种在实际项目中出现频率极高。掌握它们不仅能让代码更灵活、可维护，还能提升你理解框架源码的能力。下面逐一讲解其核心意图、适用场景、解决的问题，并附上精简的 Java 代码示例。

---

### 1. 工厂模式（Factory Method）

**意图**：定义一个创建对象的接口，但由子类决定实例化哪一个具体类。工厂方法让类的实例化延迟到子类。

**解决的问题**：当客户端不知道应该创建哪个具体类，或者创建逻辑复杂、易变时，将创建过程封装起来，降低耦合。

**适用场景**：日志记录器（不同环境输出到文件/控制台）、数据库连接（不同数据库）、支付渠道（微信/支付宝）等。
```
// 产品接口
interface Product {
    void use();
}

// 具体产品 A
class ProductA implements Product {
    @Override
    public void use() { System.out.println("Using Product A"); }
}

// 具体产品 B
class ProductB implements Product {
    @Override
    public void use() { System.out.println("Using Product B"); }
}

// 抽象工厂
abstract class Factory {
    public abstract Product createProduct();
}

// 具体工厂 A
class FactoryA extends Factory {
    @Override
    public Product createProduct() { return new ProductA(); }
}

// 具体工厂 B
class FactoryB extends Factory {
    @Override
    public Product createProduct() { return new ProductB(); }
}

// 客户端
public class Client {
    public static void main(String[] args) {
        Factory factory = new FactoryA();
        Product p = factory.createProduct();
        p.use(); // Using Product A
    }
}
```

### 2. 单例模式（Singleton）

**意图**：确保一个类只有一个实例，并提供一个全局访问点。

**解决的问题**：全局共享资源（如配置管理、连接池、日志管理器）需要唯一实例，避免重复创建造成资源浪费或状态不一致。

**适用场景**：Spring 中的 Bean 默认单例、Runtime 类、数据库连接池。
```
// 懒汉式（双重检查锁，线程安全）
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {} // 私有构造

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

// 枚举式（最简洁，线程安全，防止反序列化）
public enum SingletonEnum {
    INSTANCE;
    public void doSomething() { /* ... */ }
}
```

### 3. 策略模式（Strategy）

**意图**：定义一系列算法，将每个算法封装起来，并使它们可以相互替换。策略模式让算法独立于使用它的客户端而变化。

**解决的问题**：避免大量 if-else 或 switch 分支，将不同行为抽取为独立的策略，便于扩展和维护。

**适用场景**：支付方式（信用卡、PayPal）、优惠计算、排序算法、出行方式（飞机、火车）等。
```
// 策略接口
interface PaymentStrategy {
    void pay(int amount);
}

// 具体策略：信用卡支付
class CreditCardPayment implements PaymentStrategy {
    private String cardNumber;
    public CreditCardPayment(String cardNumber) { this.cardNumber = cardNumber; }
    @Override
    public void pay(int amount) {
        System.out.println("Paid " + amount + " using credit card " + cardNumber);
    }
}

// 具体策略：PayPal支付
class PayPalPayment implements PaymentStrategy {
    private String email;
    public PayPalPayment(String email) { this.email = email; }
    @Override
    public void pay(int amount) {
        System.out.println("Paid " + amount + " using PayPal account " + email);
    }
}

// 上下文
class ShoppingCart {
    private PaymentStrategy paymentStrategy;
    public void setPaymentStrategy(PaymentStrategy strategy) {
        this.paymentStrategy = strategy;
    }
    public void checkout(int amount) {
        paymentStrategy.pay(amount);
    }
}

// 客户端
public class Client {
    public static void main(String[] args) {
        ShoppingCart cart = new ShoppingCart();
        cart.setPaymentStrategy(new CreditCardPayment("1234-5678"));
        cart.checkout(100);
    }
}
```

### 4. 观察者模式（Observer）

**意图**：定义对象间的一对多依赖关系，当一个对象状态改变时，所有依赖它的对象都会得到通知并自动更新。

**解决的问题**：需要解耦事件发布者和订阅者，支持广播通信。

**适用场景**：事件监听（GUI 按钮点击）、消息队列订阅、MVC 中的 Model-View 同步、股票价格更新。
```
import java.util.ArrayList;
import java.util.List;

// 观察者接口
interface Observer {
    void update(String message);
}

// 具体观察者
class User implements Observer {
    private String name;
    public User(String name) { this.name = name; }
    @Override
    public void update(String message) {
        System.out.println(name + " received: " + message);
    }
}

// 被观察者（主题）
class NewsAgency {
    private List<Observer> observers = new ArrayList<>();
    private String news;

    public void addObserver(Observer o) { observers.add(o); }
    public void removeObserver(Observer o) { observers.remove(o); }

    public void setNews(String news) {
        this.news = news;
        notifyObservers();
    }

    private void notifyObservers() {
        for (Observer o : observers) {
            o.update(news);
        }
    }
}

// 客户端
public class Client {
    public static void main(String[] args) {
        NewsAgency agency = new NewsAgency();
        User alice = new User("Alice");
        User bob = new User("Bob");
        agency.addObserver(alice);
        agency.addObserver(bob);
        agency.setNews("Breaking: Java 21 released!");
        // 输出：
        // Alice received: Breaking: Java 21 released!
        // Bob received: Breaking: Java 21 released!
    }
}
```

### 5. 装饰器模式（Decorator）

**意图**：动态地给一个对象添加一些额外的职责。就增加功能而言，装饰器比生成子类更为灵活。

**解决的问题**：避免为每种扩展组合都创建子类，导致类爆炸；支持运行时组合功能。

**适用场景**：Java I/O（BufferedInputStream 装饰 FileInputStream）、UI 组件添加边框/滚动条、日志增强（添加时间戳或加密）。
```
// 组件接口
interface Coffee {
    String getDescription();
    double getCost();
}

// 具体组件
class SimpleCoffee implements Coffee {
    @Override
    public String getDescription() { return "Simple coffee"; }
    @Override
    public double getCost() { return 5.0; }
}

// 装饰器抽象类
abstract class CoffeeDecorator implements Coffee {
    protected Coffee decoratedCoffee;
    public CoffeeDecorator(Coffee coffee) { this.decoratedCoffee = coffee; }
    @Override
    public String getDescription() { return decoratedCoffee.getDescription(); }
    @Override
    public double getCost() { return decoratedCoffee.getCost(); }
}

// 具体装饰器：加牛奶
class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) { super(coffee); }
    @Override
    public String getDescription() { return decoratedCoffee.getDescription() + ", milk"; }
    @Override
    public double getCost() { return decoratedCoffee.getCost() + 1.5; }
}

// 具体装饰器：加糖
class SugarDecorator extends CoffeeDecorator {
    public SugarDecorator(Coffee coffee) { super(coffee); }
    @Override
    public String getDescription() { return decoratedCoffee.getDescription() + ", sugar"; }
    @Override
    public double getCost() { return decoratedCoffee.getCost() + 0.5; }
}

// 客户端
public class Client {
    public static void main(String[] args) {
        Coffee coffee = new SimpleCoffee();
        coffee = new MilkDecorator(coffee);
        coffee = new SugarDecorator(coffee);
        System.out.println(coffee.getDescription() + " costs $" + coffee.getCost());
        // 输出: Simple coffee, milk, sugar costs $7.0
    }
}
```

### 6. 代理模式（Proxy）

**意图**：为另一个对象提供一个替身或占位符以控制对这个对象的访问。

**解决的问题**：控制访问权限（保护代理）、延迟加载（虚拟代理）、缓存结果（缓存代理）、远程访问（远程代理）。

**适用场景**：Spring AOP 动态代理、Hibernate 延迟加载、权限校验、日志记录。
```
// 真实主题接口
interface Image {
    void display();
}

// 真实主题：高分辨率图片
class HighResolutionImage implements Image {
    private String fileName;
    public HighResolutionImage(String fileName) {
        this.fileName = fileName;
        loadFromDisk();
    }
    private void loadFromDisk() { System.out.println("Loading " + fileName); }
    @Override
    public void display() { System.out.println("Displaying " + fileName); }
}

// 代理：延迟加载
class ImageProxy implements Image {
    private HighResolutionImage realImage;
    private String fileName;
    public ImageProxy(String fileName) { this.fileName = fileName; }
    @Override
    public void display() {
        if (realImage == null) {
            realImage = new HighResolutionImage(fileName); // 第一次访问时才加载
        }
        realImage.display();
    }
}

// 客户端
public class Client {
    public static void main(String[] args) {
        Image image = new ImageProxy("photo.jpg");
        // 此时并未真正加载图片
        image.display(); // 这里才加载并显示
    }
}
```

### 7. 适配器模式（Adapter）

**意图**：将一个类的接口转换成客户希望的另一个接口。适配器使原本接口不兼容的类可以一起工作。

**解决的问题**：系统需要使用已有的类，但它的接口不符合系统需求；或者需要复用第三方库但接口不匹配。

**适用场景**：不同日志框架的适配（SLF4J）、不同数据库驱动适配、电源适配器（不同电压/插头）、新旧 API 转换。
```
// 已有系统（不兼容）
class LegacyPrinter {
    public void printOld(String text) {
        System.out.println("Legacy printing: " + text);
    }
}

// 目标接口
interface Printer {
    void print(String text);
}

// 适配器
class PrinterAdapter implements Printer {
    private LegacyPrinter legacy;
    public PrinterAdapter(LegacyPrinter legacy) { this.legacy = legacy; }
    @Override
    public void print(String text) {
        // 转换调用
        legacy.printOld(text);
    }
}

// 客户端使用目标接口
public class Client {
    public static void main(String[] args) {
        LegacyPrinter legacy = new LegacyPrinter();
        Printer printer = new PrinterAdapter(legacy);
        printer.print("Hello Adapter!"); // 输出: Legacy printing: Hello Adapter!
    }
}
```

---

### 补充：抽象工厂 vs 工厂方法

工厂方法通常用于创建单一产品，而抽象工厂用于创建产品族。如果你遇到创建相关或依赖对象家族的需求（如不同操作系统的 UI 控件），可进一步学习抽象工厂。

---

### 总结


| **模式**  | **一句话核心作用**        |
| :------- | :------------------ |
| **工厂**  | 封装对象创建，延迟到子类       |
| **单例**  | 保证全局唯一实例           |
| **策略**  | 封装可互换的算法           |
| **观察者** | 状态变化时通知所有依赖者       |
| **装饰器** | 动态叠加功能，避免子类泛滥      |
| **代理**  | 控制对对象的访问（延迟、权限、缓存） |
| **适配器** | 让接口不兼容的类协同工作       |

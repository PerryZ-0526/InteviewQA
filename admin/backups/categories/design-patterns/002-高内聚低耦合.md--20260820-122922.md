## 面试直接答

> 高内聚与低耦合是评价模块划分质量的两个核心维度：内聚度量一个模块内部各元素围绕单一目标聚集的紧密程度，耦合度量模块之间相互依赖的强度。核心机制是通过职责分配与依赖控制，让一起变化的代码放在一起、变化原因不同的代码相互隔离，从而降低需求变更的波及面与修改成本。它的适用边界在于：解耦本身要付出间接层成本，对稳定不变、性能敏感的代码不应机械套用。

先看内聚。内聚描述模块内部元素联系的紧密程度，回答的问题是「这个类或函数里的代码，是不是在共同完成同一件事」。结构化设计理论把内聚从低到高分为七层：偶然内聚、逻辑内聚、时间内聚、过程内聚、通信内聚、顺序内聚和功能内聚，其中功能内聚是理想状态——一个模块只完整地承担一项职责。低内聚最典型的形态是「上帝类」：一个类既解析订单又算折扣、既存数据库又发邮件，表面上省了几个类，实际上任何一处需求变更都会牵动整个类，测试时也无法隔离无关逻辑。判断内聚有一个实用的「一句话测试」：如果描述模块用途必须用「和」「以及」连接多个动词，说明内聚有问题。

再看耦合。耦合描述模块之间相互依赖的紧密程度，按强度从高到低分为内容耦合、公共耦合、外部耦合、控制耦合、标记耦合和数据耦合。内容耦合指一个模块直接读写另一个模块的内部数据；公共耦合指多个模块共享全局可变状态；控制耦合指调用方通过传 flag 指挥被调方的执行路径；数据耦合则只通过参数传递最小必要的基础数据，是经典分类中最理想的一档。高耦合的典型症状是：改一个字段十几个类跟着编译报错，想复用一个函数必须连带着搬走半个系统。需要强调的是，低耦合不等于零耦合，模块之间完全不交互就组不成系统，关键是让依赖发生在稳定的抽象契约上，而不是易变的实现细节上。

这两个维度直接决定软件的修改成本。高内聚让一个变化原因只落在一个模块里，改动范围小、回归风险低；低耦合让模块可以独立编译、独立测试、独立部署、独立复用。工程上它们还直接对应可测试性——紧耦合的代码无法把依赖替换成测试替身，单元测试根本写不出来，这正是依赖注入成为现代框架基础设施的原因。值得注意的是两者高度相关但不完全等同：一个功能单一的大模块可能被所有人依赖，形成高内聚高耦合；一个被拆得过碎的模块群则可能低耦合但散沙般低内聚，理解成本反而上升。

落到实践上，提高内聚的主要手段是单一职责原则，判断标准是「这个类是否只有一个引起它变化的原因」；降低耦合的主要手段是依赖倒置与接口隔离，让模块只依赖抽象而不依赖具体实现，再配合分层架构、领域事件、消息队列等更粗粒度的边界控制。但两者存在张力：拆得越细，模块间的交互协议越复杂，接口、事件、配置本身就是新型耦合。微服务把代码级耦合换成了网络级的契约耦合，还引入了分布式事务和数据一致性等新成本，所以拆分粒度要按业务边界和变化频度来决定，而不是越细越好。

总结来说，高内聚低耦合是手段而不是目的，最终目标是让软件在面对持续变化时保持低修改成本。判断设计好坏要看真实的变化场景：频繁一起修改的代码应该放得近，变化节奏不同的代码应该分开；如果一个抽象只有一个实现、一个解耦点从未发生过替换，它很可能只是无用的间接层，反而应该合并回去。

### 通俗版：用生活场景快速理解

把软件系统想象成一栋房子。高内聚就是「专业的人干专业的事」：电工只负责电路，水管工只负责管道，工种内部的所有技能都服务于同一件事，出了问题知道该找谁。低内聚就像一个人什么都会一点——既做设计又敲代码还兼做运维，看起来全能，实际上任何一个环节出问题都得找他，他也最容易成为瓶颈。

低耦合则像标准的接口协议：电器不需要知道发电厂怎么运转，只要墙上的插座提供 220V 标准接口，换任何品牌的电器、换任何一家供电公司，都不影响对方。高耦合就像电器内部零件被焊死——换个灯泡必须拆开整面墙重新装修。

两个概念合起来，就是把系统设计成一盒乐高：每块积木自身形状完整（高内聚），积木之间只通过标准的卡扣连接（低耦合），哪块坏了换哪块，还能自由拼出新造型。但也要记住类比的反面：如果为了一次性小工具也拆出几百块积木，拼装说明书本身就比产品更复杂了——解耦过头同样是问题。

## 详细解析

### 一、内聚的七个层次

内聚的经典七层分类出自 Stevens、Myers 与 Constantine 1974 年发表于 IBM Systems Journal 的论文《Structured Design》（1979 年收录进 Yourdon &amp; Constantine 的同名著作）。七层从低到高：


| 层次   | 定义                  | 一句话特征                | 评价         |
| ---- | ------------------- | -------------------- | ---------- |
| 偶然内聚 | 元素之间没有实质关联，只是碰巧放在一起 | 无法用一句话描述模块用途         | 最差，应避免     |
| 逻辑内聚 | 逻辑上同类但功能不同，靠参数选择执行  | 传个 type 参数干不同的事      | 差，是控制耦合的温床 |
| 时间内聚 | 只因在同一时刻执行而放在一起      | initialize / cleanup | 可接受于生命周期边界 |
| 过程内聚 | 按固定执行顺序串起来，数据无关联    | 步骤 A→B→C             | 弱，难以复用     |
| 通信内聚 | 多个动作操作同一份数据         | 都围绕同一个对象             | 中等，可接受     |
| 顺序内聚 | 前一步的输出是后一步的输入       | 流水线                  | 较好         |
| 功能内聚 | 所有元素为完成单一功能而存在      | 一句话能说清               | 理想目标       |


**偶然内聚**——方法之间毫无关联，只因「都是杂项」被塞进同一个类：
```
// 偶然内聚：三个方法没有任何共享数据和共同目标
public class MiscUtils {
    public static String maskPhone(String phone) {
        return phone.replaceAll("(\\d{3})\\d{4}(\\d{4})", "$1****$2");
    }

    public static int fib(int n) {
        if (n <= 1) return n;
        return fib(n - 1) + fib(n - 2);
    }

    public static double parsePrice(String s) {
        return Double.parseDouble(s.replace(",", ""));
    }
}
// 症状：任何团队都在改这个类，git blame 密密麻麻，测试也要一起跑
```

**逻辑内聚**——逻辑上「都叫解析」，实际是完全不同的功能，靠参数分派：
```
// 逻辑内聚：看似一类，实为多类，调用方必须知道内部支持哪些 type
public class FileParser {
    public Object parse(String type, String content) {
        if ("csv".equals(type)) {
            return content.split(",");
        } else if ("json".equals(type)) {
            return parseJson(content);
        } else if ("xml".equals(type)) {
            return parseXml(content);
        }
        throw new IllegalArgumentException("unknown type: " + type);
    }

    private Object parseJson(String c) { /* ... */ }
    private Object parseXml(String c) { /* ... */ }
}
// 改进方向：按格式拆成三个类，用策略模式分派（见 001 题策略模式示例）
```

**时间内聚**——只因「启动那一刻都要执行」而放在一起：
```
// 时间内聚：数据上毫无关联，只共享执行时机
public class AppBootstrap {
    public void startup() {
        loadConfig();            // 读配置文件
        openDatabasePool();      // 建连接池
        startScheduledTasks();   // 起定时任务
        registerShutdownHook();  // 挂退出钩子
    }
    // 四个方法互不调用、互不共享数据
}
// 评价：生命周期边界（启动/清理）天然是时间内聚，不必强拆
```

**过程内聚**——按固定流程顺序执行，但步骤之间没有数据流动：
```
// 过程内聚：步骤只是"碰巧按这个顺序做"
public class ReportRunner {
    public void run() {
        checkPermission();   // 产出的"能否执行"没人接收
        fetchReportData();   // 与上一步无数据依赖
        formatHtml();        // 与上一步无数据依赖
    }
}
```

**通信内聚**——多个动作围绕同一份数据展开：
```
// 通信内聚：都读 order，但各干各的事
public class OrderValidator {
    public List<String> validate(Order order) {
        List<String> errors = new ArrayList<>();
        checkAmount(order, errors);
        checkAddress(order, errors);
        checkStock(order, errors);
        return errors;
    }
}
```

**顺序内聚**——上一步的输出是下一步的输入，天然流水线：
```
// 顺序内聚：数据依次流过三个环节
public class ImportPipeline {
    public List<RawRow> parse(String csv) { /* String -> RawRow */ }

    public List<CleanRow> clean(List<RawRow> rows) { /* RawRow -> CleanRow */ }

    public int persist(List<CleanRow> rows) { /* CleanRow -> 数据库行数 */ }

    public int run(String csv) {
        return persist(clean(parse(csv)));
    }
}
```

**功能内聚**——只做一件事，而且这件事完整，能通过「一句话测试」：
```
// 功能内聚：一句话说清——根据订单计算最终应付金额
public class OrderPricing {
    public BigDecimal calculate(Order order) {
        BigDecimal subtotal = BigDecimal.ZERO;
        for (Item item : order.getItems()) {
            subtotal = subtotal.add(
                    item.getPrice().multiply(BigDecimal.valueOf(item.getQty())));
        }
        return subtotal.add(shippingFee(order)).subtract(discount(order));
    }

    private BigDecimal shippingFee(Order order) { /* ... */ }
    private BigDecimal discount(Order order) { /* ... */ }
}
```

一句话测试（sentence test）是识别内聚层次的实用技巧：描述模块用途时，句子出现「和」「以及」等多个动词，多半是通信或顺序内聚；出现「首先」「然后」「当……时」等时间词，多半是顺序或时间内聚；谓语对象含糊（如「处理所有数据」），多半是逻辑内聚。

### 二、耦合的类型

耦合分类与内聚同源，出自同一篇《Structured Design》。从强到弱：


| 类型   | 强度  | 特征                  | 典型表现                |
| ---- | --- | ------------------- | ------------------- |
| 内容耦合 | 最强  | 直接访问、修改对方内部数据或代码    | 改对方的字段、跳进对方的代码      |
| 公共耦合 | 强   | 共享全局可变状态            | static 全局变量、全局单例状态  |
| 外部耦合 | 中强  | 双方共同依赖外部强加的格式/协议/设备 | 都依赖同一第三方接口契约        |
| 控制耦合 | 中   | 传 flag 指挥对方走哪条分支    | process(type)       |
| 标记耦合 | 较弱  | 传整个大对象却只用一两个字段      | 传 Order 只取 amount   |
| 数据耦合 | 弱   | 只传最小必要的基础数据         | 传 BigDecimal amount |


**内容耦合**——一个模块直接伸手改另一个模块的内部数据：
```
// 内容耦合：绕过了 Order 的所有封装和规则
public class Order {
    public BigDecimal total;             // 内部状态裸露
}

public class DiscountEngine {
    public void apply(Order order) {
        order.total = order.total.multiply(new BigDecimal("0.8"));
    }
}
// Java 里表现为 public 字段，C++ 里表现为 friend，还有通过反射强改 private 的做法
```

**公共耦合**——多个模块共享同一份全局可变状态：
```
// 公共耦合：谁都能读、谁都能改
public class GlobalConfig {
    public static volatile String currentLanguage = "zh-CN";
}

public class ReportService {
    public String title() {
        return "zh-CN".equals(GlobalConfig.currentLanguage) ? "日报" : "Daily Report";
    }
}

public class SettingsPage {
    public void switchTo(String lang) {
        GlobalConfig.currentLanguage = lang;
    }
}
// 症状：并发下 bug 难复现，单元测试之间要通过全局状态互相隔离
```

**控制耦合**——调用方传 flag 指挥被调方走哪条分支：
```
// 控制耦合：调用方必须背下编号语义，新增渠道必须改被调方
public class Notifier {
    public static final int SMS = 1;
    public static final int EMAIL = 2;
    public static final int PUSH = 3;

    public void notify(int channel, String message) {
        if (channel == SMS) sendSms(message);
        else if (channel == EMAIL) sendEmail(message);
        else if (channel == PUSH) sendPush(message);
    }
}
```

**标记耦合**——为了一个小数，把整个大对象传进去：
```
// 标记耦合：实际只用 order.getAmount() 一个字段
public class TaxCalculator {
    public BigDecimal calculate(Order order) {
        return order.getAmount().multiply(new BigDecimal("0.13"));
    }
}
// 问题：Order 任何一个无关字段变化都可能波及这里，测试还要构造整个 Order
```

**数据耦合**——只传最小必要的基础数据：
```
// 数据耦合：依赖面最小，测试只需一个数值
public class TaxCalculator {
    public BigDecimal calculate(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.13"));
    }
}
// 调用方：tax.calculate(order.getAmount())
```

### 三、重构实战：上帝类 → 高内聚低耦合

先看重构前的上帝类——同时承担六种职责，既是低内聚，也是高耦合：
```
// 重构前：解析/校验/计价/存库/邮件/日志全包
public class OrderProcessor {

    public void handle(String json) throws Exception {
        // 职责1：解析 JSON
        ObjectMapper mapper = new ObjectMapper();
        Order order = mapper.readValue(json, Order.class);

        // 职责2：校验（业务规则硬编码在这里）
        if (order.getAmount() == null || order.getAmount().signum() <= 0) {
            throw new IllegalArgumentException("非法金额: " + order.getAmount());
        }

        // 职责3：计价
        BigDecimal total = order.getAmount().multiply(new BigDecimal("1.13"));

        // 职责4：存库（连接串、SQL 全部内嵌）
        try (Connection conn = DriverManager.getConnection(
                "jdbc:mysql://localhost:3306/shop", "root", "123456")) {
            PreparedStatement ps = conn.prepareStatement(
                    "INSERT INTO orders(id, amount, total) VALUES(?, ?, ?)");
            ps.setLong(1, order.getId());
            ps.setBigDecimal(2, order.getAmount());
            ps.setBigDecimal(3, total);
            ps.executeUpdate();
        }

        // 职责5：发邮件（SMTP 细节内嵌）
        SmtpClient smtp = new SmtpClient("smtp.example.com", 25);
        smtp.send("user@example.com", "订单已创建: " + order.getId());

        // 职责6：打日志
        System.out.println("order created: " + order.getId());
    }
}
// 一个变化全部遭殃：换短信渠道要改它，表结构变了要改它，校验规则变了还要改它
```

依赖结构一目了然——一个模块直接钉死在所有外部细节上：
```
重构前：一个模块直接钉死在所有细节上
        ┌───────────────────────────────┐
        │         OrderProcessor        │
        │ 解析/校验/计价/存库/邮件/日志    │
        └──┬──────┬──────┬──────┬───────┘
           │      │      │      │
         MySQL  SMTP  控制台   JSON库      ← 每换一个外部依赖都要改处理类
```

重构后，每类只干一件事（高内聚），依赖只指向接口（低耦合）：
```
// 重构后：职责各自成类，依赖全部指向抽象

// —— 领域层：稳定的抽象契约，只描述"做什么" ——
public interface OrderRepository {
    void save(Order order);
}

public interface Notifier {
    void notifyOrderCreated(Order order);
}

// 功能内聚：只负责算钱
public class PricingService {
    public BigDecimal price(Order order) {
        return order.getAmount().multiply(new BigDecimal("1.13"));
    }
}

// —— 应用层：只做编排，不干具体活 ——
public class OrderService {
    private final PricingService pricing;
    private final OrderRepository repository;
    private final Notifier notifier;

    // 构造注入：依赖显式可见，替换实现只需换构造参数
    public OrderService(PricingService pricing,
                        OrderRepository repository,
                        Notifier notifier) {
        this.pricing = pricing;
        this.repository = repository;
        this.notifier = notifier;
    }

    public void create(Order order) {
        if (order.getAmount() == null || order.getAmount().signum() <= 0) {
            throw new IllegalArgumentException("非法金额: " + order.getAmount());
        }
        order.setTotal(pricing.price(order));
        repository.save(order);
        notifier.notifyOrderCreated(order);
    }
}

// —— 基础设施层：具体实现，可以整块替换 ——
public class MysqlOrderRepository implements OrderRepository {
    @Override
    public void save(Order order) {
        // JDBC 细节全部收敛在这里，换 H2/PostgreSQL 不影响任何调用方
    }
}

public class EmailNotifier implements Notifier {
    @Override
    public void notifyOrderCreated(Order order) {
        // SMTP 细节全部收敛在这里，换短信/站内信不影响任何调用方
    }
}
```
```
重构后：依赖只指向接口，实现藏在边界外
                 OrderService
                     │ 依赖接口
        ┌────────────┼────────────┐
        ▼            ▼            ▼
  OrderRepository  Notifier   PricingService
        ▲            ▲
        │ 实现        │ 实现
  MysqlOrderRepo  EmailNotifier
  H2OrderRepo     SmsNotifier      ← 测试替身 / 新渠道随时可插拔
```

低耦合最直接的收益是**可测试性**——单元测试可以用替身隔离所有外部依赖：
```
// 单元测试：不碰 MySQL，也不发真邮件
public class OrderServiceTest {

    @Test
    public void create_savesAndNotifies() {
        OrderRepository fakeRepo = new InMemoryOrderRepository();
        List<Order> notified = new ArrayList<>();
        Notifier fakeNotifier = notified::add;

        OrderService service =
                new OrderService(new PricingService(), fakeRepo, fakeNotifier);

        Order order = new Order();
        order.setId(1L);
        order.setAmount(new BigDecimal("100"));
        service.create(order);

        assertEquals(new BigDecimal("113"), order.getTotal());
        assertEquals(1, fakeRepo.count());
        assertEquals(1, notified.size());
    }
}
```

对比重构前的版本：想测 `handle` 必须先起一个 MySQL、一个 SMTP 服务器，然后解析控制台输出才能断言——这正是高耦合对工程效率的真实伤害。这道题的姊妹篇 [001-高质量代码与工程级代码](../engineering-practice/001-%E9%AB%98%E8%B4%A8%E9%87%8F%E4%BB%A3%E7%A0%81%E4%B8%8E%E5%B7%A5%E7%A8%8B%E7%BA%A7%E4%BB%A3%E7%A0%81.md) 也从六个质量维度讨论过这个主题。

### 四、框架里的体现：以 Spring 为例

依赖注入方式本身就是耦合强度的选择。字段注入隐藏了依赖，让类在脱离容器后仍然可以 `new` 出来但不工作：
```
// 反例：字段注入——依赖被框架偷偷塞进来
@Service
public class OrderService {
    @Autowired
    private OrderRepository repository;
}

// 正例：构造注入——依赖在编译期显式可见，测试时手动 new 就能传替身
@Service
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {  // 单构造器可省略 @Autowired
        this.repository = repository;
    }
}
```

更粗粒度的解耦是领域事件——发布方不知道、也不关心谁在监听，新增订阅者无需改动发布方：
```
// 时间/空间解耦：发布方只发事件，不管消费
@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public OrderService(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void create(Order order) {
        repository.save(order);
        publisher.publishEvent(new OrderCreatedEvent(order));
    }
}

// 新增"下单发优惠券"模块时，OrderService 一行都不用改
@Component
public class CouponListener {
    @EventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        couponService.grant(event.getOrder().getUserId());
    }
}
```

### 五、如何度量：LCOM、CBO 与 ArchUnit

内聚和耦合都有可计算的指标。**LCOM**（Lack of Cohesion in Methods，方法缺乏内聚度）统计类中不共享字段的方法对数量，方法对越分散说明类内聚越低；**CBO**（Coupling Between Objects，对象间耦合度）统计一个类依赖的其他类的个数。工具层面，SonarQube、JDepend、IntelliJ 的依赖结构矩阵都能输出这些指标。

比事后看指标更进一步的做法，是把「高内聚低耦合」写成 CI 可执行的架构测试——ArchUnit 是 Java 生态最常用的方案：
```
// ArchUnit：把设计约束写进测试，随构建一起执行
@AnalyzeClasses(packages = "com.example.shop")
public class ArchitectureRulesTest {

    // 1. 禁止包间循环依赖（模块级低耦合）
    @ArchTest
    static final ArchRule no_cycles =
            slices().matching("com.example.shop.(*)..").should().beFreeOfCycles();

    // 2. 依赖只允许指向内层：领域层不依赖任何基础设施
    @ArchTest
    static final ArchRule domain_isolated =
            noClasses().that().resideInAPackage("..domain..")
                    .should().dependOnClassesThat()
                    .resideInAnyPackage("..infrastructure..", "..web..");

    // 3. 经典分层：Controller -> Service -> Repository，不许跳层
    @ArchTest
    static final ArchRule layers =
            layeredArchitecture()
                    .layer("Controller").definedBy("..controller..")
                    .layer("Service").definedBy("..service..")
                    .layer("Repository").definedBy("..repository..")
                    .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
                    .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
                    .whereLayer("Repository").mayOnlyBeAccessedByLayers("Service");
}
```

### 六、面试追问

**追问 1：内聚高就一定耦合低吗？**

不一定，两个维度相关但独立。一个功能单一的大模块若被所有其他模块直接依赖（典型的「公共工具包」「核心大对象」），就是高内聚高耦合；反之，把系统拆成一堆彼此无关的散沙类，会得到低耦合低内聚，理解成本反而上升。GRASP 之所以把 Low Coupling 和 High Cohesion 列为两个独立的职责分配模式，正是因为两者需要分别评估。

**追问 2：耦合是不是越低越好？什么场景下可以接受高耦合？**

不是。判断标准是「依赖双方会不会各自独立变化」。不会独立变化的强依赖没必要解耦：聚合根内部的实体共享可变状态（DDD 的聚合边界内）、语言内置类、成熟稳定的标准库，都是合理的高耦合。反过来，为想象中的变化解耦是过度设计——一个接口只有一个实现、从未发生过替换，就该把间接层删掉。性能敏感的热路径上，解耦引入的虚调用和间接层也是真实成本。

**追问 3：控制耦合传 flag 不好，那策略模式、命令模式不也在传控制信息吗？**

区别在于控制信息是否泄露实现细节。控制耦合传递的是裸开关——调用方必须理解被调方内部的编号语义，新增分支必须修改被调方；策略和命令模式把控制信息提升为对象，选择逻辑封装在类型系统里，调用方只依赖抽象接口，新增分支只需新增实现类。同样是「让被调方做不同的事」，前者把分派逻辑留在被调方内部，后者把分派逻辑外移给了多态。

**追问 4：微服务把系统拆小，是不是就自动实现高内聚低耦合了？**

不是。微服务只是把进程内耦合换成了网络契约耦合：接口从方法签名变成 HTTP/gRPC 协议，还要额外支付序列化、网络延迟、超时重试、分布式事务、服务发现等成本。拆分不当会得到「分布式单体」——服务之间频繁同步调用、共享数据库，耦合度反而更高。正确做法是按限界上下文（业务内聚）和团队边界拆，而不是按技术层拆；这也正是 Conway 定律的推论：系统结构最终会镜像组织结构。

**追问 5：高内聚低耦合和 DRY 原则冲突怎么办？**

冲突点在于：两段相似的代码，变化原因可能不同。此时强行 DRY 合并反而制造耦合——一处业务改动被迫兼容另一种场景，函数里长出 if/else 分支。原则是「先看变化原因，再决定是否复用」：变化原因相同就提取共享；变化原因不同就保留重复。业界那句「宁可复制粘贴，不要错误抽象」说的就是这种误合并。

**追问 6：LCOM、CBO 这些指标真的可信吗？怎么用工具卡指标？**

指标是指南而不是判决。LCOM 高的类值得人工看一眼，但可能是有意为之（如策略注册表）；指标能管住下限——架构腐化，却管不住上限——设计好坏最终要看真实变更成本。实践上建议分层使用：用 ArchUnit 把依赖方向和环依赖卡成硬规则，随 CI 每次构建执行；把 LCOM、CBO 当趋势信号做观察，变化异常时再人工介入。

## 详细解析

LangGraph 构建多智能体系统的核心范式，主要围绕 **“如何组织智能体之间的协作与决策流程”** 展开。目前，业界公认的三种经典范式是 **主管（Supervisor）模式**、**群组（Swarm）模式** 和 **层级（Hierarchical）模式**。此外，还有一些基于这些范式演变出的高级模式。

### **🧠 三大经典协作范式**

- **主管模式（Supervisor Pattern）**：由一个中央“主管”智能体负责接收任务、<span style="background-color: #fff3cd">分析并分发给最合适的专业智能体</span>。结构清晰、易于控制，适合有明确分工的层次化流程。LangGraph 提供了 `langgraph-supervisor` 包来快速实现。
- **群组模式（Swarm Pattern）**：采取`对等网络结构`，智能体完成任务后可直接将控制权“移交”给下一个。灵活性极高，适合开放式、动态变化的任务。LangGraph 官方提供了 `langgraph-swarm` 库支持。
  > <span style="color: rgb(15, 17, 21); font-size: 16px; background-color: rgb(255, 255, 255)">群组模式的核心在于</span>**将路由决策权下放给每个智能体**<span style="color: rgb(15, 17, 21); font-size: 16px; background-color: rgb(255, 255, 255)">，让系统在运行时动态决定协作路径，从而实现去中心化的灵活协作</span>
- **层级模式（Hierarchical Pattern）**：引入多层管理结构，顶层主管分解任务给中层，中层再协调基层执行。适合超大规模、需要多层抽象的企业级系统。LangGraph 可通过“图中有图”的子图机制实现。

### **🚀 高级与衍生范式**

- **路由器模式（Router Pattern）**：是主管模式的简化版，<u style="text-decoration-color: #e63946">由一个路由节点根据规则将任务**并行**分发给多个专用智能体</u>，最后汇总结果。适合需要并行处理的场景（如同时查询多个知识库）。
-  **规划-执行-聚合模式**：通过“规划器”生成步骤，由“执行器”完成，再由“聚合器”整合。适合需要详细规划的复杂任务。执行失败时可引入“重新规划器”动态调整计划。
- **辩论/对抗模式（Debate Pattern）**：让多个智能体扮演不同角色（如提出者、批判者）进行多轮讨论以达成共识。适合需要深度分析和事实核查的高风险决策。
- **网络模式（Network Pattern）**：允许智能体间多对多自由通信，形成网状拓扑。最灵活但复杂度最高，适合高度动态的协作。

### **💡 核心设计原则**

- **状态是真理**：所有通信通过**共享状态（State）** 进行，保证数据一致。
- **节点功能纯粹**：节点接收状态、执行逻辑、返回更新，不依赖外部变量。
- **善用Reducer**：多节点并行写入同一状态键时必须用 Reducer 合并，防止冲突。
- **从简开始**：能用单个智能体解决的，就别用复杂的多智能体系统。

选择哪种范式，取决于你的任务是需要**严格的层级控制**（选 Supervisor）、**灵活的同伴协作**（选 Swarm），还是**复杂的多层规划**（选 Hierarchical）。

## 结构图

### 1. 主管模式（Supervisor Pattern）—— 星型调度

**特点**<span style="color: rgb(15, 17, 21); font-size: 16px; background-color: rgb(255, 255, 255)">：所有请求必须经过中央“主管”，由它决定交由哪个专家处理，结果回流至主管后再输出。</span>
```
                       ┌─────────────────┐
                       │     用户输入     │
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │  主管智能体      │  <-- 全局上下文 & 决策路由
                       │  (Central Brain) │
                       └────────┬────────┘
                                │ 分发任务 (Assign)
              ┌─────────────────┼─────────────────┐
              │                 │                 │
              ▼                 ▼                 ▼
         ┌────────┐       ┌────────┐       ┌────────┐
         │ 专家A  │       │ 专家B  │       │ 专家C  │  <-- 各自执行子任务
         │(研究)  │       │(编码)  │       │(测试)  │
         └───┬────┘       └───┬────┘       └───┬────┘
              │                 │                 │
              └─────────────────┼─────────────────┘
                                │ 返回结果 (Return)
                                ▼
                       ┌─────────────────┐
                       │  主管智能体      │  <-- 聚合结果，决定下一步或结束
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │    最终输出      │
                       └─────────────────┘
```

              │                 │                 │

                                ▼
                       ┌─────────────────┐

                   │                         │
              不满足 (继续)              满足 (终止)
                   │                         │
                   │ (Loop Back)              │

                                     │    最终输出      │

### **🛑 循环退出的三种“终止条件”**

在代码中，主管节点必须显式输出一个 `next` **路由指令**。LangGraph 通过 `add_conditional_edges` 拦截该指令，决定是跳回循环还是走向 `END`。

实践中，终止条件分为以下三等：


| **终止等级**        | **判断逻辑**                                                           | **适用场景**                     |
| :--------------- | :------------------------------------------------------------------ | :---------------------------- |
| **1. 显式工具调用**   | 主管的 LLM 在输出中直接调用 `"FINISH"` 或 `"__END__"` 工具。                      | 最标准的做法，由大模型语义判断“我觉得搞定了”。     |
| **2. 轮次硬截断**    | 在 State 中维护一个 `step_count`，当 `step_count >= max_step`（如 5 轮）时强制终止。 | **必备安全兜底**，防止模型陷入死循环或无限自纠。   |
| **3. 状态键完整性检查** | 检查 State 中是否包含所有必需的字段（如 `result_A` 和 `result_B` 都存在）。              | 确定性极高的业务（如必须查完 3 个数据库才允许输出）。 |


### **🧠 最精妙的点：状态（State）的“累积汇总”而非“覆盖”**

你提到的“汇总结果”，在循环中并不是把旧结果丢掉，而是**不断累积**。

- **第一次循环**：主管派 A 写代码，State 变成 `{"code": "..."}`。
- **第二次循环**：主管派 B 审查代码，State 变成 `{"code": "...", "review": "..."}`（新增键，不变旧值）。
- **第三次循环**：主管发现审查不通过，派 A 修改代码，State 变成 `{"code": "修改后的新代码", "review": "...", "revision_history": [...]}`。

<u style="text-decoration-color: rgb(230, 57, 70)">主管每次读取的是**叠加后的完整 State**。这就决定了它的决策是动态的，可以执行“写 -&gt; 审 -&gt; 改 -&gt; 再审”这种复杂的迭代流程</u>，直到满足条件 2 或条件 3 才退出。

> **主管模式就是一个“主管拍板、专家干活、主管复查、不满意再派人”的闭环工坊，直到主管亲口说出“FINISH”为止。**

### **2. 群组模式（Swarm Pattern）——** `对等网络`

**特点**：没有中央管控，智能体之间对等连接。当前智能体完成任务后，将“控制权”和“上下文状态”直接移交给下一个智能体。

> #### **🤔 为什么说它是“动态”的**
>
> 群组模式的动态性体现在以下几个层面：
>
> 1. **移交决策者是智能体本身**：在群组模式中，**是智能体自己决定何时以及将任务移交给谁**。每个智能体都内置了 `handoff` 工具，它完成任务后可以自主调用，将控制权转给下一个最合适的专家。这是一个**运行时（Runtime）** 的动态决策。
> 2. **没有中心化的“大脑”**：主管模式依赖一个中央“主管”来统筹全局，这容易成为瓶颈。而群组模式是**去中心化**的，没有单一控制点，每个智能体都是对等的，共同协作解决问题。
> 3. **适应开放式问题**：群组模式尤其擅长处理<u style="text-decoration-color: rgb(230, 57, 70)">复杂、开放的问题</u>。由于执行路径不固定，它能更好地应对那些`最优解决路径无法事先预测的任务`。
```
                       ┌─────────────────┐
                       │     用户输入     │
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │   路由节点       │  <-- 仅负责启动初始智能体
                       └────────┬────────┘
                                ▼
          ┌─────────────────────────────────────────────┐
          │                                             │
          ▼                                             ▼
 ┌─────────────────┐     (自主handoff)     ┌─────────────────┐
 │   智能体 A      │ ──────────────────▶ │   智能体 B      │
 │  (当前活跃)     │                     │  (下一个活跃)    │
 └─────────────────┘                     └─────────────────┘
        │                                             │
        │ (自主handoff)                               │ (自主handoff)
        ▼                                             ▼
 ┌─────────────────┐                     ┌─────────────────┐
 │   智能体 C      │ ◀───────────────── │   智能体 D      │
 │  (下一个活跃)   │                     │  (下一个活跃)    │
 └─────────────────┘                     └─────────────────┘
        │
        ▼ (任务完成)
 ┌─────────────────┐
 │     结束         │
 └─────────────────┘
```

### **3. 层级模式（Hierarchical Pattern）—— 树状分解**

**特点**：多层管理。顶层做`宏观拆解`，中层做`微观调度`，<u style="text-decoration-color: rgb(230, 57, 70)">底层负责具体执行</u>。适合大规模复杂项目。
```
                       ┌─────────────────┐
                       │     用户输入     │
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │  顶层主管 (Root) │  <-- 拆解为若干大型子任务
                       └────────┬────────┘
                                │ 任务划分
                ┌───────────────┴───────────────┐
                ▼                               ▼
         ┌──────────────┐              ┌──────────────┐
         │ 中层主管 A   │              │ 中层主管 B   │  <-- 各自拆解为原子任务
         │ (模块A负责人)│              │ (模块B负责人)│
         └──────┬───────┘              └──────┬───────┘
                │ 分配                        │ 分配
         ┌──────┴──────┐               ┌──────┴──────┐
         ▼             ▼               ▼             ▼
      ┌────┐        ┌────┐         ┌────┐        ┌────┐
      │执行│        │执行│         │执行│        │执行│  <-- 基层只负责干活
      │A1  │        │A2  │         │B1  │        │B2  │
      └──┬─┘        └──┬─┘         └──┬─┘        └──┬─┘
         │             │               │             │
         └─────────────┴───────┬───────┴─────────────┘
                               │ 逐层汇总结果
                               ▼
                       ┌─────────────────┐
                       │    最终输出      │
                       └─────────────────┘
```

### **4. 路由器模式（Router Pattern）—— 并行扇出/扇入**

**特点**：主管模式的变种，但无需逐轮决策。<u style="text-decoration-color: rgb(230, 57, 70)">路由节点一次性将任务**并行**分发，最后统一合并结果</u>。
```
                       ┌─────────────────┐
                       │     用户输入     │
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │  路由节点        │  <-- 仅负责拆分，不负责思考
                       │  (Splitter)     │
                       └────────┬────────┘
                                │ 并行扇出 (Fan-out)
              ┌─────────────────┼─────────────────┐
              │                 │                 │
              ▼                 ▼                 ▼
         ┌────────┐       ┌────────┐       ┌────────┐
         │ 代理1  │       │ 代理2  │       │ 代理3  │  <-- 互不依赖，同时执行
         │(查A库) │       │(查B库) │       │(查C网) │
         └───┬────┘       └───┬────┘       └───┬────┘
              │                 │                 │
              └─────────────────┼─────────────────┘
                                │ 并行扇入 (Fan-in)
                                ▼
                       ┌─────────────────┐
                       │  聚合节点        │  <-- 合并/去重/排序
                       │  (Aggregator)   │
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │    最终输出      │
                       └─────────────────┘
```

### **5. 规划-执行-聚合模式（Plan-Execute-Aggregate）—— 闭环迭代**

**特点**：先做计划，再执行，执行中遇到错误则触发“重新规划”闭环，最终聚合输出。适合长周期、多步骤任务。
```
                       ┌─────────────────┐
                       │     用户输入     │
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │   规划器节点     │  <-- 生成 Step 1, 2, 3...
                       │  (Planner)      │
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │   执行器节点     │  <-- 执行当前步骤，调用工具
                       │  (Executor)     │
                       └────────┬────────┘
                                ▼
                       ┌─────────────────┐
                       │  验证 / 检查点   │  <-- 判断是否成功
                       └────┬──────┬─────┘
                            │      │
                      失败   │      │ 成功
                     (Replan)│      │
                            ▼      ▼
                    ┌───────────┐ ┌───────────┐
                    │重新规划器 │ │ 聚合器    │
                    │(修正计划) │ │(整合结果) │
                    └─────┬─────┘ └─────┬─────┘
                          │             │
                          └──────┬──────┘ (失败时重新规划跳回执行器，成功则输出)
                                 ▼
                       ┌─────────────────┐
                       │    最终输出      │
                       └─────────────────┘
```

### **💡 选型速记口诀（供参考）**


| **范式**    | **核心连接方式** | **最佳适用场景**               |
| :--------- | :---------- | :------------------------ |
| **主管**    | 中心辐射（一对一多） | 职责明确、需强控流程的业务（如客服分单）     |
| **群组**    | 对等移交（手递手）  | 动态上下文流转（如长文档接力翻译）        |
| **层级**    | 树状递归       | 组织架构清晰、需逐级拆解的大项目（如软件开发）  |
| **路由器**   | 并行分叉合并     | 强调速度、子任务无依赖（如批量查数据库）     |
| **规划-执行** | 带反馈环的线性流   | 开放式任务、需多步推理和纠错（如自动化市场分析） |



## supervisor & swam

这是一个非常经典的架构选型问题。要回答清楚，我们需要跳出“哪个更好”的思维，回到**控制权与信息可见性**的本质差异上。

> 简单来说：**主管模式是“中央集权”，适合**`确定性流程`**；群组模式是“地方自治”，适合**`涌现性探索`**。**

我为你从四个核心维度进行硬核对比，最后附上一个速查决策树。

---

### **1. 决策机制：计划 vs. 应急**


| **维度**   | **主管模式（Supervisor）**        | **群组模式（Swarm）**                   |
| :-------- | :--------------------------- | :--------------------------------- |
| **决策者**  | 唯一的中央大脑（LLM Supervisor）     | 当前持有控制权的智能体（Local Decision）       |
| **决策依据** | **全局上下文**（所有专家的历史产出）        | **局部上下文**（当前智能体自身的任务结果）           |
| **路径性质** | **计划性**。主管在派活前就知道自己要达到什么目的。 | **应急性**。A 做完后才发现“这活需要找 B”，于是现场移交。 |


**场景映射**：

- 适合主管：**客服工单系统**。必须由主管先判断“是退款、技术还是物流问题”，再派给固定专家，专家只需执行，无需思考下一步。
- 适合群组：**跨部门协作查案**。比如财务专家查账时突然发现“资金流向涉及跨境法务”，<u style="text-decoration-color: rgb(230, 57, 70)">只有财务专家本人能感知到这个细节，因此由他当场决定移交法务专家</u>。

---

### **2. 状态可见性：上帝视角 vs. 任务视角**


| **维度**         | **主管模式（Supervisor）**                                                                                                                  | **群组模式（Swarm）**                                                                                                       |
| :-------------- | :------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| **可见范围（广度）**   | **全局可见**。主管能看到 <u style="text-decoration-color: rgb(230, 57, 70)">**所有专家** 的 **最终产出物**</u>（Result\_A + Result\_B + Result\_C）。        | **局部可见**。当前智能体只知道 **上一个移交者** 传来的那部分上下文。                                                                               |
| **可见范围（深度）**   | **表面可见**。主管 **看不到** 某个专家内部为了得出 Result\_A 而进行的多轮工具调用、报错重试等中间过程。                                                                        | **表面可见**。同样，移交的信息也只是处理后的结论，<u style="text-decoration-color: rgb(230, 57, 70)">不包含接收方内部思考的草稿</u>。                      |
| **信息冗余（修正原因）** | **高（**`横向累加`**）**。<br>因为主管要挂载所有专家的最终产出物（哪怕是一份50页的报告），<u style="text-decoration-color: rgb(230, 57, 70)">随着轮次增加，State 累积的总数据量非常庞大</u>。 | **低（**`纵向裁剪`**）**。<br>因为<u style="text-decoration-color: rgb(230, 57, 70)">任务上下文在移交时被“裁剪”了，过时的信息被丢弃，只保留当下最相关的部分</u>。⭐ |


> supervisor “信息冗余高”，**绝对不是因为主管能看内部草稿**，而是因为：
>
> - 主管必须把“所有专家最终生成的巨型结果”全部挂载在 State 中，<u style="text-decoration-color: rgb(230, 57, 70)">以备随时交叉比对</u>。
>
> 即使每个专家的“最终结果”只是一句话，5个专家就是5句话；但如果每个专家返回的是 10MB 的 JSON 数据或长文档，主管的上下文负担就极其沉重。这才是“冗余高”的真实含义。
>
> 而群组模式的“冗余低”，是因为它不需要背所有专家的结果，只需要背`“上一个专家传过来的那一张便签”`。

**场景映射**：

- 适合主管：`多源情报`**分析**。需要将气象数据、卫星图、地面情报汇总到一处，<u style="text-decoration-color: rgb(230, 57, 70)">由主管做最终交叉验证。必须拥有上帝视角</u>。
- 适合群组：**长文本**`接力`**翻译**。A 翻译第 1-3 章，把“术语表”和“未完的句子”传给 B，B 不需要知道 A 翻译第一页时的所有思考细节。避免上下文窗口爆炸。

---

### **3. 流程稳定性：写死 vs. 失控边界**


| **维度**   | **主管模式（Supervisor）**                | **群组模式（Swarm）**                     |
| :-------- | :----------------------------------- | :----------------------------------- |
| **可预测性** | **极高**。路由路径可控，易调试，不易跑偏。             | **较低**。可能出现“A→B→C→A”的移交死循环，或交接信息丢失。 |
| **容错难度** | 容易。直接限制 `max_step` 或修改主管 Prompt 即可。 | 困难。需要为每个智能体单独设计 Handoff 的防御逻辑。      |


**场景映射**：

- 适合主管：**金融风控审批**。必须按“反欺诈→信用评分→人工复核”的硬性逻辑走，不允许 AI 自由发挥乱跳流程。
- 适合群组：**开源社区 Issue 自动分派**。机器人先看报错日志，如果判断是前端就交前端组，前端组排查后发现是后端 API 挂了，再主动移交后端。<u style="text-decoration-color: rgb(230, 57, 70)">这种“跑偏”反而是系统需要的灵活性</u>。

---

### **4. 扩展性与瓶颈**


| **维度**   | **主管模式（Supervisor）**                                                                        | **群组模式（Swarm）**                                                                               |
| :-------- | :------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- |
| **性能瓶颈** | **主管 LLM**。<span style="background-color: rgb(255, 243, 205)">所有流量汇聚，上下文越长，主管推理越慢越贵。</span> | **无中心瓶颈**。<span style="background-color: rgb(255, 243, 205)">流量分散在多个 Agent 间，天然支持水平扩展。</span> |
| **新增专家** | 需修改主管的 System Prompt（增加路由选项），重启服务。                                                          | 只需注册新专家并让老专家知道“可以移交给它”，解耦性强。                                                                  |


**场景映射**：

- 适合主管：专家数量少（&lt; 5 个），且任务复杂度不高。
- 适合群组：微服务架构中拥有几十个专用 Agent，随时可能热插拔新服务。

---

### **🧭 决策速查表（拿来即用）**


| **判断条件**              | **首选模式** |
| :--------------------- | :-------- |
| 任务有明确的硬性流程（如审批、SOP）   | **主管模式** |
| 任务需要全局信息交叉验证才能决策      | **主管模式** |
| 专家数量少（≤5个），成本可控       | **主管模式** |
| 任务步骤依赖于运行时发现的新线索      | **群组模式** |
| 单个 Agent 的上下文较长（如长文档） | **群组模式** |
| 需要动态增减专家，不想频繁重启系统     | **群组模式** |
| 担心 AI 幻觉导致流程跑飞，要求强控   | **主管模式** |
| 追求极致的去中心化和弹性扩展        | **群组模式** |

### **⚠️ 一个反直觉的陷阱**

**不要用“任务是否复杂”来判断，而要用“复杂性的来源”来判断。**

- 如果复杂性来源于**需要多领域知识汇总**（如写年报要财务+市场+人事数据）→ 选 **主管**，因为必须汇聚汇总。
- 如果复杂性来源于**执行顺序不确定**（如修 Bug，可能改代码、可能改配置、可能重装环境）→ 选 **群组**，让执行者自己决定下一步。

> 最后给你一个实用建议：生产环境中，**主管模式占 80% 的落地场景**，因为易控、易测、好解释。
>
> 只有<u style="text-decoration-color: rgb(230, 57, 70)">当你明确感到“主管的 Prompt 写不下去了，它根本不知道怎么派活”时</u>，才果断转向群组模式。


## 主管模式本身是带循环的，那么其下的专家智能体也带循环吗？

> **当然可以，而且这恰恰是 LangGraph 构建复杂系统的核心优势——它天然支持**`“嵌套循环”（Nested Loops）`**。**

主管模式下的专家智能体，**完全可以是自带**`内部循环`**的**。这意味着你的系统会形成一种“双重循环”结构：

- **外层大循环（主管级）**：主管<u style="text-decoration-color: rgb(230, 57, 70)">反复指派专家、汇总结果，直到任务终结</u>。
- **内层小循环（专家级）**：某个专家在被主管选中后，内部进行多轮推理或工具调用，<u style="text-decoration-color: rgb(230, 57, 70)">直到得出阶段性结论，才把控制权交还给主管</u>。

下面我为你拆解专家智能体具备内部循环的三种形态，以及它们的执行逻辑。

---

### 形态一：专家是“ReAct 智能体”（最主流）

这是 LangGraph 中最常见的实践。专家节点不是一个简单的 API 调用，而是一个完整的 **ReAct（推理-行动）循环**。
```
         【外层：主管循环】
         ┌─────────────────────────────────────────┐
         │                                         │
         ▼                                         │
   ┌─────────────┐                                │
   │  主管派活    │                                │
   └──────┬──────┘                                │
          │                                        │
          ▼                                        │
┌──────────────────────────────────────┐          │
│    专家节点（内部自带 ReAct 循环）    │          │
│  ┌─────────┐   ┌─────────┐         │          │
│  │ 思考/推理 │──▶│ 调用工具 │         │          │
│  └────┬────┘   └────┬────┘         │          │
│       │             │              │          │
│       ▼             ▼              │          │
│  ┌─────────────────────────┐       │          │
│  │ 判断：结论是否已得出？   │       │          │
│  └──────┬──────────┬───────┘       │          │
│         │ 否       │ 是             │          │
│         └──────────┘               │          │
│                    │ (跳出内部循环) │          │
└────────────────────┼───────────────┘          │
                     │ 返回结果给主管             │
                     ▼                           │
              ┌─────────────┐                    │
              │ 主管汇总判断 │────────────────────┘
              └─────────────┘
```

**典型场景**：专家是“代码工程师”，被主管要求写一段 Python 脚本。它内部可能需要先检索文档（工具1），再编写代码（工具2），再运行测试（工具3），如果测试失败还要自动修改（再次循环）。这一切都在专家内部闭环完成，直到脚本跑通，才把最终代码返回给主管。

---

### 形态二：专家本身是“嵌套子图”

在 LangGraph 中，一个图节点可以被另一个完整的图（Graph）替代。这就意味着，你可以让一个专家以**主管模式**或**群组模式**再次组织自己的“小弟”去干活。
```
【主管模式】
   │
   ├── 专家A (是一个独立的 Subgraph)
   │     │
   │     ├── 子主管 (A的内部主管)
   │     │      ├── 子专家 A1
   │     │      └── 子专家 A2
   │     └── (子主管循环调度 A1/A2，直到完成)
   │
   └── 专家B (普通节点)
```

**典型场景**：顶层主管负责“制作一份市场分析报告”，它将“数据分析”这个子任务派给“数据分析专家”。这个“数据分析专家”本身是一个子图，内部包含“数据清洗主管”、“建模主管”和“可视化主管”，由它们内部循环协作完成，最后只将图表和分析结论返回给顶层主管。

---

### 形态三：专家内部是“简单的多步顺序执行”（无复杂循环）

为了节约成本和延迟，你<u style="text-decoration-color: rgb(230, 57, 70)">也可以把专家设计成没有智能循环的“工具人”——它内部只有线性（DAG）步骤，跑完即止，不带有</u> `while` <u style="text-decoration-color: rgb(230, 57, 70)">判断。这在生产环境中常用于高频率、低延迟的子任务</u>。
```
专家节点 (无内部循环)
  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ 步骤 1  │───▶│ 步骤 2  │───▶│ 步骤 3  │  (无条件跳转回主管)
  └─────────┘    └─────────┘    └─────────┘
```

---

### **⚙️ 执行逻辑的关键规则：原子性（Atomicity）**

无论专家内部循环多少次，**对于上层主管来说，这个专家节点是一次性的原子调用**。

- 主管调用专家节点后，会**挂起等待**。
- 专家节点内部的循环**必须完全运行结束**（达到内部设置的 `END` 条件），并将结果写入 State 后，控制权才会返回给主管的下一轮决策。
- 主管不会在专家内部循环到一半时强行介入（除非你设置了复杂的交叉中断，一般不推荐）。

---

### **🚨 实战中的两大“坑”与对策**

当你引入专家内部循环时，必须注意以下两个致命陷阱：


| **陷阱**                   | **后果**                                                                     | **对策**                                                                                                                              |
| :------------------------ | :-------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------- |
| **递归步数爆炸**               | LangGraph 默认 `recursion_limit=25`。假设外层循环 3 次，每次专家内部循环 10 步，总和 30 步，直接报错中断。 | 运行时必须调大限制：`config={"recursion_limit": 100}`。且 **限制值应 ≥ (主管循环次数 × 专家内部最大步数)**。                                                       |
| **状态污染（State Conflict）** | 专家内部使用临时变量（如 `internal_thought`）进行推理，如果不加清理就返回，可能干扰主管或其他专家。                | <u style="text-decoration-color: rgb(230, 57, 70)">采用 **State 隔离设计**：专家内部使用</u> `PrivateState`，只在返回时映射需要暴露给外层的字段（如 `final_result`）。 |


---

### **💡 总结与建议**


| **专家类型**           | **是否有内部循环** | **适用场景**                  |
| :------------------ | :----------- | :------------------------- |
| **ReAct 智能体**      | ✅ 是（工具调用循环） | 专家需要独立查阅资料、执行代码、反复试错。     |
| **嵌套子图（Subgraph）** | ✅ 是（内部独立调度） | 专家本身就是一个复杂的项目组，需要再拆分子任务。  |
| **纯函数/线性节点**       | ❌ 否（单次计算）   | 专家只做简单的格式化、提取、翻译，成本敏感型任务。 |


**我的建议是**：优先将专家设计为带内部循环的 ReAct 智能体，这是 LangGraph 最拿手的模式，能极大减轻顶层主管的决策负担（主管不用关心“怎么查资料”，只关心“查什么资料”）。但务必在测试阶段先跑通小样本，算好最大步数，防止线上超时报错。

如果你打算把某个专家设计成 Subgraph，我可以给你画一下 LangGraph 中子图 State 映射的详细代码结构，需要的话告诉我。😊

## supervisor的带循环专家Agent的三形态混合

**完全正确！而且这不仅是“可行的”，更是 LangGraph 在生产环境落地的标准实践（Best Practice）。**

> 在实际的工业级多智能体系统中，**几乎不存在清一色全是 ReAct 智能体或全是线性节点的系统**。真正的工程化系统一定是**“混血架构”**，<u style="text-decoration-color: #e63946">根据每个专家的职责、成本敏感度和延迟要求，灵活搭配三种形态</u>。

下面我为你展示一个**三层混血架构**的真实结构，以及它们如何协同工作。

---

### **🧩 混血架构全景图（主管 + 三形态混合）**
```
                          ┌─────────────────────────┐
                          │   顶层主管 (Supervisor)  │  <-- 仅做宏观路由，无内部循环（轻量级）
                          └───────────┬─────────────┘
                                      │ 任务分发（依据意图）
              ┌───────────────────────┼──────────────────────────┐
              │                       │                          │
              ▼                       ▼                          ▼
     ┌────────────────┐    ┌─────────────────────┐   ┌─────────────────────┐
     │  专家 A         │    │  专家 B              │   │  专家 C             │
     │  (形态三: 线性) │    │  (形态一: ReAct)     │   │  (形态二: 嵌套子图) │
     │  纯函数/格式化  │    │  带工具循环的推理专家 │   │  内部自带小团队主管  │
     └───────┬────────┘    └──────────┬──────────┘   └──────────┬──────────┘
             │                        │                          │
             │ 无循环，秒级返回        │ 内部 while 循环调工具    │ 内部子主管再次分发
             │                        │ (查API、写代码、自测)     │ (内部包含 A/B 形态)
             │                        │                          │
             └────────────────────┬───┴──────────────────────────┘
                                  │ 所有结果汇聚回 State
                                  ▼
                       ┌─────────────────────────┐
                       │ 主管再次决策（循环/结束）│
                       └─────────────────────────┘
```

---

### **📋 三种形态在“混血系统”中的具体职责划分**


| **专家类型**       | **形态**         | **内部结构**                                   | **典型职责**                    | **成本/延迟**         |
| :-------------- | :-------------- | :------------------------------------------ | :--------------------------- | :----------------- |
| **专家A（信息提取器）** | **形态三（线性）**    | 纯 Python 代码，无 LLM 调用，仅做正则或 JSON 解析。        | 提取用户输入中的日期、ID、金额。           | **极低**，&lt;100ms  |
| **专家B（代码工程师）** | **形态一（ReAct）** | 内部 `while` 循环：思考 → 写代码 → 执行 → 报错则重试（最多3次）。 | 根据需求编写 Python 脚本，必须自测通过才返回。 | **高**，可能耗时 5\~15s |
| **专家C（市场报告组）** | **形态二（嵌套子图）**  | 内部包含“数据清洗主管”和“图表绘制主管”，由内部子主管调度。            | 生成包含多维度图表的市场分析报告。           | **极高**，可能耗时 30s+  |


---

### **🚀 为什么要混合？（三大核心优势）**

1. **成本精准控制（Cost Optimization）**：

- 如果所有专家都用 ReAct（形态一），每个任务都会产生大量无意义的工具调用 Token 消耗。
- 将简单的“格式化”“提取”任务交给线性节点（形态三），能**节省 80% 以上的 LLM 调用开销**。

2. **延迟分级保障（Latency SLA）**：

- 用户期望“查余额”这类简单操作秒级响应（走形态三）。
- “生成周报”这类复杂操作可以容忍十几秒延迟（走形态一或二）。
- 混合架构允许你<u style="text-decoration-color: #e63946">为不同专家设置不同的超时和重试策略</u>。

3. **逻辑解耦与复用（Reusability）**：

- 形态二（嵌套子图）最擅长`复用`。比如“数据分析子图”是一个成熟的独立子系统，它可以被顶层“市场主管”调用，也可以被“研发主管”调用，无需重复开发。

---

### **🧠 主管如何“看待”这些形态各异的专家？**

在主管的视角（Prompt）里，它完全**不需要知道**专家内部是线性还是 ReAct：

- 主管只看到专家列表：`["信息提取器", "代码工程师", "市场报告组"]`。
- 主管只需要知道每个专家的**功能描述**和**输入/输出格式**。
- 至于专家内部是花 0.1 秒还是 10 秒，主管**不关心**，它只等待节点返回结果。

这正是`封装（Encapsulation）的魅力`所在。

---

### **⚙️ 实现上的技术要点（避坑指南）**

当你在代码中混合这三种形态时，唯一需要注意的是 **State 定义的一致性**：


| 形态                  | State 读写模式                         | 注意事项                                                            |
| :------------------- | :---------------------------------- | :--------------------------------------------------------------- |
| **形态三（线性）**         | 只读 `user_input`，只写 `extracted_id`。 | 必须确保返回的 Key 在全局 State 中预定义过，否则会报 KeyError。                      |
| **形态一（ReAct）**      | 频繁读写内部临时变量（如 `tool_results`）。      | 强烈建议将内部变量放在**私有命名空间**（如 `agent_b_private`）中，防止 Key 冲突污染其他专家。    |
| **形态二（嵌套Subgraph）** | 子图内部有自己的 State Schema。             | 父图调用子图时，必须定义 `input/outut mapping`，只映射必要的字段进出，避免子图内部海量中间态泄露到父图。 |


**推荐实践**：在 State 中<u style="text-decoration-color: #e63946">设置一个</u> `shared` <u style="text-decoration-color: #e63946">字典用于专家间通信</u>，每个<u style="text-decoration-color: #e63946">专家内部的临时变量使用</u> `private_<agent_name>` <u style="text-decoration-color: #e63946">存储</u>，并在节点返回时使用自定义 Reducer 只更新 `shared` 部分。

---

### **💡 总结**

你的直觉完全正确——**三形态混合是 LangGraph 多智能体系统设计的最终归宿**。

- **顶层主管**：通常设计为无循环或<u style="text-decoration-color: #e63946">极简循环（只做决策），保持轻量</u>。
- **中层专家**：根据任务性质，灵活选择线性（快）、ReAct（聪明）、子图（复杂）。
- **底层原子**：最底层的工具（Tools）必须是纯粹的同步/异步函数，不带任何 Agent 循环。


## supervisor 子 Agent 之间绝对可以进行通信

**答案是肯定的：子 Agent 之间绝对可以进行通信。**

但关键在于，这种通信不是“手递手”的直接传递，而是**通过**`“共享黑板”（Shared State）`**进行的**`间接通信`。这正好呼应了我之前提到的 `shared` 字典的作用。

> 在 Supervisor 模式下，子 Agent 之间的通信遵循 `“数据共享，控制集中”` 的原则。

---

### 1. 通信机制：间接的“黑板报”模式

所有子 Agent 不直接向对方发送消息，而是<u style="text-decoration-color: #e63946">统一向全局 State（黑板）上写数据，并从 State 上读数据</u>。通信流程如下：
```
          ┌─────────────────────────────────────────────────┐
          │              全局 State (共享黑板)              │
          │  {                                             │
          │    "shared": {                                 │
          │      "research_data": "...",  ← 专家A 写的     │
          │      "code_version": "v2"     ← 专家B 写的     │
          │    }                                           │
          │  }                                             │
          └───────────┬─────────────────┬─────────────────┘
                      │                 │
        ┌─────────────┴─────┐  ┌───────┴──────────┐
        │   专家 A (写)      │  │   专家 B (读)      │
        │  "我查完了资料"    │  │ "我看看A查了啥"   │
        └───────────────────┘  └──────────────────┘
                      │                 │
                      └────────┬────────┘
                               │ 控制权必须回流主管
                               ▼
                    ┌─────────────────────┐
                    │  主管 (控制调度)     │  <-- 决定何时让 B 读取 A 的结果
                    └─────────────────────┘
```

---

### 2. 两个关键维度：数据流 vs. 控制流

为了更清晰地理解，我们需要区分这两种“流”：


| **维度**        | **实现方式**                             | **方向**                      |
| :------------- | :------------------------------------ | :--------------------------- |
| **数据流（通信内容）** | 专家 A **写**入 State，专家 B **读**取 State。 | **专家 A → State → 专家 B**（间接） |
| **控制流（执行权限）** | 专家 A 完成后，**必须**回到主管，主管决定是否、何时调用专家 B。 | **专家 A → 主管 → 专家 B**（集中调度）  |


> **关键规则**：子 Agent **不能**绕开主管直接将控制权移交给另一个子 Agent。<u style="text-decoration-color: #e63946">如果 A 想通知 B 干活，A 只能把“通知”写成数据放在 State 里，由主管在下一轮决策中读取并下达指令</u>。

---

### 3. 实战例子：代码审查场景

假设你有一个“代码工程师”和“代码审查员”两个子 Agent：

1. **第一轮**：主管派“代码工程师”写代码。
2. **工程师内部**：完成代码，返回 `{"shared": {"draft_code": "print('hello')"}}` 并写入 State。
3. **主管决策**：主管看到 State 中有 `draft_code`，决定派“审查员”上场。
4. **审查员内部**：从 State 读取 `shared["draft_code"]` 进行审查，返回 `{"shared": {"review_result": "通过"}}`。
5. **主管决策**：主管看到 `review_result` 为“通过”，结束任务。

**在这个流程中，工程师和审查员并没有直接通话，但通过 State 实现了“书面交接”。**

---

### 4. 为什么你不能让子 Agent 直接通信？（设计边界）

有人可能会问：“既然都拿到数据了，为什么不直接让审查员在工程师节点结束后立刻运行？”

- **破坏**`单一职责`：如果工程师节点内部硬编码“完成后去调用审查员”，那么工程师就变成了半个主管，导致调度逻辑分散在各处，系统越改越乱。
- **丧失**`可见性`：直接通信会让主管（中央大脑）完全不知道 A 和 B 之间发生了什么，无法进行<u style="text-decoration-color: #e63946">全局的异常处理和任务中断</u>。

---

### 5. 那么，`shared` 和 `private` 到底怎么用？

基于上面的机制，推荐的做法是：

- `shared` **字典**：**显式用于跨 Agent 通信**。<span style="background-color: #fff3cd">任何需要被其他 Agent 看见的数据（如“上一步的产出”），都放进这里</span>。
- `private_<agent_name>` **字典**：**用于 Agent 内部私有数据**。比如<u style="text-decoration-color: #e63946">某个 ReAct Agent 内部调用了 5 次 API 产生的中间思考日志，这些只归它自己用，别人无需看见</u>，就锁在 `private_code_engineer` 里，不污染全局通信空间。

---

### 6. 这个机制与“群组模式”的本质区别

现在你应该更能理解我为什么说 Supervisor 和 Swarm 完全不同了：

- **主管模式**：**数据共享（通过黑板），控制集中（通过主管）**。<u style="text-decoration-color: #e63946">通讯可靠，流程可预测，但有中心瓶颈</u>。
- **群组模式**：**数据和控制一并移交（Handoff）**。A 做完后直接把“上下文 + 执行权”打包丢给 B，主管不参与。通讯动态，效率高，但流程难以干预。

---

### **💡 总结一句**

在 Supervisor 模式下，子 Agent 不仅可以通信，而且通信非常频繁——**只是它们都在跟 State 这个“黑板”通信，而非“手拉手”直接对话**。正是这种**数据与控制的解耦**，<u style="text-decoration-color: #e63946">让 Supervisor 模式既保持了流程的稳定可控，又具备了数据流动的灵活性</u>。

如果你在代码中遇到了“A 做完，B 必须立刻启动”的`强依赖需求`，那意味着你需要转向 **“主管 + 路由器（DAG）”混合模式**（我之前提到的分批次执行）。想了解这种混合模式的 State 设计细节吗？可以继续聊。😊

## 子agent内部的中间思考内容是否 值得/应该 被supervisor看到？⭐

你这个问题触及了多智能体系统设计<span style="font-size: 1em">中的一个核心</span>权衡：**是完全封装，还是适度透明？**

> 你的直觉很敏锐——在某些情况下，<u style="text-decoration-color: #e63946">将子智能体的内部思考过程有选择地暴露给主管，确实能提升系统的协作能力和决策质量</u>。这并非空想，而是当前一个活跃的研究方向，已有不少理论和实践探索。

### **📚 理论基础：从“信息不对称”到“主管-代理问题”**

传统上强调封装，是为了<u style="text-decoration-color: #e63946">防止子智能体的“内部噪音”干扰主管决策，并控制成本</u>。但这会带来`“信息不对称”`（Information Asymmetry）——主管只看到结果，不了解过程，<u style="text-decoration-color: #e63946">决策质量可能因此受限</u>。

因此，一个新兴的学术视角将多智能体系统视为“**主管-代理问题**”（Principal-Agent Problems）。

> 该理论认为，<u style="text-decoration-color: #e63946">当子智能体（代理）拥有主管未知的私有信息时，它们可能会出于自身目标（如“自保”）而策略性地扭曲或隐瞒信息</u>，即`“欺骗”（Scheming）`。

### **🧪 前沿研究：探索“透明度”的价值**

学术界已开始探索如何通过“透明度”来应对这些问题：

- **共享完整推理数据**：允许子智能体将**所有中间步骤**（如链式思考、工具调用）写入共享通道。这能让其他智能体理解其推理过程，提升整体协作与推理能力。
- `结构化内省日志（Introspection Logs）`：让子智能体生成包含 `proposed output（提议输出）`, `supporting reasoning（支持性推理）`, confidence score（置信度评分）, `self-reflection（自我反思）`的日志并共享。
  > 在一个临床多智能体系统的研究中，这种方法将**诊断准确率从20%提升到了80%**，同时平均响应时间**减少了约28%**。
- **内部状态监控**：研究呼吁对主管和子智能体的内部状态进行监控。实验发现，**“隐形”的主管架构会导致集体“解离”（dissociation）**，损害系统鲁棒性，因此建议提供“**透明度模式**”（transparency mode）来增强系统稳健性。
- **信息可见性的安全风险**：一项针对365次多智能体运行的研究发现，**“隐形”的主管架构导致了<u style="text-decoration-color: #e63946">严重的内部状态退化</u>，但任务输出本身却依然完美**。这警示我们：**仅仅检查最终输出，完全不足以评估系统的健康与安全**。
- **反思与记忆机制**：一些框架引入了`智能体内与智能体间的双重反思机制`，或让智能体将“**同伴生成的反思**”整合进提示词以更新行为。共享的反思积累成“**集体记忆**”，可增强系统的泛化与协调能力。
- **不可变推理账本（Forensic Log）**：通过将子智能体的内部思维链序列化为**不可篡改的账本**，为事后的行为审计和责任追溯提供了可能。

### **🏗️ 工程实践：如何<u style="text-decoration-color: #e63946">有选择地共享</u>？**

一些框架和库已开始支持这种有选择的透明度，例如允许在共享状态下有选择地包含中间步骤。这通常通过**State（状态）设计**来实现：

- **共享区（Shared Zone）**：存放需要暴露给主管或其他智能体的信息，如`关键推理摘要、`工具调用结果。
- **私有区（Private Zone）**：存放海量的、对他人无直接价值的内部思考日志，避免状态爆炸。

> 你可以<u style="text-decoration-color: #e63946">在主管的提示词中指导它如何利用共享区信息进行决策，实现“**适度透明**”</u>。

### **⚖️ 何时需要透明度：一个决策框架**

何时应该让主管“窥探”子智能体的内心？可以参考以下框架：

- **高透明度**：适用于**医疗诊断、金融风控、法律分析**等高风险、高不确定性领域。准确性和可解释性优先，即使成本较高。
- **适度透明度**：适用于**复杂项目管理、研究分析**等需要<u style="text-decoration-color: #e63946">跨智能体协调的场景</u>。通过共享`关键推理摘要`来平衡性能与成本。
- **低透明度**：适用于**数据提取、格式转换**等简单、确定性的任务。<u style="text-decoration-color: #e63946">追求极致的速度和成本控制</u>。

> 选择的关键在于**评估“透明度带来的收益”是否大于“状态膨胀带来的成本”**。

总而言之，你提出的问题非常有前瞻性。虽然“完全私有”仍是许多场景下的默认选择，但“**有选择的透明度**”已被证明是提升多智能体系统在复杂、高风险任务中表现的关键路径。

### **三、专家智能体定义（方案 A）**


| **专家名称**   | **形态选择**  | **理由**                                  | **核心工具**         |
| :---------- | :--------- | :--------------------------------------- | :---------------- |
| **新生引导专家** | **ReAct** | 需要多轮对话了解新生困惑，检索政策后可能需追问澄清               | 读画像、知识库检索、在线信息检索 |
| **学术资源专家** | **嵌套子图**  | 内部需要“校内资源检索子专家”+“在线学术检索子专家”并行工作，各自有内部循环 | 读画像、校内资源库、在线学术检索 |
| **升学规划专家** | **嵌套子图**  | 内部需要“学校推荐子专家”+“导师推荐子专家”+“研究方向分析子专家”协作   | 读画像、在线信息检索、推荐算法  |
| **就业规划专家** | **ReAct** | 需要根据画像推荐岗位，再根据岗位差距推荐学习内容，可多轮推理          | 读画像、在线信息检索、推荐算法  |
| **政策解读专家** | **线性**    | 政策检索是确定性操作，无需多轮推理，降低成本                  | 知识库检索            |


**为什么学术资源和升学规划用嵌套子图？**

- 这两个专家内部有**明确的子任务分工**（学术资源 = 校内 + 在线；升学规划 = 学校 + 导师 + 方向）
- 子图可以将内部状态隔离，避免中间推理污染全局 State
- 子图内部可以有自己的小循环，不影响 Supervisor 的调度

### **四、Supervisor Prompt 设计（方案 A）**

采用**三层结构**：角色定位 → 可用专家列表 → 决策规则。

<span style="color: rgb(15, 17, 21); font-size: 12px">text</span>
```
# 角色定位
你是一名大学全生命周期学生发展服务系统的首席调度官（Supervisor）。你的职责是理解学生的需求，调度最合适的专家团队来提供帮助。

# 可用专家团队
1. **新生引导专家** (onboarding_advisor)
   - 职责：新生入学适应、校园生活引导、选课咨询
   - 何时调用：用户是新生、询问校园生活、选课问题

2. **学术资源专家** (academic_resource_agent)
   - 职责：推送校内科研资源（实验室、导师项目）、在线学术资源（论文、课程）
   - 何时调用：用户询问科研机会、学术资源、论文查找

3. **升学规划专家** (career_graduate_agent)
   - 职责：推荐研究生院校、推荐导师、推荐研究方向
   - 何时调用：用户询问考研、保研、出国、选择研究方向

4. **就业规划专家** (career_job_agent)
   - 职责：推荐岗位、推荐需学习的技能和知识
   - 何时调用：用户询问就业、求职、岗位推荐、技能提升

5. **政策解读专家** (policy_agent)
   - 职责：解读学校政策、规章制度
   - 何时调用：用户询问奖学金、评优、学籍、毕业要求等政策

# 决策规则
1. 每次只调用一个专家，等待结果后再决定下一步
2. 如果问题涉及多个领域，按优先级依次调用：政策 → 引导 → 资源 → 升学 → 就业
3. 如果学生画像显示低年级（大一/大二），优先考虑新生引导和学术资源
4. 如果学生画像显示高年级（大三/大四），优先考虑升学和就业
5. 如果已有足够信息回答用户，输出 "FINISH"

# 输出格式
仅输出下一个要调用的专家名称或 "FINISH"，不要输出其他内容。
```

### **五、终止条件设计**

#### **Supervisor 外层终止条件**


| **终止条件**            | **类型** | **实现方式**                           | **阈值** |
| :------------------- | :------ | :---------------------------------- | :------ |
| **Supervisor 主动结束** | 语义条件   | Supervisor 输出 `"FINISH"`           | —      |
| **最大循环轮次**          | 硬截断    | State 中 `step_count >= max_rounds` | 5 轮    |
| **信息完备性**           | 语义条件   | State 中已包含回答所需的所有关键字段              | 动态判断   |


<span style="color: rgb(15, 17, 21); font-size: 12px">python</span>
```
def should_continue(state: State) -> Literal["supervisor", "__end__"]:
    # 条件1: Supervisor 主动结束
    if state.get("next") == "FINISH":
        return "__end__"
    # 条件2: 超过最大轮次
    if state.get("step_count", 0) >= 5:
        return "__end__"
    # 条件3: 信息完备性检查（示例：升学问题需要 school_list + professor_list）
    if state.get("user_intent") == "graduate" and \
       state.get("school_list") and state.get("professor_list"):
        return "__end__"
    return "supervisor"
```

#### **专家内部终止条件**


| **专家类型**     | **内部终止条件**                | **说明**       |
| :------------ | :------------------------- | :------------ |
| **ReAct 专家** | 工具调用完成 + LLM 判断“已有足够信息”   | 内部最多 5 轮工具调用 |
| **嵌套子图专家**   | 子图内部 Supervisor 输出 FINISH | 子图有自己的终止逻辑   |
| **线性专家**     | 执行完所有步骤即终止                | 无循环          |

### **六、State 设计（Shared vs Private）**

<span style="color: rgb(15, 17, 21); font-size: 12px">python</span>
```
from typing import TypedDict, List, Optional, Annotated
import operator

# ============================================
# 1. 全局 State（Supervisor 可见）
# ============================================
class GlobalState(TypedDict):
    # --- 基础信息 ---
    user_id: str
    user_input: str
    messages: Annotated[List[dict], operator.add]  # 对话历史
    
    # --- 学生画像（从画像系统读取）---
    student_profile: dict  # {年级, 专业, GPA, 科研经历, 社团活动, ...}
    
    # --- 路由与循环控制 ---
    next: str  # Supervisor 决策输出
    step_count: int  # 当前循环轮次
    user_intent: str  # 入口路由判断的意图
    
    # --- Shared 通信区（专家间共享）---
    shared: dict  # 详见下方 SharedState
    
    # --- 最终输出 ---
    final_answer: Optional[str]


# ============================================
# 2. Shared 通信区（专家间共享数据）
# ============================================
class SharedState(TypedDict):
    # 新生引导
    onboarding_advice: Optional[str]
    
    # 学术资源
   校内_resources: Optional[List[dict]]   # 校内科研资源
    online_resources: Optional[List[dict]] # 在线学术资源
    
    # 升学规划
    recommended_schools: Optional[List[dict]]
    recommended_professors: Optional[List[dict]]
    research_directions: Optional[List[str]]
    
    # 就业规划
    recommended_jobs: Optional[List[dict]]
    skill_gaps: Optional[List[str]]        # 需学习的技能
    
    # 政策解读
    policy_answer: Optional[str]


# ============================================
# 3. 专家私有 State（子图内部，Supervisor 不可见）
# ============================================
# 示例：学术资源专家的私有 State
class AcademicResourcePrivateState(TypedDict):
    # 这些字段只在子图内部可见，不会穿透到 GlobalState[reference:11]
    raw_search_results: List[dict]      # 原始搜索结果
    search_retry_count: int              # 重试次数
    internal_thoughts: List[str]         # 内部推理链
    filtered_results: List[dict]         # 过滤后的结果（最终只映射到 shared）
```

**关键设计原则**：

1. **Shared 区**：专家之间、专家与 Supervisor 之间的**唯一通信通道**
2. **Private 区**：专家的**内部工作间**，中间报错、重试日志、原始数据全部隔离
3. **状态穿透**：子图只将 `filtered_results` 等“干净”数据映射到父图的 `shared` 区

<span style="color: rgb(15, 17, 21); font-size: 12px">python</span>
```
# 子图状态映射示例
class AcademicResourceSubgraph:
    def __init__(self):
        self.graph = StateGraph(AcademicResourcePrivateState)
        # ... 构建子图内部逻辑 ...
    
    def output_mapping(self, private_state: AcademicResourcePrivateState) -> dict:
        # 只把干净的结果映射到父图的 shared 区
        return {
            "shared": {
                "校内_resources": private_state["filtered_results"]["internal"],
                "online_resources": private_state["filtered_results"]["online"]
            }
        }
```

### **七、关于“子智能体内部决策是否共享给 Supervisor”**

这是一个效果与成本的权衡问题。


| **共享内容**      | **收益**              | **成本**       | **建议**             |
| :------------- | :------------------- | :------------ | :------------------ |
| **专家最终结论**    | Supervisor 可做全局决策   | 低            | ✅ **必须共享**         |
| **专家置信度分数**   | Supervisor 可判断结果可靠性 | 低            | ✅ **推荐共享**         |
| **专家关键推理摘要**  | Supervisor 可理解结论来源  | 中            | ⚠️ **按需共享**（仅复杂任务） |
| **专家完整内部推理链** | Supervisor 可获得完整上下文 | 极高（Token 爆炸） | ❌ **不共享**          |


**如何衡量是否提升了精度？**

建议采用 **A/B 测试** 的方法：

1. **对照组**：专家只输出最终结论（不共享推理摘要）
2. **实验组**：专家输出最终结论 + 关键推理摘要（3-5 句话）
3. **评估指标**：
  - 任务完成率（Supervisor 是否做出了正确的下一步决策）
  - 平均轮次（共享后是否减少了不必要的专家调用）
  - Token 消耗（增加的推理摘要成本 vs 减少的轮次成本）

我在之前的回答中提到的相关研究表明，在临床诊断等高复杂性任务中，共享结构化内省日志（含置信度评分和自我反思）可将准确率从 20% 提升至 80%，同时平均响应时间减少约 28%。在教育场景中，这种“适度透明”策略同样值得尝试——建议从**升学规划和就业规划**这两个高复杂性专家开始试点。

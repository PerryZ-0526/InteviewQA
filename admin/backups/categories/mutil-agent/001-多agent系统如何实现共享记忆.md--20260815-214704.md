# ✅多 Agent 系统如何实现共享记忆？

## 题目

多个 Agent 之间如何实现共享记忆？有哪些架构方案和一致性问题？

## 面试直接答

### 1. 原生回答

多 Agent 的“共享记忆”要先拆成三类：

- `消息`负责传输；
- `协作状态`负责记录当前任务的权威事实；
- `长期记忆`负责跨任务复用经验。

它们的生命周期、一致性和存储方式不同，不能都塞进一个向量库或消息列表。

1. 对单个任务，我通常使用`结构化状态库`或`黑板`保存`目标、约束、计划、产物和外部操作状态`，并用`版本号`或`事务`控制并发写入。
2. Agent <span style="background-color: rgb(255, 243, 205)">通过消息传递工作结果</span>，但只有`经过验证的事实`才能晋升为共享状态。
3. <span style="background-color: rgb(255, 243, 205)">大段轨迹和文档可外置</span>，向量检索只负责找`候选证据`，不承担余额、任务状态等权威可变数据。
4. 长期记忆要有来源、作用域、版本、验证状态、权限和过期策略。`冲突`不能按“最后写入”或模型置信度简单覆盖，而要<span style="background-color: rgb(255, 243, 205)">保留证据并由规则、外部状态或人工裁决</span>。
```
真正难点不是让 Agent 都能读写，而是控制谁能写什么、何时可见、如何追溯和恢复。
```

---

### 2. ChatGPT 评估

这版回答整体是不错的，技术判断基本正确，而且明显比“共享一个向量数据库 / 所有 Agent 共用 conversation history”这种回答高一个层次。我会给它大概 8/10。

最大的优点是你把“共享记忆”拆成了三个不同问题：

- 消息：Agent 之间交换信息；
- 协作状态：当前任务中的权威事实；
- 长期记忆：跨任务积累和复用的信息。

这个划分很重要，因为面试官问“共享记忆怎么实现”，实际上往往是在考：你是否知道共享上下文、状态管理、长期记忆不是一回事。你后面提到“向量检索只负责候选证据，不承担余额、任务状态等权威可变数据”，这个观点也很好，体现出了数据库设计和 Agent 架构结合的意识。

不过目前有一个比较明显的问题：**讲得有点像架构原则，而没有完全回答“如何实现”。**

例如面试官追问一句：

> “所以你具体会怎么做？几个 Agent 到底怎么共享？”

你现在这版就需要继续补充。

比较理想的是把实现方式稍微落地，例如：

> 单任务内，我会给多个 Agent 一个`共享的结构化状态`，例如 `LangGraph State`、`Redis 或数据库中的 Task State`。
>
> 每个 Agent <span style="background-color: rgb(255, 243, 205)">不直接共享完整上下文，而是读取自己需要的状态字段，并把执行结果以结构化方式写回</span>。写入时通过版本号、事务或者乐观锁解决并发覆盖问题。

这样面试官马上知道你是真正做过系统设计，而不只是知道概念。

另外一句：

> “只有经过验证的事实才能晋升为共享状态。”

这个思想很好，但“晋升”稍微有点抽象。面试现场最好进一步说明，例如：

Agent 输出首先作为 observation/result 保存，经过规则校验、工具执行结果确认或者 Reviewer 检查之后，再更新 Task State。

这样就形成了：
```
Agent 输出 → 临时结果 → 验证 → 共享状态
```

这其实是非常好的`多 Agent 状态治理模式`。

### 3. ChatGPT 改写版

我建议你把整段压缩和调整成下面这版，更适合作为面试中的正式回答：

> 多 Agent 的共享记忆我一般不会简单理解成“大家共享一个向量库”，而是`拆成三层`：
>
> ```
> Agent 之间的消息、单次任务的共享状态，以及跨任务的长期记忆。
> ```
>
> 在一次任务内部，我会维护一个`结构化的共享状态`，比如任务目标、约束、计划、各 Agent 的执行结果和外部系统状态。
>
> Agent 之间可以通过消息传递信息，但不会直接把所有消息都当成事实写入共享状态，而是先形成执行结果，经过规则、工具结果或者 Reviewer 验证以后，再更新共享状态。多个 Agent 并发修改时，可以通过版本号、事务或者乐观锁避免状态覆盖。
>
> `大段文档、历史轨迹这类非结构化信息`可以放到外部存储，通过向量检索按需召回，但向量库只负责检索，不应该承担任务状态、余额这类需要强一致性的权威数据。
>
> `跨任务的长期记忆`则需要额外管理来源、作用域、版本、权限、有效期和可信状态。多个 Agent 对同一事实产生`冲突`时，也不能简单按照最后写入或者模型置信度覆盖，而应该保留来源和证据，通过外部事实、规则或者人工进一步裁决。
>
> 所以多 Agent 共享记忆真正困难的地方不是“让所有 Agent 都能读写”，而是设计好**状态的所有权、写入权限、一致性、可见范围以及可追溯性**。

这版相比你原来的回答只增加了一点实现细节，但面试效果会明显好一些。

还有一个值得注意的地方：

- **如果这是后端 / AI Platform 岗位，我反而建议保留你现在这种回答风格，不要过多展开各种“Memory 框架”。** 
- 面试官真正感兴趣的通常不是你知不知道 Mem0、向量数据库之类，而是你能否意识到多 Agent 本质上会引入一个`分布式状态管理问题`：
```
谁拥有状态 → 谁可以修改 → 修改如何并发控制 → 什么是权威事实 → 冲突如何解决 → 历史如何恢复。
```

这其实才是你这版回答最有价值的地方。

## 详细解析

### 一、三类数据


| 类型   | 目的             | 合适机制           |
| ---- | -------------- | -------------- |
| 消息   | Agent 间传递任务和结果 | 队列、事件、RPC      |
| 协作状态 | 当前任务的权威事实      | 事务数据库、版本化状态、黑板 |
| 长期记忆 | 跨任务复用知识        | 文档库、结构化库、向量检索  |


共享状态可以是会话内临时数据，不必持久化；黑板也可以由持久数据库实现，并非天然单点或内存态。

### 二、一致性

写入携带 expected\_version，成功后版本递增；冲突时重新读取并合并，而不是静默覆盖。读操作也要保证一致快照。需要原子更新的字段进入同一事务，跨系统副作用则记录操作 ID、回执和未知状态。

### 三、向量库边界

Embedding 相似度<span style="background-color: rgb(255, 243, 205)">适合召回相关文本</span>，不适合强一致状态。

约束、审批、幂等和任务进度使用结构化字段；检索结果只作为候选证据，并回到原文验证时效和权限。

### 四、记忆准入

只有稳定、可复用、来源可靠且允许保存的信息进入长期记忆。写入时记录 subject、scope、source、version、valid\_from/to、verification\_status 和 ACL。模型自报 confidence 只能<span style="background-color: rgb(255, 243, 205)">辅助排序</span>，不能替代真值。

### 五、框架示例的版本风险

LangGraph 等框架的消息 reducer 需要处理消息 ID、更新和删除，普通列表相加只适合最简单追加场景。框架 API 应标明版本，示例若未运行要明确称伪代码。

### 六、共享状态的写入协议⭐

Agent 读取版本 `verision` 后提交 patch 和 `expected_version = version`。存储层若发现版本已变化，拒绝静默覆盖；调用方重新读取，判断字段是否可自动合并。追加证据通常可合并，修改同一决策或资源所有权通常需要协调。

写入分为候选、已验证和已发布。

> 模型推断<span style="background-color: rgb(255, 243, 205)">先进入候选区，只有通过工具、规则或授权人验证后才成为其他 Agent 默认依赖的共享事实</span>。这样能阻止一次幻觉立即污染整个团队。

### 七、记忆条目的最小字段

一条`可治理记忆`至少包含内容、类型、来源、作者 Agent、任务/租户作用域、创建时间、适用版本、验证状态、权限、有效期和源指针。还应记录 supersedes/contradicts 关系，避免新写入直接抹掉历史证据。

- “置信度”可以帮助排序，但不能决定真值。
- 工具回执、数据库状态和用户明确决定的权威性通常高于模型自评；
- 过期但曾经正确的记忆也不应被简单标为错误。

### 八、读取一致性与权限

<span style="background-color: rgb(255, 243, 205)">一个计划步骤需要的多个字段应来自</span>`同一快照`，否则 Agent 可能读到新目标和旧约束的组合。读缓存要绑定状态版本；版本变化后失效。长期记忆检索先做租户、角色、任务和数据级权限过滤，再做相似度排序，避免“检索到了”就越权暴露。

### 九、消息、事件与状态的关系

消息表示某个 Agent 声称发生了什么，事件表示系统接受并记录了什么变化，`当前状态`是`事件折叠后的可读快照`。消息丢失可重放事件，状态损坏可从日志重建；但这不要求所有系统都完整采用事件溯源，复杂度要与审计和恢复需求匹配。

### 十、冲突与遗忘

1. 冲突<span style="background-color: #fff3cd">先区分适用范围</span>：两个结论可能对应不同版本、地区或用户。真正互斥时保留双方来源，优先使用可验证外部状态或明确授权裁决。
2. 遗忘包括： TTL、被新版本取代、用户删除和安全撤销；向量索引、缓存和派生摘要都要同步处理。

### 十一、评估共享记忆

用需要跨 Agent 传递约束、并发更新、历史经验复用和权限隔离的任务测试。指标包括任务成功率、`错误记忆引用率`、冲突丢失率、`陈旧读取率`、检索延迟、存储增长和删除传播时间。

> 共享内容更多并不等于协作更好。

### 十二、案例：并发更新同一计划

Agent A 读取版本 7 后把步骤 X 标为完成，Agent B 同时基于版本 7 修改 X 的验收条件。A 先提交成为版本 8，B 的 `expected_version=7` 被拒绝。

B 重新读取后发现验收已变化，<span style="background-color: #fff3cd">应重新验证 X，而不是把旧 patch 强行合并</span>。

> 版本冲突在这里保护了`业务语义`。

### 十三、案例：`错误经验传播`

一个 Agent 因临时 API 故障推断“接口已下线”，若直接写入全局长期记忆，其他 Agent 会停止使用正常接口。正确流程把它标为未验证观察，附带时间和错误回执；只有官方版本信息或持续验证支持后才晋升。故障恢复后，TTL 或失效事件应让旧观察退出默认检索。

### 十四、黑板的适用边界

黑板适合`多个角色围绕同一任务异步贡献`，尤其是目标和中间产物可结构化时。它不自动解决写冲突、权限和垃圾数据；规模很小且步骤固定的流程，显式消息和工作流状态可能更简单。

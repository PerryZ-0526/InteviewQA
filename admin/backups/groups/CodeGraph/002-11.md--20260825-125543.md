# MARK 接入 KG

## CodeGraph

> CodeGraph 是面向 Claude Code、Codex、Cursor 等 Coding Agent 的本地代码知识图谱工具。它通过 Rust 内核解析多种语言，从源码中抽取函数、类、方法、调用、导入、继承和框架路由等实体关系，将结果持久化到项目本地的 SQLite 数据库，并使用 FTS5 提供全文检索。执行 `codegraph init` 后，它会监听文件变化并增量同步图谱，使 Agent 能够查询相关源码、调用路径和修改影响范围。CodeGraph 默认只向 MCP 客户端暴露一个综合工具 `codegraph_explore`，一次返回相关符号源码、调用链和影响范围；其他 `node`、`search`、`callers`、`callees`、`impact`、`files`、`status` 工具默认隐藏，但可以通过环境变量重新开放。它不允许 Agent 直接编写 SQL 或 Cypher查询底层图数据库。[项目README](https://github.com/colbymchenry/codegraph)

## CodeGraphContext

> CodeGraphContext 是一个开源的代码知识图谱工具箱，通过 Tree-sitter 和可选的 SCIP 索引，将源码转换为文件、符号、调用、导入、继承和包含关系图，并支持 FalkorDB、KuzuDB、Neo4j 等图数据库后端。它同时提供 CLI 和 MCP Server，Agent 可以调用符号搜索、调用关系分析、复杂度分析和数据源查询等结构化 Tool，也可以通过 `execute_cypher_query` 执行受限的只读 Cypher。因此，它既可作为 Coding Agent 的上下文服务，也适合开发者研究、扩展和直接操作代码知识图谱。[CodeGraphContext](https://github.com/CodeGraphContext/CodeGraphContext)

## Potpie

> Potpie 是面向 AI Native SDLC 的开源 Context Graph，关注的不只是源码结构，还包括 Git 历史、PR、Issue、工程决策、文档、团队知识和研发过程事件。它将这些信息组织成带来源、时间和生命周期的事实与关系，并向 Agent 返回排序后的证据包，而不是直接生成不可审计的自然语言结论。Potpie 当前采用 CLI-first 和 Agent Skill 的接入方式，Agent 可使用 `resolve`、`search`、`graph neighborhood` 等命令读取上下文，并通过 `graph propose → graph commit --verify` 的受控流程沉淀长期知识。[Potpie](https://github.com/potpie-ai/potpie)

## Aider Repo Map

> Aider Repo Map 是 Aider 内部的仓库上下文压缩机制，并不是独立的图数据库或 MCP 服务。它利用 Tree-sitter 抽取仓库中的关键类、函数、方法和签名，再根据文件之间的依赖关系构建图并进行重要性排名，最终在指定 Token 预算内生成精简的仓库地图。Aider 会根据当前对话和正在编辑的文件动态选择 Repo Map 内容，并自动放入模型上下文，使模型在不读取整个仓库的情况下了解主要文件、公共接口和代码结构。[Aider Repo Map](https://aider.chat/docs/repomap.html)

## Sourcegraph

> Sourcegraph 是面向组织级代码资产的集中式代码搜索与代码智能平台，能够统一索引多个代码托管平台上的大量仓库、分支、提交和历史记录。它结合 Zoekt 代码搜索、SCIP 精确代码导航、自然语言搜索、Code Finder 和 Deep Search，为用户及 Coding Agent 提供跨仓库搜索、文件读取、定义跳转、引用查找、提交与 Diff 检索等能力。Sourcegraph 可通过 MCP 接入 Codex、Claude Code 等 Agent，但不会直接暴露底层 Code Graph 或数据库查询，而是提供受权限控制的搜索和导航 Tool，并继承用户原有的仓库访问权限。[Sourcegraph MCP](https://sourcegraph.com/docs/api/mcp)

关键结论：

- **CodeGraph** 采用“默认一个强 Tool”的策略，说明 MCP Tool 并非越多越好。[CodeGraph README](https://github.com/colbymchenry/codegraph)
- **CodeGraphContext** 是五者中唯一明确把只读 Cypher作为普通 MCP Tool 暴露的产品。[CodeGraphContext MCP Tools](https://github.com/CodeGraphContext/CodeGraphContext/blob/main/docs/MCP_TOOLS.md)
- **Potpie** 强调结构化证据和受控图操作，不把底层查询语言作为主要 Agent 接口。[Potpie](https://github.com/potpie-ai/potpie)
- **Aider Repo Map** 不属于 MCP 查询产品，而是自动上下文生成机制。[Aider Repo Map](https://aider.chat/docs/repomap.html)
- **Sourcegraph** 与 ground-truth-kg 所在维度最接近：都是跨仓库集中式能力，但 Sourcegraph以代码搜索和符号导航为核心，ground-truth-kg以跨项目技术资产、服务依赖及证据为核心。[Sourcegraph MCP](https://sourcegraph.com/docs/api/mcp)



## 接入 MARK

当前成熟产品的共同选择：默认让 Agent 使用语义稳定、结果受限的工具；需要自由度时提供受约束的遍历或搜索 DSL；只有 CodeGraphContext 这类偏开发者图工具箱的产品，才把只读 Cypher直接作为普通 MCP Tool 暴露。



这也提供了另一种值得 ground-truth-kg 借鉴的设计：
```
默认：
kg_explore
    输入自然语言问题、实体提示、查询范围
    一次返回实体、关系、路径、证据、候选项和影响范围

高级可选：
kg_get_status
kg_resolve_entities
kg_get_context
kg_traverse_graph
kg_get_evidence
kg_query
```

即默认只给 Agent 一个高质量综合入口，降低 Tool 选择错误和 Tool Schema 的上下文消耗；精细工具保留给需要确定性控制的 MARK 工作流。

---

ground-truth-kg 不应该走两个极端：
```
极端一：只有几个僵化 Tool
极端二：直接把 Neo4j/Cypher 完全暴露给所有 Agent
```

推荐形态：


| Profile    | 暴露能力                  | 使用者                         |
| ---------- | --------------------- | --------------------------- |
| `core`     | 5 个领域 Tool            | MARK、Codex、Claude Code 默认使用 |
| `graph`    | core + 结构化 `kg_query` | 复杂跨仓库分析                     |
| `advanced` | graph + 只读 Cypher     | KG 开发人员、受信任调试任务             |



| Tool                         | Profile  | 核心作用                |
| ---------------------------- | -------- | ------------------- |
| `kg_get_status`              | core     | 检查 KG 可用性和当前数据版本    |
| `kg_resolve_entities`        | core     | 把自然语言、仓库名等解析为标准实体   |
| `kg_get_context`             | core     | 获取某个实体的完整 Agent 上下文 |
| `kg_traverse_graph`          | core     | 从实体出发进行受限图遍历        |
| `kg_get_evidence`            | core     | 获取事实对应的原始证据         |
| `kg_query`                   | graph    | 使用结构化 DSL 组合复杂查询    |
| `kg_execute_readonly_cypher` | advanced | 执行受限的只读 Cypher      |


## 1. `kg_get_status`

### Tool 描述

> 获取 Ground Truth KG 当前服务状态、活动数据版本、图规模、数据覆盖率和可用能力。Agent 在首次使用 KG 或怀疑数据异常时应优先调用。

### Agent 何时使用

- 一次任务中第一次访问 KG。
- 查询返回空结果，需要判断是“确实不存在”还是“数据未准备好”。
- 在技术设计中记录使用的 KG release。
- MCP 连接异常

## 2. `kg_resolve_entities`

### Tool 描述

> 将自然语言描述、服务名、仓库名、接口路径或资源名称解析为 Ground Truth KG 中的标准实体，返回精确匹配和排序后的候选匹配。

它解决的是“先找到正确实体，再进行图查询”。

### Agent 何时使用

- 用户只给了一个模糊业务名称。
- PRD 中出现服务或系统名称，但没有标准 ID。
- 查询接口前不知道它属于哪个 Service。
- 准备执行 `kg_get_context` 或 `kg_traverse_graph`。

## 3. `kg_get_context`

### Tool 描述

> 获取指定实体的任务相关上下文，包括关联仓库、服务、入口点、上下游依赖、数据资源、部署信息、候选关系、证据和数据缺口。

默认情况下最重要的 Tool，相当于 Agent 的“一站式上下文包”。

### Agent 何时使用

- 开始分析一个 Service 或 Repo。
- PRD 暗示存在跨服务影响。
- 准备编写技术方案或任务拆分。
- 需要同时获得关系、证据、候选项和覆盖率。
- 不确定应该调用哪一种专门查询。

## 4. `kg_traverse_graph`

### Tool 描述

> 从一个或多个起始实体出发，沿白名单关系进行有界图遍历，返回满足方向、深度、类型和属性条件的路径与实体。

“受限但通用”的图遍历接口。

### Agent 何时使用

- 分析多跳服务调用链。
- 寻找某个服务的两跳上游。
- 查哪些 Service 通过 EntryPoint 间接连接。
- 从 DataAsset 反向寻找影响服务。
- `kg_get_context` 返回的一跳信息不足。

## 5. `kg_get_evidence`

### Tool 描述

> 根据 `fact_id`、实体或关系获取产生该事实的证据，包括来源系统、源码位置、观察时间、证据类型和原始摘要。

回答：“KG 为什么认为这件事是真的？”

### Agent 何时使用

- 准备把 KG 关系写进技术设计。
- canonical 与当前代码看起来冲突。
- 需要定位关系对应的源码位置。
- 判断关系是代码扫描、运行时还是人工证据。
- 需要验证数据是否过期。

## 6. `kg_query`

### Tool 描述

> 使用受控的声明式查询 DSL 对 Ground Truth KG 执行组合查询。适用于领域 Tool 无法覆盖的复杂筛选、关系组合、分组和路径查询。

比 `kg_traverse_graph` 更灵活，但仍不暴露 Cypher。

### 服务端处理流程
```
校验 DSL
  → 检查实体与关系白名单
  → 注入用户权限范围
  → 添加深度和数量限制
  → 编译为参数化 Cypher
  → 执行只读事务
  → 拼接 evidence/coverage
  → 返回统一 envelope
```

### Agent 何时使用

- 多个条件组合查询。
- 同时匹配多类关系。
- 需要分组、排序或投影。
- `kg_get_context` 和 `kg_traverse_graph` 无法表达问题。
- 希望保持查询自由度，但没有高级 Cypher 权限。

## 7. `kg_execute_readonly_cypher`

### Tool 描述

> 对当前 Ground Truth Neo4j release 执行经过解析、审计和资源限制的只读 Cypher。仅供受信任用户进行高级分析、KG 调试和临时探索。

### Agent 何时使用

- KG Schema 开发和验证。
- 编写新领域 Tool 前探索查询逻辑。
- 临时分析尚未被 `kg_query` DSL 支持的关系。
- 排查 KG 数据异常。
- 受信任的高级技术研究。




| DSL                        | Cypher                 |
| -------------------------- | ---------------------- |
| 只提供业务需要的有限表达能力             | 完整图数据库查询语言             |
| Agent 不需要了解内部 Neo4j Schema | Agent 必须了解 Label、关系和属性 |
| 容易限制深度、关系、数量和权限            | 自由度高，也更容易产生高成本查询       |
| 后端可从 Neo4j 换成其他数据库         | 与图数据库实现耦合              |
| 可自动补充证据、覆盖率和候选信息           | 默认只返回图查询结果             |

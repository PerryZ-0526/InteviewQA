## 选型建议

### 个人开发者或中小仓库

- 已经使用 Aider：优先使用内置 Repo Map，不必立即增加独立图服务。
- 使用 Codex、Claude Code 或 Cursor，并经常查询调用链：优先试用 CodeGraph。
- 希望研究和直接操作图数据：选择 CodeGraphContext，并从嵌入式后端开始。

### 中大型单仓库或多语言仓库

- 需要调用链、影响分析、测试定位、文档一致性：CodeGraph 更接近开箱即用。
- 需要 Neo4j/Cypher、自定义 Schema 或将图数据提供给其他系统：CodeGraphContext 更合适。
- 需要把长期决策、Issue、文档和代码共同纳入 Agent 上下文：在代码图之外增加 Potpie。

### 企业多仓库环境

- 仓库数量多、代码托管平台多、权限要求高：Sourcegraph 更有优势。
- Sourcegraph 可作为组织级检索与精确导航底座，再通过 MCP 为 Codex、Claude Code 等 Agent 提供上下文。
- Potpie 可位于 Sourcegraph 之上或旁侧，管理 Sourcegraph 不直接表达的项目决策、工程事件和团队知识。
- CodeGraph/CodeGraphContext 可作为开发者本地增强，但要避免与企业集中索引重复消耗资源。



&nbsp;

&nbsp;

当前成熟产品的共同选择：默认让 Agent 使用语义稳定、结果受限的工具；需要自由度时提供受约束的遍历或搜索 DSL；只有 CodeGraphContext 这类偏开发者图工具箱的产品，才把只读 Cypher直接作为普通 MCP Tool 暴露。

---

ground-truth-kg 不应该走两个极端：
```
极端一：只有几个僵化 Tool
极端二：直接把 Neo4j/Cypher 完全暴露给所有 Agent
```

推荐形态：


| Profile    | 暴露能力                  | 使用者                         |
| ---------- | --------------------- | --------------------------- |
| `core`     | 5 个领域 Tool            | MARK、Codex、Claude Code 默认使用 |
| `graph`    | core + 结构化 `kg_query` | 复杂跨仓库分析                     |
| `advanced` | graph + 只读 Cypher     | KG 开发人员、受信任调试任务             |



| Tool                         | Profile  | 核心作用                |
| ---------------------------- | -------- | ------------------- |
| `kg_get_status`              | core     | 检查 KG 可用性和当前数据版本    |
| `kg_resolve_entities`        | core     | 把自然语言、仓库名等解析为标准实体   |
| `kg_get_context`             | core     | 获取某个实体的完整 Agent 上下文 |
| `kg_traverse_graph`          | core     | 从实体出发进行受限图遍历        |
| `kg_get_evidence`            | core     | 获取事实对应的原始证据         |
| `kg_query`                   | graph    | 使用结构化 DSL 组合复杂查询    |
| `kg_execute_readonly_cypher` | advanced | 执行受限的只读 Cypher      |


## 1. `kg_get_status`

### Tool 描述

> 获取 Ground Truth KG 当前服务状态、活动数据版本、图规模、数据覆盖率和可用能力。Agent 在首次使用 KG 或怀疑数据异常时应优先调用。

### Agent 何时使用

- 一次任务中第一次访问 KG。
- 查询返回空结果，需要判断是“确实不存在”还是“数据未准备好”。
- 在技术设计中记录使用的 KG release。
- MCP 连接异常

## 2. `kg_resolve_entities`

### Tool 描述

> 将自然语言描述、服务名、仓库名、接口路径或资源名称解析为 Ground Truth KG 中的标准实体，返回精确匹配和排序后的候选匹配。

它解决的是“先找到正确实体，再进行图查询”。

### Agent 何时使用

- 用户只给了一个模糊业务名称。
- PRD 中出现服务或系统名称，但没有标准 ID。
- 查询接口前不知道它属于哪个 Service。
- 准备执行 `kg_get_context` 或 `kg_traverse_graph`。

## 3. `kg_get_context`

### Tool 描述

> 获取指定实体的任务相关上下文，包括关联仓库、服务、入口点、上下游依赖、数据资源、部署信息、候选关系、证据和数据缺口。

默认情况下最重要的 Tool，相当于 Agent 的“一站式上下文包”。

### Agent 何时使用

- 开始分析一个 Service 或 Repo。
- PRD 暗示存在跨服务影响。
- 准备编写技术方案或任务拆分。
- 需要同时获得关系、证据、候选项和覆盖率。
- 不确定应该调用哪一种专门查询。

## 4. `kg_traverse_graph`

### Tool 描述

> 从一个或多个起始实体出发，沿白名单关系进行有界图遍历，返回满足方向、深度、类型和属性条件的路径与实体。

“受限但通用”的图遍历接口。

### Agent 何时使用

- 分析多跳服务调用链。
- 寻找某个服务的两跳上游。
- 查哪些 Service 通过 EntryPoint 间接连接。
- 从 DataAsset 反向寻找影响服务。
- `kg_get_context` 返回的一跳信息不足。

## 5. `kg_get_evidence`

### Tool 描述

> 根据 `fact_id`、实体或关系获取产生该事实的证据，包括来源系统、源码位置、观察时间、证据类型和原始摘要。

回答：“KG 为什么认为这件事是真的？”

### Agent 何时使用

- 准备把 KG 关系写进技术设计。
- canonical 与当前代码看起来冲突。
- 需要定位关系对应的源码位置。
- 判断关系是代码扫描、运行时还是人工证据。
- 需要验证数据是否过期。

## 6. `kg_query`

### Tool 描述

> 使用受控的声明式查询 DSL 对 Ground Truth KG 执行组合查询。适用于领域 Tool 无法覆盖的复杂筛选、关系组合、分组和路径查询。

比 `kg_traverse_graph` 更灵活，但仍不暴露 Cypher。

### 服务端处理流程
```
校验 DSL
  → 检查实体与关系白名单
  → 注入用户权限范围
  → 添加深度和数量限制
  → 编译为参数化 Cypher
  → 执行只读事务
  → 拼接 evidence/coverage
  → 返回统一 envelope
```

### Agent 何时使用

- 多个条件组合查询。
- 同时匹配多类关系。
- 需要分组、排序或投影。
- `kg_get_context` 和 `kg_traverse_graph` 无法表达问题。
- 希望保持查询自由度，但没有高级 Cypher 权限。

## 7. `kg_execute_readonly_cypher`

### Tool 描述

> 对当前 Ground Truth Neo4j release 执行经过解析、审计和资源限制的只读 Cypher。仅供受信任用户进行高级分析、KG 调试和临时探索。

### Agent 何时使用

- KG Schema 开发和验证。
- 编写新领域 Tool 前探索查询逻辑。
- 临时分析尚未被 `kg_query` DSL 支持的关系。
- 排查 KG 数据异常。
- 受信任的高级技术研究。




| DSL                        | Cypher                 |
| -------------------------- | ---------------------- |
| 只提供业务需要的有限表达能力             | 完整图数据库查询语言             |
| Agent 不需要了解内部 Neo4j Schema | Agent 必须了解 Label、关系和属性 |
| 容易限制深度、关系、数量和权限            | 自由度高，也更容易产生高成本查询       |
| 后端可从 Neo4j 换成其他数据库         | 与图数据库实现耦合              |
| 可自动补充证据、覆盖率和候选信息           | 默认只返回图查询结果             |

第一版依赖建议：
```
Python 3.11
mcp 2.x
neo4j 5.x
pydantic 2.x
```

版本需要在 `requirements.lock` 中锁定，不建议生产镜像每次安装最新版。
